## Introducción

Los sistemas operativos son unos de los tipos de programas más interesantes debido a su complejidad y a la gran cantidad de áreas que involucran, como la de hardware. El sistema operativo es el que se comunica con esta área.

---
## ¿Qué es un SO?

Pensemos el caso en que no existiera un SO. Si tenemos que hacer un "hello world", sería muy complicado porque no vamos a simplemente hacer el código C como solemos hacer. Este programa implica interactuar con la pantalla, cosa que se dificulta mucho sin un SO de por medio. Es como querer hacer un programa sin tener la librería estándar.

En Arqui estudiamos los distintos modos, **kernel** y **user**. Recordemos que el kernel tiene una serie de privilegios que el user no tiene. La primera ventaja de esto es la seguridad y la segunda es que le permite al SO realmente administrar recursos. Cuando se prende la computadora, el sistema operativo es el primer programa en ejecutarse y se encuentra con la máquina "en cero", es decir que es 100% configurable. Entonces lo primero que hace es bloquear todo para los procesos que corran después. Incluso es él mismo el que ejecuta los otros procesos.

El usuario admin y el usuario invitado no tienen nada que ver con los modos anteriores. Por más que yo sea el admin, no voy a tener acceso a todo lo que puede realizar el kernel. Son dos conceptos totalmente ortogonales.

La **shell** es un intérprete de comandos. Es un proceso como todos los demás, no tiene ningún privilegio extra. La diferencia es que puede llamar a otros procesos y ejecutarlos. Si tuviéramos que elegir un solo programa para ejecutar, sería lógico tomar la shell porque puede ejecutar a todo el resto. Todo este poder viene de poder utilizar las syscalls, que son los servicios del sistema operativo.
![[Pasted image 20261123200530.png|center|387]]

El user interface program es esta API de syscalls que es la que le permite a los procesos, que son como los clientes, comunicarse con el sistema operativo. El sistema operativo vendría a ser el bibliotecario y el hardware la biblioteca.

Podríamos resumir que las responsabilidades de un SO son administrar los recursos (suponemos que nos encontramos en un ambiente hostil donde todos los procesos van a querer todos los recursos para ellos) y proveer un conjunto abstracto y limpio de los recursos (**máquina extendida**). Los procesos quieren acceder a la memoria, a la red, al mouse, etc., pero los detalles de cada periférico son diversos y no podemos escribir un programa para cada tipo de mouse, por ejemplo. Entonces el SO se encarga de los detalles de lo que queramos correr, como por ejemplo imprimir en la pantalla.

Cuando se habla de administrar recursos, esto incluye multiplexar el espacio y el tiempo. Si dos procesos intentan simultáneamente imprimir un documento sin un SO de por medio, no queda claro qué va a pasar. El sistema operativo va a ser el encargado de ordenarlos para que ambos puedan acceder al documento. El scheduler es un caso de un algoritmo que multiplexa el tiempo.

Las abstracciones son unas de las claves para comprender los SO. Todos los sistemas operativos ofrecen más o menos el mismo conjunto de servicios. Si yo tuviera que escoger uno para mi computadora, me debería fijar en estos servicios que ofrecen.

## Revisión del Hardware

Recordemos lo que ya vimos en Arqui. Vamos a continuar trabajando con los siguientes elementos conectados a un único bus.
![[Pasted image 20261123200553.png|center|470]]

El CPU ejecuta instrucciones que acceden a la memoria, y recordemos que algunos controladores pueden acceder directamente sin el procesador de por medio. Su ciclo básico consiste en obtener la siguiente instrucción, determinar su tipo y operandos, y ejecutarla. Cada procesador tiene su conjunto de instrucciones.

Recordemos que existía un registro `RFLAGS` para las flags, que tiene la forma de la imagen.
![[Pasted image 20261123200622.png|center|508]]

Los bits verdes son bits de status o estado. Describen en qué estado quedó luego de ejecutarse un proceso. Los amarillos son los system flags. Podemos ver el IF que habilita o deshabilita las interrupciones. Otro caso son los dos bits de privilegio IOPL. El resto no los vamos a usar.

**Multicore** consiste en replicar los núcleos independientes, mientras que **multithreading** consiste en mantener el estado de 2 threads e intercambiar entre ellos rápidamente cuando sea necesario. No es paralelismo. Dos threads pueden, por ejemplo, compartir variables globales. No hay un context switch cuando se pasa de uno a otro. Los sistemas multicore pueden soportar múltiples threads.

La memoria nos permite almacenar datos, algunos de manera volátil y otros no, pero lo importante es entender que hay distintos tipos según capacidad, velocidad y costo. A mayor capacidad y/o velocidad, mayor será el costo. Entonces, cuanto más rápida es la memoria, menos "cantidad" tenemos:

| **Typical access time** |                 | **Typical capacity** |
| :---------------------: | :-------------: | :------------------: |
|         1 nsec          |    Registers    |        <1 KB         |
|         2 nsec          |      Cache      |         4 MB         |
|         10 nsec         |   Main memory   |        1-8 GB        |
|         10 msec         |  Magnetic disk  |        1-4 TB        |

Cuando nos quedemos sin memoria (RAM), vamos a bajar algunos procesos al disco, y es muy importante saber elegir cuáles.

Los discos rígidos son un conjunto de "platos" que giran sobre su eje (como se ve en la imagen) y que guardan información sobre sus dos caras.
![[Pasted image 20261123200658.png|center|417]]

Dada una posición de los cabezales, cada cabezal puede leer un **track**. Todos los tracks forman un **cylinder** y cada uno está dividido en **sectors**. Es mucho más lento que la RAM porque es algo mecánico.

Los dispositivos I/O trabajan de tres maneras:
- **Busy Waiting**: el procesador le está preguntando constantemente al dispositivo si ya tiene el dato.
- **Interrupción**: el procesador ejecuta procesos hasta que le llega una señal del dispositivo indicando que terminó la operación.
- **DMA** (Direct Memory Access).

La cronología del uso del procesador por parte de los dispositivos de entrada/salida es la siguiente:
![[Pasted image 20261123200739.png|center|319]]
1. El driver le indica al controlador qué hacer. Este inicia la operación en el dispositivo.
2. El controlador señaliza al controlador de interrupciones (CI).
3. Cuando el CI está listo (otras interrupciones), setea el pin correspondiente en el CPU.
4. El CI escribe el número de dispositivo (vector de interrupciones) en el bus.

Vimos que el SO tiene los privilegios de kernel porque "es el primero en llegar". Esto se refiere a que es lo primero que se levanta en el booteo. La placa madre posee un programa llamado **BIOS** (Basic Input/Output System). La BIOS posee instrucciones para interactuar con la pantalla, el teclado y el disco, y cumple con las siguientes funciones:
1. Chequear cuánta memoria tenemos y si ciertos dispositivos como el teclado están instalados y responden correctamente.
2. Escanear los buses PCIe y PCI en busca de dispositivos instalados.
3. Determinar el dispositivo de booteo.
4. Se carga el primer sector en memoria y se ejecuta. Suele leer una tabla de particiones y se carga un segundo sector.
5. Se carga en memoria el SO y se ejecuta.
6. El SO consulta a la BIOS los dispositivos conectados.

## Tipos de Sistemas Operativos

Los sistemas operativos no se encuentran únicamente en nuestros celulares o computadoras, sino en una serie mucho más amplia de dispositivos. A continuación tenemos una lista de mayor a menor "tamaño" de SOs:
- **Mainframe**: mucho almacenamiento y memoria. Orientado a muchos procesos simultáneos. Soporta trabajos por lotes, transacciones y timesharing. OS/390, tendencia a UNIX.
- **Server**: computadoras personales o incluso mainframes. Impresoras, archivos o webs. Solaris, FreeBSD, Linux y Windows Server. Se provee soporte a varios usuarios (a diferencia de la personal computer).
- **Multiprocesador**: necesaria la separación, porque las computadoras personales viejas no eran multiprocesador.
- **Personal Computer**: proveer soporte a un único usuario. Linux, FreeBSD, Windows y Apple's OS X.
- **HandHeld Computer**: tablets y smartphones. Android y iOS. A partir de aquí se comienza a tener más en cuenta la eficiencia energética. A pesar de ser un usuario, sigue siendo multiproceso.
- **Embedded**: electrodomésticos y teléfonos antiguos. ROM, no permite la instalación de aplicaciones. Embedded Linux, QNX y VxWorks.
- **Sensor-node**: redes de nodos. Poseen CPU, RAM y ROM. Sensan diferentes condiciones. Conexión inalámbrica. TinyOS.
- **Real Time**: necesitamos que una acción ocurra en un momento específico. Hard vs. soft. Industria, aviónica, milicia y multimedia. eCos y FreeRTOS.
- **Smart Card**: pagos electrónicos. Del tamaño de una tarjeta de crédito. Restricciones de potencia y memoria muy altas. Obtienen energía por inducción o al conectarse a un lector.

De los últimos 3 cabe preguntarse si son sistemas operativos, pero hay una interacción entre un usuario y hardware, por lo que tomaremos que sí.

## Estructura de Sistemas Operativos

Podemos encontrar estos 3 tipos de estructuras para los sistemas operativos (entre varios más):
- Monolithic Systems
- Microkernels
- Virtual Machines

Las dos primeras tienen claras diferencias, pero cabe hacer la distinción con la máquina virtual.

En los **sistemas monolíticos**, todo el SO se compila como un único binario. Toda función tiene visibilidad del resto de las funciones, lo que lo hace eficiente pero también lo complejiza al escalarlo. Otra característica es que un error en cualquier función hace fallar el sistema operativo completo. Además, soportan shared libraries o DLLs. Su estructura es la siguiente.
![[Pasted image 20261123200823.png|center|378]]

Algunos ejemplos son Linux, FreeBSD, OpenBSD, NetBSD, Microsoft Windows (95, 98, Me), Solaris, HP-UX, DOS, OpenVMS y XTS-400.

La idea de los **sistemas microkernel** es que el kernel sea lo más pequeño posible, es decir que tenga la menor cantidad de código posible. A diferencia de la estructura anterior, un error fuera del kernel no hace fallar a todo el sistema operativo. Todo el resto de componentes corren en user mode usando los servicios del kernel.
![[Pasted image 20261123200911.png|center|495]]

Como el kernel tiene muy poco código, es poco probable que falle, haciendo que el sistema tenga una alta confiabilidad (real time). Algunos ejemplos son Integrity, K42, L4, PikeOS, QNX, Symbian y MINIX.

El **reincarnation server** es el padre de todos los drivers y servers. Chequea constantemente si los drivers y servers están vivos, limpia los muertos y chequea en una tabla la acción por defecto (por ejemplo, reiniciarlo). Esta posibilidad no está en los sistemas monolíticos, pues los drivers corren en modo kernel.

Si comparamos ambas estructuras, obtenemos lo siguiente.
![[Pasted image 20261123200937.png|center]]

Una estrategia para reducir el tamaño del kernel es separar entre **mecanismo** y **política**. Lo que podemos hacer es colocar el mecanismo en el kernel y la política por fuera. Por ejemplo, podemos tener un mecanismo que permita asignar prioridades a los procesos, y por fuera la política para la asignación de prioridades a cada uno. Es decir, cuál tiene más prioridad se define por fuera del kernel.

Las **máquinas virtuales** son básicamente un proceso más corriendo un sistema operativo en modo usuario, al igual que un juego. Pero el SO que está corriendo dentro de esa máquina virtual debe poder ejecutar instrucciones privilegiadas. Para que esto suceda, el CPU tiene que ser virtualizable. Los **hipervisores** son software que permite tener más de un sistema operativo. Hay distintos tipos de hipervisores.
![[Pasted image 20261123201008.png|center|595]]

El de tipo 1 se encarga de arbitrar el acceso a hardware para ambos sistemas operativos. El de tipo 2 (que es el más común entre los que usamos) tiene un sistema operativo host (donde corre el hipervisor) y luego el sistema operativo guest (el que corre dentro del hipervisor).

## System Calls

Una **syscall** es un llamado a función, pero al realizarlo cambiamos el modo de ejecución de user a kernel. Es decir, cambia a privilegios elevados. Un ejemplo es cuando queremos leer un archivo del disco. Cuando llamamos a una syscall, estamos ejecutando código del kernel, pues están programadas en dicho lugar, pero no lo está ejecutando para sí mismo.

El mecanismo para realizar una system call depende de la arquitectura y debe expresarse en assembler. Se provee una librería para poder realizarlas desde un lenguaje de alto nivel. Es importante destacar que las syscalls son costosas de invocar, entonces nos va a importar como desarrolladores de usuario si una función las utiliza o no.

Vamos a utilizar `strace` para ver todas las syscalls que invoca un proceso y con qué parámetros se ejecutan. Va a consumir muchos recursos, por lo que no es recomendable utilizarlo en producción.

Tomemos el ejemplo de la syscall `read()`:
```c
count = read(fd, buffer, nbytes);
```

Esta syscall recibe el file descriptor, un buffer y la cantidad de bytes que quiero leer, y retorna cuántos pudo leer. Primero, el caller pushea los parámetros (1, 2 y 3) y se llama a `lib_read` (4), que setea un registro (RAX) con el número de syscall (5) y luego ejecuta una instrucción TRAP (`int 0x80` / `syscall`) (6). El dispatcher (que está en kernel space) selecciona el handler correspondiente en función del número de syscall (7). El handler de `read` A) leerá `nbytes` del file descriptor `fd` y lo guardará en `buffer` (8) o B) bloqueará el proceso. El retorno vuelve a user mode y continúa la ejecución de `lib_read` (9), que retorna al caller (10). El caller restaura el SP (11).
![[Pasted image 20261123201055.png|center|422]]

Hay dos estándares para las syscalls, que son **POSIX** (más nuevo) y **System V**. Lo que hacen es definir una serie de syscalls y su comportamiento. Algunos ejemplos para el primero son:

| **Process management**             | **Description**                              |
| ---------------------------------- | -------------------------------------------- |
| `pid = fork()`                     | Create a child process identical to the parent |
| `pid = waitpid(pid, &statloc, options)` | Wait for a child to terminate           |
| `s = execve(name, argv, environp)` | Replace a process' core image                |
| `exit(status)`                     | Terminate process execution and return status |

| **File management**                    | **Description**                          |
| -------------------------------------- | ---------------------------------------- |
| `fd = open(file, how, ...)`            | Open a file for reading, writing, or both |
| `s = close(fd)`                        | Close an open file                       |
| `n = read(fd, buffer, nbytes)`         | Read data from a file into a buffer      |
| `n = write(fd, buffer, nbytes)`        | Write data from a buffer into a file     |
| `position = lseek(fd, offset, whence)` | Move the file pointer                    |
| `s = stat(name, &buf)`                 | Get a file's status information          |

| **Directory- and file-system management** | **Description**                             |
| ----------------------------------------- | ------------------------------------------- |
| `s = mkdir(name, mode)`                   | Create a new directory                      |
| `s = rmdir(name)`                         | Remove an empty directory                   |
| `s = link(name1, name2)`                  | Create a new entry, name2, pointing to name1 |
| `s = unlink(name)`                        | Remove a directory entry                    |
| `s = mount(special, name, flag)`          | Mount a file system                         |
| `s = umount(special)`                     | Unmount a file system                       |

| **Miscellaneous**           | **Description**                          |
| --------------------------- | ---------------------------------------- |
| `s = chdir(dirname)`        | Change the working directory             |
| `s = chmod(name, mode)`     | Change a file's protection bits          |
| `s = kill(pid, signal)`     | Send a signal to a process               |
| `seconds = time(&seconds)`  | Get the elapsed time since Jan. 1, 1970  |

La función `fork` es un wrapper de una syscall que se llama `clone`. Lo que hace es clonar un proceso. Sabemos que este tiene un montón de registros, archivos abiertos, un pid y más información que va a clonar (no todo) en lo que se llama el proceso hijo. En algún momento un proceso puede estar ejecutando dentro de la función `fork`, es decir que el instruction pointer está apuntando dentro de `fork(){ … }`. En la copia que hace, cambia algo de información, como por ejemplo el pid. Va a tener un parent pid (ppid) que va a tener el pid del proceso padre. El RIP de este segundo proceso va a estar apuntando al mismo lugar. En caso de haber un error, el valor de retorno es `-1`.
![[Pasted image 20261123201120.png|center|411]]
Cuando aparece un `ret` dentro de la función `fork`, se va a ejecutar 2 veces, una dentro del proceso 3 y otra del proceso 4. Para el primero, `fork` retorna el child pid y en el segundo retorna cero. Es decir que el padre conoce el identificador del hijo. El mismo código de proceso del padre está en el hijo, pero retorna dos cosas distintas.

En el siguiente caso de una shell básica, el `fork` sirve para que el padre espere a que el hijo termine de ejecutar para "volver". Por ejemplo, en la terminal cuando se está compilando algo, el `$` no aparece y no podemos escribir una instrucción hasta que no termine el proceso:
```c
    // Read and run input commands.
    while(getcmd(buf, sizeof(buf)) >= 0){
      if(buf[0] == 'c' && buf[1] == 'd' && buf[2] == ' '){
        // Chdir must be called by the parent, not the child.
        buf[strlen(buf)-1] = 0;  // chop \n
        if(chdir(buf+3) < 0)
          printf(2, "cannot cd %s\n", buf+3);
        continue;
      }
      if(fork1() == 0)
        runcmd(parsecmd(buf));
      wait();
    }
    exit();
}
```

Si queremos cambiar el código del hijo, se utiliza `execve`, que es lo que hace `runcmd()` en el caso anterior. Esto lo que hace es llevar el RIP del proceso hijo a otro lado. Como reemplaza el código, también reemplaza el stack donde se encuentran los argumentos, stackframes, etc., lo que es lógico dado que cambia el código y no tiene sentido guardar el stack viejo.

Notemos que el `wait()` no se va a ejecutar dos veces. En el `if`, se va a clonar todo el código y `fork()` al padre le va a retornar un número distinto de cero, por lo que salta al `wait()`. En cambio, para el caso del hijo, el `fork()` va a devolver 0 y va a entrar en el `if`. Como se usa un `execve`, el código inferior se "pisa" y pasa a ejecutar otro código. Una vez que termina, NO retorna, sino que directamente sigue ejecutando el padre que está esperando a que termine con `wait()`.

Otro dato importante de cada proceso es el **working directory**, porque no es lo mismo ejecutar en un directorio que en otro. A un hello world no le va a importar, pero se debe guardar. En el ejemplo de la shell, se está implementando el comando `cd` que cambia de directorio. Vemos que no se ejecuta dentro de un `fork`, porque lo que queremos es que tenga efecto en la shell, no en el hijo que se podría crear con dicha función.

El proceso hijo tiene exactamente la misma memoria (heap, stack, memory maps) que el padre. Si se debiera copiar esta memoria cada vez que se llama a `fork`, sería muy lento y un desperdicio de RAM. Muchas veces, los procesos llaman a `exec` justo después de `fork` y terminan no usando la memoria del proceso padre. Entonces, lo que hace Linux es dejarlos compartir la RAM física y solamente copia la memoria cuando uno quiere escribir. Esto lo hace dándoles a los procesos tablas de páginas iguales, pero se asegura de que sean read-only. Cuando un proceso trata de escribir una dirección de memoria compartida:
1. Salta un page fault.
2. Linux hace una copia de la página y actualiza la tabla de páginas.
3. El proceso continúa sin enterarse.

## File Descriptors

Los sistemas UNIX usan enteros para trackear los archivos abiertos, llamados **file descriptors** (fd). El comando `lsof` (list open files) muestra los archivos abiertos de un proceso. Se utiliza `lsof -p 1212`, donde 1212 debe ser el pid del proceso. Los file descriptors pueden referirse a:
- Archivos en disco
- Pipes
- Sockets
- Terminales
- Dispositivos
- Etc.

Cuando se lee o escribe en un archivo, pipe o conexión de red, se utiliza un file descriptor como método de identificación. Por ejemplo, `fd = open("archivo.txt")` lo que hace es guardar en la variable `fd` el file descriptor asignado a "archivo.txt". Casi todo proceso tiene 3 file descriptors estándar:
- `stdin → 0`
- `stdout → 1`
- `stderr → 2`
