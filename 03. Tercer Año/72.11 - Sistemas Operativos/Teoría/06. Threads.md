## Introducción

Tradicionalmente, un proceso tiene su espacio de direcciones y un único **hilo (thread)** de ejecución. Podemos pensar que con un único dedo podemos seguir la traza de ejecución de un proceso. Tiene un único instruction pointer avanzando en su código.

Existen casos en los que es muy útil tener múltiples hilos en un mismo espacio de direcciones corriendo de forma pseudo paralela, como si fueran procesos separados, salvo por el espacio de direcciones, es decir que comparten el código y el heap (junto con las variables globales).

Si hacemos un `fork`, recordemos que se copia la memoria también, por lo que las variables globales no son compartidas. En cambio, con la creación de threads esto no sucede, quedando las mismas compartidas.

---
## Justificación

Si tenemos múltiples hilos y uno se bloquea, el resto va a seguir ejecutando: no se bloquea todo el conjunto. Esto tiene algunas consecuencias:
- Aumenta el uso del CPU
- Simplifica la programación
- Aprovecha arquitecturas con múltiples CPUs

En los threads tenemos la misma noción del modelo de procesos, donde no nos importan las interrupciones que ocurren durante la ejecución, ya que son transparentes para nosotros. Podemos abstraer detalles y pensar en procesos secuenciales, con el agregado de que comparten un espacio de direcciones.

Los hilos son más "baratos" que los procesos, porque no necesitamos crear toda la estructura de un proceso junto con el mapeo, la caché, etc. Crear uno es hasta 10 a 100 veces más rápido que crear un proceso.

Si queremos que los threads accedan simultáneamente a la memoria que comparten, se los debe sincronizar, tal como vimos en la comunicación entre procesos.

Supongamos que tenemos un editor de texto con las siguientes herramientas:
- Corrector ortográfico
- Autoguardado
- Procesar input
- Visualizar contenido

Todos estos procesos van a compartir el buffer donde se encuentra el texto que se está editando. Notemos que al utilizar hilos se ahorra tener que armar una comunicación entre ellos, ya que el espacio de direcciones compartido viene "gratis".

Supongamos ahora que tenemos un servidor web, que se caracteriza por tener que atender múltiples conexiones simultáneamente. No podemos tener un único hilo que atienda a todas, porque si le pedimos una página web que no está en memoria y el hilo se bloquea esperándola, no puede atender las otras solicitudes. Entonces, los servidores web tienen un hilo cuyo único trabajo es atender las solicitudes entrantes (como un secretario) y derivar cada conexión a un nuevo thread. Está constantemente listo, atendiendo las nuevas solicitudes y haciendo las derivaciones. Cada cliente se conecta al servidor a través de un thread exclusivo. Por lo tanto, si este se bloquea, solo dicho cliente debe esperar a que se obtenga la página, no todo el resto.
![[Pasted image 20261123204440.png|center|345]]

Podríamos hacerlo nuevamente con procesos, pero como la construcción y destrucción de hilos es menos costosa y los servidores manejan cientos o miles de solicitudes, es mucho más eficiente usar estos últimos. Si no tuviéramos threads y debiéramos usar un único proceso (pues si no sería repetir lo anterior), tendríamos que tener syscalls no bloqueantes y almacenar el estado de cada pedido para retomarlo cuando llegue la página del disco. En este caso se pierde la noción de computación secuencial (pues se salta de una función a otra o entre contextos) y en el fondo estamos simulando threads "the hard way".

## Modelo de Threads

El stack de cada thread debe ser privado, ya que allí se guardan, por ejemplo, las variables locales. Si tenemos una función con varios threads ejecutándola en distintas instrucciones, se pueden generar una serie de problemas.

Recordemos el modelo de procesos, donde hay una agrupación basada en la agrupación de recursos y en las características de la ejecución (valor de los registros, stack, etc.) de cada uno:

|  **Process management**   |     **Memory management**     | **File management** |
| :-----------------------: | :---------------------------: | :-----------------: |
|         Registers         | Pointer to text segment info  |   Root directory    |
|      Program counter      | Pointer to data segment info  |  Working directory  |
|    Program status word    | Pointer to stack segment info |  File descriptors   |
|       Stack pointer       |                               |       User ID       |
|       Process state       |                               |      Group ID       |
|         Priority          |                               |                     |
|   Scheduling parameters   |                               |                     |
|        Process ID         |                               |                     |
|      Parent process       |                               |                     |
|       Process group       |                               |                     |
|          Signals          |                               |                     |
| Time when process started |                               |                     |
|       CPU time used       |                               |                     |
|    Children's CPU time    |                               |                     |
|    Time of next alarm     |                               |                     |

Para cada thread deben ser exclusivos: el stack pointer, el program counter (instruction pointer), el CPU time used, la máscara de señales, el registro RFLAGS (program status word), el estado del thread, la prioridad y el ID.

## Procesos vs. Threads

Podemos comparar procesos con threads observando que un thread está contenido en un proceso, pero el proceso agrupa recursos y el thread es una entidad programada (scheduled) para ejecución en el CPU. Por otro lado, los threads permiten múltiples ejecuciones en el mismo conjunto de recursos. Tener múltiples threads en un proceso es análogo a tener múltiples procesos en una PC. En un caso se comparten el espacio de direcciones, los archivos, las señales, etc. En el otro se comparten la memoria, los dispositivos de entrada y salida, etc.

Podemos tener los siguientes casos.
![[Pasted image 20261123204511.png|center|551]]

Podemos tener varios procesos, cada uno con un hilo, o un único proceso con varios hilos. Algunas características propias de los procesos y de los hilos son:

|    **Per-process items**    | **Per-thread items** |
| :-------------------------: | :------------------: |
|        Address space        |   Program counter    |
|      Global variables       |      Registers       |
|         Open files          |        Stack         |
|       Child processes       |        State         |
|       Pending alarms        |                      |
| Signals and signal handlers |                      |
|   Accounting information    |                      |

Los threads comparten el espacio de direcciones; por lo tanto, un thread podría modificar información mientras otro la está leyendo, lo que ya vimos que es una race condition. No existe protección provista por el kernel ante esta situación, porque la memoria es compartida y el thread tiene el permiso para editarla.

## Implementación en User Space

La forma tradicional de implementar threads es hacerlo enteramente dentro del kernel. Sin embargo, se los puede implementar dentro del espacio de usuario o incluso tener implementaciones híbridas.

Comenzando por la implementación en el espacio de usuario, el kernel va a desconocer completamente su existencia. Desde su punto de vista, son procesos con un único thread. Realizarlo en este espacio es útil en caso de que el kernel no provea dicha implementación. Se implementa como una librería, como se ve en la figura del lado izquierdo de la imagen, a diferencia del lado derecho, que contiene la implementación en el kernel.
![[Pasted image 20261123204639.png|center|523]]

Cada circunferencia representa un proceso y cada hilo un thread. La "cajita" dentro del proceso (**run-time system**) es la librería que se encarga de gestionar los threads, para lo cual necesita una **tabla de hilos**. El kernel solo ve su tabla de procesos, a diferencia de la implementación en kernel de la derecha. Esta tabla de threads es privada de cada proceso y es análoga a la tabla de procesos.

Si un thread se bloquea localmente (esperando por otro thread del mismo proceso), se realiza el switch en espacio de usuario. Es un orden de magnitud (o más) más rápido que el switch usual con interrupciones y la intervención del kernel, y no es necesario flushear la caché. Las funciones para manejar los bloqueos se encuentran en el run-time system que vimos antes. Cada proceso puede tener su propio algoritmo de scheduling de threads.

Existe un problema en la implementación de threads en el espacio de usuario, y se relaciona con las syscalls bloqueantes. Hasta ahora consideramos threads que se bloquean esperando a otros del mismo proceso. Pero si, por ejemplo, uno realiza un `read`, la librería no lo puede manejar, pues es trabajo del kernel. Una vez que este recibe la llamada, bloquea el proceso entero, pues no sabe que existen threads que no necesitan bloquearse. Para resolver este problema, se puede hacer que las syscalls no sean bloqueantes, pues algunas permiten recibir parámetros que indican dicho comportamiento. Otra opción es hacer un `select`, despertándose por cualquier evento que se indique en la syscall.

Otro problema que va a generar un bloqueo es el page fault, en caso de que un hilo quiera acceder a un dato que no se encuentra en memoria. El kernel bloquea el proceso entero, busca la página y luego lo desbloquea. Además, un thread puede correr indefinidamente hasta que voluntariamente libere el CPU, lo que se podría arreglar mediante la solicitud de una señal, pero no es eficiente.

El uso de threads tiene sentido para separar distintos hilos de ejecución cuando alguno o algunos de ellos se van a bloquear. Ese es el objetivo principal del uso de threads, porque si no se bloquearan, podríamos usar un único hilo. Otra ventaja es poder modularizar y organizar el código.

## Implementación en Kernel Space

En este caso, no son necesarios el run-time system ni la tabla de threads (en espacio de usuario). Un thread se bloquea como es usual y el kernel elige otro thread (u otro proceso). Debido al mayor costo, se pueden reutilizar los threads. Notemos en la imagen anterior que ahora tenemos la tabla de threads directamente en el kernel (**TCB**, thread control block). Las decisiones de scheduling tienen en cuenta si se trata de un thread o de un proceso.

Si un proceso que tiene threads ejecuta un `fork`, es interesante plantearse qué sucede con ellos (en clase no se dio una respuesta concreta). En el caso de las señales, en Linux se le envían a todo el proceso, y se entregan a alguno de sus hilos que no las tenga bloqueadas.

## Implementación Híbrida

Vimos que la implementación en el kernel nos solucionaba muchos problemas de la de usuario, como los threads bloqueantes, pero a su vez traía una baja en la eficiencia de ejecución. En la **implementación híbrida** se tiene un poco de cada mundo: por ejemplo, los threads siguen existiendo del lado del kernel y se manejan dentro del user space con una implementación de threads a nivel de usuario. Si, por ejemplo, un thread de kernel se bloquea (tomemos el derecho de la imagen), solamente se van a bloquear los dos threads de usuario conectados a él, mientras que los otros tres siguen ejecutando.
![[Pasted image 20261123204718.png|center|463]]

Si tenemos varias tareas que sabemos que no van a ser bloqueantes, las podemos asociar a un hilo de kernel y dejar las que sí lo son con otro.

Las **scheduler activations** intentan atacar el problema más grave de la implementación en el espacio de usuario, que es el hecho de que se bloquea todo el proceso. La solución es la siguiente.
![[Pasted image 20261123204737.png|center|419]]

Supongamos que tenemos threads en espacio de usuario con su funcionalidad en espacio de kernel. Al bloquearse uno, se crea un nuevo thread de kernel y se hace un **upcall**, que viola la estructura de un sistema de capas, pues las llamadas se supone que van "hacia abajo". Esta llamada notifica al run-time system (thread manager, que es la librería), que se encarga de resumir, es decir, de poner en ejecución otro thread. La librería sabe cuál es el hilo bloqueado porque es el actual cuando llega la upcall.
