## Introducción

La **capa de enlace**, junto con la capa física conforman la capa de acceso. Esta capa intenta resolver la comunicación hacia el siguiente nodo. Todos los dispositivos se van a llamar nodos. Los paquetes, ahora se van a encapsular y se van a pasar a llamar frames.

Los servicios que ofrece esta capa son:
- Encapsulamiento: como vimos, los paquetes se encapsulan. Esto proporciona estructura a los datos para que puedan transmitirse de manera organizada y ser reconocidos en el destino.
- Acceso al medio: decide cuándo y cómo un dispositivo puede usar el canal de comunicación compartido, para transmitir sin interferencias con otros dispositivos.
- Comunicación confiable: garantiza que los datos lleguen correctamente y en el orden adecuado desde el emisor hasta el receptor, sin duplicados ni pérdidas.
- Control de flujo.
- Detección y corrección de errores.

## Tipos de Comunicación

Existen dos tipos de comunicaciones a nivel de enlace:
- **Red Broadcast (LAN)**: Redes donde un dispositivo puede enviar un mensaje que todos los demás dispositivos reciben. Un ejemplo son las redes Ethernet. ![[Pasted image 20260814115549.png|193]]
- **Red Punto a punto (WAN)**: Comunicación directa entre solo dos dispositivos. Un ejemplo es un enlace entre dos routers conectados con un cable serial o un túnel. ![[Pasted image 20260814115613.png|center|263]]
**SLIP** es un protocolo muy simple que permite enviar paquetes IP sobre enlaces seriales (como una conexión por módem o cable serie). Este protocolo encapsula paquetes IP para transmitirlos por una línea serie. No añade encabezados complejos, solo un carácter especial para marcar el fin del paquete.
![[Pasted image 20260814115640.png|center|445]]

**PPP (Point-to-Point Protocol)**, definido en la RFC 1661 en 1992, es el sucesor directo de SLIP y proporciona una solución mucho más robusta para enlaces punto a punto. PPP permite el encapsulamiento de múltiples protocolos de red, no solo IP, e incluye mecanismos de detección de errores mediante CRC. También soporta autenticación de usuarios a través de protocolos como PAP y CHAP, asignación dinámica de direcciones IP, negociación de opciones (como tamaño de trama o compresión), y evaluación de la calidad del enlace antes y durante la comunicación. Por estas razones, PPP es ampliamente utilizado en conexiones como módems, enlaces seriales y VPNs.

En las redes broadcast, todos los dispositivos comparten un único canal de comunicación. Esto significa que cuando un nodo transmite, la señal es recibida por todos los demás nodos en la red. Al tratarse de un canal compartido, existe la posibilidad de interferencia si dos o más nodos intentan transmitir al mismo tiempo. Esto provoca una colisión, donde las señales se superponen y se pierden. Para evitar estas colisiones, debe existir una norma o protocolo que defina cómo los nodos comparten el canal, es decir, cuándo y cómo pueden transmitir. La coordinación entre los nodos se realiza utilizando el mismo canal de datos, lo cual requiere mecanismos eficientes para gestionar el acceso al medio.

Los **protocolos de acceso múltiple** regulan cómo varios nodos pueden compartir un canal de comunicación común sin interferirse entre sí. Son esenciales en redes donde el medio es compartido, como Ethernet o redes inalámbricas.
![[Pasted image 20260814115722.png|center|491]]
**Acceso Aleatorio (Random Access)**:
- Los nodos transmiten sin coordinación previa.
- Si hay colisión, se detecta o se asume, y se retransmite después de esperar un tiempo aleatorio.
- El protocolo a usar debe definir cómo detectar colisiones y cómo actuar frente a ellas.
![[Pasted image 20260814115755.png|center|490]]
**Acceso Controlado (Controlled Access)**:
- El acceso al canal es coordinado y ordenado, evitando colisiones.
- Se asignan turnos o permisos para transmitir.
**Acceso por División (Channelization)**:
- El canal se divide en tiempo, frecuencia o códigos, y cada nodo tiene su propia “porción” asignada.
- No hay colisiones.

**Token Ring** es una tecnología de red LAN (Local Area Network) que utiliza un protocolo de acceso al medio controlado basado en el paso de un token. Es un sistema de acceso controlado y determinista, lo que significa que solo el nodo que posee el token puede transmitir datos. El funcionamiento es el siguiente:
1. El token circula de nodo a nodo.
2. El nodo que recibe el token puede transmitir sus datos.
3. Después de la transmisión, el token se pasa al siguiente nodo. ![[Pasted image 20260814115849.png|center|398]]

**ALOHA Puro** es un protocolo de acceso múltiple aleatorio utilizado para la transmisión de datos en redes donde varios dispositivos comparten el mismo canal. Su funcionamiento es el siguiente:
1. Un nodo transmite datos en el canal sin verificar si está ocupado.
2. Si no hay colisión, la transmisión es exitosa.
3. Si hay colisión, el nodo espera un tiempo aleatorio (backoff) y vuelve a intentar la transmisión.
4. El proceso se repite hasta que la transmisión es exitosa. 
![[Pasted image 20260814115935.png|center|597]]

Otro protocolo de acceso múltiple aleatorio es **CSMA (Carrier Sense Multiple Access)**. Antes de transmitir, el nodo escucha el canal para asegurarse de que no esté ocupado (Carrier Sense). Si el canal está libre, puede transmitir. Si está ocupado, espera. El funcionamiento es el siguiente:
1. Escucha: El nodo escucha el canal para verificar si está ocupado.
2. Transmisión: Si el canal está libre, el nodo transmite su mensaje.
3. Colisión: Si dos nodos transmiten al mismo tiempo, ocurre una colisión. Ambos nodos detectan la colisión y esperan un tiempo aleatorio antes de intentar retransmitir.
4. Repetición: Después de un tiempo aleatorio (backoff), los nodos intentan retransmitir.
![[Pasted image 20260814120028.png|center|566]]

**CSMA/CD** es una variante del protocolo CSMA utilizado principalmente en redes Ethernet para mejorar la eficiencia y gestionar las colisiones. Este protocolo permite que los nodos compartan un canal de comunicación, detectando y gestionando las colisiones de manera eficiente. El funcionamiento es el siguiente:
1. Escucha: El nodo escucha el canal para verificar si está libre antes de transmitir.
2. Transmisión: Si el canal está libre, el nodo transmite su mensaje.
3. Detección de colisión: Mientras transmite, el nodo sigue escuchando el canal. Si detecta que otro nodo también transmitió, ocurre una colisión.
4. Señal de colisión: Ambos nodos detienen la transmisión y envían una señal de colisión a la red.
5. Espera y retransmisión: Los nodos esperan un tiempo aleatorio y luego intentan retransmitir sus datos.
![[Pasted image 20260814120112.png|center|555]]

## Ethernet

**Ethernet** es una tecnología de red de área local (LAN) utilizada para la transmisión de datos entre dispositivos dentro de una red. Tiene la principal ventaja de que es muy económica y simple.

La **topología de bus** fue una de las primeras estructuras utilizadas en Ethernet. En esta topología, todos los dispositivos de la red están conectados a un único cable compartido llamado bus o backbone, a través del cual se transmiten los datos. Esto presenta una alta probabilidad de colisiones. Si la red crece, se la divide en segmentos (dominios de colisión). 
![[Pasted image 20260814120141.png|center|194]]

En una **topología de estrella**, cada computadora o host de la red se conecta a un switch central. Este tipo de configuración es común en las redes modernas porque mejora la eficiencia y confiabilidad en comparación con la topología de bus. Tiene las siguientes características:
- Cada computadora se conecta a un switch.
- Cada host se puede conectar o desconectar sin afectar al resto de la red.
- Dirige los datos por el puerto al que está conectado el host, pudiendo encolar distintas tramas (frames).
- Se basan en el número de placa (MAC address)
- Se deben evitar los ciclos.
![[Pasted image 20260814120216.png|center|149]]

La **dirección MAC** es un identificador único asignado a la interfaz de red de un dispositivo, como una tarjeta de red (NIC), que permite la identificación y comunicación en la capa de enlace de datos del modelo OSI (Capa 2). La dirección MAC es única para cada dispositivo de red, ya que está asignada por el fabricante de la tarjeta de red y no se repite. De hecho, el primer bloque de la dirección MAC identifica al fabricante (Organizationally Unique Identifier, OUI). 

El formato es el siguiente:
- Una dirección MAC tiene 48 bits (6 bytes) de longitud.
- Usualmente se representa en formato hexadecimal y se divide en 6 grupos de 2 dígitos, separados por dos puntos o guiones, por ejemplo: `00:1A:2B:3C:4D:5E`.
- Primer bloque (los primeros 3 bytes): OUI (Organizationally Unique Identifier). Este bloque identifica al fabricante de la tarjeta de red.
- Últimos 3 bloques (los siguientes 3 bytes): Identificador único del dispositivo asignado por el fabricante.  
- Dirección global vs. local: Si el primer bit del primer byte es `0`, la dirección MAC es globalmente única (es decir, asignada por el fabricante). Si el primer bit es `1`, la dirección MAC es localmente administrada, lo que significa que puede ser configurada por el administrador de red.
![[Pasted image 20260814120320.png|center|526]]

Las tramas Ethernet tienen la siguiente estructura:
![[Pasted image 20260814120340.png|center]]
- `Preámbulo`: secuencia de bits (alternancia de unos y ceros) utilizada para sincronizar los dispositivos que están enviando y recibiendo la trama. Ayuda a que el receptor detecte el inicio de la trama.
- La `dirección MAC` del dispositivo al que se envía la trama y luego de quien lo envía. Es un identificador único asignado a cada interfaz de red.
- `SFD`: marca el comienzo real de la trama y señala el final del preámbulo. Es una secuencia especial de bits (`10101011`) que indica al receptor que la trama está a punto de comenzar.
- `EtherType`: indica el protocolo de la capa superior que se está utilizando en la trama. Por ejemplo, `0x0800` para IPv4, `0x0806` para ARP, y `0x86DD` para IPv6.
- `Datos`: carga útil de la trama, es decir, la información real que se está transmitiendo. Este campo puede contener desde 46 hasta 1500 bytes de datos.
- `CRC`: Valor calculado que asegura la integridad de la trama.

## Address Resolution Protocol (ARP)

**ARP (Address Resolution Protocol)** es un protocolo de la capa de red utilizado para resolver direcciones IP a direcciones MAC en redes locales, como Ethernet. Cuando un host quiere comunicarse con otro dentro de la misma red local y solo conoce su dirección IP, necesita saber cuál es su dirección MAC para poder encapsular la trama correctamente. ARP permite hacer esta traducción.
![[Pasted image 20260814120515.png|center|485]]

El protocolo ARP se utiliza de 4 formas
- **ARP**: un host con dirección IP necesita conocer la dirección MAC de otro host del cual conoce la dirección IP.
- **RARP**: un host sin almacenamiento (diskless workstation) conoce su dirección MAC pero “olvidó” su dirección IP.
 - **InARP**: un host conoce la dirección MAC de otro host pero no su IP.
 - **Proxy ARP**: un host responde a un request para otro host.

Tomemos el siguiente ejemplo. En ambos casos el host A envía un paquete IP al host B. Suponiendo que las tablas ARP están vacías, ¿cuántos paquetes ARP se envían en cada caso?
![[Pasted image 20260814120555.png|center|439]]
1. A examina su tabla de ruteo y determina que el gateway para llegar a B es `192.168.2.1`.
2. A envía ARP request. ![[Pasted image 20260814120628.png|center|415]]
3. El router envía ARP reply. ![[Pasted image 20260814120700.png|center|423]]
4. A envía paquete IP. ![[Pasted image 20260814120723.png|center|424]]
5. El router examina su tabla de ruteo y determina que B está en la misma red `10.2.0.0/16`. 
6. El router envía ARP request. ![[Pasted image 20260814120800.png|center|426]]
7. B envía ARP reply. ![[Pasted image 20260814120826.png|center|426]]
8. El router envía paquete IP  a B. ![[Pasted image 20260814120855.png|center|425]]
**Proxy ARP** es una técnica donde un dispositivo (como un router o firewall) responde a solicitudes ARP en nombre de otro dispositivo que está en una red diferente, como si fuera él mismo. Permite que dos dispositivos en subredes distintas se comuniquen como si estuvieran en la misma red local, sin necesidad de configurar rutas explícitas o usar un gateway.

Tomemos el siguiente caso. Si el host A solicita nro MAC de C o D, el router responde con su propio nro MAC, por lo que la relación entre número de MAC y nro de IP no es 1 a 1.
![[Pasted image 20260814120927.png|center|454]]

ARP no contempla autenticación, cualquiera puede responder un ARP request para relacionar un IP con un MAC, lo que permite distintos tipos de ataque:
- Man-in-the-middle
- Denial-of-service
- Session hijacking

Tomemos el siguiente caso. El host A, una vez  que aprende las direcciones IP, envía ARP reply en forma periódica con las IPs conocidas y su MAC. 
![[Pasted image 20260814121011.png|center|325]]

Los hosts comenzarán a enviar paquetes con IP correcta pero con la MAC del atacante. ¿Qué debe hacer el atacante para negarle servicio a B y C? Para realizar un ataque de Denegación de Servicio (DoS), el atacante simplemente no reenvía los paquetes que recibe destinados a B y C o incluso descarta directamente los paquetes entrantes, bloqueando toda comunicación hacia esos hosts. Puede también enviar respuestas falsas adicionales diciendo que la IP de B no está disponible.

¿Cómo se pueden defender los hosts? Algunas opciones son:
- Tablas ARP estáticas: configurar entradas fijas IP-MAC en los dispositivos críticos. Imposibilita la sobrescritura por ARP spoofing.
- Uso de protocolos seguros: por ejemplo, HTTPS, SSH o IPSec, para cifrar y autenticar el tráfico aunque se intercepte.
- Switches inteligentes: configurar funciones como Port Security, DHCP Snooping y Dynamic ARP Inspection en switches de nivel 2 gestionables.

Existen algunos usos legales de ARP spoofing:
- Redireccionar equipos no registrados a una página de registro
- Acceso a Internet en hoteles a dispositivos móviles
- Implementar redundancia en servicios de red

## Caso Práctico

Tomemos el siguiente caso. Asumiendo que las tablas ARP están vacías, detallar los paquetes que se generan en la red privada si se enciende el host A y se conecta con HTTP a `campus.itba.edu.ar`.
![[Pasted image 20260814121112.png|center|447]]

El procedimiento es el siguiente:

| **Protocolo**     | **Detalle**          | **Origen**        | **Destino**                 |
| ----------------- | -------------------- | ----------------- | --------------------------- |
| **DHCP discover** | id/mac               | `0.0.0.0`         | `255.255.255.255`           |
| **DHCP offer**    | yaddr: `10.1.1.3`    | `10.1.1.5`        | `10.1.1.3` (MAC: broadcast) |
| **DHCP request**  | -                    | `0.0.0.0`         | `255.255.255.255`           |
| **DHCP ack**      | -                    | `10.1.1.5`        | `10.1.1.3` (MAC: broadcast) |
| **ARP request**   | MAC de `10.1.1.4`?   | MAC de `10.1.1.3` | `FFFF...`                   |
| **ARP reply**     | MAC de `10.1.1.4`    | MAC de `10.1.1.4` | MAC de `10.1.1.3`           |
| **DNS query**     | IP de campus?        | `10.1.1.3`        | `10.1.1.4`                  |
| **DNS response**  | IP de campus         | `10.1.1.4`        | `10.1.1.3`                  |
| **ARP request**   | MAC de `10.1.1.1`?   | MAC de `10.1.1.3` | `FFFF...`                   |
| **ARP reply**     | MAC de `10.1.1.1`    | MAC de `10.1.1.1` | MAC de `10.1.1.3`           |
| **TCP syn**       | puerto destino: `80` | `10.1.1.3`        | IP de campus                |
| **TCP synack**    | -                    | IP de campus      | `10.1.1.3`                  |
| **TCP ack**       | -                    | `10.1.1.3`        | IP de campus                |
| **HTTP**          | `GET`                | `10.1.1.3`        | IP de campus                |
| **HTTP**          | `301`                | IP de campus      | `10.1.1.3`                  |
| **TCP rst**       | -                    | `10.1.1.3`        | IP de campus                |
Si el servidor DNS no conoce la respuesta, debe ir a `8.8.8.8` a buscarla, como se ve en la imagen. No hacemos el caso porque es lo que venimos viendo. En el parcial puede ser que no aparezca un ejercicio donde se tenga que ver si está en desorden o hay pasos de más.

En el caso de HTTP, nos va a pedir que se use HTTPS, por lo que devuelve un redirect (`301`). Se debe repetir el proceso desde el TCP `syn` pero en lugar de al puerto `80`, irá al puerto `443`. Si hubiéramos ido directo a HTTPS, nos ahorrábamos todo ese paso.
