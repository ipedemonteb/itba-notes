## SSL

Todas las capas que estudiamos hasta ahora (HTTP y TCP) no ofrecen ningún tipo de seguridad para transferir información. Podríamos usar una capa entre HTTP y TCP que encripte y desencripte. Vamos a ver un concepto básico para esto. 

Cuando entramos a un banco y tenemos un candado en el browser en la parte superior, es porque estamos en una conexión segura. Para encriptar datos desde y hacia el servidor, un Web Server puede usar **SSL (Secure Sockets Layer)**, que es un protocolo desarrollado por Netscape en 1994. Es una capa intermedia entre los protocolos de aplicación y transporte. Permite a un servidor que "hable" SSL autenticarse a sí mismo con un cliente que “hable” SSL, así como a un cliente autenticarse con un servidor y encriptar la conversación entre ambos.

## Encriptación

Para poder hacer esto, vemos el siguiente caso con Roy y Moss. Al querer intercambiar información de forma segura, el texto plano de Roy se encripta mediante un algoritmo con la clave de Roy. Esta clave puede ser única para cada end o puede ser la misma, según el algoritmo. Una vez que llega el texto cifrado, se debe aplicar el algoritmo de desencriptación con la clave de Moss para obtener nuevamente el texto plano y que Moss lo pueda leer.

- $M$: Mensaje en texto plano
- $K_R(M$): Mensaje cifrado con clave $K_R$
- $M=K_R(K_R(M))$

Otro mecanismo son las **[[04. Cifrado Asimétrico y Firma Digital#Criptografía Asimétrica|claves asimétricas]]**, donde el texto codificado con la clave pública de Moss sólo se puede desencriptar con la clave privada de Moss. De esta forma se logra asegurar la confidencialidad. Se usa generalmente para compartir la clave y luego un algoritmo robusto con clave compartida.

Esto tiene otra arista. Lo que se encripta con la clave privada, sólo se puede desencriptar con la pública. Esto sirve para validar autenticidad, demostrando que fue encriptado por la clave pública de la que viene.

Pero ahora, ¿cómo hace Roy para asegurarse que habla con Moss y no con alguien que se hace pasar por él? Le envía una frase encriptada para que Moss lo desencripte y lo encripte con su privada, para así validar que realmente es él.

## Certificados

SSL permite la creación de **certificados**. Sirven para tener autenticidad de que cuando nos conectamos a un sitio, sea realmente ese sitio:
1. Crear una clave pública y privada.
2. Crear un certificado que incluya la clave del servidor.
3. Firmar el certificado, por un CA (entidad certificante) reconocido o por uno mismo.

Cuando me conecto al puerto `443` (seguro) me descarga el certificado si no lo tengo. Puedo confiar en el certificado por la firma de la entidad. Los browser suelen traer algunos certificados por default.

## TLS (Transport Layer Security)

[[05. Protocolos Criptográficos#Canal Seguro TSL|TLS 1.0]] es un protocolo basado en SSL 3.0 (a veces TLS es llamado SSL 3.1). RFC 5246 define TLS 1.2. Ofrece conexión segura por puerto: `443` para HTTPS, `993` para IMAPs, `995` para POPs, etc; y usa SSL. Brinda a su vez conexión segura por protocolo: comienza con un `hello` inseguro y luego cambia a una conexión segura. Un ejemplo es el comando `STARTTLS` en SMTP. TLS y SSL proporcionan el mismo nivel de encriptación. Difieren en cómo se inicia la conexión segura.

Esto sirve sólo con conexiones que usen TCP, es decir que tengan aplicaciones en un servidor. No es el caso de DNS, por lo que no se puede usar en este caso. Para usar un DNS en forma segura, podemos directamente aprovechar HTTPS y la encriptación.

## DNS Over TLS

Como dijimos antes, la manera de usar DNS de forma segura es aprovechar la encriptación con HTTPS y TLS. Por defecto, toma el puerto `853` y está incorporado en forma nativa en algunos Linux. Presenta dos modos:
- **Modo Estricto**: Toda la parte recursiva DNS es siempre segura. Es decir si no tiene la respuesta y se debe buscar en otro lado, esta otra conexión debe ser también segura.
- **Modo de Privacidad Oportunista**: Intenta establecer la conexión encriptada mediante TLS. Si el servidor DNS de destino no lo soporta o falla la negociación segura, degrada automáticamente a la consulta DNS tradicional sin encriptar (puerto `53`) en lugar de bloquear el tráfico.
![[Pasted image 20260813202008.png|center|401]]

El cliente usa `GET` o `POST` para enviar una query DNS codificada. Esto nos deja tranquilos de que todos los nombres que resolvemos son seguros.

## HTTPS y Proxy HTTP

Como vimos, los proxies HTTP se utilizan para cachar contenido, filtrar accesos y mejorar el rendimiento. Cuando el tráfico es HTTP, el proxy puede inspeccionar, modificar y almacenar las respuestas. Con HTTPS, el tráfico está cifrado entre el cliente y el servidor, lo que impide que un proxy vea el contenido directamente. Entonces, ¿cómo logran los proxies bloquear sitios o cachear contenido cifrado?

Para inspeccionar HTTPS, los proxies utilizan técnicas de "Man-in-the-Middle" (MITM), que funcionan de la siguiente manera:
1. El cliente inicia una conexión HTTPS a un sitio web.
2. El proxy intercepta la conexión y genera un certificado falso en su lugar.
3. Si el cliente confía en el certificado del proxy (porque fue instalado por el administrador de red), la conexión es aceptada.
4. El proxy establece otra conexión segura con el servidor real y retransmite los datos.

Esto permite que el proxy lea y modifique el contenido antes de reenviarlo al cliente. Es común en redes corporativas, escuelas y gobiernos para filtrar contenido o aplicar políticas de seguridad.

Para detectar un proxy MITM:
- Verificar el certificado SSL en el navegador.
- Si el emisor del certificado no es la entidad oficial (ejemplo: Let's Encrypt, DigiCert), podría ser un MITM.
- Uso de herramientas como Wireshark o extensiones de navegador para inspeccionar la conexión.

Las limitaciones del MITM son:
- No funciona si el cliente no confía en el certificado del proxy.
- Sitios con HSTS (HTTP Strict Transport Security) pueden rechazar conexiones con certificados no confiables.
- Algunas aplicaciones y navegadores alertan sobre certificados sospechosos.

Aún sin romper el cifrado HTTPS, los proxies pueden bloquear sitios web analizando el SNI (Server Name Indication) en el handshake TLS, filtrar a nivel DNS evitando que los clientes resuelvan ciertos dominios  y usar listas de IP bloqueadas de servidores sospechosos. Esto permite restringir accesos sin necesidad de ver el contenido real.

En conclusión, los proxies pueden inspeccionar HTTPS mediante MITM, pero requieren un certificado confiable en el cliente. Sin romper el cifrado, pueden bloquear sitios mediante SNI, DNS o IPs bloqueadas. Esta es una técnica utilizada en empresas, gobiernos y redes educativas. Los usuarios pueden detectar y mitigar MITM revisando certificados y usando herramientas de seguridad.
