## Introducción

**Secure Shell (SSH)** es un protocolo pero también puede ser visto o analizado como una herramienta para encriptar, una aplicación cliente/servidor o una interfaz de comandos. En su forma más habitual o común SSH puede ser visto como un reemplazo seguro para Telnet, ya que tanto los comandos como los datos viajan encriptados. Aunque SSH es mucho más potente y versátil que un mero login remoto encriptado.

El protocolo SSH ofrece:
- **Autenticación**: SSH utiliza SSL, es decir que en la primera conexión se piden los certificados. 
- **Encriptación**: En el caso superior de la siguiente imagen, podríamos tener spoofing mediante un man in the middle.
- **Integridad**: Se asegura que no se alteren los datos enviados.
![[Pasted image 20260814121705.png|center|581]]

SSH es el reemplazo seguro de varias aplicaciones:
![[Pasted image 20260814121728.png|center|453]]

Los principales servidores SSH son:
- OpenSSH: Windows, Unix y Linux
- SSH Communications: Windows, Unix y Linux 
- VanDyke's Vsheel, Bit Vise.

Nosotros utilizaremos OpenSSH, que viene instalado por defecto en las distribuciones Linux.

## OpenSSH

Las componentes básicas de OpenSSH:
- `sshd`: Es el demonio que maneja las conexiones entrantes. No debe ser iniciado por `inetd` o `xinetd`. 
- `ssh`: Comando que reemplaza a otros como `rsh` y `rlogin`, para loguearse en forma remota o enviar un comando a un servidor remoto.
- `scp`: Versión segura de `rcp`, que permite copiar archivos.
- `sftp`: Versión segura de FTP.
- `ssh-keygen`: generador de claves públicas y privadas.

El archivo principal de configuración es `/etc/sshd_config`. Algunas de las opciones generales son:
```properties
#Port 22
#Protocol 2,1
#ListenAddress 0.0.0.0
#ListenAddress ::

#LoginGraceTime 120
PermitRootLogin no
#StrictModes yes
```

Por defecto escucha del puerto `22`, pero podríamos cambiarlo para esconderlo si es de uso personal. Cualquier hacker intentará acceder a ese puerto para ganar acceso a nuestra computadora. 

Vemos en la configuración que tiene dos versiones, pero es recomendado no usar la 1 porque tiene agujeros de seguridad. Además, podemos declarar las IPs de la que puede escuchar. En el primer caso, IPv4 y en el segundo IPv6, ambos con todos ceros para escuchar todos. 

El `LoginGraceTime` es un tiempo que se otorga para realizar el login, porque si se generan muchas conexiones y se llega al límite, no se van a aceptar nuevas y nos pueden hacer un DoS. Luego se puede permitir el acceso como root y que las carpetas como la .ssh estén invisibles.

Un ejemplo de uso:
```bash
user@server:~$ ssh pi@pampero.itba.edu.ar
Password: ******
Last Login Wed May 4 16:12:22 from ....
Linux 2.4.25-lids1.2.0rc2
user@server:~$ ...
user@server:~$ logout
```

Se puede además hacer la ejecución remota de un comando en lugar de conectarse.
```bash
user@server:~$ ssh user@host rm / tmp - r
```

Algunos flags útiles son:

| **Opción**                       | **Descripción**                                                      |
| -------------------------------- | -------------------------------------------------------------------- |
| **`-1`**                         | Fuerza ssh a usar SSH versión 1.                                     |
| **`-2`**                         | Fuerza ssh a usar SSH versión 2.                                     |
| **`-C`**                         | Comprime los datos.                                                  |
| **`-c blowfish \| 3des \| des`** | Elegir método de encriptación.                                       |
| **`-v`**                         | Muestra información de depuración (_verbose_).                       |
| **`-4`**                         | Forzar a IPv4.                                                       |
| **`-6`**                         | Usar únicamente IPv6.                                                |
| **`-E log_file`**                | Envía la información de depuración (_debug_) a un archivo.           |
| **`-p port`**                    | Usar un puerto distinto a 22.                                        |
| **`-N`**                         | Sólo conecta, no ejecuta comando remoto (útil para port forwarding). |
La última opción permite conectar pero no figura un prompt para ejecutar comandos. Más adelante vamos a ver para qué puede servir.

## Local Port Forwarding

Como se establece una conexión, se utiliza TCP. Podríamos aprovechar que el SSH está en el mismo servidor por ejemplo de una base de datos Postgres u otra aplicación para utilizar la encriptación y demás beneficios de SSH para comunicarse con el cliente. SSH permite hacer túneles y transferir datos de la aplicación entre el cliente y el servidor.

En la siguiente imagen, pareciera como si las aplicaciones cliente y servidor estuvieran conectadas directamente pero en realidad se aprovecha SSH para encriptar en forma transparente el flujo de datos. Esto es mejor que estar trabajando con muchos puertos. 
![[Pasted image 20260814122230.png|center|539]]
```bash
ssh -L8080:webserver: 80 SSHserver
```

Con este comando se corre un socket pasivo en el cliente ssh, que se conecta al servidor ssh en el puerto 80, que podría ser también otro puerto o incluso una IP de la red local. 
- `-L8080:webserver:80`: indica que se está creando un túnel local.
- `8080`: es el puerto local en el host cliente (puede ser localhost:8080).
- `webserver`: es el nombre o IP del servidor al que se quiere llegar (desde el servidor SSH).
- `80`: es el puerto del destino (el puerto típico de HTTP).
- `SSHserver`: es el servidor SSH al que se quiere conectar para establecer el túnel.

En este caso SSH, que es un protocolo de aplicación, está llevando datos de otro protocolo de aplicación.

![[Pasted image 20260814122411.png|center|613]]

El túnel es local o remote según dónde se encuentra el socket pasivo. Si está en el cliente, el túnel es local. Otro comando para crear un túnel por ejemplo en pampero:
```bash
ssh ipedemonteberthoud@pampero.itba.edu.ar -L 127.0.0.1:1234:localhost:1234
```

Esto lo que hace es crear un socket pasivo en localhost (`127.0.0.1`) en el puerto `1234`, por lo que los primeros dos "parámetros" son para el socket pasivo. Los segundos son para el socket activo, en este caso pampero, que lo creará en localhost en el puerto `1234`. Podemos evitar el `127.0.0.1` ya que es el por defecto que toma `ssh`, como en el caso de arriba.

Para un túnel remoto se usa `-R` y se mantiene el resto igual, por lo que el primer parámetro sigue siendo para el socket pasivo (ahora en el servidor) y el segundo para el activo. 

Como dijimos, LPF funciona sólo con TCP, no funciona con protocolos basados en UDP como DNS, DHCP, NFS, NetBIOS. Veamos el siguiente caso: Moss quiere conectarse a un servidor SMTP remoto pero por alguna razón no puede o no quiere hacerlo directamente.
![[Pasted image 20260814122551.png|center|459]]
Moss accede a un servidor web que está "escondido" en una red privada. Pero tenemos acceso a un servidor SSH dentro de esa red. En la imagen se usa HTTP pero no cambia nada para el ejemplo.
![[Pasted image 20260814122623.png|center|514]]
Primero, debe establecer la conexión
```bash
moss@reynholm~$ ssh -L2001:10.1.0.10:80 -1 user sshserver
```
Se establece una sesión remota con el servidor sshserver pero además hará que todo lo enviado al puerto local 2001 sea enviado a través de la sesión SSH al puerto 80 de webServer. Para acceder a un recurso del webserver se puede hacer:
```bash
moss@reynholm~$ curl localhost:2001 ...
```
El procedimiento es el siguiente:
1. `Curl` se conecta con TCP a (localhost:2001).
2. Envía los requests .
3. El cliente local SSH lee el puerto `2001`, encripta los datos, y los envía al servidor SSH.
4. El servidor SSH desencripta los datos y los envía a `10.1.0.10:80`.
5. Las respuestas son enviadas por el mismo túnel.

¿Qué debería cambiar si el servidor web funciona en el mismo host que el servidor SSH? En este caso, no hace falta redirigir el tráfico a otro equipo de la red interna, porque el destino ya es el propio servidor SSH. Solo se necesita que el SSH reenvíe el tráfico al puerto `80` local.

Para el web server ¿quién hizo el request? Para el web server, el request provino del mismo host en el que está corriendo, es decir, del localhost (o `127.0.0.1`). Desde su punto de vista, la conexión entró localmente, no desde una máquina remota. 

También se puede hacer forwarding, pues el socket escucha solamente de `127.0.0.1`, por lo que solamente nosotros podemos acceder. Con el flag `-g` se genera que se escuche de `0.0.0.0`, por lo que, en la siguiente imagen, para los dos personajes superiores el web server va a estar en la IP privada de Moss. Esto se conoce como **gateway**.
![[Pasted image 20260814155621.png|center]]
```bash
sshclient:~$ ssh -g -L2001:webserver:80 -1 user sshserver
```

Tomemos el siguiente caso: tenemos que presentar para PAW y el integrante que prepara la BD nos pasa la siguiente IP: `192.168.1.15`. Claramente la IP es privada, por lo que no nos podemos conectar. Ahora tenemos un caso inverso al que vimos previamente, porque ahora la aplicación servidor está en el cliente ssh. Entonces, lo que debe hacer nuestro integrante es crear un túnel local, es decir con las bocas invertidas, como se ve a continuación.
![[Pasted image 20260814155706.png|center|549]]

Entonces ahora nuestra base de datos va a estar en pampero en el puerto `9999`. 
```bash
ssh -R9999:webserver: 80 pampero.itba.edu.ar
```
Esto tiene una contra, y es que no vamos a poder regular quienes acceden como en gateway. Todo pampero se va poder conectar a ese puerto, teniendo o no acceso. 

Supongamos que estamos en la época del ITBA donde los laboratorios no tenían acceso a internet, ya que el proxy no tomaba los pedidos de la IP de esa subred. Lo que hacían los estudiantes de informática, era crear túneles locales con pampero porque para el proxy, era pampero quien hacía la solicitud y sí tenía acceso. Pero para esto se necesita el servidor destino y sabemos que los recursos no siempre están en el mismo. Entonces, en su lugar se debe usar un **túnel dinámico**.
```bash
ssh -D 9090 pampero.itba.edu.ar
```
Este tipo de túnel no se puede usar para cualquier cosa, ya que utiliza un tipo especial de socket dinámico. Esto nos puede servir también por ejemplo para ser anónimos para el proxy del ITBA, ya que para él sería pampero el que hace todos los pedidos.

## Autenticación

Existen tres formas de autenticar un cliente SSH:
- **Claves**: Es la forma más común y controla que el nombre de usuario y clave sean válidos, generalmente usando el archivo `/etc/passwd` o `/ etc/shadow`. Se puede deshabilitar:
```properties
PasswordAuthentication no
```
- **Claves Públicas**: Requiere que cada usuario genere un archivo con su clave pública y otro con su clave privada. La clave pública debe ser copiada al servidor y la clave privada debe estar en el host. En el archivo `sshd_config` debe figurar:
```properties
PubkeyAuthentication yes

AuthorizedkeysFile  .ssh/authorized keys
```
- **Basada en el host**.

Pasos a seguir en el host cliente Linux
```bash
user@server:~$ ssh-keygen -d
Generating public/private dsa key pair.
Enter file in which to save the key
   (/home/.../.ssh/id_dsa) :
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
Your identification has been saved in id dsa Your public key has been saved in id ds.pub
```
Ahora el usuario dispone de archivos con clave pública y clave privada. Debe conservar la clave privada en el o los hosts origen y almacenar la clave pública en el o los hosts destino. Pasos a seguir en el host servidor: Copiar el archivo `.pub`:
```bash
user@server:~$ cd
user@server: ~$ cat id_dsa. pub >>.ssh/authorized_keys
user@server:~$ rm id dsa.pub
```

## Modelo de Capas SSH

El modelo de capas para ssh es el siguiente:
![[Pasted image 20260814160103.png|center|436]]

**Transporte (SSH Transport Layer Protocol)**:
- Provee autenticación de servidor, privacidad e integridad
- Opcionalmente puede comprimir datos
- Utiliza los servicios de TCP
**Autenticación (SSH User Authentication Protocol)**:
- Provee autenticación del lado del cliente
**Conexión (SSH Connection Protocol)**:
- Se encarga de multiplexar el túnel seguro  en los distintos canales lógicos
- Algunos canales lógicos posibles
	- Sesiones de shell seguras
	- TCP port forwarding
	- Conexiones X11
