## Previo a HTTP

Para establecer una conexión entre dos dispositivos, se requiere que ambos utilicen los mismos protocolos. Vía FTP se obtenía un documento o texto. En base a las referencias se debía acceder a otro sitio FTP y descargar el/los textos deseados. Surge la necesidad de aplicaciones basadas en "hipertextos".

En 1991 surge HTTP 0.9, un protocolo basado en texto de recuperación de información. 
- Mecanismo request – response.
- Contenido estático.
- No mantiene estado (no establece una sesión).
- Orientado a "línea de comando".
![[Pasted image 20260811110610.png|center|495]]

En 1996, surge el protocolo HTTP 1.0, donde ya no sólo se orienta sólo a hipertextos, haciéndolo browser friendly. Se tienen códigos de estado y comandos como `GET`, `POST`, `HEAD`.
![[Pasted image 20260811110645.png|center|568]]

En un HTML con 6 imágenes, no vale la pena hacer 6 request por cada una, ya que se debe establecer una conexión por cada una. Se requirieron **conexiones persistentes**, es decir que no se corte la comunicación una vez enviado el recurso.

Esto se implementó en HTTP 1.1 (1999), y se agregaron además cabeceras en las peticiones y los métodos `PUT`, `DELETE`, `TRACE`, `OPTIONS`. Cada recurso se identifica con una **URI (Uniform Resource Identifier)**. Se incluyó también la negociación de contenido y la posibilidad de crear headers extendidos, ya que el recurso podría ser código, un programa al que se le pasan parámetros.
![[Pasted image 20260811110737.png|center|553]]

Finalmente, surgió HTTP/2, que consiste de un protocolo binario con compresión de headers, multiplexación de recursos y server push, que consiste en enviar los recursos mientras se parsea el HTML para ganar tiempo y anticiparse.

Un **recurso** es un bloque de información identificado por su URI. Puede ser un archivo (físico) o generado por un programa (abstracto). Para obtener el recurso:
```xml
<scheme>://<authority><path>?<query>
```
El `path` termina con el primer `?` o `#`, o si no hay más caracteres. Puede ser relativo o absoluto. Si representa una aplicación puede recibir parámetros.

La **Uniform Resource Locator (URL)** identifica el recurso por su ubicación:
```xml
<scheme>://<user>:<password>@<host>:<port>/<path>?<query>
```
- **`<scheme>` (Esquema/Protocolo):** Protocolo a utilizar (por ejemplo: `HTTP`, `FTP`, `FILE`).
- **`<user>:<password>` (Credenciales):** Algunos sitios o recursos requieren autenticación.
- **`<host>` (Host/Servidor):** Dominio o dirección IP del servidor.
- **`<port>` (Puerto):** Puerto de red de destino (opcional si es el puerto por defecto, por ejemplo `80` para HTTP).
- **`<path>` (Ruta):** Identificación del recurso dentro del servidor.
- **`<query>` (Consulta/Parámetros):** Parámetros enviados al recurso (separados por `&` y precedidos por `?`).

Algunos ejemplos:
```
http://soyyo:miclave@www.unsitio.com:90
http://192.168.0.100
http://localhost:8080
http://soyyo:miclave@www.unsitio.com:90/index.html
http://soyyo:miclave@www.unsitio.com:90/pagZZ.html?width=1024&lang=es
```

Al final se puede incluir un fragmento de la siguiente forma:
```
http://www.unsitio.com/intro.html#chapter1
```

La **Uniform Resource Name (URN)** identifica un recurso por su nombre. No implica que el recurso exista o cómo acceder a él.
```
urn:isbn:0132856204
urn:isan:0000-0002-3C36-0000-Y-0000-0000-9
urn:uuid:6e8bc430-9c3a-11d9-9669-0800200c9a66
urn:www.apache.org:
```

Las URIs pueden ser usadas para acceder a recursos, ya sea por medio de URL o URN. Por ejemplo, en HTML:
```
<a href="/img/logo.png">
<a href="urn:isbn:0453457513">
```

## Mensajes HTTP

El cliente y el servidor intercambian **mensajes HTTP**:
- **Request message**: cliente → servidor
- **Response message**: servidor → cliente

Las **solicitudes (request)** son:
- `GET`: Solicita un recurso al servidor.
- `HEAD`: Solicita solo los headers del recurso.
- `POST`: Envía información al servidor para ser procesada.
![[Pasted image 20260811131919.png|474]]

Podemos ver el siguiente ejemplo, que muestra tal cuál viaja la información. Si una persona pudiera interceptarlo accedería a toda la información:
![[Pasted image 20260811132029.png|center|532]]

Vemos que por más que se establece una conexión, se identifica el host clarín porque un mismo servidor puede tener por ejemplo también el de la nación. Para identificar el contenido del recurso se deja una línea vacía, buscando una solución lo más simple posible.

Las **respuestas (response)** tienen un start line con versión, código de respuesta y mensaje:

| Rango     | Significado / Descripción                          |
| :-------- | :------------------------------------------------- |
| **`1XX`** | Información – El proceso continúa                  |
| **`2XX`** | Éxito - Acción recibida, comprendida y aceptada    |
| **`3XX`** | Redirección – Se requiere nueva acción             |
| **`4XX`** | Error en cliente – Sintaxis y/o Semántica inválida |
| **`5XX`** | Error en servidor – Falló pedido correcto          |

## Tipos de Información

Si HTTP sólo transmite texto, ¿cómo puedo transferir imágenes, video, etc.? Utiliza **Multipurpose Internet Mail Extensions (MIME)** para describir contenido multimedia. Cada objeto es etiquetado por el web server:
- text/html
- text/plain
- video/mp4
- image/jpeg
- application/pdf
![[Pasted image 20260811132359.png|center|507]]

Si comparamos los tipos de request `GET` y `POST` vemos que:
- Los `GET` pueden ser "cacheados" (si hago f5 y refresco, se tienen guardados en la caché) y los `POST` no.
- Los `GET` son mantenidos en el historial por el browser, mientras que el `POST` no.
- Los `GET` pueden ser "bookmarked" a diferencia de los `POST`.
- Los `GET` tienen longitud acotada porque los parámetros son parte de la URL que tiene un máximo. En los `POST` esto no es así.
- Los `GET` son sólo para pedir datos.

El comando `OPTIONS` consulta los métodos permitidos y las capacidades del servidor para un recurso sin modificarlo. La respuesta suele incluir un encabezado `Allow` que lista los métodos disponibles para ese recurso:
![[Pasted image 20260811132516.png|center|501]]

El comando `TRACE` es utilizado para realizar una prueba de diagnóstico, devolviendo el contenido exacto de la solicitud que se envió al servidor. Esto permite verificar el recorrido de la solicitud a través de los proxies y otros intermediarios.

## Headers HTTP

Los **headers** en HTTP tienen la siguiente estructura:
```
<nombre>: <valor asociado>
```
Finalizan con una línea en blanco y se tienen los siguientes tipos que generalmente se envían en el orden planteado:
- Generales
- De solicitudes
- De respuestas
- De contenido

Algunos son headers **generales** son:
- `Cache-Control`: directivas para el cache.
- `Connection`: Se definen opciones de conexión.
- `Date`: Fecha de creación del mensaje.
- `Transfer-Encoding`: Indica el encoding de transferencia .
- `Via`: Muestra la lista de intermediarios por los que pasó el mensaje.

Los headers de **solicitud** son:
- `Accept` : Tipo de contenido aceptado por el cliente.
- `Accept-Charset`: Charset (ISO-xxxx, UTF-8) aceptado por el cliente.
- `Accept-Encoding`: Encoding (gzip, compress) aceptado por el cliente.
- `Expect`: Comportamiento esperado del server frente al request.
- `From`: Email del usuario de la aplicación que generó el request.
- `Host`: Servidor y puerto destino del request.
- `If-Modified-Since`: Condiciona al request a la fecha indicada. 
- `Referer`: URL del documento que generó el request.
- `User-Agent`: Aplicación que generó el request.
- `Upgrade`: solicita que use otro protocolo.
- `Range`: solicita un rango (en bytes) del recurso.

Los headers de **respuesta** son:
- `Age`: Estimación en segundos del tiempo que fue generada la respuesta en el server. 
- `Connection`: close, keep-alive.
- `Location`: URI a redireccionar.
- `Retry-After`: Tiempo de delay para reintento.
- `Server`: Descripción del software del server. 
- `Authorization`: indica que el recurso necesita autorización.

Finalmente, los headers de **contenido** son:
- `Allow`: Métodos aplicables al recurso. 
- `Content-Encoding `: Algoritmo de compresión/codificación aplicado al cuerpo del mensaje (por ejemplo: gzip, deflate).
- `Content-Length `: Tamaño del cuerpo del mensaje en bytes.
- `Content-Location `: Ubicación alternativa o URI directa del recurso devuelto.
- `Content-MD5`: Hash MD5 del cuerpo del mensaje para verificar la integridad del contenido.
- `Content-Type `: Tipo de medio (MIME type) y formato del recurso enviado (por ejemplo: text/html, application/json).
- `Expires`: Fecha de expiración del recurso. 
- `Last-Modified`: Fecha de modificación del recurso

## Proxy Servers

Un **proxy server** actúa como intermediario entre una aplicación cliente y un web server. Cada vez que se solicita un recurso, se hace con el proxy que actúa tanto de cliente como servidor según el momento. Puede ser explícito o transparente.
![[Pasted image 20260811133141.png|center|471]]

Una finalidad es hacer de filtro, ya que todo pasa por él, permitiendo controlar el acceso a determinados sitios o páginas. Por otro lado, tienen la utilidad de almacenar en caché recientes consultas. 
![[Pasted image 20260811133341.png|center|475]]

A diferencia del proxy directo (o Forward Proxy) que se encuentra del lado del cliente, un **proxy reverso** se encuentra del lado del servidor.
![[Pasted image 20260811133602.png|center|502]]

El que genera el recurso, tiene que saber si el mismo es algo que se puede cachear. Tiene que determinar si tiene sentido o no, como por ejemplo si es muy pequeño, no es conveniente. Si el recurso no está en la caché, el proxy lo busca en el servidor. Si luego el cliente vuelve a pedir ese recurso no cacheable, el proxy lo debe volver a buscar. El siguiente caso plantea dos hosts accediendo a un servidor proxy.
![[Pasted image 20260811133625.png|center|507]]

Otra opción es darle un `max_age`, es decir asignarle un tiempo útil que el proxy lo cachea. El browser va a tener también esta directiva, es decir que si pide el recurso nuevamente antes del tiempo establecido, lo va a tener directamente, no necesita ni ir al proxy. Si otro browser quiere el mismo recurso, lo pide y el proxy se lo da directo.
![[Pasted image 20260811133703.png|center|513]]

Si el recurso es pesado, se utiliza `last-modified` para conocer si hubo una modificación y es realmente necesario volver a recibirlo. De esto se encarga el proxy. Si no hubo modificaciones, no lo solicita nuevamente al servidor.
![[Pasted image 20260811133738.png|center|511]]

Estas últimas dos opciones pueden ser combinadas para eficientizar el funcionamiento del proxy server.

## Cookies

Las **cookies** son un pequeño texto de información enviada por el servidor y almacenada por el browser. Se utilizan para mantener un estado entre el cliente y el servidor. El flujo es: el servidor envía la cookie al cliente HTTP (`«set-cookie»` response header) y luego el este retorna la cookie al servidor (`«cookie»` request header). 

La **persistencia** en el contexto de las cookies se refiere a cómo se gestionan y mantienen las cookies en el dispositivo del usuario:
- **Cookies de Desión (Session Cookies)**: Son temporales y se eliminan cuando el usuario cierra el navegador. No tienen una fecha de expiración definida.
- **Cookies Persistentes (Persistent Cookies)**: Son cookies que se guardan en el dispositivo durante un tiempo determinado, incluso después de cerrar el navegador. Estas cookies tienen una fecha de expiración que puede ser horas, días, meses o incluso años, y se utilizan para recordar preferencias o mantener al usuario autenticado en un sitio entre sesiones.

Además se tienen:
- **Third-Party Cookies**: Una cookie creada por un dominio diferente al del sitio web que el usuario está visitando.
- **Secure Cookie**: Una cookie que sólo se transmite a través de conexiones HTTPS seguras, protegiendo la información.

## Herramientas

`cURL` es una herramienta de línea de comandos para transferir recursos en base a URLs a través de diferentes protocolos, como HTTP, HTTPS, FTP, entre otros. Permite enviar solicitudes y recibir respuestas de servidores, útil para probar APIs o realizar descargas de archivos desde la terminal.

Algunos casos incorrectos:
- `curl https:asite.com`
- `curl https:asite.com –head`

Algunos casos correctos:
- `curl http://google.com/humans.txt`
- `curl https://www.google.com/humans.txt -i`
- `curl -X POST -F 'locale=en' url`

Otra herramienta es `wget` que sirve para descargar archivos desde la web a través de protocolos como HTTP, HTTPS y FTP. Es especialmente útil para descargar contenido de forma automática, soportando descargas en segundo plano y reanudación de archivos interrumpidos. Algunos casos de uso:
- `wget https://wordpress.org/latest.zip`
- `wget -i files.txt`
- `wget --limit-rate=500k …`
- `wget -r -l1 -H -nd -A pdf https://ahira.com.ar/revistas/patoruzu`

`Netcat` (o `nc`) es una herramienta de red que permite leer y escribir datos a través de conexiones de red, utilizando los protocolos TCP o UDP. Se le conoce como "la navaja suiza" de las redes, ya que se puede usar para depuración, transferencia de archivos, escaneo de puertos, y establecer conexiones entre sistemas. Algunos casos de uso:
- `netcat www.google.com 80`
- `netcat –l –p 8080 -v`
