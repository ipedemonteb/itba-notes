Los más conocidos son TCP y UDP, y vamos a ver un poco de SCTP. Son los encargados de conectar las aplicaciones. Se ejecutan solamente en las puntas. Se deben usar si o si, no hay manera de bypassearlos.

## Servicios

La capa de transporte provee la comunicación lógica entre dos procesos que corren en distintos hosts, y como dijimos se ejecutan en las "puntas finales". El que envía: separa los mensajes en segmentos y los entrega al nivel de red. El que recibe: reensambla los segmentos en mensajes y los pasa al nivel de aplicación.
![[Pasted image 20260813202815.png|center|482]]

TCP ofrece:
- Flujo de bytes (byte stream): No preserva los límites de los `send()` / `write()`
- Establecimiento de conexión
- Control de flujo
- Control de congestión

UDP ofrece:
- Datagramas
	- Preserva los límites de cada mensaje
	- Servicio de datagramas, no confiable ("mejor esfuerzo", como IP)

NO ofrecen:
- Mínimo de demora o latencia
- Mínimo de ancho de banda

Cuando queremos ofrecer una conexión TCP, tiene que iniciarse un flujo de datos. Además de enviar la información, debe verificar si llegaron porque dijimos que es seguro. Si no se pudieron enviar, debe guardarlos y reenviarlos.

El **socket** es el "canal" que  se crea para enviar y recibir información. La capa de transporte en base al puerto sabe a qué proceso se corresponde la información que llega. 
![[Pasted image 20260813203039.png|center|541]]

## User Datagram Protocol (UDP)

El formato de UDP es el siguiente, donde vemos que los encabezados son mucho más sencillos. El `checksum` sirve para verificar si el mensaje llegó de forma correcta o se corrompió en el trayecto.
![[Pasted image 20260813203702.png|center|498]]

UDP transporta datos de manera no confiable entre hosts. Es no orientado a conexión y no confiable. No ofrece verificación de software para la entrega de segmentos, no reensambla los mensajes entrantes, no utiliza acuses de recibo (`ACK`) y no proporciona control de flujo.

## Demultiplexación Orientada a Conexión

Para la demultiplexación orientada a conexión, cada socket identificado por:
- IP origen
- Puerto origen
- IP destino
- Puerto destino

El Host que recibe usa los 4 valores para dirigir el segmento al proceso que corresponde. Cuando se tienen conexiones simultáneas, cada una opera con su socket. Es como si se abriera un canal por cada cliente que se conecta al servidor.
![[Pasted image 20260813203800.png|center|478]]

La diferencia ahora es que, como hay 3 clientes, hay 3 sockets. Los puertos destino son todos iguales, pero la clave son 4 valores con las IPs, por lo que los pued identificar. Si son de la misma máquina, van a tener misma IP pero puerto distinto, por lo que igual las va a poder diferenciar.

## Transferencia de Datos Confiable

Si el protocolo de red es confiable, se garantiza que no se alteran bits, no se pierden paquetes y estos llegan en orden. La lógica a implementar es muy simple:
```
Sender
1. Esperar llamada de aplicación
2. Leer datos a enviar
3. Armar paquete
4. Pedir a capa de red que lo envíe

Receiver
1. Esperar llamada de nivel de red
2. Leer datos recibidos
3. Extraer datos del paquete
4. Enviar datos a aplicación
```

Para brindar la confiabilidad, TCP debe numerar los paquetes para verificar que llegaron todos, ordenarlos si llegan desordenados y reenviar los que se pierden. El protocolo de red puede alterar algunos bits. Para recuperarse de errores se utiliza `ACK` y `NAK`. El sender debe retransmitir ante `NAK` o falta de `ACK`.

Una posibilidad es el siguiente caso conocido como **stop & wait**.
![[Pasted image 20260813203938.png|center|486]]
Espera a que llega el `ACK` para realizar el segundo envío. Se garantiza el orden. Si no se recibe respuesta, se pone un tiempo máximo. Es muy ineficiente. 
![[Pasted image 20260813204007.png|center|529]]
Entonces, lo que se suele hacer es realizar varios envíos, y el destino envía el `ACK` especificando hasta dónde recibió.
![[Pasted image 20260813204036.png|center|485]]

## Transmission Control Protocol (TCP)

El formato para un mensaje TCP es el siguiente:
![[Pasted image 20260813204125.png|center|494]]

El número de secuencia es para enumerar en cuanto al desplazamiento de bytes. Cada uno tiene lo mismo que el anterior pero sumada la cantidad de bytes en `Data`. El `acknowledgment` es hasta qué número de secuencia espero. Hay paquetes de TCP que son vacíos y lo único que tienen es el `acknowledgment`. Dentro de los flags, el `URG` indica si los datos son urgentes. Por eso se tiene también el `Urgent Pointer`. `RST` sirve para cerrar la conexión abruptamente. `SYN` indica que se está queriendo generar una conexión. `FIN` es para finalizar una conexión de forma "polite". 

TCP ofrece un circuito virtual entre aplicaciones de usuario final.  Es orientado a conexión y confiable. Divide los mensajes salientes en segmentos y reensambla los mensajes en el host destino. Vuelve a enviar lo que no se ha recibido. Tiene control de flujo (RFC 7323) y control de congestión (RFC 5681)

Para establecer la conexión, en primer lugar se debió crear el socket pasivo y esperar conexiones, mientras se encuentra en modo listen. Para generar la conexión, el cliente envía un paquete con el `SYN` en `1` y un número random de `SEQ`. Allí, el cliente entra en un estado llamado `SYN SENT`, es decir esperando que le contesten. Cuando el servidor recibe el `SYN`, envía un paquete con el `ACK` en `1` y el `Ackn` en `x + 1`. El servidor entra en estado `SYN RCVD`. 
![[Pasted image 20260813204337.png|center|517]]

Una vez que se intercambiaron estos mensajes se puede comenzar a enviar información entre cliente y servidor. Los acuse de recibos (`ACK`) no son por segmentos sino por bytes pues el canal es un flujo de datos.
![[Pasted image 20260813204403.png|center|487]]

En el siguiente caso, si se pierde el `seq=120`, podemos ver que no se envía el `ACK` de `180`, porque no se recibió el anterior. Vemos que termina surgiendo un timeout. Cuando se envía el `180` por segunda vez, se descarga.
![[Pasted image 20260813204436.png|center|478]]

El `timeout` no es un valor fijo, porque si es muy pequeño puedo no llegar a mandar la respuesta y hacer muchos envíos. Si es largo y se pierde uno, va a quedar esperando mucho tiempo. Entonces para elegir se toma cuánto tardó la respuesta del saludo inicial para estimar.

Para cerrar la conexión, se manda el pedido de cierre (se enciende el `FIN`). El que manda esta solicitud puede seguir recibiendo pero ya no puede enviar, y puede ser el cliente o servidor. Recordemos que en TCP sólo importa quién es cliente y quién es servidor a la hora de comenzar la conexión.
![[Pasted image 20260813204525.png|center|506]]

## Control de Flujo

El **control de flujo** tiene que ver con las dos puntas, solamente tiene que ver con TCP, no le importa la red. Recordemos que tenemos buffer de entrada y buffer de salida. Puede suceder que mi aplicación esté mandando datos y sature el buffer de entrada de la otra punta (esto puede suceder porque la aplicación de la otra punta no los lee), por lo que los datos que llegan y no se pueden almacenar se dropean. 

En el campo `window` se contempla cuántos bytes hay libres en el buffer de entrada, por lo que se manda siempre. Entonces, podemos decir que el receptor controla al emisor, de modo que el emisor no sobrecargue el buffer del receptor.

## Control de Congestión

El **control de congestión** entra en juego cuando TCP se da cuenta que la red está dropeando muchos paquetes. Esto puede suceder debido a, por ejemplo, cuellos de botella. TCP se da cuenta de que hay paquetes que se están perdiendo por el timeout. 

Por lo tanto, el emisor incrementa la tasa de transmisión (tamaño de ventana) hasta que detecta pérdida de paquete (timeout).
- **Additive Increase**: incrementa tamaño de ventana en relación al MSS (maximum segment size) por cada RTT (round trip time) hasta que detecta pérdida.
- **Multiplicative Decrease**: al detectar pérdida reduce tamaño de ventana a la mitad.
![[Pasted image 20260813204856.png|center|250]]
Esto es interno de cada host.

## Network Address Port Translation (NAPT)

Hasta mediados de los '90, para usar Internet se necesitaba una IP pública en el host. En el caso de las universidades, se tenían laboratorios con computadoras con una IP pública que podían acceder a internet, y las que estaban fuera con una IP privada no. Los routers solamente forwardeaban lo que recibían al destino indicado. No se podía enviar paquetes con IP privada a estos routers.

Entonces, se pensó un nuevo protocolo con muchos más bits que 32, porque no iban a alcanzar. Pero cambiar un protocolo de red llevaría mucho tiempo. Lo que surgió fue darle al router la capacidad de modificar la IP de origen. Si una PC tiene una IP privada y quiere salir a internet, el firewall del router mantiene una tabla con su puerto e IP original y lo manda al internet con la IP pública.
![[Pasted image 20260813205314.png|center|480]]

NAP cambia únicamente la IP, y NAPT puede cambiar tanto network address como el puerto. Esto último se cambia para que pueda haber más de un host eligiendo el mismo puerto de entrada. La tabla que mantiene para NAPT el firewall tiene la siguiente forma:

| **IP origen** | **Pto origen** | **IP destino** | **Pto destino** | **IP salida**  | **Pto salida** |
| ------------- | -------------- | -------------- | --------------- | -------------- | -------------- |
| `192.168.1.2` | `900`          | `200.32.54.11` | `80`            | `24.16.14.132` | `770`          |
| `192.168.1.3` | `900`          | `200.32.54.11` | `80`            | `24.16.14.132` | `771`          |
La IP de salida (la pública) se guarda en la tabla porque se puede tener asignada más de una IP pública.

## Destination Network Address Translation (DNAT)

Hay una opción que consiste en cambiar la IP destino de los paquetes que llegan al router. En el siguiente caso, queremos montar un servidor para la IP `192.168.1.4` en el puerto `8080`. Una opción sería tener dos IPs públicas, asignándole una al servidor y otra para el router. Esto no tiene sentido por el costo y por seguridad, ya que el servidor queda expuesto.

Lo que hacemos es pedirle al firewall que todo lo que llegue al puerto `80` en este caso, se envíe al servidor. Ahora, cuando llega el paquete que quiere abrir una conexión en el puerto `80`, se agrega a la tabla y cambia el IP destino por la del servidor.

## Stream Control Transmission Protocol (SCTP)

**SCTP (Stream Control Transmission Protocol)** es un protocolo de transporte similar a TCP y UDP, pero diseñado para proporcionar una mayor fiabilidad y control en la transmisión de datos. Entre sus características más destacadas se encuentran el soporte para multi-streaming (múltiples flujos de datos independientes dentro de una misma conexión) y multihoming.

**Multihoming** en SCTP permite que un único host esté asociado a múltiples direcciones IP dentro de una misma conexión (o asociación, como se denomina en SCTP). Esto significa que tanto el emisor como el receptor pueden tener varias interfaces de red configuradas y utilizadas por la misma sesión. La principal ventaja es la tolerancia a fallos. Si una de las direcciones o interfaces falla, SCTP puede redirigir automáticamente el tráfico a través de otra dirección disponible, sin necesidad de cerrar o restablecer la conexión. Esto proporciona alta disponibilidad, especialmente útil en entornos donde la continuidad de la comunicación es crítica, como en telecomunicaciones o sistemas industriales.
![[Pasted image 20260813210034.png|center|458]]

**Multistreaming** es una característica clave que permite enviar múltiples flujos de datos independientes dentro de una misma conexión (asociación SCTP). A diferencia de TCP, donde todos los datos viajan en un solo flujo ordenado, SCTP permite dividir la comunicación en streams o flujos separados, lo que evita que un retraso en un flujo afecte a los demás. Esto se conoce como evitar el "head-of-line blocking".
![[Pasted image 20260813210145.png|center|509]]
![[Pasted image 20260813210241.png|center|512]]

SCTP es un protocolo **orientado a mensaje**, lo que significa que preserva los límites de los mensajes que se envían. Cada unidad de datos que se transmite (llamada mensaje o chunk) llega al destino como fue enviada, sin dividirse ni fusionarse con otros mensajes. Esto contrasta con TCP, que es orientado a byte, donde los datos llegan como un flujo continuo de bytes y el receptor no sabe dónde comienza o termina un mensaje original (por lo tanto, se necesitan mecanismos adicionales para delimitar mensajes).
![[Pasted image 20260813210318.png|center|502]]

Gracias a esta orientación a mensajes, SCTP garantiza que cada mensaje completo y separado llegue tal como fue enviado, lo que lo hace más adecuado para aplicaciones que requieren una comunicación clara y estructurada, como señalización en redes de telecomunicaciones o protocolos de control.

El **inicio protegido** en SCTP se refiere a su mecanismo de establecimiento de conexión más seguro y resistente a ataques que el de TCP. Mientras que TCP usa un handshake de 3 pasos (`SYN`, `SYN-ACK`, `ACK`), vulnerable a ataques como SYN flood (donde un atacante satura el servidor con solicitudes falsas), SCTP utiliza un handshake de 4 pasos que incluye un mecanismo de verificación antes de asignar recursos. Este procedimiento se llama cookie mechanism, y funciona así:
1. El cliente envía un `INIT` al servidor.
2. El servidor responde con un `INIT-ACK` que contiene una cookie criptográfica.
3. El cliente responde con `COOKIE-ECHO`, reenviando la cookie.
4. Si la cookie es válida, el servidor responde con `COOKIE-ACK` y se establece la conexión.

Durante este proceso, el servidor no guarda estado hasta recibir la cookie válida, lo que previene el consumo innecesario de recursos y protege contra ataques de denegación de servicio (DoS).
![[Pasted image 20260813210419.png|center|562]]

SCTP realiza el cierre de conexión de manera segura y ordenada, similar a su inicio protegido. Utiliza un proceso simétrico y confiable, evitando que una sola parte pueda cerrar la conexión de forma unilateral sin confirmación. El cierre de conexión en SCTP se realiza en cuatro pasos:
1. Un extremo envía un mensaje `SHUTDOWN` indicando que no enviará más datos.
2. El otro extremo responde con `SHUTDOWN-ACK`, confirmando que recibió la solicitud de cierre.
3. El primer extremo contesta con `SHUTDOWN-COMPLETE`, lo que indica que ambos lados están de acuerdo en cerrar la conexión.
4. Luego se liberan los recursos en ambos extremos.
![[Pasted image 20260813210511.png|center|568]]

Podemos ver la comparación con TCP y UDP en la siguiente tabla:

| **Característica**                                           | **SCTP** | **TCP** | **UDP** |
| ------------------------------------------------------------ | -------- | ------- | ------- |
| Estado almacenado en los hosts                               | SI       | SI      | NO      |
| Transferencia de datos confiable                             | SI       | SI      | NO      |
| Control de congestión                                        | SI       | SI      | NO      |
| Delimitación de límites de mensajes                          | SI       | NO      | SI      |
| Fragmentación e integración de datos                         | SI       | SI      | NO      |
| Multiplexación                                               | SI       | SI      | NO      |
| Soporte de multi-homing                                      | SI       | NO      | NO      |
| Soporte de multi-streaming                                   | SI       | NO      | NO      |
| Envío de datos desordenado                                   | SI       | NO      | SI      |
| Cookie de seguridad para evitar ataques de inundación de SYN | SI       | NO      | NO      |
| Mensaje heartbeat                                            | SI       | NO      | NO      |

Pero, y si es tan bueno, ¿por qué no lo usamos? Hay una serie de motivos para no usar este protocolo:
- Compatibilidad limitada: Muchos sistemas operativos y dispositivos de red no soportan SCTP de forma nativa, especialmente en comparación con TCP y UDP.
- Restricciones en firewalls y NATs: SCTP utiliza un número de protocolo IP diferente al de TCP y UDP, lo que puede causar problemas con dispositivos de red que no lo reconocen o lo bloquean por defecto.
- Falta de soporte en navegadores y aplicaciones: La mayoría de las aplicaciones web y navegadores están diseñados para funcionar sobre TCP, y cambiar a SCTP requeriría modificaciones significativas.
- HTTP/2: Introduce la multiplexación de múltiples flujos sobre una sola conexión TCP. Esto reduce el HOL a nivel de aplicación, pero no elimina el HOL a nivel de transporte, ya que sigue utilizando TCP.
- HTTP/3: Utiliza el protocolo QUIC, que se basa en UDP y proporciona múltiples flujos independientes con confiabilidad incorporada. Esto elimina el HOL tanto a nivel de aplicación como de transporte.

## UDP Hole Punching

Cuando queremos tener una llamada por WhatsApp, no tenemos una situación cliente servidor como lo que venimos viendo, sino que tenemos una situación P2P (peer to peer - cualquiera puede enviar información, no hay un cliente y un servidor).

Lo ideal sería que la comunicación sea entre ellos, no con un servidor. Cuando un usuario quiere llamar a otro, necesita la IP pública, la cuál la tiene el servidor de WhatsApp. A su vez, indica también el puerto que abre el receptor dinámicamente para poder recibir la llamada. Si no lo puede abrir, entonces el puerto se abre dinámicamente en el host de la persona que llama y el receptor de la llamada se conecta a él. 

**NAT Traversal** es un conjunto de técnicas utilizadas para permitir que los dispositivos dentro de redes privadas (que están detrás de un NAT) se comuniquen con dispositivos fuera de esas redes, superando los problemas causados por el NAT.
- **Full Cone NAT**: una vez que un dispositivo dentro de la red privada realiza una conexión saliente, cualquier host externo puede enviar paquetes de vuelta a esa dirección IP pública. ![[Pasted image 20260813210717.png|447]]
- **Restricted Cone NAT**: permite que un host externo envíe paquetes al host interno solo si el host interno ya le ha enviado datos previamente, pero restringe por IP: solo esa IP externa específica puede responder, aunque use cualquier puerto. ![[Pasted image 20260813210753.png|center|435]]
- **Symmetric NAT**: asigna un puerto diferente para cada conexión saliente a una IP y puerto específicos, y solo el host externo que recibió esa conexión puede responder. Es el tipo de NAT más restrictivo y dificulta el establecimiento de conexiones entrantes. ![[Pasted image 20260813210820.png|center|425]]
**UDP Hole Punching** es una técnica utilizada para permitir la comunicación directa entre dos dispositivos (hosts) detrás de NATs (routers que usan direcciones IP privadas). Buscamos engañar al Firewall y sólo funciona para UDP. Funciona como se ve en la siguiente imagen:
![[Pasted image 20260813210855.png|center|583]]

El proceso es el siguiente: 
1. El host A envía al servidor que quiere conectarse al host B. 
2. El servidor envía las credenciales y a su vez le manda también las credenciales al servidor A, donde se quiere conectar B.
3. El host A envía un paquete desde el mismo puerto a B, pero como nunca envió un paquete a esa dirección lo rechaza (cruz roja).
4. El host B envía el paquete a A, el cual se recibe porque tiene registrado que envió un paquete a la dirección de B, por lo que se toma como la respuesta.
5. Se establece la conexión entre ambos.
