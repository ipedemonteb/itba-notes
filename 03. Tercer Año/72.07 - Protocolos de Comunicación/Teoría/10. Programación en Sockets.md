## Definición

Un **socket** es un punto final de comunicación entre dos dispositivos en una red. Está compuesto por una dirección IP y un número de puerto, y permite que las aplicaciones puedan enviar y recibir datos. Los sockets son usados por protocolos como TCP o UDP para establecer una conexión entre procesos que se comunican a través de la red.

---
## Sockets Bloqueantes

Una **operación bloqueante** es aquella en la que el proceso que la ejecuta queda detenido (bloqueado) hasta que la operación se completa. Por ejemplo, al hacer una lectura de red con un socket bloqueante, el programa se queda esperando hasta que llegan los datos.

Un cliente podría bloquearse por ejemplo esperando un recurso, pero no un servidor, porque este último atiende a varios clientes al mismo tiempo. La comunicación entre procesos puede darse:
- En un mismo host: definido por el S.O.
- En diferentes hosts: intercambio de mensajes.

Si tenemos un protocolo de aplicación, le vamos a pedir servicios a transporte, entonces no me importa si el otro proceso está en otra computadora o en la misma. Necesitamos algún concepto de red, porque podemos por ejemplo saturar o tener pérdidas según nuestras elecciones. Ya sabemos que:
- **Proceso cliente**: proceso que inicia la conexión
- **Proceso servidor**: proceso que espera conexiones

Los procesos se identifican con el número de puerto, y cada host se identifica por la IP. Si en un host corren muchos procesos, se sabe a dónde responder también por el número de puerto. El puerto del servidor debe ser conocido. El del cliente puede no ser especificado, sino que dejamos que el SO elija alguno libre.

El protocolo de nivel de aplicación va a tener que definir:
- Tipos de mensaje que se intercambian. Tenemos que definir si elegimos un protocolo binario o de texto.
- Sintaxis de los mensajes. 
- Semántica de los mensajes.
- Reacción frente a errores. Siempre debe ser lo más fácil posible y no ambiguo. 

El estándar TCP/IP sugiere que las API contemplen las siguientes operaciones básicas:
- Reservar los recursos locales para la comunicación: por ejemplo un buffer de entrada y salida para los protocolos de transporte.
- Especificar endpoints origen y destino: poder decir en qué puerto escucho y en cuál leo y definir IPs para la comunicación.
- Iniciar una conexión (desde el cliente).
- Enviar un datagrama (desde el cliente).
- Esperar una conexión (desde el servidor).
- Enviar y recibir datos.
- Poder determinar cuándo arriba información.
- Generar datos urgentes.
- Manejar el arribo de datos urgentes.

Sólo han tenido aceptación unas pocas API para los protocolos TCP/IP:
- socket API (Berkeley), diseñada para UNIX. Es casi el estándar.
- Windows Socket (Microsoft).
- Transport Layer Interface TLI (AT&T), diseñada para System V UNIX.

Berkeley sockets fue diseñado en los 80 para UNIX. Utiliza system calls ya existentes cuando sea posible y provee funciones generales que soportan comunicaciones con distintos protocolos, no sólo TCP/IP. Las funciones trabajan con familias de protocolos, indicando el usuario qué tipo de familia (p.e. TCP/IP) y qué tipo de servicio requiere (con conexión o sin conexión).

## Conceptos Básicos

El servidor debe estar en ejecución antes de que el cliente intente conectarse. Debe tener un socket (como una "puerta") abierto, por el cual recibir y enviar mensajes (segmentos). Los clientes necesitan un socket y conocer IP y número de puerto del socket del servidor.

## Creación de Sockets

Los sockets se crean de la siguiente manera:
```c
#include <sys/socket.h>

// Returns: file (socket) descriptor if OK, -1 on error
int socket (int domain, int type, int protocol;
```

El domain indica la naturaleza de la comunicación y formato de la dirección
- `AF_INET`: IPv4	
- `AF_INET6`: IPv6	
- `AF_UNIX`: Es interno de UNIX, no por TCP/IP
- `AF_UNSPEC`

El tipo es el tipo de conexión que vamos a usar:
- `SOCK_DGRAM`: Se va a utilizar para intercambiar datagramas. 
- `SOCK_RAW`: Se arma un paquete directamente sobre IP, no usa un protocolo de transporte. Se puede utilizar en el caso que queramos mandar algo mal formado o particular que un servicio de transporte nos modificaría.
- `SOCK_SEQPACKET`: no lo vamos a usar.
- `SOCK_STREAM`: El canal que vamos a usar es confiable y orientado a bytes. 

El protocol es generalmente cero para que se seleccione el protocolo por defecto de acuerdo a domain y type. Sino, se le puede indicar:
- `IPPROTO_IP`
- `IPPROTO_IPV6` 	
- `IPPROTO_ICMP`
- `IPPROTO_RAW`
- `IPPROTO_TCP`
- `IPPROTO_UDP`
- `IPPROTO_SCTP`

La función devuelve el número de file descriptor en caso de no fallar, donde devuelve `-1.` 

Un esquema con TCP podría ser el siguiente, comparando con un teléfono. Tener el socket pasivo sería como tener el teléfono pero apagado. En el `bind` se tiene que especificar una IP y un puerto donde debemos escuchar. Es como publicar el número de teléfono. El `listen` es como sacar el modo avión para ponernos a escuchar. Una vez que está en `listen`, un cliente puede hacer un `connect`, es decir llamar. No podemos rechazar la conexión de un determinado IP sin primero hacer el `accept` (es una operación bloqueante). `Accept` devuelve el file descriptor del socket activo que se va a utilizar. Si fuera iterativo, con `recv` y `send` envío. Esto nos permite atender únicamente a un cliente. Si fuera concurrente, podríamos usar `fork` (no es como lo vamos a hacer) para tener varios procesos y atender a varios clientes.
![[Pasted image 20260814164631.png|center|513]]

Si lo vemos directamente desde el servidor para el orientado a conexión, sin la analogía:
1. Crear un socket y ligarlo (bind) a un puerto
2. Aceptar un pedido de conexión a través del socket
3. Obtener un nuevo socket para la conexión
4. Leer un request del cliente
5. Enviar una respuesta
6. Si el cliente no finalizó, volver al punto 4
7. Cerrar el socket creado en punto 3
8. Volver al punto 2

>[!TIP] Envío Bloqueante
>El envío de TCP es bloqueante, porque se tiene el buffer de salida ocupado.

Si tomamos el caso no orientado a conexión:
1. Crear un socket y ligarlo (bind) a un puerto
2. Leer un datagrama request de un cliente
3. Enviar datagrama/s como respuesta
4. Volver al punto 2

La comunicación en un socket es **bidireccional**. Se puede deshabilitar I/O con shutdown (no la vamos a usar):
```c
#include <sys/socket.h>

int shutdown (int sockfd, int how);
```
Los posibles valores para how son:
- `SHUT_RD`	
- `SHUT_WR` 	
- `SHUT_RDWR`

Una dirección identifica un **socket endpoint**. El formato es específico para cada familia, y se castean a un formato genérico.
```c
struct sockaddr {
	sa_family_t sa_family;    // address family
	char        sa_data[...]; // variable-length address
	...
};
```

Todos esperan esta estructura, y luego se tienen otras más específicas para las que se deben utilizar casteos, como en el siguiente caso:
```c
struct in_addr {
    in_addr_t s_addr;            /* IPv4 address */
};

struct sockaddr_in {
    sa_family_t  sin_family;     /* address family: unsigned short */
    in_port_t    sin_port;       /* port number:    uint16_t */
    struct in_addr sin_addr;     /* IPv4 address:   uint32_t */
    unsigned char  sin_zero[8];  /* Linux: relleno */
};
```

```c
int bind(int socket, const struct sockaddr *address, socklen_t address_len);
```

```c
struct sockaddr_in myAddress;
...
bind(socket, (struct sockaddr *)(&myAddress), sizeof(myAddress));
```

Estas estructuras las vamos a usar tanto para conectarnos a un servidor como para recibir. Si queremos escribir esta estructura a mano, tenemos que tener cuidado, porque asignar por ejemplo `80` al puerto estaría mal, porque recordemos que el estándar es *big endian* y nuestra computadora puede estar en *little endian*. Deberíamos usar una función específica para estos casos.

La estructura para IPv6 es:
```c
struct in6_addr {
    uint8_t s6_addr[16];          /* IPv6 address */
};

struct sockaddr_in6 {
    sa_family_t     sin6_family;   /* address family: unsigned short */
    in_port_t       sin6_port;     /* port number:    uint16_t */
    uint32_t        sin6_flowinfo; /* traffic class and flow info */
    struct in6_addr sin6_addr;     /* IPv6 address */
    uint32_t        sin6_scope_id; /* set of interfaces for a scope */
};
```

```c
struct sockaddr_in6 myAddress;
...
bind(socket, (struct sockaddr *)(&myAddress), sizeof(myAddress));
```

El `flow` recordemos que nos servía para identificar una secuencia de paquetes que comparten ciertas características, como IP origen y destino, puerto, protocolo, etc.

Un cliente debe especificar la dirección de un servidor utilizando la estructura `sockaddr_in`. ¿Qué sucede si el programa cliente conoce sólo el FQDN del servidor?
- `inet_addr`: convierte de notación con puntos (“200.132.2.15”) a decimal.
- `gethostbyname`: dado un string que contiene el FQDN de un host retorna una estructura que contiene (entre otras cosas)  el IP del host en forma decimal.
- `getaddrinfo`: más completa que la anterior. 

```c
#include <sys/socket.h>
#include <netdb.h>

int getaddrinfo(const char *restrict host,
                const char *restrict service,
                const struct addrinfo *restrict hint,
                struct addrinfo **restrict res);

void freeaddrinfo(struct addrinfo *ai);
```

Vemos que `getaddrinfo` llena la lista res con la respuesta que se busca. El service es un string que puede ser el número de puerto, o HTTP o SMTP y lo va a resolver al número de puerto por defecto. Para `localhost` se podrían tener dos estructuras, `127.0.0.1` y `::1`. El parámetro `hint` se refiere a una estructura con información que guía al sistema operativo sobre qué tipo de socket querés queremos crear o buscar. La estructura `addrinfo` contiene al menos los siguientes campos:
```c
struct addrinfo {
    int              ai_flags;     // personalizar comportamiento
    int              ai_family;    // familia de direcciones
    int              ai_socktype;  // tipo de socket
    int              ai_protocol;  // protocolo
    socklen_t        ai_addrlen;   // longitud en bytes de la dirección
    struct sockaddr *ai_addr;      // dirección
    char            *ai_canonname; // nombre canónico del host
    struct addrinfo *ai_next;      // siguiente en la lista
};
```

Los posibles valores para el campo de `ai_flags `son:

| **Flag**             | **Descripción**                                                                                                                               |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| **`AI_ADDRCONFIG`**  | Consulta únicamente el tipo de dirección (IPv4 o IPv6) que esté configurado en el sistema local.                                              |
| **`AI_ALL`**         | Busca tanto direcciones IPv4 como IPv6 (usado únicamente junto con `AI_V4MAPPED`).                                                            |
| **`AI_CANONNAME`**   | Solicita el nombre canónico del host (en lugar de un alias).                                                                                  |
| **`AI_NUMERICHOST`** | La dirección del host se especifica en formato numérico; no intenta resolverla por DNS/nombre.                                                |
| **`AI_NUMERICSERV`** | El servicio se especifica como un número de puerto numérico; no intenta resolverlo por nombre de servicio.                                    |
| **`AI_PASSIVE`**     | La dirección de socket devuelta está pensada para ser utilizada en una llamada a `bind()` para escuchar conexiones entrantes (socket pasivo). |
| **`AI_V4MAPPED`**    | Si no se encuentran direcciones IPv6, devuelve direcciones IPv4 mapeadas en formato IPv6.                                                     |

## Ejemplo Resolución de Nombres

Todos los códigos de los ejemplos a continuación se encuentran en la siguiente [carpeta](https://drive.google.com/drive/folders/1IzoSBcLlCac7pMZcgjdvKrKyLSdobenA). El siguiente código es un programa de ejemplo para resolver nombres de host y servicios a direcciones IP usando `getaddrinfo()` y mostrar información sobre las posibles direcciones de red que devuelve. Realiza los siguientes pasos:
1. Lee argumentos desde la línea de comandos: Requiere al menos un argumento (el host, por ejemplo: `google.com`). Opcionalmente, un segundo argumento que sería el servicio (por ejemplo: HTTP, FTP, 80, etc.).
2. Prepara un `hint`: Usa `memset` para inicializar en cero la estructura.  Activa la bandera `AI_CANONNAME` para que se devuelva el nombre canónico del host (nombre completo oficial).
3. Llama a `getaddrinfo()`: Resuelve el nombre del host (y opcionalmente el servicio) y guarda una lista de estructuras `addrinfo` en `ailist`.
4. Recorre la lista de resultados (`aip = ailist; aip != NULL; aip = aip->ai_next`): Muestra información como: flags (`printFlags`), familia (IPv4/IPv6) (`printFamily`), tipo de socket (TCP/UDP) (`printType`), protocolo (`printProtocol`), nombre del host (`ai_canonname`), dirección y puerto (`printAddressPort`).
5. Libera memoria: Usa `freeaddrinfo(ailist)` al final.

Las funciones de print están en el `util.c`. 
```c
int
main(int argc, char *argv[])
{
    struct addrinfo    *ailist, *aip;
    struct addrinfo    hint;
    int                err;
    char               *service;
    char               *addrString;
    char               addr[64];

    if (argc < 2)
        log(FATAL, "usage: %s host [service]", argv[0]);
    if ( argc >= 3 )
        service = argv[2];
    else
        service = NULL;

    addrString = argv[1];

    memset(&hint, 0, sizeof(hint));
    hint.ai_flags = AI_CANONNAME;
    if ((err = getaddrinfo(addrString, service, &hint, &ailist)) != 0)
        log(FATAL, "getaddrinfo error: %s", gai_strerror(err));
    for (aip = ailist; aip != NULL; aip = aip->ai_next) {
        printFlags(aip);
        printf(" family: %s ", printFamily(aip));
        printf(" type: %s ", printType(aip));
        printf(" protocol %s ", printProtocol(aip));
        printf("\n\thost %s", aip->ai_canonname? aip->ai_canonname:"-");
        printf("address: %s", printAddressPort(aip, addr));
        putchar('\n');
    }
    freeaddrinfo(ailist);
    return 0;
}
```

De la lista que obtengo, si obtenemos una primera IP que no funciona, deberíamos tomar el segundo elemento, porque podríamos tener por ejemplo un servidor con 3 IPs públicas, y que en una no esté aceptando conexiones. 

Hay otra variante de está función que es asincrónica, para no bloquearse en el caso de que lo hiciéramos en un servidor, dado que esta función es bloqueante. Si somos el cliente sí podemos usarla, porque no nos molesta bloquearnos hasta obtener respuesta.

## Ejemplo Cliente/Servidor

Vamos a implementar un ECHO, que repite lo que se le envía mediante TCP. Tomamos los siguientes archivos:
- Cliente ECHO: `tcpEchoClient.c`
- Servidor ECHO iterativo: `tcpEchoServer.c`

Veamos primero el del cliente, que se conecta a un servidor dado, le envía una cadena (string), espera que el servidor le devuelva la misma cadena (eco) e imprime la respuesta recibida.

En este caso, tomando la función `tcpClientSocket()`, que crea un socket cliente TCP y establece una conexión con un servidor especificado por nombre/IP y puerto (dentro de `tcpClientUtil.c`) nos va a importar llenar los siguientes parámetros:
```c
addrCriteria.ai_family = AF_UNSPEC;     // v4 or v6 is OK
addrCriteria.ai_socktype = SOCK_STREAM; // Only streaming sockets
addrCriteria.ai_protocol = IPPROTO_TCP; // Only TCP protocol
```

Resolver dirección y puerto con `getaddrinfo`:
```c
// Get address(es)
struct addrinfo *servAddr; // Holder for returned list of server addrs
int rtnVal = getaddrinfo(host, service, &addrCriteria, &servAddr);
if (rtnVal != 0) {
    log(ERROR, "getaddrinfo() failed %s", gai_strerror(rtnVal))
    return -1;
}
```

Luego, se recorre la lista devuelta, porque como vimos, si no se puede usar la primera dirección se debe pasar a la siguiente:
```c
int sock = -1;
for (struct addrinfo *addr = servAddr; addr != NULL && sock == -1; addr = addr->ai_next) {
    // Create a reliable, stream socket using TCP
    sock = socket(addr->ai_family, addr->ai_socktype, addr->ai_protocol);
    if (sock >= 0) {
        errno = 0;
        // Establish the connection to the server
        if ( connect(sock, addr->ai_addr, addr->ai_addrlen) != 0) {
            log(INFO, "can't connectto %s: %s", printAddressPort(addr, addrBuffer), strerror(errno))
            close(sock);    // Socket connection failed; try next address
            sock = -1;
        }
    } else {
        log(DEBUG, "Can't create client socket on %s", printAddressPort(addr, addrBuffer))
    }
}

freeaddrinfo(servAddr);
return sock;
```

La función socket podría fallar por ejemplo si se le pide algo para TCP y luego se le especifica UDP como protocolo. En este caso, va a estar siempre bien formado, solo va a poder fallar si no quedan recursos.

Si en alguna se puede conectar, se devuelve el file descriptor del socket correspondiente, y si no se devuelve `-1`. En ambos casos se libera la lista antes de retornar. 

Volviendo al `tcpEchoClient.c`, una vez que se obtiene el socket, se realiza el `send` del string que se necesita enviar. Se envía sin flags (el cero), y es bloqueante por defecto. El `send` va a devolver negativo si hubo error.
```c
size_t echoStringLen = strlen(echoString); // Determine input length

// Send the string to the server
ssize_t numBytes = send(sock, echoString, echoStringLen, 0);
if (numBytes < 0 || numBytes != echoStringLen)
    log(FATAL, "send() failed expected %zu sent %zu", echoStringLen, numBytes);
```

Ahora, se debe recibir el string desde el servidor, para lo que se hace un `while` hasta que la cantidad de bytes recibidos sea igual al enviado. Se utiliza la función `recv()` es bloqueante por defecto porque no recibió nada. Si devuelve cero, es porque la otra punta hizo un `close`. 
```c
// Receive the same string back from the server
unsigned int totalBytesRcvd = 0; // Count of total bytes received
log(INFO, "Received: ")          // Setup to print the echoed string
while (totalBytesRcvd < echoStringLen && numBytes >= 0) {
    char buffer[BUFSIZE];
    /* Receive up to the buffer size (minus 1 to leave space for a null terminator) bytes from the sender */
    numBytes = recv(sock, buffer, BUFSIZE - 1, 0);
    if (numBytes < 0) {
        log(ERROR, "recv() failed")
    }
    else if (numBytes == 0)
        log(ERROR, "recv() connection closed prematurely")
    else {
        totalBytesRcvd += numBytes; // Keep tally of total bytes
        buffer[numBytes] = '\0';    // Terminate the string!
        log(INFO, "%s", buffer);    // Print the echo buffer
    }
}

close(sock);
return 0;
```

Ahora tomamos el caso del servidor en `tcpEchoServer.c`, que escucha conexiones entrantes y atiende a cada cliente. Recibe el puerto en el que se van a escuchar conexiones:
```c
if (argc != 2) {
    log(FATAL, "usage: %s <Server Port>", argv[0]);
}

char * servPort = argv[1];

int servSock = setupTCPServerSocket(servPort);

    return 1;
```

Tiene un ciclo infinito porque está constantemente esperando y resolviendo solicitudes. 
```c
while (1) { // Run forever
    // Wait for a client to connect
    int clntSock = acceptTCPConnection(servSock);
    if (clntSock < 0)
        log(ERROR, "accept() failed")
    else {
        handleTCPEchoClient(clntSock);

```

Ahora vamos al archivo de `tcpServerUtil.c` para ver las implementaciones. El `setUp` recibe el string del servicio, como por ejemplo el puerto o el ECHO. Se usan los siguientes flags:
```c
int setupTCPServerSocket(const char *service) {
    // Construct the server address structure
    struct addrinfo addrCriteria;                   // Criteria for address match
    memset(&addrCriteria, 0, sizeof(addrCriteria)); // Zero out structure
    addrCriteria.ai_family = AF_UNSPEC;             // Any address family
    addrCriteria.ai_flags = AI_PASSIVE;             // Accept on any address/port
    addrCriteria.ai_socktype = SOCK_STREAM;         // Only stream sockets
    addrCriteria.ai_protocol = IPPROTO_TCP;         // Only TCP protocol

    struct addrinfo *servAddr;                      // List of server addresses
    int rtnVal = getaddrinfo(NULL, service, &addrCriteria, &servAddr);
    if (rtnVal != 0) {
        log(FATAL, "getaddrinfo() failed %s", gai_strerror(rtnVal));
        return -1;
    }
}
```

El nombre, que es el primer parámetro del getaddrinfo, se pasa en `NULL` porque se quieren crear sockets pasivos. No se quiere escuchar solamente en un puerto, sino que se quiere escuchar en varios lugares. No queremos que resuelva nada, sino que nos devuelva una lista de estructuras con IP vacía. Si quisiéramos que fuera local, pondremos `localhost`.

Al igual que en el cliente, luego se itera por la lista de estructuras, con un esquema parecido. Se crea el socket, se mira si falla, se hace un bind para decir la IP en la que se quiere escuchar, en qué puerto, con qué recursos. Puede fallar si por ejemplo el puerto ya está ocupado por otro proceso o es menor a 1024 y no se es root. 
```c
int servSock = -1;
// Intentamos ponernos a escuchar en alguno de los puertos asociados al servicio, sin especificar una IP en particular
// Iteramos y hacemos el bind por alguna de ellas, la primera que funcione, ya sea la general para IPv4 (0.0.0.0) o IPv6 (::/0) .
// Con esta implementación estaremos escuchando o bien en IPv4 o en IPv6, pero no en ambas
for (struct addrinfo *addr = servAddr; addr != NULL && servSock == -1; addr = addr->ai_next) {
    errno = 0;
    // Create a TCP socket
    servSock = socket(addr->ai_family, addr->ai_socktype, addr->ai_protocol);
    if (servSock < 0) {
        log(DEBUG, "Can't create socket on %s : %s ", printAddressPort(addr, addrBuffer), strerror(errno));
        continue;     // Socket creation failed; try next address
    }

    // Bind to ALL the address and set socket to listen
    if ((bind(servSock, addr->ai_addr, addr->ai_addrlen) == 0) && (listen(servSock, MAXPENDING) == 0)) {
        // Print local address of socket
        struct sockaddr_storage localAddr;
        socklen_t addrSize = sizeof(localAddr);
        if (getsockname(servSock, (struct sockaddr *) &localAddr, &addrSize) >= 0) {
            printSocketAddress((struct sockaddr *) &localAddr, addrBuffer);
            log(INFO, "Binding to %s", addrBuffer);
        }
    } else {
        log(DEBUG, "Can't bind %s", strerror(errno));
        close(servSock);  // Close and try with the next one
        servSock = -1;
    }
}

freeaddrinfo(servAddr);

return servSock;
```

El `MAXPENDING` es el tamaño de cola de conexiones que se aceptan. El `listen()` no debería fallar, pero por las dudas se valida. Si se pueden hacer `bind` y `listen`, entonces el puerto se puede usar el puerto. Si no se puede en ninguno de la lista, devuelve el `-1` y sino en el `FD`.

La función `accpetTCPConnection()` llama a `accept()` para devolver el socket activo sobre el cual se va a poder leer y escribir. 
```c
int acceptTCPConnection(int servSock) {
    struct sockaddr_storage clntAddr; // Client address
    // Set length of client address structure (in-out parameter)
    socklen_t clntAddrLen = sizeof(clntAddr);

    // Wait for a client to connect
    int clntSock = accept(servSock, (struct sockaddr *) &clntAddr, &clntAddrLen);
    if (clntSock < 0) {
        log(ERROR, "accept() failed");
        return -1;
    }

    // clntSock is connected to a client!
    printSocketAddress((struct sockaddr *) &clntAddr, addrBuffer);
    log(INFO, "Handling client %s", addrBuffer);

    return clntSock;
}
```

Finalmente, la función `handleTCPEchoClient()` es específica para el caso que estamos implementado (los otros son genéricos). 
1. Recibe datos del cliente (`recv()`).
2. Se los devuelve (`send()`).
3. Repite mientras el cliente siga enviando datos.
4. Cierra el socket al terminar.

Vemos que el ciclo espera hasta que el `recv()` devuelva `0` o menor. Recordemos que si devuelve cero es porque se cerro la conexión por el lado del cliente, y entonces allí se cierra el socket por el lado del servidor. Sería muy fácil hacerle un DoS, porque simplemente habría que conectarse y nunca mandar nada.

## Ejemplo Cliente/Servidor UDP

En el caso expuesto en `udpEchoClient.c`, no se hace la iteración por la lista. No se hace porque es imposible saber si la información llegó o no. Entonces si la lista no es vacía, se devuelve el socket sobre el primer valor obtenido de la lista. 
```c
int udpClientSocket(const char *host, const char *service, struct addrinfo **servAddr) {
    // Pedimos solamente para UDP, pero puede ser IPv4 o IPv6
    struct addrinfo addrCriteria;
    memset(&addrCriteria, 0, sizeof(addrCriteria));
    addrCriteria.ai_family = AF_UNSPEC;             // Any address family
    addrCriteria.ai_socktype = SOCK_DGRAM;          // Only datagram sockets
    addrCriteria.ai_protocol = IPPROTO_UDP;         // Only UDP protocol

    // Tomamos la primera de la lista
    int rtnVal = getaddrinfo(host, service, &addrCriteria, servAddr);
    if (rtnVal != 0) {
        log(FATAL, "getaddrinfo() failed: %s", gai_strerror(rtnVal));
        return -1;
    }

    // Socket cliente UDP
    return socket((*servAddr)->ai_family, (*servAddr)->ai_socktype, (*servAddr)->ai_protocol); // Socket descriptor for client
}
```

Desde el cliente tampoco hay una lógica muy distinta. Se justificaría un ciclo si se quiere enviar un texto muy largo, para enviarlo en datagramas. Como es no orientado a conexión, al ser cliente podríamos enviar a distintos servidores desde un mismo socket. 
```c
// Enviamos el string
ssize_t numBytes = sendto(sock, echoString, echoStringLen, 0, servAddr->ai_addr, servAddr->ai_addrlen);
if (numBytes < 0) {
    log(FATAL, "sendto() failed: %s", strerror(errno))
} else if (numBytes != echoStringLen) {
    log(FATAL, "sendto() error, sent unexpected number of bytes");
}

// Guardamos la direccion/puerto de respuesta para verificar que coincida con el servidor
struct sockaddr_storage fromAddr; // Source address of server
socklen_t fromAddrLen = sizeof(fromAddr);
char buffer[echoStringLen + 1];
```

Una vez que se hace el `sendto`, se espera la respuesta. Como es UDP, necesitamos no bloquearnos. Por ahora, vamos a poner un timeout con la función `setsockopt()`. 
```c
// Guardamos la direccion/puerto de respuesta para verificar que coincida con el servidor
struct sockaddr_storage fromAddr; // Source address of server
socklen_t fromAddrLen = sizeof(fromAddr);
char buffer[echoStringLen + 1];

// Establecemos un timeout de 5 segundos para la respuesta
struct timeval tv;
tv.tv_sec = 5;
tv.tv_usec = 0;
if (setsockopt(sock, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv)) < 0) {
    log(ERROR, "setsockopt error: %s", strerror(errno))
}
```

Con el `recvfrom`, estamos escuchando en el puerto que se envió de salida, al que cualquiera podría mandar, entonces esta función indica si los sockets son los mismos. Se busca que la IP y puerto coincidan para no leer de cualquiera. 
```c
numBytes = recvfrom(sock, buffer, echoStringLen, 0, (struct sockaddr *) &fromAddr, &fromAddrLen);
if (numBytes < 0) {
    log(ERROR, "recvfrom() failed: %s", strerror(errno))
} else {
    if (numBytes != echoStringLen)
        log(ERROR, "recvfrom() error. Received unexpected number of bytes, expected:%zu received:%zu ", echoStringLen, numBytes);

    // "Autenticamos" la respuesta
    if (!sockAddrSEqual(servAddr->ai_addr, (struct sockaddr *) &fromAddr))
        log(ERROR, "recvfrom() received a packet from other source");

    buffer[numBytes] = '\0';
    printf("Received: %s\n", buffer);
}
freeaddrinfo(servAddr);
close(sock);
return 0;
```

El "Autenticamos" está entre comillas porque solamente se compara que coincidan puerto e IP al que se envió, pero un atacante podría hacerse pasar por el receptor. 

Desde el lado del servidor, se setea creando los socket con los siguientes flags:
```c
// Construct the server address structure

memset(&addrCriteria, 0, sizeof(addrCriteria)); // Zero out structure

addrCriteria.ai_socktype = SOCK_DGRAM;          // Only datagram socket
addrCriteria.ai_protocol = IPPROTO_UDP;         // Only UDP socket

if (rtnVal != 0)
    log(FATAL, "getaddrinfo() failed %s", gai_strerror(rtnVal))
```

Luego, se itera para escuchar en alguno de los puertos asociados al servicio. 
```c
int servSock = -1;
// Intentamos ponernos a escuchar en alguno de los puertos asociados al servicio, sin especificar una IP en particular
// Iteramos y hacemos el bind por alguna de ellas, la primera que funcione, ya sea la general para IPv4 (0.0.0.0) o IPv6 (::/0) .
// Con esta implementación estaremos escuchando o bien en IPv4 o en IPv6, pero no en ambas
for (struct addrinfo *addr = servAddr; addr != NULL && servSock == -1; addr = addr->ai_next) {
    errno = 0;
    // Create UDP socket
    servSock = socket(addr->ai_family, addr->ai_socktype, addr->ai_protocol);
    if (servSock < 0) {
        log(DEBUG, "Can't create socket on %s : %s ", printAddressPort(addr, addrBuffer), strerror(errno));
        continue;     // Socket creation failed; try next address
    }

    // Bind to ALL the address
    if (bind(servSock, addr->ai_addr, addr->ai_addrlen) == 0) {
        // Print local address of socket
        struct sockaddr_storage localAddr;
        socklen_t addrSize = sizeof(localAddr);
        if (getsockname(servSock, (struct sockaddr *) &localAddr, &addrSize) >= 0) {
            printSocketAddress((struct sockaddr *) &localAddr, addrBuffer);
            log(INFO, "Binding to %s", addrBuffer);
        }
    } else {
        log(DEBUG, "Can't bind %s", strerror(errno));
        close(servSock);  // Close and try with the next one
        servSock = -1;
    }
}

freeaddrinfo(servAddr);

return servSock;
```
