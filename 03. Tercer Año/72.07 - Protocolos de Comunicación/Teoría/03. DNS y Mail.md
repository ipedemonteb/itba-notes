## Resolución de Nombres

La **resolución de nombres** es el proceso de traducir un nombre de dominio (como `www.ejemplo.com`) a una dirección de IP (como `192.0.2.1`).  Es fundamental porque facilita el acceso a hosts usando nombres fáciles de recordar en lugar de direcciones IP numéricas. Es esencial para la comunicación en redes y el acceso a recursos en internet. 

Podemos definir:
- Un **dominio** es una colección de computadoras que pueden ser accedidas usando un nombre en común.
- Un **nombre de dominio** hace referencia al nombre de múltiples hosts que son referenciados colectivamente (itba.edu.ar, ibm.com, etc.).

Los dominios tienen distintos niveles, siendo `.com` el dominio top-level más conocido de ellos. Ver RFC 1591 y RFC 3071.

Dentro de un **top-level domain**, una organización tiene su propio dominio o dominios. A su vez dentro del dominio puede haber **sub-dominios**. Y cada host tiene su nombre propio (**hostname**). Uniendo el nombre del host con el dominio al cual pertenece se forma el **Fully Qualified Domain Name (FQDN)**.
![[Pasted image 20260811134608.png|center|433]]

Para obtener un número IP a partir de un FQDN, existen dos posibilidades. En la primera se utiliza el archivo de `/etc/hosts`, donde se contiene una línea por cada número de IP y el o los nombres asociados a dicho IP. Cuando una aplicación (como Opera en la siguiente imagen) solicita la dirección IP de un dominio, el sistema primero revisa el archivo `/etc/hosts` en busca de una entrada que asocie el dominio con una IP. Si encuentra una coincidencia, usa esa IP sin necesidad de consultar servidores externos. Este método es útil para configuraciones locales o pruebas.
![[Pasted image 20260811134758.png|center|348]]
![[Pasted image 20260811134823.png|center|551]]

Otra opción es utilizar el archivo `resolv.conf` y un servidor DNS. Si el dominio no está en `/etc/hosts`, el sistema utiliza el DNS Resolver del kernel para consultar un servidor DNS externo. El archivo `/etc/resolv.conf` contiene las direcciones IP de los servidores DNS a los que el sistema puede consultar. La consulta viaja a través de la red hasta un servidor DNS, que devuelve la IP correspondiente al dominio.
![[Pasted image 20260811135005.png|center|467]]

Las opciones de configuración de `/etc/resolv.conf` son: 
- `nameserver [direcciones]`: Números IP de los servidores de nombres que consultará el resolver (hasta 3). Si no hay ningún `nameserver` utilizará al propio host como servidor de nombres.
- `domain [nombre]`: Dominio local por defecto. El resolver agrega este nombre a todo hostname que no contenga un punto antes de resolverlo.
- `search [dominios]`: Similar al anterior pero pueden ser varios dominios (no se usan ambas opciones en simultáneo).
- `sortlist [red[/mascara]]`: En caso de recibir múltiples direcciones IP para un nombre, reordena las direcciones en base a las redes listadas en esta opción.
- `options [opción]`: Usada para seteos opcionales. Las posibles opciones son:
	- `debug`
	- `ndots:n`
	- `timeout:n`
	- `attempts:n`
	- `rotate`
	- `no-check-names`
	- `inet6`

Tomemos el siguiente ejemplo de `/etc/resolv.conf` del host `192.168.2.20`:
```
domain     itba.edu.ar
nameserver 192.168.2.1
nameserver 8.8.8.8
nameserver 200.49.159.69
```
Donde:
- `nameserver 192.168.2.1`: Especifica un servidor DNS local (probablemente un servidor dentro de la red interna). Se consultará primero para resolver nombres de dominio.
- `nameserver 8.8.8.8`: Es un servidor DNS público de Google. Se usará si el primer servidor (192.168.2.1) no responde.
- `nameserver 200.49.159.69`: Es otro servidor DNS, probablemente de un proveedor de Internet local. Se usará si los servidores anteriores fallan.

Linux incluye las utilidades `dig` y `host` para resolver nombres, ya sea para obtener el IP en base a un nombre o el nombre en base a un IP (reverse DNS). Por defecto se consulta primero el archivo `/etc/hosts` y luego (de ser necesario) al DNS resolver. Esto puede cambiarse editando el archivo `/etc/host.conf`, el que típicamente contiene una sola línea:
```
order	hosts, bind
```
En caso de querer que se consulte siempre al DNS resolver sólo hay que cambiar el orden, como el ejemplo siguiente:
```
order	bind, hosts
```
Es importante saber que un host mantiene en su caché los nombres que ha podido resolver.

## DNS

Algunos nombres de dominio a resolver se pueden encontrar en `/etc/hosts`, pero en la mayoría de los casos deberán ser resueltos preguntando a un servidor DNS. Estos servidores pueden ser:
- **Recursivos**: Realizan la consulta completa en nombre del cliente.
- **Autorizados**: Contienen la información definitiva sobre nombres de dominio específicos.
- **Raíz DNS**: Nivel más alto de la jerarquía, administrado por ICANN.

DNS es un sistema jerárquico distribuido para traducir nombres de hosts a direcciones IP. La información en DNS puede ser vista como un árbol invertido donde la raíz hace referencia a servidores de nombres raíz (root name servers).
![[Pasted image 20260811135730.png|center|443]]

Los DNS root name servers son usados cuando el servidor de nombres local no puede resolver un nombre. Se encargan de:
- Contactar name server autorizado si no conoce la respuesta.
- Almacenar.
- Retornar respuesta al servidor de nombres local.
![[Pasted image 20260811135800.png|center|578]]

Los **Top-Level Domain (TLD)** servers son responsables de `com`, `org`, `net`, `edu`, `aero`, `jobs`, `museums`, y todos los países (`ar`, `uk`, `uy`, `tv`, etc.). Para los authoritative DNS servers, cada organización mantiene su propio servidor(es) DNS o lo mantiene a través de un proveedor. En el caso de los DNS locales, no necesariamente pertenecen a la jerarquía. Cada ISP tiene uno, conocido como **default name server**. Cuando un host realiza una consulta DNS, es enviada al servidor DNS local y:
- Busca en la caché si tiene el par nombre-dirección y no caducó.
- Actúa como un proxy.

Tomemos el ejemplo:
```bash
user@server:~$ host www.dc.uba.ar
www.dc.uba.ar is an alias for www-1.dc.uba.ar.
www-1.dc.uba.ar is an alias for dc.uba.ar
dc.uba.ar has address 157.92.27.127
```

```bash
user@server:~$ host 157.92.27.21
21.27.92.157.in-addr.arpa domain name pointer dc.uba.ar.
```

Para poder responder un **DNS reverse**, se usa un árbol especial en base a los números IP.
![[Pasted image 20260811145316.png|center|438]]

Veamos el formato de las consultas. Suponamos que el servidor DNS local está recién instalado, no sabe quién resuelve qué.  Va a preguntar primero en alguno de los de raíz.
![[Pasted image 20260811145559.png|center|518]]

Vemos que en el primer caso devuelve que `ar` viene del nameserver (`NS`) `c.dns.ar`. Luego va a ese servidor y le envía la misma pregunta. No le puede dar tampoco la página pero le puede dar `edu.ar`. Así sucesivamente, hasta que se llega al servidor que tiene la página. Una vez que se obtiene en el servidor DNS local la respuesta autorizada del último servidor, la respuesta que le llega al host no es autorizada porque no fue a un servidor autorizado. Si ahora quisiera `www.itba.edu.ar`, directamente se hace el anteúltimo paso, no se repite todo el proceso por lo que dijimos que almacena.

Una vez que el servidor de nombres aprende el mapeo, vimos que lo almacena en caché. Estos expiran tras un tiempo llamado **Time To Live (TTL)**. Los servidores de nombre generalmente cachean la dirección de los servidores TLD. Los Root Servers no suelen visitarse. Si cambiamos la IP de un servidor dentro de nuestra red sin actualizar los registros DNS o el archivo `/etc/hosts`, los clientes que dependen del antiguo IP no podrán acceder hasta que se actualicen los registros.

Los servidores raíz DNS son operados por la **Internet Engineering Task Force (IETF)**. Cuando alguien obtiene un nombre de dominio es el responsable de mantener, en un servidor DNS (master) primary, actualizado ese dominio. En Unix y Linux DNS es implementado generalmente con BIND (Berkeley Internet Name Domain). Existen cuatro niveles de configuración:
- Resolver only systems 
- Caching-only servers
- (Master) Primary servers
- (Slave) Secondary servers

Un **caching-only server** aprende las respuestas acerca de los nombres de dominios de otro servidor. Una vez que aprende esa respuesta, la almacena para futuras preguntas. Todos los servidores utilizan esta técnica pero un caching-only server es la única técnica que utiliza. No es considerado un server autorizado porque su información es de segunda mano. El programa dnscache funciona solo como cache de servidores de nombre, y puede ser usado en caching-only servers.
![[Pasted image 20260811161309.png|center|609]]

Un **primary server** es la fuente autorizada para toda la información de una zona específica. Lee la información sobre el dominio desde un archivo construido por el administrador. Es un server autorizado para un dominio o parte de un dominio pues puede responder con autoridad preguntas sobre ese dominio.

Un **secondary server** transfiere información completa de una zona desde un master server y la almacena en un archivo en el disco local. Mantiene información completa y actualizada de una zona y puede responder preguntas sobre zona en forma autorizada.

## Registros DNS

DNS es una base de datos distribuida de **Resource Records (RR)**. El formato RR es `(name, value, type, ttl)` y los tipos son:

| Type    | Name                          | Value                                                                         |
| :------ | :---------------------------- | :---------------------------------------------------------------------------- |
| `A`     | Nombre del host               | IP                                                                            |
| `NS`    | Dominio                       | Nombre del host autorizado a resolver nombres del dominio                     |
| `CNAME` | Alias para el nombre canónico | Nombre canónico                                                               |
| `MX`    | Dominio                       | Nombre del servidor de mails para el dominio                                  |
| `AAAA`  | Nombre del host               | IPv6                                                                          |
| `SOA`   | Start of Authority            | Inicio de información autorizada                                              |
| `SRV`   | Localizador de servicios      | Para no crear nuevos registros tipo MX                                        |
| `RP`    | Persona responsable           | Normalmente el mail del responsable                                           |
| `TXT`   | *Texto libre*                 | Un texto libre                                                                |
| `SPF`   | *Dominio*                     | Lista de IPs de hosts autorizados para enviar mails en nombre de este dominio |
Algunos ejemplos de registros DNS son:
1. **Registros `A` (Address) y `AAAA`:**  `A` asocia un nombre de dominio con una dirección IPv4 y `AAAA` asocia un nombre de dominio con una dirección IPv6.
```properties
ejemplo.com. IN A 192.0.2.1
  
ejemplo.com. IN AAAA 2001:0db8::1
```
2. **Registros `CNAME` (Canonical Name):** Asocia un alias a un nombre de dominio canónico.
```properties
ejemplo.com. IN CNAME ejemplo.com.
```
3. **Registros `MX` (Mail Exchange):** Especifica los servidores de correo para un dominio.
```properties
ejemplo.com. IN MX 10 mail.ejemplo.com.
ejemplo.com. IN MX 20 backupmail.ejemplo.com.
```
4. **Registros `TXT` (Text):** Almacena información de texto para varios usos, como verificación de dominio y políticas de correo.
```properties
ejemplo.com. IN TXT "v=spf1 include:_spf.ejemplo.com ~all"
```
5. **Registros `NS` (Name Server):** Indica los servidores DNS autoritativos para el dominio.
```properties
ejemplo.com. IN NS ns1.ejemplo.com.
ejemplo.com. IN NS ns2.ejemplo.com.
```
6. **Registros `SRV` (Service):** Define la ubicación (host y puerto) de servicios específicos. La sintaxis es `_service._proto.name. TTL class SRV priority weight port target.`
```properties
_sip._tcp.ejemplo.com. 3600 IN SRV 10 60 5060 sipserver.ejemplo.com.
```
7. **Registros `PTR` (Pointer):** Utilizados en la resolución inversa para mapear una dirección IP a un nombre de dominio.
  ```properties
1.2.0.192.in-addr.arpa. IN PTR [www.ejemplo.com](https://www.ejemplo.com).
  ```

Vemos el siguiente ejemplo de configuración para un DNS:
```properties
$TTL 86400            ; Tiempo de vida predeterminado para los registros (en segundos)
$ORIGIN example.com.  ; Define el dominio raíz de la zona

@   IN SOA ns1.example.com. hostmaster.example.com. (
            2024031201 ; Número de serie (incrementar en cada cambio)
            3600       ; Período de actualización (refresh) - 1 hora
            600        ; Período de reintento (retry) - 10 minutos
            1w         ; Expiración de la zona (expire) - 1 semana
            3h )       ; Tiempo de vida mínimo para respuestas negativas - 3 horas

; Servidores de nombres (DNS) de la zona
@   IN NS ns1.example.com.      ; Servidor DNS primario
@   IN NS ns2.example.com.      ; Servidor DNS secundario
@   IN NS ns.outsider.com.      ; Servidor DNS externo de respaldo

; Registros A (direcciones IPv4)
ns1     IN A 192.168.0.1        ; Dirección del servidor DNS primario
ns2     IN A 201.13.248.106     ; Dirección del servidor DNS secundario
www     IN A 192.168.0.3        ; Dirección del sitio web principal
ftp     IN A 192.168.0.4        ; Servidor FTP
mail    IN A 204.13.248.106     ; Servidor de correo
printer IN A 192.168.0.100      ; Impresora

; Registros AAAA (direcciones IPv6)
ns1     IN AAAA 2001:db8::1     ; IPv6 del servidor DNS primario
www     IN AAAA 2001:db8::2     ; IPv6 del servidor web

; Registros CNAME (alias)
smtp    IN CNAME mail.example.com. ; Alias para el servidor SMTP
blog    IN CNAME www.example.com.  ; Alias para un subdominio de blog

; Registros MX (servidores de correo)
@   IN MX 10 mail.example.com.     ; Servidor principal de correo
@   IN MX 20 backup.example.com.   ; Servidor de respaldo de correo

; Registros TXT (información adicional, SPF, DKIM, etc.)
@      IN TXT "v=spf1 mx -all"            ; Política SPF para evitar spoofing
_dmarc IN TXT "v=DMARC1; p=none;"         ; Configuración básica de DMARC

; Registros SRV (para servicios específicos como VoIP o XMPP)
_xmpp-server._tcp IN SRV 5 0 5269 xmpp.example.com. ; Servidor XMPP
_sip._udp         IN SRV 10 60 5060 sip.example.com.  ; Servidor SIP
```

El **arroba (`@`)** surgió para separar nombre de usuario de nombre de dominio, principalmente cuando se comenzó a enviar mails entre distintos dominios y podían surgir conflictos. La reverse-zone es de la siguiente forma:
```properties
$TTL 86400                           ; Tiempo de vida predeterminado para los registros
$ORIGIN 0.168.192.in-addr.arpa.      ; Zona de resolución inversa para 192.168.0.x

@   IN SOA ns1.example.com. hostmaster.example.com. (
            2024031201 ; Número de serie (incrementar en cada cambio)
            3600       ; Refresh - 1 hora
            600        ; Retry - 10 minutos
            1w         ; Expire - 1 semana
            3h )       ; Minimum TTL - 3 horas

; Servidores de nombres para la zona inversa
@   IN NS ns1.example.com.
@   IN NS ns2.example.com.

; Registros PTR (mapear IPs a nombres de dominio)
1   IN PTR ns1.example.com.
2   IN PTR ns2.example.com.
3   IN PTR www.example.com.
4   IN PTR ftp.example.com.

; Zona inversa para la IP pública 201.13.248.106
$ORIGIN 248.13.201.in-addr.arpa.
106 IN PTR ns2.example.com.

; Zona inversa para la IP pública 204.13.248.106 (servidor de correo)
$ORIGIN 248.13.204.in-addr.arpa.
106 IN PTR mail.example.com.
```

- `host`

## Utilidades DNS

Algunas utilidades que tenemos para todo lo que es DNS son:
- **host**: informa, dado un nombre de host, el número IP que le corresponde.
```bash
user@server:~$ host clarin.com
www.clarin.com has address 200.42.136.212
clarin.com mail is handled by O
clarin-com.mail.protection.outlook.com.
```
- **dig**: permite ver los registros para un dominio
