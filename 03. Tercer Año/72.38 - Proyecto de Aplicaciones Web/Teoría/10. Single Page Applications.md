## Definición

**Single Page Applications (SPA)** es una metodología de crear un cliente de frontend que maneje dinámicamente el input del usuario. Con esto, se elimina la necesidad de interactuar con el backend lo máximo posible. En nuestro caso, pasamos de una lógica thin client a un thick client. Mucha responsabilidad va a caer ahora sobre el front. 

---
## Autenticación y Seguridad

Nuestra **autenticación** va a cambiar, principalmente la parte del cliente. Hasta ahora usamos cookies y Spring Security. Ahora, como dijimos, vamos a tener clientes más pesados, y el front va a pasar a tener un poco más de responsabilidades. Por ejemplo, los `403` pueden no pasar por el servidor.

El manejo de autenticación, login, registro, cambio de contraseña, sesión, así como la parte de acceso se va a empezar a hacer en el front. Vamos a pasar de cookies a local storage. Las cookies son susceptibles a MitM, en especial cuando todos los requests envían ambos tokens. Además, nos dan menos control de cuándo mandarse, sumando así el overhead de red, que impacta a todo (incluído assets).

---
## Internacionalización

La **internacionalización** pasa también a ser responsabilidad del front. Vamos a tener que buscar la librería de internacionalización, ya que no se pueden perder features a la hora de realizar la migración para el final. El approach va a ser similar, pero vamos a modificar la metodología. Podemos usar herramientas para extraer sus keys hacia un archivo y luego utilizarlo en el front actualizado.

## Optimización

La Single Page se carga una única vez, entonces se nos va a pedir una serie de optimizaciones. Una estrategia es la minificación de JS, que consiste en reducir el tamaño de los archivos JS eliminando todo lo innecesario para la ejecución del código, sin cambiar su funcionalidad. Por ejemplo:
```Javascript
function saludar(nombre) {
  console.log("Hola, " + nombre);
}
```
Pasa a ser:
```Javascript
function saludar(n){console.log("Hola, "+n);}
```

Esta técnica se puede usar también para CSS. Nos deja un código ilegible, pero que optimiza mucho los recursos. Generalmente lo hacen los frameworks que usamos, pero es importante chequear.

Lighthouse es una herramienta de código abierto de Google que analiza páginas web y genera informes sobre su rendimiento, accesibilidad, SEO, buenas prácticas y experiencia en dispositivos móviles. Genera un informe con puntajes del 0 al 100 para cada categoría, junto con sugerencias específicas para mejorar.

## Hosting

Vamos a querer hacer un `mvn package` y que genere un paquete que tenga todo lo del front también, independientemente del framework que usemos. Para esto, vamos a usar un plugin que es el Frontend Maven Plugin ([link](http://github.com/eirslett/frontend-maven-plugin)). 

Hay que tocar la configuración del proyecto webapp para que devuelva todos los recursos estáticos nuevos, y hay que agregar la dependencia del módulo frontend para que se ejecute primero.

Existe además server side rendering (no se nos va a pedir), es una técnica en la que el contenido de una página web se genera en el servidor en lugar de en el navegador del usuario (cliente). Básicamente:
1. Prepara un first impression que se baje MUY rápido.
2. Luego baja la página entera y la recarga sin que el usuario se de cuenta.

No vamos a poder utilizar nada en referencia a window en nuestro first impression. Tampoco podemos usar por ejemplo `localStorage`, ya que no va a correr en el browser.

## Cache

Va a ser un requisito importante de la entrega final. Notemos que no nos va a mejorar el Time To First Load, sino que es una optimización para un usuario recurrente, pero que mejora mucho la experiencia ya que disminuye tiempos a cero.

Hay dos tipos de caching:
- **Cache Condicional**: Antes de usar la copia local, el navegador pregunta al servidor si ha cambiado el recurso. Es más restringido porque actúa en base a una condición. El problema es que nos ahorramos la descarga, pero sigue estando el ping al servidor. 
- **Cache No Condicional**: El navegador o proxy usa directamente una copia en caché del recurso si aún no ha expirado. Es el que se nos va a pedir. 

Lo que vamos a hacer en caché no condicional es darle tiempo infinito a todos los recursos que cambian. El root de la aplicación nunca se puede cachear. Al acceder al `/`, obtenemos el `index.html` con todos los recursos que pueden o no estar cacheados. Bajo la premisa de que los assets que nunca cambian mantienen su estructura y lo que cambia es su nombre, los recursos que sí cambian tienen un proceso que se llama **file revving**, que se basa en técnicas de hashing en base a los nombres. Entonces, si queremos cambiar el `style.css`, agregamos `style2.css` y, como tiene otro nombre, el browser lo va a tener que pedir.

El caching tiene esta parte de file revving que aplicaremos en el front, y otra de Spring, donde se le debe indicar esta configuración que detallamos anteriormente.
