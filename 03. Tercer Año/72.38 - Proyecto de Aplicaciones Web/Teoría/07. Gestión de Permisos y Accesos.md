## Spring Security

La gestión de permisos y accesos la vamos a manejar con **Spring Security**, que es otro módulo que gestiona el control de acceso. Su motor de reglas es independiente del contexto de la aplicación. 

Spring Security implementa el patrón más estándar para el control de acceso, [[06. Seguridad en Aplicaciones#Control de Acceso|ACL (Access Control List)]]. Trabaja en torno a tres controles:
- Roles
- Recursos
- Set de permisos que definen si un cierto rol puede o no acceder a un cierto recurso.

Notemos que hablamos de roles y no de perfiles de usuario. Esta distinción es importante, porque una buena práctica a la hora de usar este tipo de sistemas es que los roles definan la funcionalidad y no necesariamente mapee uno a uno con los perfiles de usuario. Esto nos permite por ejemplo tener reglas dinámicas de acceso. 

>[!TIP] Recursos
>Los **recursos** tradicionalmente son acciones, como por ejemplo en nuestro caso endpoints de la aplicación web. Los permisos indican si se está autorizado o no a realizar dicha acción. 

Spring Security va a ser una excepción para la regla que veníamos usando de mantener las versiones  de todos los módulos de Spring sincronizadas. No salían en conjunto las versiones de Spring y Spring Security. La vamos a definir a parte en el POM del proyecto y luego en el webapp.

Ahora, para mantener todo ordenado vamos a hacer un nuevo `webconfig` para lo que es Spring Security. Para simplificar el código, vamos a extender a `WebSecurityConfigurerAdapter`. Luego, armamos la configuración (ver guía).

Vamos a usar un `Filter` ahora que va a interceptar todos los requests entrantes y va a aplicar todas las reglas que definimos. Esto lo vamos a definir en nuestro `web.xml` de la siguiente forma:
```xml
<filter>
    <filter-name>springSecurityFilterChain</filter-name>
    <filter-class>org.springframework.web.filter.DelegatingFilterProxy</filter-class>
</filter>
<filter-mapping>
    <filter-name>springSecurityFilterChain</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>
```

Spring Security configura automáticamente múltiples providers para distintos mecanismos de autenticación según la configuración que realicemos (user y password, cookie de remember me, OAuth, HTTP-Authentication, etc.), pudiendo siempre el desarrollador crear uno propio.

Todos estos providers terminan obteniendo un `username`, con el que delegar al `UserDetailsService` para obtener el `User` y luego, de ser necesario, delega en un `PasswordEncoder` para hashear la password y compararla con la recuperada por el `UserDetailsService`. 

El `PasswordEncoder` utilizado por defecto es `PlainTextPasswordEncoder` que para nuestro ejemplo básico es suficiente. Igualmente, en una aplicación real (como la desarrollada durante el TP), debieramos configurar un buen `PasswordEncoder` como ser `BCryptPasswordEncoder`, y asegurarnos de usarlo en nuestra aplicación al momento de crear/modificar la password de nuestros usuarios.

Entonces, debemos escribir nuestra propia implementación para la clase `PawUserDetailService` en la carpeta auth dentro de webapp. No es un service como los que veníamos trabajando en nuestro proyecto. 
```Java
@Component
public class PawUserDetailsService implements UserDetailsService {

    @Autowired
    private UserService us;

    @Override
    public UserDetails loadUserByUsername(final String username) throws UsernameNotFoundException {
        final User user = us.findByEmail(username).orElseThrow(() -> new UsernameNotFoundException("No user by the name " + username));
        final Collection<? extends GrantedAuthority> authorities = Arrays.asList(
                new SimpleGrantedAuthority("ROLE_USER"),
                new SimpleGrantedAuthority("ROLE_ADMIN")
        );
        return new org.springframework.security.core.userdetails.User(username,
                user.getPassword(), authorities);
    }
}
```

Para no devolver el user de Spring Security, podemos usar uno propio en una nueva clase dentro de `auth`, llamada `PawAuthUser`, de la siguiente manera:
```Java
public class PawAuthUser extends User {

    private static final long serialVersionUID = 5465377571748379930L;

    public PawAuthUser(final String username, final String password, Collection<? extends GrantedAuthority> authorities) {
        super(username, password, authorities);
    }

    public PawAuthUser(final String username, final String password, boolean enabled, boolean accountNonExpired,
                       boolean credentialsNonExpired, boolean accountNonLocked, Collection<? extends GrantedAuthority> authorities) {
        super(username, password, enabled, accountNonExpired, credentialsNonExpired, accountNonLocked, authorities);
    }
}
```

Los múltiples constructores de la clase `User` de Spring Security permiten diferencia usuarios bloqueados, desactivados, con passwords expiradas, etc. y disparar los flujos correspondientes. Adicionalmente, estamos estableciendo por defecto que todos los usuarios tienen los roles `ROLE_ADMIN` y `ROLE_USER`, aunque en la práctica esto será generado dinámicamente basado en información de nuestro sistema. 

Cabe destacar que las `authorities` son un `Set`, por lo que es normal que querramos que un usuario tenga múltiples roles (`ROLE_USER`, `ROLE_ADMIN`, `ROLE_TEAM_OWNER` , etc.) y de esa forma al definir las reglas no tener que asumir herencias entre roles, ni tener que redefinir todas las reglas si decidimos agregar un rol. 

Con esto así, creamos nuestra página de login (Ver guía). Agregamos a nuestro controller:
```Java
@RequestMapping("/login")
public ModelAndView login() {
    return new ModelAndView("login");
}
```

Vamos a probar obtener el usuario logueado desde la landing, para lo que vamos a agregar:
```Java
@RequestMapping("/")
public ModelAndView helloWorld() {
    final ModelAndView mav = new ModelAndView("helloworld/index");
    final String email = (String) SecurityContextHolder.getContext().getAuthentication().getPrincipal();
    final long userId = us.findByEmail(email).orElseThrow(UserNotFoundException::new).getId();
    return new ModelAndView("redirect:/" + userId);
    //return mav;
}
```

Además, para que funcione, vamos a tener que encodear las contraseñas de los usuarios, agregando lo siguiente:
```Java
@Configuration
@EnableWebSecurity
@ComponentScan("ar.edu.itba.paw.webapp.auth")
public class WebAuthConfig extends WebSecurityConfigurerAdapter {

    @Autowired
    private PawUserDetailsService userDetailsService;

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    @Autowired
    public void configureGlobal(AuthenticationManagerBuilder auth) throws Exception {
        auth.userDetailsService(userDetailsService).passwordEncoder(passwordEncoder());
    }
}
```

Debemos ahora también agregarlo en el registro del usuario, agregando el encode dentro de service en `UserServiceImpl`:
```Java
@Service
public class UserServiceImpl implements UserService {

    private UserDao userDao;
    private final PasswordEncoder passwordEncoder;

    @Autowired
    public UserServiceImpl(final UserDao userDao, final PasswordEncoder passwordEncoder) {
        this.userDao = userDao;
        this.passwordEncoder = passwordEncoder;
    }

    @Override
    public User createUser(String email, String password) {
        return userDao.create(email, passwordEncoder.encode(password));
    }
}
```

## Logging

**Logging** (registro de eventos o registro de logs) es el proceso de generar y almacenar mensajes sobre el comportamiento y las actividades de una aplicación o sistema a lo largo de su ejecución. Estos mensajes pueden contener información como errores, advertencias, eventos de depuración, información de estado y otros detalles relevantes para el monitoreo y mantenimiento del sistema.

En Java, la configuración del log está atada a como se loguea una clase, lo que está a su vez atado al árbol de paquetes y clases jerárquico. Podemos definir un `logger` en la raíz o uno dentro de cada clase. En tiempo de ejecución, el árbol se recorre hacia arriba buscando este `logger`. El appender es el que escribe los logs en donde corresponda. Todos los logs tienen un nivel, y podemos definir algunos nosotros. 

**Logback** es un framework de logging para aplicaciones Java. Es el sucesor natural de Log4j y es ampliamente utilizado por su rendimiento, flexibilidad y buena integración con Spring Boot. La configuración es muy sencilla (ver guía).

El siguiente código va a configurar un root logger (que recibe todos los mensajes de la aplicación) con un filtro a nivel `DEBUG`, enviando todo el output a un appender llamado `STDOUT` que no es otra cosa que la consola. Esto si bien puede ser útil en desarrollo, claramente no es óptimo para un ambiente productivo, donde no se debe loguear ni en consola ni en modo `DEBUG` .
```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <property name="defaultPattern" value="%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n" />

    <appender name="STDOUT" class="ch.qos.logback.core.ConsoleAppender">
        <encoder>
            <pattern>${defaultPattern:-}</pattern>
        </encoder>
    </appender>

    <root level="DEBUG">
        <appender-ref ref="STDOUT" />
    </root>
</configuration>
```

En el level de root podemos cambiarlo para mover el logging a distintos puntos del árbol, como vimos. A su vez, estamos imprimiendo los logs en `STDOUT`, lo que nos es muy útil en desarrollo pero es un problema de seguridad en producción, por lo que deberíamos tener dos configuraciones, una para cada instancia. 

Lo que vamos a hacer es tener 2 archivos de configuración, producción (`logback.xml`) y desarrollo (`logback-test.xml`) ambos en `src/main/resources`, de modo que en desarollo siempre encuentre primero la configuración de desarrollo, pero luego configurar Maven para dejar afuera del war generado el archivo `logback-test.xml` así en producción siempre usa la configuración definida en `logback.xml`.

Lo primero que hacemos es renombrar `logback.xml` a `logback-test.xml` dentro de la misma carpeta `src/main/resources`, dejando así el `ConsoleAppender` que usábamos la clase pasada para desarrollo. Luego vamos a generar un nuevo `logback.xml` en `src/main/resources` con una configuración más acorde a producción, es decir, logueando a archivos, pero asegurándonos de que estos logs no crezcan infinitamente (dejando al servidor sin espacio en disco), y sobre todo, que no esté logueando en un nivel demasiado bajo.
```xml
<?xml version="1.0" encoding="UTF-8"?>
<configuration>
    <property name="defaultPattern" value="%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n" />

    <appender name="root-appender" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <maxHistory>5</maxHistory>
            <fileNamePattern>logs/warnings.%d{yyyy-MM-dd}.log</fileNamePattern>
        </rollingPolicy>
        <encoder>
            <pattern>${defaultPattern:-}</pattern>
        </encoder>
    </appender>

    <appender name="paw-appender" class="ch.qos.logback.core.rolling.RollingFileAppender">
        <rollingPolicy class="ch.qos.logback.core.rolling.TimeBasedRollingPolicy">
            <maxHistory>5</maxHistory>
            <fileNamePattern>logs/paw.%d{yyyy-MM-dd}.log</fileNamePattern>
        </rollingPolicy>
        <encoder>
            <pattern>${defaultPattern:-}</pattern>
        </encoder>
    </appender>

    <root level="WARN">
        <appender-ref ref="root-appender" />
    </root>

    <logger name="ar.edu.itba" level="DEBUG" additivity="false">
        <appender-ref ref="paw-appender" />
    </logger>
</configuration>
```
Con el `additivity` en `false`, lo que hacemos es que no se sigan buscando loggers en el árbol hacia arriba una vez que se encuentra el correspondiente.

Luego, en el POM de webapp, configuramos el plugin que genera el `war` para omitir la configuración de desarrollo (definiendo la versión de la guía):
```xml
<plugin>
    <groupId>org.apache.maven.plugins</groupId>
    <artifactId>maven-war-plugin</artifactId>
    <version>${maven-war-plugin.version}</version>
    <configuration>
        <packagingExcludes>**/logback-test.xml</packagingExcludes>
    </configuration>
</plugin>
```

Finalmente, estamos en condiciones de agregar nuestros propios logs en nuestra aplicación. Para esto, debemos en la clase done querramos loguear cosas, definir un `Logger`, lo que en el caso del `UserController` se hace de la siguiente manera:
```Java
private static final Logger LOGGER = LoggerFactory.getLogger(UserController.class);
```

Debemos tener cuidado de usar las clases `Logger` y `LoggerFactory` de SLF4J, así somos independientes de la implementación concreta que se esté utilizando. Luego podríamos loguear mensajes en cualquier log level usando los métodos provistos por el logger. 

Debemos también recordar no concatenar `Strings` ya que es muy ineficiente. En lugar de eso, podemos usar como placeholder `{}` y pasar cualquier objeto para reemplazarlos como argumentos variables. Por ejemplo en el register:
```Java
@RequestMapping(value = "/register", method = RequestMethod.POST)
public ModelAndView register(
        @Valid @ModelAttribute("registerForm") final UserForm userForm,
        final BindingResult errors
) {
    if (errors.hasErrors()) {
        return registerForm(userForm);
    }
    final User user = us.createUser(userForm.getEmail(), userForm.getPassword());
    LOGGER.info("Registering user: {}", user);
    return new ModelAndView("redirect:/" + user.getId());
}
```

A los loggers podemos agregarle un último parámetro del tipo throwable y automáticamente se va a guardar en el log todo el stack trace de la excepción por ejemplo. Es importante usar bien los distintos niveles de logs, no poner todos en el mismo.
