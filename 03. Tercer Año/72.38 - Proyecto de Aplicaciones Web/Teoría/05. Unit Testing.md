## Testeo

Los **testeos** deben ser adecuados para los casos en los que se vea involucrada la lógica de la aplicación. Cuando un test falla, queremos saber exactamente qué es lo que ocasionó el problema. 

Generalmente, un test consiste de 3 etapas:
1. **Setup**: Se establecen las condiciones iniciales o precondiciones.
2. **Ejercitar**: Idealmente es una llamada a un único método.
3. **Validaciones**: Se evalúa el resultado de la operación, se lo conoce como postcondiciones. Tienen que ser pocas (4 como mucho).

Vamos a usar una librería que nos va a ayudar para esto, que son JUnit y TestNG. Ambas son muy parecidas, la diferencia es el orden de los parámetros en los assertions. Vamos a usar JUnit nosotros.

Primero, vamos a setear los POMs con JUnit, y luego armamos la clase de testeo en `src/test/java`. Vemos que vamos a invocar las clases concretas, porque no queremos desentendernos de la implementación. Vamos a poder hacer validaciones sobre métodos que no están en la interfaz pública.

Hay tests que pueden fallar según los datos que tengamos dentro de la base de datos, como por ejemplo un create. La primera vez va a funcionar, pero la segunda va a arrojar error porque ya existe el usuario. Esto se soluciona controlando las dependencias y los objetos que necesita transitivamente. Para esto, se usan: 
- `stubs`: implementación vacía.
- `mocks`: implementación "programable".
- `fake`: implementación limitada pero funcional.

También se suele usar HyperSQL que es una base de datos escrita en Java embebible. Es muy pequeña y sencilla, y maneja la persistencia en memoria o archivo en disco. Esto permite garantizar que no importa cuántas veces corramos el test, siempre comenzamos en las mismas condiciones.

Configuramos esta base de datos HSQL:
```Java
@Before
public void setUp() {
    final SimpleDriverDataSource ds = new SimpleDriverDataSource();
    ds.setDriverClass(JDBCDriver.class);
    ds.setUrl("jdbc:hsqldb:mem:test");
    ds.setUsername("ha");
    ds.setPassword("");

    userDao = new UserDaoImpl(ds);
}
```

Ahora podemos testear por ejemplo:
```Java
@Test
public void testCreateUser() {
    //Preconditions


    //Exercise
    User user = userDao.create(USERNAME, "passtest");

    //Postconditions
    assertNotNull(user);
    assertEquals(USERNAME, user.getEmail());
}
```

En el siguiente caso, si limpiáramos la base de datos con un método de `UserDao`, podríamos obtener un error propio de este método y no del `findById`. El objeto siendo testeado NO puede ser manipulado en las precondiciones ni en las postcondiciones. Sólo se puede tocar en la ejercitación. Además, usamos Spring Test para facilitar el testeo con bases de datos. 

Agregamos las dependencias y creamos el `JdbcTemplate` con el ds anterior. Podemos verificar que funcione el create mediante: 
```Java
adderEquals(1, JdbcTestUtils.countRowsInTable(JdbcTemplate, “users”));
```
Y haciendo un `deleteFromTables` en las precondiciones. Ahora, el test de `findById` nos queda:
```Java
@Test
public void testFindByIdDoesntExist() {
    //Preconditions
    JdbcTestUtils.deleteFromTables(jdbcTemplate, USER_TABLE);

    //Exercise
    Optional<User> maybeUser = userDao.findById(1);

    //Postconditions
    assertFalse(maybeUser.isPresent());
}
```

Para el caso que el usuario exista, primero debemos configurar el `JdbcInsert`:
```Java
private UserDaoImpl userDao = new UserDaoImpl(null);
private JdbcTemplate jdbcTemplate;
private SimpleJdbcInsert jdbcInsert;

@Before
public void setUp() {
    final SimpleDriverDataSource ds = new SimpleDriverDataSource();
    ds.setDriverClass(JDBCDriver.class);
    ds.setUrl("jdbc:hsqldb:mem:test");
    ds.setUsername("ha");
    ds.setPassword("");

    userDao = new UserDaoImpl(ds);
    jdbcTemplate = new JdbcTemplate(ds);
    jdbcInsert = new SimpleJdbcInsert(jdbcTemplate)
            .withTableName(USER_TABLE)
            .usingGeneratedKeyColumns("id");
}
```

Y luego desarrollamos el test:
```Java
@Test
public void testFindByIdExist() {
    //Preconditions
    JdbcTestUtils.deleteFromTables(jdbcTemplate, USER_TABLE);
    Number key = jdbcInsert.execute(Map.of("username", USERNAME));

    //Exercise
    Optional<User> maybeUser = userDao.findById(key.longValue());

    //Postconditions
    assertTrue(maybeUser.isPresent());
    assertEquals(USERNAME, maybeUser.get().getEmail());
}
```

Esto todavía no va a correr porque nunca creamos las tablas correspondientes. Podríamos hacerlas en el setup, pero no estaría del todo bien. Entonces, vamos a crear un nuevo directorio dentro de `src/test/resources` y vamos a crear un `schema.sql`.
```sql
CREATE TABLE IF NOT EXISTS users(
    id INTEGER IDENTITY PRIMARY KEY,
    mail VARCHAR(100),
    password VARCHAR(100)
);
```

Vamos ahora a crear nuestro `TestConfig` y setear el `UserDaoTest` con lo siguiente: 
```Java
@RunWith(SpringJUnit4ClassRunner.class)
@ContextConfiguration(classes = TestConfig.class)
```

Y así podemos declarar el data source como `private` en la clase con `Autowired`, haciendo que Spring lo busque automáticamente. Para agregar el esquema SQL y poblar la base de datos, vamos a usar:
```Java
@Configuration
public class TestConfig {

    @Value("classpath:schema.sql")
    private Resource schemaSql;

    @Bean
    public DataSource dataSource() {
        final SimpleDriverDataSource ds = new SimpleDriverDataSource();
        ds.setDriverClass(JDBCDriver.class);
        ds.setUrl("jdbc:hsqldb:mem:paw");
        ds.setUsername("ha");
        ds.setPassword("");

        return ds;
    }

    @Bean
    public DataSourceInitializer datasourceInitializer() {
        DataSourceInitializer dsi = new DataSourceInitializer();
        dsi.setDataSource(dataSource());
        dsi.setDatabasePopulator(databasePopulator());

        return dsi;
    }

    private DatabasePopulator databasePopulator() {
        ResourceDatabasePopulator populator = new ResourceDatabasePopulator();
        populator.addScript(schemaSql);
        return populator;
    }
}
```
Esta misma lógica se puede usar para poblar la base de datos de producción.

## Mocking

Ahora, debemos ver cómo hacer **mocking**. Si ahora debemos hacer tests en la capa de servicios, queremos que los errores de los Daos no hagan fallar los test de servicios. Vamos a usar Mockito, agregando las dependencias. Creamos el test para `UserServiceImpl`. Con lo siguiente:
```Java
userDao = Mockito.mock(UserDao.class)
```
Obtenemos un "nice" mock, que significa que devuelve según el tipo:
- Si es nullable, devuelve `null`.
- Si es Number, devuelve `0`.
- Si es boolean, devuelve `false`.

Pero como es un mock, es programable, podemos decirle lo que debe devolver, como por ejemplo:
```Java
userDao = mock(UserDao.class); // "nice" mock
User user = new User(1, "foo");
when(userDao.create(anyString())).thenReturn(user)
        .thenReturn(null)
        .thenThrow(new NullPointerException());
```

Debemos modificar la implementación que teníamos de `UserService`, eliminando el constructor y haciendo que `userDao` sea `Autowired`. Podemos hacer un setter que esté sólo disponible para el package. Entonces, tenemos el siguiente setup y test:
```Java
@Before
public void setUp() {
    userDao = mock(UserDao.class);
    userService = new UserServiceImpl();
    userService.setUserDao(userDao);
}

@Test
public void testCreateUser() {
    //Preconditions
    User user = new User(1, "test@test.com", "test");
    when(userDao.create(anyString(), anyString())).thenReturn(user);

    //Exercise
    userService.createUser(USERNAME, PASSWORD);

    //Postconditions

}
```

Para las postcondiciones, nos podríamos ver tentados de usar:
```Java
Mockito.verify(userDao.create(USERNAME, PASSWORD));
```

>[!WARNING] Cuidado
>Esto estaría mal, porque no estaríamos validando nuestro contrato, sino una implementación particular. Es recomendable NO utilizar el método `verify`, pues queremos verificar comportamiento, no la implementación. 

Podemos llegar a tener casos donde no necesitamos postcondiciones, sino que simplemente queremos testear que el método no falle. Para esto, podemos agregar un `try-catch`:
```Java
//Exercise
try {
    userService.createUser(USERNAME, PASSWORD);
} catch (Exception e) {
    Assert.fail("Unexpected error during operation create user.");
}
```

Mockito tiene además su propio runner de JUnit, por lo que nos ahorramos usar el de Spring. Este entiende de anotaciones propias de Mockito como `@Mock`, que nos permite no tener el `userDao = mock(UserDao.class);` y `@InjectMocks` que busca dentro de en este caso `UserServiceImpl` si tiene mocks para aplicar, haciendo que no necesitemos setter. Con esto, limpiamos el `setUp` y nos queda:
```Java
@RunWith(MockitoJUnitRunner.class)
public class UserServiceImplTest {

    private static final String USERNAME = "user@test.com";
    private static final String PASSWORD = "password";

    @InjectMocks
    private UserServiceImpl userService = new UserServiceImpl();
    @Mock
    private UserDao userDao;

}
```
