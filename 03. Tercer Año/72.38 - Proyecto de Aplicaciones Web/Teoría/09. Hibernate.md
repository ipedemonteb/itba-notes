## Object Relational Mapping

Ahora, vamos a reemplazar nuestra capa de persistence, dado que vamos a dejar de usar JDBC de forma directa. Vamos a pasar a usar un **ORM (Object Relational Mapping)**, que es una técnica de programación que permite interactuar con bases de datos relacionales utilizando objetos en el lenguaje de programación. En lugar de escribir consultas SQL directamente, los desarrolladores usan clases y métodos para crear, leer, actualizar y eliminar datos.

Se nos va a abstraer y por lo tanto simplificar las maneras de acceder a la base de datos. Existen múltiples formas de hacer estos mapeos:
- **JPA (Java Persistence API)**: Es una especificación estándar de Java que define cómo debe manejarse la persistencia de datos en aplicaciones Java. JPA no es una implementación en sí, sino una interfaz que debe ser implementada por proveedores como Hibernate, EclipseLink, entre otros. Utiliza anotaciones para mapear clases Java a tablas en la base de datos. Es ampliamente usado en aplicaciones empresariales por su flexibilidad y estandarización. Vamos a usar principalmente este.
- **JPO (Java Persistence Object)**: Es una alternativa más simple y ligera a JPA. No es una especificación oficial ni requiere de proveedores externos. JPO permite realizar operaciones CRUD (crear, leer, actualizar, eliminar) sin necesidad de anotaciones ni configuraciones complejas. Es ideal para proyectos pequeños o donde se busca simplicidad, aunque no es tan común en la industria como JPA.

---
## Hibernate

**Hibernate** es un framework de Java que permite trabajar con bases de datos relacionales utilizando objetos Java, sin necesidad de escribir directamente consultas SQL en la mayoría de los casos, es decir, es un proveedor de JPA. Hibernate traduce automáticamente las operaciones realizadas sobre objetos Java en instrucciones SQL que interactúan con la base de datos.

>[!INFO] Tradeoff Importante
>Con esta herramienta, vamos a tener un tradeoff importante, ya que vamos a ganar mucho pero también vamos a dejar bastante sobre la mesa. La gran ventaja va a ser la simpleza y la velocidad, ya que vamos a simplificar muchísimo los mapeos y queries a la base de datos. Pero no vamos a ver estas queries, por lo que perdemos mucho control y algo de performance. Vamos a tener además capas de abstracción extra, agregando un lenguaje intermedio. 

La **herencia** no existe en el mundo relacional, o el valor `null`. Esto en objetos es fundamental, pero en este otro mundo se pierde. Los objetos es común tener atributos que sean `null` para indicar que algo no tiene valor o no está definido. En el mundo relacional también existe el concepto de `NULL`, pero su interpretación puede ser problemática, ya que en SQL, `NULL` no significa exactamente lo mismo que en programación: en SQL, `NULL` representa "valor desconocido" o "sin valor", y su comportamiento en consultas y comparaciones es especial (por ejemplo, `NULL = NULL` no da true, sino `unknown`).

La **impedancia** (más específicamente, impedancia entre el mundo objeto y el mundo relacional) se refiere a la dificultad de adaptar y sincronizar dos paradigmas muy distintos: el paradigma orientado a objetos (usado en lenguajes como Java, Python, etc.) y el paradigma relacional (usado en bases de datos como MySQL, PostgreSQL, etc.). Para manejarlo, nosotros venimos utilizando convenciones para así poder unificar los dos mundo con Jdbc.

Ahora, va a ser nuestra responsabilidad como desarrolladores conocer las convenciones del ORM que escogemos, en este caso, Hibernate.

## Configuración

Lo primero es declarar las dependencias correspondiente en el POM padre, que se encuentran en los archivos de las clases. En persistence vamos a agregar la dependencia de Spring que trabaja con ORMs y luego las de Hibernate. También tendremos que agregar las correspondientes en `model` y en `webapp`.

Ahora, vamos a establecer el funcionamiento en el `WebConfig` dentro de `webapp`:
```Java
@Bean
public LocalContainerEntityManagerFactoryBean entityManagerFactory() {
    final LocalContainerEntityManagerFactoryBean factoryBean = new LocalContainerEntityManagerFactoryBean();
    factoryBean.setPackagesToScan("ar.edu.itba.model");
    factoryBean.setDataSource(dataSource());

    final JpaVendorAdapter vendorAdapter = new HibernateJpaVendorAdapter();
    factoryBean.setJpaVendorAdapter(vendorAdapter);

    final Properties properties = new Properties();
    properties.setProperty("hibernate.hbm2ddl.auto", "update");
    properties.setProperty("hibernate.dialect", "org.hibernate.dialect.PostgreSQL92Dialect");

    // Si ponen esto en prod, hay tabla!!!
    properties.setProperty("hibernate.show_sql", "true");
    properties.setProperty("format_sql", "true");

    factoryBean.setJpaProperties(properties);

    return factoryBean;
}
```

En el campo `properties.setProperty(“...”, “update”)`, NUNCA hay que usar `create` en el segundo campo porque dropea todo y crea de cero. El `update` hace un best effort para actualizar el esquema. No hay que confiarse que la base se actualiza sola. En la segunda property, tenemos que elegir la que se adapte a nuestra BD.

Las últimas dos properties van a estar imprimiendo las queries en `STDOUT`, por lo que está MUY MAL tenerlas en producción, solamente las vamos a usar en desarrollo. 
 
Ahora, tenemos que modificar el `transactionManager`:
```Java
@Bean
public PlatformTransactionManager transactionManager(final EntityManagerFactory emf) {
    return new JpaTransactionManager(emf);
}
```

Con esto podemos ir a cambiar nuestra implementación de persistencia directamente. Ahora, vamos a tener un único objeto que va a manejar los modelos, ya no vamos a tener dos como en JDBC. Vamos a agregar la anotación `@PersistenceContext` que se utiliza para inyectar automáticamente una instancia de `EntityManager` en un componente gestionado por el contenedor. El `EntityManager` es la interfaz principal que se usa para interactuar con la base de datos: permite persistir, actualizar, eliminar y consultar entidades. Pero en lugar de crear manualmente un `EntityManager`, se puede usar `@PersistenceContext` para que el contenedor lo gestione por nosotros y lo inyecte donde lo necesitemos.
```Java
@Repository
public class UserHibernateDao implements UserDao {

    @PersistenceContext
    private EntityManager em;
```

La anotación `@Repository` se utiliza para marcar una clase como componente de acceso a datos, es decir, como una clase que se encarga de interactuar con la base de datos.

Ahora, el `create` nos queda:
```Java
@Override
public User create(final String username, final String password) {
    final User user = new User(username, password);
    em.persist(user);
    return user;
}
```

User ya no va a recibir el `ID` porque no lo vamos a conocer, sino que comienza en `null`. Una vez que creamos el usuario, el `EntityManager` se va a encargar de setearlo según corresponda. Si le pasamos el `ID, persist` en lugar de hacer un `INSERT` va a hacer un `UPDATE` porque asume que ya existe.

El `findById` queda mucho más sencillo, casi trivial:
```Java
@Override
public User findById(long id) {
    return em.find(User.class, id);
}
```

La búsqueda por user va a ser un poco más compleja, ya que vamos a tener que escribir la query, pero que no va a ser SQL sino como sigue:
```Java
@Override
public User getByUsername(final String username) {
    final TypedQuery<User> query = em.createQuery("from User as u where u.username = :username", User.class);
    query.setParameter("username", username);
    final List<User> list = query.getResultList();
    return list.isEmpty() ? null : list.get(0);
}
```

En el `u.username`, no estamos escribiendo el nombre de una columna, sino que se vincula con un atributo de nuestro modelo. Podríamos tener por ejemplo `u.pets.name`, donde se podría tener una lista de mascotas.

Ahora, debemos mapear nuestro modelo con JPA agregando annotations:
```Java
@Entity
@Table(name = "users")
public class User {
```

`Entity` dice que se tiene una entidad del modelo, y `Table` el nombre de la tabla. Además, dentro de user debemos especificar que el `Id` es autogenerado de la siguiente manera:
```Java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "users_userid_seq")
@SequenceGenerator(sequenceName = "users_userid_seq", name = "users_userid_seq", allocationSize = 1)
@Column(name = "userid")
private Long id;
```

Luego, debemos declarar el `username` y `password` como columnas también de la tabla con algunas restricciones:
```Java
@Column(length = 100, nullable = false, unique = true)
private String username;

@Column(length = 100, nullable = false)
private String password;

/* package */ User() {
    // Just for Hibernate, we love you!
}
```

En general los default son buenos, pero tenemos que tener mucho cuidado y agregar todo para que las cosas coincidan. El uso de `@Table` no es obligatorio, salvo que querramos evitar algún default. En este caso, queremos que se siga usando la tabla users en lugar de la que generaría por default `User` (nótese el casing). Análogamente, el `@Column` en la columna id responde a que no queremos usar el nombre default, sino que tenga el `@Id` alcanzaría.

Por defecto, Hibernate en PostgreSQL crea una única secuencia, llamada `hibernate_sequence` y la utiliza para todas las entidades. Nosotros ya teníamos una secuencia `users_userid_seq` para los ids de esta tabla. Deseamos seguir usándola,  por lo tanto debemos agregar el atributo generator a `@GeneratedValue` y agregar la annotation `@SequenceGenerator` indicando cuál es el generator que queremos usar.

Hibernate requiere un constructor default para poder crear instancias de nuestros modelos y luego por reflection popular las properties. Por eso agregamos el constructor de `User() {}` vacío. Además, se restringe a crear tablas o columnas que no existen. Si por ejemplo cambiamos en username `length` a `255`, Hibernate no va a actualizar la tabla. Tampoco va a borrar columnas que no se usen.

## Mapeos

Hasta ahora tuvimos únicamente una entidad sin relaciones. Para agregar complejidad, creamos un nuevo modelo Issue con id, descripción, autor, asignado, prioridad. Ver apunte de clase.

Definimos que la relación con `User` es opcional para la asignación, ya que no es una relación fuerte (pueden existir issues que no fueron asignados a nadie); pero es requerida para la creación (alguien tuvo que haberlos creado).

Por su parte, `Priority` es un enum standard de java:
```Java
public enum Priority {
    LOW,
    MEDIUM,
    HIGH,
    UNBREAK_NOW,
}
```

Como ya vimos en clase `@Enumerated` tiene varias opciones para mapear enums, según qué queramos priorizar. En general, `EnumType.STRING` es una buena opción, pues favorece la legibilidad de los datos en la base de datos. Se debe tener cuidado si se agregan nuevos valores al enum en garantizar que sus nombres entren en el ancho de columna que haya generado Hibernate. Dentro de `Issue` nos queda:
```Java
@Enumerated(EnumType.STRING)
private Priority priority;
```

Si miramos nuestro diagrama de entidad-relación, tenemos lo siguiente:
![[Pasted image 20260819184422.png|center|575]]
Notemos que tenemos relaciones "uno a muchos", ya que un usuario puede crear muchos issues, pero cada una sólo puede ser creada por un usuario, y a su vez un usuario puede tener asignadas muchas issues pero cada una sólo está asignada a un usuario.  

Para mapear esto, vamos a, dentro de `Issue`, declarar las siguientes anotaciones:
```Java
@ManyToOne(fetch = FetchType.EAGER, optional = false)
private User createdBy;

@ManyToOne(fetch = FetchType.EAGER, optional = true)
private User assignedTo;
```

Vemos que es "muchas a una", porque estamos parados dentro del `Issue`. Podemos decir si es opcional o no y además podemos declarar el `FetchType`, que es una enumeración en JPA  que define cuándo se deben cargar los datos relacionados con una entidad, especialmente en relaciones como `@OneToMany`, `@ManyToOne`, `@OneToOne` o `@ManyToMany`. En otras palabras, controla la estrategia de carga de las asociaciones entre entidades. 
- `FetchType.EAGER`: significa carga inmediata. Cuando se recupera la entidad principal desde la base de datos, también se recuperan automáticamente todos los datos relacionados. Es útil cuando se sabe que siempre se necesitan  los datos asociados, pero puede causar un impacto en el rendimiento si hay muchas relaciones o datos pesados. Sólo lo vamos a usar cuando estemos MUY seguros que necesitamos TODOS los datos y teniendo en cuenta que no nos traiga casi toda la BD en cadena. Deberían ser la menor cantidad de casos posible.
- `FetchType.LAZY`: significa carga diferida o bajo demanda. Cuando se recupera la entidad principal, no se cargan los datos relacionados inmediatamente. En su lugar, se cargan sólo cuando se accede explícitamente a la propiedad relacionada. Es más eficiente cuando las relaciones no siempre son necesarias.

Ahora, podemos desde `User` mapear las relaciones en forma inversa:
```Java
@OneToMany(fetch = FetchType.LAZY, orphanRemoval = false, mappedBy = "assignedTo")
private List<Issue> assignedIssues;

@OneToMany(fetch = FetchType.LAZY, orphanRemoval = true, mappedBy = "createdBy")
private List<Issue> createdIssues;
```

En la anotación, el atributo `orphanRemoval` se usa para indicar que, si un objeto hijo deja de estar asociado con su padre, debe ser eliminado automáticamente de la base de datos.

Hibernate va a detectar que tenemos dos entidades que se están mapeando entre sí, dado que tienen una relación uno a muchos. En nuestro caso, las columnas se tienen que cargar en Issue porque tiene las claves foráneas. El atributo `mappedBy` se utiliza en asociaciones bidireccionales para indicar cuál es el lado dueño de la relación, es decir, cuál entidad se encarga de manejar la clave foránea en la base de datos. El lado que tiene el `mappedBy` no es el propietario de la relación; simplemente refleja la relación que está controlada por el otro lado.

## Contexto de Persistencia

Tomemos el siguiente ejemplo en la capa de servicios:
```Java
@Transactional
@Override
public void orderIssuesByPriority(final long id) {
    final User user = userDao.findById(id);
    Collections.sort(user.getPendingFixes(), new Comparator<IssueTPE>() {
        @Override
        public int compare(final IssueTPE o1, final IssueTPE o2) {
            return o2.getPriority().ordinal() - o1.getPriority().ordinal();
        }
    });
}
```

En este caso, se define un método `orderIssuesByPriority(long id)` que obtiene un `User` desde la base de datos, accede a su lista de `pendingFixes`, y la reordena en memoria usando `Collections.sort(...)`. Lo interesante es que nunca se llama explícitamente a un método `save()` o `update()` para indicar que el usuario fue modificado. Sin embargo, cuando termina la transacción, Hibernate detecta automáticamente que la colección asociada al objeto `User` cambió (porque está dentro del contexto de persistencia) y sin que el programador lo pida explícitamente, sincroniza esa modificación con la base de datos.

Un contexto de persistencia implica que no solo se tiene una conexión activa, sino que se tiene un entorno gestionado que se encarga de controlar automáticamente las entidades. Ese contexto mantiene un seguimiento de los objetos que están siendo gestionados (persistentes), detecta cuándo cambian sus valores y se encarga de sincronizarlos con la base de datos cuando es necesario (por ejemplo, al hacer `flush()` o al commit de una transacción).

El caso anterior es posible porque el objeto user fue obtenido dentro de una transacción activa (`@Transactional`) y está siendo gestionado por el `EntityManager`. Por eso se dice que es una instancia "managed". En este estado, Hibernate observa sus atributos y detecta si han cambiado: si detecta que algo se modificó, lo marca como dirty (sucio) y lo actualiza al hacer el `flush()` o al cerrar la transacción. Esto ofrece gran comodidad y reducción de código, pero también introduce ciertos compromisos:
1. Nos atamos a usar JPA / Hibernate, volver a JDBC implica perder la persistencia sin que el código deje de compilar.
2. Tenemos poco control de cuando se están ejecutando las queries y cuales. Si usasemos un filtro para tener una sesión abierta en la vista, esto no ocurriría hasta que no se termine de renderizar la respuesta

Notemos que esto funciona porque el `User` es creado por el contexto de persistencia actual. Si `User` es pasado por argumento, y no tenemos un filtro u otro método alrededor que nos mantenga dentro de un mismo contexto, esto no ocurriría, por el contrario, `user.getPendingFixes()` podría tirar una excepción al querer hacer lazy loading de la colección sin tener una sesión asociada. El `EntityManager` ofrece métodos para reasociar una instancia al mismo, pero exponer estos métodos al servicio lo ensucian y exponen detalles de implementación del DAO (el uso de JPA/Hibernate).

Igualmente, se puede hacer explícito mediante una llamada al método `save()`, cuya implementación en persistence sería la siguiente:
```Java
@Override
public void save(User user) {
    em.persist(user);
}
```

Recordemos que `persist` hace un `update` en caso de encontrar el usuario. Es importante ser consistentes con esto a lo largo del TP.

Otro punto interesante sobre este método es analizar lo que está haciendo Hibernate para persistir el cambio de orden de la colección. Podemos ver que borra todas las relaciones entre el usuario y todos sus issues y vuelve a crearlos en el orden apropiado. Esto se debe a que están usando el `ROWID` de la tabla relación para usar el orden, y necesita que el orden de inserción sea el orden en que queremos recuperarlos.

## Paginación en JPA

En el TP tenemos implementado búsquedas con paginación. En nuestra query ahora que estamos en un contexto de entidades, el `LIMIT` de SQL representa cuántas filas se obtienen, pero si nosotros queremos 10 resultados, en realidad podemos estar buscando 10 entidades y que no coincidan con solamente una fila.

Lo que vamos a hacer es lo siguiente, vamos a hacer una query nativa para obtener los `id` que deben aparecer en la página que se está buscando. Luego, se va a hacer la query JPA para popular esos usuarios con todas sus relaciones. Esta forma va a ser totalmente segura con respecto al problema que planteamos inicialmente.
```Java
@Override
public List<User> listUsers(int page, int pageSize) {
    Query nativeQuery = em.createNativeQuery("SELECT id FROM users", Long.class);
    nativeQuery.setFirstResult((page - 1) * pageSize);
    nativeQuery.setMaxResults(pageSize);
    List<Long> filteredIds = (List<Long>) nativeQuery.getResultList();

    final TypedQuery<User> query = em.createQuery("from users where id IN :filteredIds", User.class);
    query.setParameter("filteredIds", filteredIds);
    return query.getResultList();
}
```

Esta técnica se aplica también para JDBC.

## Sesiones

Hibernate usa internamente algo llamado **sesión** (`Session` en Hibernate o `EntityManager` en JPA), que está asociado a un contexto de persistencia. Este contexto es un espacio en memoria donde Hibernate almacena y gestiona objetos de entidad que están "vivos" (es decir, que están siendo monitoreados para detectar cambios). Este contexto de persistencia se crea automáticamente cuando se inicia una transacción (por ejemplo, cuando empieza un método marcado con `@Transactional`) y se destruye cuando la transacción termina (cuando el método termina y se hace `commit` o `rollback`).

Mientras un objeto está en ese contexto (por ejemplo, un `User` que se trae con `findById` dentro de una transacción), Hibernate lo considera "gestionado": sabe qué atributos tiene, y si cambia alguno, lo puede detectar automáticamente y sincronizar con la base de datos. Pero esa "magia" sólo dura mientras existe la sesión, es decir, mientras el contexto de persistencia esté activo.

El problema aparece cuando se tienen múltiples llamadas transaccionales separadas. Por ejemplo:
1. En la primera transacción, se trae un objeto `User` y  se lo modifica.
2. Luego, en una segunda transacción, se vuelve a trabajar con ese mismo `User`.

El `User` de la segunda transacción no es el mismo objeto en memoria que el de la primera. Son nuevas instancias, traídas de nuevo de la base de datos o pasadas como parámetros. Hibernate no conserva automáticamente la historia de ese objeto entre transacciones, porque el contexto de persistencia se cerró al terminar la primera transacción. Ya no tiene memoria de qué pasó con él. Por eso, si modificamos un objeto fuera de una transacción y luego intentmamos usarlo dentro de otra sin volver a adjuntarlo (`merge`, por ejemplo), Hibernate no lo va a sincronizar automáticamente.

Para las sesiones, vamos a definir un nuevo filtro en el `web.xml`:
```xml
<filter>
    <filter-name>openEntityManagerInViewFilter</filter-name>
    <filter-class>org.springframework.orm.jpa.support.OpenEntityManagerInViewFilter</filter-class>
</filter>

<filter-mapping>
    <filter-name>openEntityManagerInViewFilter</filter-name>
    <url-pattern>/*</url-pattern>
</filter-mapping>
```

Es importante poner el mapping luego de Spring Security porque entonces va a implicar que hubo una sesión contra la base de datos. La contra de estas sesiones, es que nuestra conexión a la base de datos está abierta durante más tiempo, aunque seguimos en el orden de los milisegundos. Nuevamente, seguimos perdiendo control, porque se pueden ejecutar queries en momentos que no lo esperamos.

## Mapeo de Herencia

Supongamos ahora que los usuarios son abstractos y tenemos dos tipos, alumnos y profesores, con legajo los primeros y módulos asignados los segundos. Como `User` es abstracta, deja de ser una `entity` y pasa a ser una `@MappedSuperclass`. Esta anotación se utiliza para definir una clase base que no es una entidad por sí misma, pero que puede aportar campos comunes a varias entidades. Es decir, es una clase que sirve como superclase para entidades JPA, permitiendo heredar atributos persistentes sin que la clase padre tenga su propia tabla en la base de datos.

Las nuevas clases de alumno y doctor sí son entidades. Tenemos 3 formas de mapearlas:
1. Se puede mapear a tablas teniendo una única tabla con una columna `type`, pero esto nos obligaría a tener valores `null` en las columnas de legajo y módulos, que en realidad marcamos como que no queríamos.
2. Mapear cada entidad a una nueva tabla, obteniendo así tres de ellas. La contra es la necesidad de hacer `joins`. ![[Pasted image 20260819185516.png|center|536]]
3. Como `user` no nos sirve nunca solo, la última opción es tener dos tablas con todos los datos, repitiendo los atributos. La contra es que estas tablas son independientes y podríamos tener alumnos y profesores con el mismo `id`. ![[Pasted image 20260819185604.png|center]]Podemos reducir el impacto de esto declarando que el `generator` que vamos a usar para el `id` es el mismo.

La solución que escogeremos será la que mejor se adecúe a nuestro caso, ya que todas presentan tradeoffs. Si `User` no fuera abstracta, las opciones 2 y 3 son iguales.

Los métodos se mapean de la siguiente manera. Si `User` es abstracta, se usa como vimos el `@MappedSuperclass`, sino sigue siendo `Entity`. Arriba, vamos a agregar el annotation `@Inheritance(strategy = InheritanceType.OPTION)`, que nos va a dejar elegir la estrategia con la cuál queremos mapear. Las opciones son:
- `InheritanceType.SINGLE_TABLE`: Toda la jerarquía de clases se guarda en una sola tabla. Esta tabla tiene una columna discriminadora (por ejemplo, `DTYPE`) que indica a qué subclase pertenece cada fila. Es la estrategia más rápida en lectura, pero puede tener muchas columnas vacías si las subclases tienen atributos muy distintos.
- `InheritanceType.JOINED`: Se crea una tabla para cada clase (la clase base y cada subclase). Las subclases se vinculan a la tabla base mediante una clave foránea. Es una estrategia más normalizada y flexible, pero puede ser más lenta porque requiere hacer `joins` para reconstruir cada entidad.
- `InheritanceType.TABLE_PER_CLASS`: Cada subclase tiene su propia tabla, que incluye también los atributos heredados de la clase base. No hay tabla para la clase base. Es útil si las subclases son muy independientes, pero complica las consultas polimórficas (por ejemplo, hacer un `SELECT` que devuelva instancias de todas las subclases juntas).
 
En la opción de `SINGLE_TABLE`, indicamos la columna discriminatoria del usuario mediante `@DiscriminatoryColumn(name =  "userType")`. Notemos que va a agregar una tabla pero no necesitamos incluir el atributo en el modelo. En las clases hijas se debe agregar `@DiscriminatoryValue("STUDENT")` por ejemplo, o el que corresponda. 

Con respecto a evitar `ids` repetidos en el segundo método, recordemos que incluímos las siguientes dos líneas:
```Java
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "users_id_seq")
@SequenceGenerator(allocationSize = 1, sequenceName = "users_id_seq", name = ="users_id_seq")
```
Lo hicimos principalmente por motivos de compatibilidad, ya que nuestra tabla ya existía. En `Issue` hicimos lo mismo cuando en realidad no era necesario. Si no aclaramos nada, Hibernate por default genera una secuencia llamada `hibernate_sequence` y la usa para todo, es decir cualquier `entity`. Esto nos garantiza que no vamos a tener `ids` repetidos sin importar la opción elegida más arriba. 

Tenemos un caso más, que es cuando tenemos un atributo como por ejemplo apodos, que es un `Set<String>`. Como `String` no es una entidad, no tiene un mapeo uno a muchos. En este caso, vamos a agregar la anotación:
```Java
@ElementCollection
private Set<String> nicknames; // <-- tabla user id + nickname
```
