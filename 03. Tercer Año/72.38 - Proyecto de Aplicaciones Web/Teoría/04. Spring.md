## Definición

**Spring** es un framework de código abierto para el desarrollo de aplicaciones Java. Permite crear aplicaciones empresariales, como aplicaciones web, de escritorio, de línea de comando, microservicios, y más. Algunas características:
- Es modular y flexible, lo que permite implementar diferentes tipos de arquitectura.
- Facilita el desarrollo y despliegue.
- Es extensible a través de código escrito por los usuarios.
- Mejora la eficiencia de codificación.
- Reduce el tiempo total de desarrollo de aplicaciones.
- Permite delegar en el framework la gestión de instancias de objetos.
- Permite integrar de forma más directa las tecnologías de acceso a datos.
- Proporciona un marco de autenticación robusto y personalizable.

## Maven

**Maven** es una herramienta de gestión del ciclo de vida del proyecto, mucho más que la gestión de dependencias, que suele ser tomado como su único rol. Crea el proyecto, compila, genera elementos dinámicos, análisis secundarios, dependencias, etc. son varias de sus funcionalidades. Para instalarlo, vamos a usar el comando:
```bash
brew install mvn
```

Nuestro proyecto va a estar dividido en distintos módulos, es decir componentes independientes entre ellas, que se compilan y testean en forma independiente. Una ventaja es poder utilizarlas, pues van a estar autocontenidas. Además, va a mejorar la performance porque se minimiza el impacto de generar un cambio.

Para generar nuestro proyecto, vamos a utilizar: 
```bash
mvn archetype:generate
```

Luego, debemos especificar el tipo de proyecto que queremos generar. Podemos hacer una búsqueda (pom). En nuestro caso queremos la opción de `Root project archetype for creating multi module projects`. El `groupId` que nos pide es la organización donde va a guardar los paquetes, el dominio invertido. En nuestro caso, `ar.edu.itba.paw`. El `artefactId` es el nombre del paquete que estamos produciendo (por ejemplo webapp). Luego, se nos pide la versión que por default es la `1.0-SNAPSHOT`.  Cualquier cosa que no tenga esta sentencia `SNAPSHOT` se considera un release, y este luego no se puede modificar, se debe crear una nueva versión. El paquete en principio no importa.

Una vez terminado el proceso, se genera un directorio con únicamente un `pom.xml` y la configuración mínima del proyecto. Una vez que tenemos este directorio, podemos empezar a generar los módulos de nuestra aplicación estando parados en el directorio mediante:
```bash
mvn archetype:generate 
```
En nuestra búsqueda ahora podemos por ejemplo tomar `maven-archetype-webapp` y encontramos la opción que dice `An archetype which contains a sample Maven Webapp project`. Rellenamos los parámetros y vemos que ahora se nos genera otro directorio webapp dentro del anterior, pero los contenidos ahora son otros. También, se modifica el pom del directorio padre, agregando los módulos. Estos tienen su propio pom, del que podemos sacar las propiedades y pegarlas en el padre, porque luego los hijos las heredan. 

Dentro del módulo, el archivo `index.jsp` es como nuestro template, recordemos que viene del `Java Server Pages`.

Dentro del pom padre, vamos a poder definir dependencias que luego se aplicarán a todos los hijos, por más que son independientes entre sí, garantizando que por ejemplo usen las mismas versiones de todo. Si necesitamos actualizar alguna, lo hacemos únicamente en dicho pom.

Como va a haber dependencias que algunas componentes no van a necesitar y no nos sirve que las hereden, vamos a utilizar lo siguiente:
```xml
<dependencyManagement>
    <dependencies>
        <dependency>
            <groupId>org.springframework</groupId>
            <artifactId>spring-webmvc</artifactId>
            <version>4.2.5.RELEASE</version>
        </dependency>
    </dependencies>
</dependencyManagement>
```

Con esto vamos a poder, por ejemplo, definir una versión de Spring sin obligar a todos los módulos a incluirlo. Cada hijo va a decidir si lo usa o no, agregándolo en sus dependencias (sin versión para tomar la del `dependencyManagement`).

Luego, en el `web.xml` vamos a introducir nuestros servlets de la siguiente manera:
```xml
<?xml version="1.0" encoding="UTF-8"?>
<web-app id="PAW" version="2.4"
    xmlns="http://java.sun.com/xml/ns/j2ee"
    xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
    xsi:schemaLocation="http://java.sun.com/xml/ns/j2ee
    http://java.sun.com/xml/ns/j2ee/web-app_2_4.xsd">
    <display-name>PAW2025 - 1er Cuatri</display-name>

    <servlet>
        <servlet-name>dispatcher</servlet-name>
        <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>
        <load-on-startup>1</load-on-startup>
    </servlet>

    <servlet-mapping>
        <servlet-name>dispatcher</servlet-name>
        <url-pattern>/</url-pattern>
    </servlet-mapping>
</web-app>
```

Por defecto, la Application Container va a ser lazy, es decir va a generar las instancias cuando lleguen los request, lo que tiene sentido si tenemos un montón de servlets. Como en nuestro caso no hace falta, usamos el parámetro load-on-startup.

Al servlet dispatcher, le vamos a agregar un parámetro para que no tome la configuración por default del archivo XML, sino que tome una basada en código. Para esto, agregamos un parámetro de inicialización ya que queremos llamar un **setter**.
```xml
<servlet>
    <servlet-name>dispatcher</servlet-name>
    <servlet-class>org.springframework.web.servlet.DispatcherServlet</servlet-class>

    <init-param>
        <param-name>contextClass</param-name>
        <param-value>org.springframework.web.context.support.AnnotationConfigWebApplicationContext</param-value>
    </init-param>

    <load-on-startup>1</load-on-startup>
</servlet>
```

Además, vamos a definir a nivel global el contexto mediante:
```xml
<context-param>
    <param-name>contextClass</param-name>
    <param-value>org.springframework.web.context.support.AnnotationConfigWebApplicationContext</param-value>
</context-param>
<context-param>
    <param-name>contextConfigLocation</param-name>
    <param-value>ar.edu.itba.paw.webapp.config.WebConfig</param-value>
</context-param>
```
Donde la configuración la vamos a setear nosotros, como podemos ver en el `param-value`. Dentro de `src/main` vamos a definir un nuevo directorio `java` con un nuevo paquete tal como definimos antes. Dentro creamos el archivo `WebConfig.java` donde vamos a armar esta configuración. Antes de probar correrlo, debemos instalar Jetty (ver guía - IntelliJ tiene uno propio). Luego, vemos que si corremos el `web.xml` se muestra el Hello World en el `http://localhost:8080/index.jsp`

Ahora, vamos a generar nuestro primer controller. Generamos un nuevo paquete dentro de la carpeta en `src/main/java` con nuestro `HelloWorldController`. Nosotros no vamos a meternos mucho con servlets, sino que le vamos a hacer saber al front controller qué request tiene que hacernos llegar y a dónde. Esto es bastante declarativo en Spring, como vemos a continuación. 

Sabemos que el controller tiene la tarea de recibir el input del usuario, modificar el estado del modelo y elegir una vista para presentar el output de la operación. En este caso es recibir sólo el request y elegir una vista pues no se debe ejercitar el modelo. Para esto, vamos a usar `ModelAndView`.
```Java
@Controller
public class HelloWorldController {

    public ModelAndView helloWorld() {
        final ModelAndView mav = new ModelAndView("index.jsp");
        mav.addObject("username", "PAW");

        return mav;
    }
}
```

Ahora, debemos especificar a qué request queremos responder en este caso. Para este caso, agregamos lo siguiente generando un mapeo. Podemos agregar más parámetros al mapeo.
```Java
@Controller
public class HelloWorldController {

    @RequestMapping("/")
    public ModelAndView helloWorld() {
        final ModelAndView mav = new ModelAndView("index.jsp");
        mav.addObject("username", "PAW");

        return mav;
    }
}
```

```Java
@EnableWebMvc
@ComponentScan({"ar.edu.itba.paw.webapp.controller"})
@Configuration
public class WebConfig {

}
```
Especificar el paquete le permite ser mucho más eficiente y no configurar cosas de más que capaz no queremos.

Tenemos que reconfigurar la aplicación para que no se pueda. 

Todo lo que está dentro de la carpeta `WEB-INF` es privado, por lo que es un buen lugar para guardar nuestro index. Creamos un directorio `jsp` y movemos el archivo allí. Ahora debemos actualizar nuestro controlador, donde si ponemos dentro del parámetro de `new ModelAndView(“WEB-INF/jsp/index.jsp”)` lo va a encontrar. Para ser más ordenado, podemos crear una carpeta por cada controller dentro del directorio `jsp`, como por ejemplo `helloworld` en nuestro caso, y meter el jsp ahí dentro. 

Como el path `WEB-INF/jsp/helloworld/index.jsp` es muy largo y se hace repetitivo escribirlo muchas veces, Spring nos deja configurar la forma en la que resolvemos un nombre.
```Java
@EnableWebMvc
@ComponentScan({"ar.edu.itba.paw.webapp.controller"})
@Configuration
public class WebConfig {

    @Bean
    public ViewResolver viewResolver() {
        final InternalResourceViewResolver vr = new InternalResourceViewResolver();
        vr.setViewClass(JstlView.class);
        vr.setPrefix("/WEB-INF/jsp/");
        vr.setSuffix(".jsp");
        return vr;
    }
}
```

Spring internamente tiene un motor de inyección de dependencias. Nosotros usualmente programamos mediante composición de objetos, es decir objetos que llaman a otros. La forma más tradicional de usarlos es ir creando nuevas instancias. La alternativa del motor de inyección de dependencias, se separa por un lado la configuración y por otro lado, cuando uno necesita usar esas instancias, se las inyecta o provee automáticamente, sin necesidad de generar builders ni nada. Esto baja la complejidad del uso y tener un lugar centralizado para facilitar el cambio de alguna configuración. Con el `bean` lo que hacemos es reemplazar el default para un `ViewResolver` que se utilizará siempre.

## Modelo de Capas

Nosotros vamos a trabajar en lo que se llama **modelo de capas**, que lo que hace es similar a una cebolla con una serie de layers superpuestos (tantos como yo quiera) con reglas muy estrictas respecto de cómo estas se comunican. Un componente que vive en un layer particular simplemente interactúa con miembros del mismo o de la capa inmediatamente inferior. Esto NO se puede bypassear. 

Las capas van a buscar tener en un extremo al usuario y al otro la base de datos. Todo lo que vamos a construir va a seguir la lógica anterior. La cantidad de capas es relativo al proyecto que estemos desarrollando. Las capas superiores suelen ser más estándar.

La capa superior (llamada **webapp**) debe presentar la interfaz con la que el usuario interactúa, es decir nuestro front-end. Sabe de HTTP, de JSP, de Spring, etc. Es la que recibe los request del usuario y luego los pasa para ejercitar al modelo, pero esto último pertenece a otra capa. NO tiene que tener lógica de aplicación. Mismo podríamos armar una nueva capa y reemplazarla y que siga funcionando, porque no debe contener nada de la lógica. Tener lógica en esta capa se penaliza bastante en las entregas. 

En la capa más baja vamos a tener de **persistencia**, que nos va a permitir abstraernos de la base de datos. No importa cuál es la fuente real de información, puede ser un Postgres o cambiar y ser otra fuente. Tiene sus reglas, como que nadie debiera poder crear una instancia en memoria de usar si no es en la capa de persistencia, ya que tenemos pleno control y garantía de que si existe en runtime en la JVM, es por existe en la BD y tiene exactamente los mismos valores. 

En las capas intermedias vamos a tener el resto de nuestra lógica de negocio propiamente dicha. Allí viven todas las implementaciones para nuestros casos de uso. Vamos a usar una capa dedicada para esto que se llamará **servicios**. Un servicio es una implementación de un Facade (fachada), que es un patrón que consiste en presentar una interfaz sencilla para un problema complejo. Busca abstraer la complejidad. Por ejemplo, presentar un método `register(String email, String password)` y devuelve un `User`. Vemos que es sencillo crear el usuario, pero la lógica por detrás puede ser mucho más compleja. La capa de servicios tiene que seguir este principio para que la capa frontend los consuma sencillamente. 
![[Pasted image 20260817212310.png|center]]

Vamos a agregar un módulo adicional dedicado exclusivamente a contener la representación en nuestra aplicación de los datos que existen en la base de datos. Este módulo se va a llamar **modelo**. Además, vamos a agregar otro que nos va a permitir asegurarnos de que estamos cumpliendo con este modelo de capas. Existe un concepto aplicable a cualquier lenguaje que consiste en intentar armar nuestros diseños de forma tal que ciertos errores lógicos que son fáciles de cometer, se conviertan en errores de compilación. 

Las dependencias entre módulos podrían ser de la siguiente manera:

El problema de esto, es que Maven resuelve las dependencias transitivas pues en tiempo de ejecución necesitamos todos los módulos, pero si tenemos dependencias transitivas también significa que así como puedo usar métodos del modelo, también voy a poder usar de persistencia. Deberíamos hacer que esto sea un error de compilación, sumando un módulo adicional donde vamos a definir interfaces para todos los servicios y persistencia. Esto permite también que la implementación cambie sin impactar sobre los clientes. Entonces, nos quedaría:

A las dependencias entre servicios y persistencia las necesitamos en tiempo de ejecución, pero no en tiempo de compilación. Maven introdujo la idea de que existen scopes separados, y cada uno ocurre en contextos posibles. Lo define en las dependencias mediante un atributo `scope`. Si lo dejamos vacío, por default estamos usando `compile`, que significa que está disponible a la hora de correr test, a la hora de compilar, empaquetar y en runtime. Con `provided`, estamos diciendo que será una dependencia de tiempo de ejecución provista por el entorno de ejecución (`ApplicationContainer` por ejemplo). El valor runtime funciona al revés.

|  **Scope**   | **test** | **compile** | **empaquetar** | **runtime** |
| :----------: | :------: | :---------: | :------------: | :---------: |
|   **test**   |    ✅     |      ❌      |       ❌        |      ❌      |
| **compile**  |    ✅     |      ✅      |       ✅        |      ✅      |
| **provided** |    ✅     |      ✅      |       ❌        |      ✅      |
| **runtime**  |    ❌     |      ❌      |       ✅        |      ✅      |

```Java
        this.userDao = userDao;

    @Override

        return userDao.create(email, password);
    }
}
```

```Java
public class WebConfig extends WebMvcConfigurerAdapter {
    @Bean
    public ViewResolver viewResolver() {
        final InternalResourceViewResolver vr = new InternalResourceViewResolver();
        vr.setViewClass(JstlView.class);
        vr.setPrefix("/WEB-INF/jsp/");
        vr.setSuffix(".jsp");
        return vr;
    }

    @Override
    public void addResourceHandlers(ResourceHandlerRegistry registry) {
        super.addResourceHandlers(registry);
        registry.addResourceHandler("/css/**").addResourceLocations("/css/");
    }
}
```

## Base de Datos

JDBC (Java Data Base Connection) es un estándar de Java que permite conectarse y realizar operaciones con una base de datos. Se usa el paquete `java.sql` donde hay un montón de abstracciones. Esto no nos evita que lo que estamos buscando es una sentencia SQL. En lugar de usar primitivas, vamos a aprovechar las abstracciones de Spring, que van a buscar reducir código redundante (boilerplate code).  Agregamos en el pom padre la dependencia y en el pom de persistence, que es el que lo va a utilizar:
```xml
<dependencies>
    <dependency>
        <groupId>org.springframework</groupId>
        <artifactId>spring-jdbc</artifactId>
        <version>${spring.version}</version>
    </dependency>
</dependencies>
```

Para conectarnos a la base de datos, vamos a usar PostgreSQL, por lo que vamos a agregar el driver al pom padre y nuevamente en el de persistence.
```xml
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <version>${org.postgresql.version}</version>
</dependency>
```

Ahora, vamos a implementar una función de `findById` de la siguiente manera (modificando todo para que ahora tenga un id el usuario y asignándoselo arbitrariamente en el controller por ahora):
```Java
@Repository
public class UserDaoImpl implements UserDao {

    private JdbcTemplate jdbcTemplate;

    @Override
    public User create(final long id, final String email, final String password) {
        return new User(id, email, password);
    }

    @Override
    public User findById(long id) {
        List<User> users = jdbcTemplate.query("SELECT * FROM users WHERE id =" + id, new RowMapper<User>() {
            @Override
            public User mapRow(ResultSet rs, int rowNum) throws SQLException {
                return new User(rs.getLong("id"), rs.getString("email"), rs.getString("password"));
            }
        });

        return users.isEmpty() ? null : users.getFirst();
    }
}
```

`RowMapper` es una interfaz que tiene como única finalidad dar un resultset parado en una posición específica del cursor que retorna la query y convertir dicha row a un objeto. Sabe interpretar los resultados de la query. Por ser una interfaz con un único método, es lo que se conoce como una interfaz funcional, lo que quiere decir que podemos definir una lambda. Entonces, nos queda:
```Java
@Override
public User findById(long id) {
    List<User> users = jdbcTemplate.query("SELECT * FROM users WHERE id =" + id,
        (rs, rowNum) ->
            new User(rs.getLong("id"), rs.getString("email"), rs.getString("password"))
    );

    return users.isEmpty() ? null : users.getFirst();
}
```

Si ahora tuviéramos otro método para buscar por `username`, sería exactamente igual, pero generaríamos una lambda nueva (que no tiene estado - es safe para compartir) para lo mismo. Por lo tanto, podemos definirlo por fuera de las siguiente manera:
```Java
@Repository
public class UserDaoImpl implements UserDao {
    private JdbcTemplate jdbcTemplate;
    private static final RowMapper<User> USER_MAPPER = (rs, rowNum) ->
            new User(rs.getLong("id"), rs.getString("email"), rs.getString("password"));

    @Override
    public User create(final long id, final String email, final String password) {
        return new User(id, email, password);
    }

    @Override
    public User findById(long id) {
        List<User> users = jdbcTemplate.query("SELECT * FROM users WHERE id =" + id, USER_MAPPER);

        return users.isEmpty() ? null : users.getFirst();
    }
}
```

Las queries que escribimos es un error GRAVE haberlas puesto así, porque puede haber una sql injection con cómo se pasa el id. Para sanitizar el parámetro, vamos a utilizar placeholders para que se encargue la base de datos.
```Java
@Override
public User findById(long id) {
    List<User> users = jdbcTemplate.query("SELECT * FROM users WHERE id = ?", new Object[] { id }, USER_MAPPER);

    return users.isEmpty() ? null : users.getFirst();
}
```

Necesitamos inicializar el JDBC template en el momento de la construcción. Necesita siempre un data source. Armamos el constructor:
```Java
@Autowired
public UserDaoImpl(final DataSource dataSource) {
    this.jdbcTemplate = new JdbcTemplate(dataSource);
}
```

Con todo esto que vimos, ahora podemos realizar el registro de forma similar en la base de datos. En la implementación de persistance, vamos a utilizar `SimpleJdbcInsert` para no estar trabajando con las tablas y columnas, y hacerlo más sencillo.
```Java
@Repository
public class UserDaoImpl implements UserDao {

    private JdbcTemplate jdbcTemplate;
    private SimpleJdbcInsert jdbcInsert;

    private static final RowMapper<User> USER_MAPPER = (rs, rowNum) ->
            new User(rs.getLong("id"), rs.getString("email"), rs.getString("password"));

    @Autowired
    public UserDaoImpl(final DataSource dataSource) {
        this.jdbcTemplate = new JdbcTemplate(dataSource);
        this.jdbcInsert = new SimpleJdbcInsert(dataSource)
                .withTableName("users")
                .usingGeneratedKeyColumns("id");
    }

    @Override
    public User create(final String email, final String password) {
        Map<String, Object> params = Map.of("email", email, "password", password);
        final Number key = jdbcInsert.executeAndReturnKey(params);
        return new User(key.longValue(), email, password);
    }
}
```
