## Web

La **web** se basa sobre el protocolo [[02. HTTP|HTTP]], que es un protocolo request-response, que su dinámica es siempre iniciada por el cliente. Es un protocolo stateless, dado que no tiene un estado.
![[Pasted image 20260814190035.png|center|456]]

Antiguamente, con HTTP se accedía a archivos de texto plano únicamente, por esto es tan sencilla la base sobre la que se construye. La implementación de un servidor en este caso es muy sencilla, únicamente se necesita un `while TRUE` que acepte requests del tipo `GET`, y luego parsear el archivo deseado.
```
GET /index.html

/var/www/htdocs/index.html

fread(indexFd, buff...);
fwrite(socketFd, buff...);

sendfile(indexFd, socketFd);
```

Tan ineficiente es esta solución que incluso se agregó una nueva syscall `sendfile()` para hacerlo más eficiente directamente todo en el Kernel.

## Web 2.0

En un momento, la web dejó de ser solamente de lectura y pasó a ser también de escritura, dando así inicio a la llamada web 2.0. Para que esto suceda, ya no se podía tener una lectura directa de un archivo estático, ya que pueden surgir problemas de concurrencia.

El estándar CGI (hoy en día fastCGI), propone mapear en un servidor en vez de la aplicación a un directorio con archivos estáticos, mapear a assets o programas (binarios) dentro del directorio. Se puede escribir lógica arbitraria que genera una respuesta. Los programas por naturaleza y diseño son bastante sencillos, van a leer y escribir en salida estándar. No hay que preocuparse más por sockets.
```
/var/www/htdocs/index.out
```

La implementación es muy sencilla, y ya no se necesita el bucle anterior, sino que se usa `fork` y `exec` redirigiendo entradas y salidas (como vimos en SO). Los `GET`/`POST` tienen la siguiente forma:
```
GET /index.htm HTTP/1.0
clave: valor
payload
```
Donde los campos clave-valor son parte de `header` y `payload` es el contenido (en el caso de un `GET` es vacío).

Estos programas requieren un alto mantenimiento, lo que hace que la gestión y coordinación de páginas elaboradas aumente en complejidad. Esto da nacimiento a los primeros frameworks y herramientas de alto nivel que comienzan a abstraer este tipo de cosas.

## Sesiones HTTP

HTTP, si bien es stateless, permite enviar credenciales en cada request para poder trabajar, por ejemplo, con usuario. No es la forma más sencilla, porque muchas veces el browser no lo tolera muy bien. Por esto, se creó la idea de las sesiones HTTP, que son, según Sotuyo, una inmensa mentira. 

Cuando el servidor nos dice que estamos logueado, en realidad del lado del servidor se genera un identificador (`session id`) que tradicionalmente es una secuencia hexadecimal de cierta longitud lo suficientemente grande y aleatoria para que no sea fácil de adivinar. El servidor guarda el `session id` e información arbitraria en la carpeta `tmp` que luego se borra. Para mantener esta comunicación, se utilizan las cookies, que se setean y envían en cada request por parte del usuario para que el servidor lo pueda identificar, pero sigue siendo en realidad stateless.
```
Set-Cookie: JSESSIONID=xxxx
Cookie: JSESSIONID=xxxx
```
Es más, podríamos mandar un request con una cookie de otra persona y el servidor no tiene manera de validar que no somos la misma.

Esta implementación tiene una limitación, y es que si hay muchos servidores físicos detrás de una misma página, se complica enormemente. Por esto, se introduce un load balancer que distribuye el tráfico a distintos servidores que poseen todos la misma lógica.
![[Pasted image 20260814190428.png|center|351]]

Si todas las request son independientes, no nos interesa en qué servidor caen, pero si introducimos sesiones esto se complica. Surgen dos alternativas:
- La sesión no se guarda en disco, sino que se debe tener en algún medio compartido como por ejemplo una base de datos.
- El load Balancer no hace round robin y debe implementar una lógica como sticky sessions, donde recuerda qué `session id` fue a qué servidor, y manda todos los request posteriores a dicho servidor.

## Surgimiento de Java

En este contexto, entra **Java** en juego. Tenía originalmente la visión de tener código universal, es decir que se ejecute en todos los dispositivos. Con el surgimiento de la web, era una oportunidad para Java de poner a prueba esta visión universalista. 

Java podría tener una serie de dificultades para ejecutar en este contexto, como por ejemplo la performance. El `exec` cuando estoy ejecutando una aplicación en Java implica crear una JVM, cargar a memoria el código de la app y de la **JVM**, compilar **JIT (just in time)** el bytecode y empezar a ejecutar ese nuevo proceso. Es decir, por cada exec se “abre” una nueva JVM y se hace poco eficiente. La JVM, por diseño, está pensada para procesos que duran en el tiempo, y es pionera en muchas cosas que nos permiten por ejemplo tener Chrome hoy en día.

La compilación Just In Time ocurre en 4 niveles con muchos niveles de optimización. Cuando compila y empieza a entender qué caminos es más probable tomar, comienza a optimizar. Las optimizaciones se hacen en base a cada programa. Como estamos tomando el peor caso, no estamos aprovechando todas las ventajas de las JVM y sí todas las desventajas.

Entendiendo estas limitaciones, se buscó hacer Java una alternativa viable en el contexto del emergente mundo web. La solución fue atacar el problema de raíz, evitando el `fork` y `exec`, lo que es difícil porque es como está implementado el server. Lo que hicieron fue construir su propio servidor, donde hay un proceso que corre todo el tiempo escuchando las request del cliente. Como es long live, el costo inicial de start up de la JVM se paga una sola vez, y como ella aprende y optimiza, se benefician todos los request que llegan posteriormente. 

Hacer esto no es trivial, porque se debe escribir un server HTTP en Java. En algún momento, el server debe delegar la ejecución a nuestro programa. Tenemos el problema que si forkeamos, es caro y las optimizaciones se hacen sobre la copia, por lo que necesitamos una sola JVM. Por lo tanto, en vez de `fork` y `exec` se va a utilizar threads para atender varias request en paralelo. Cuando creamos el thread, se va a correr sobre la misma JVM, pero introducimos los problemas que trae trabajar con ellos, como por ejemplo de sincronización.

La decisión de que Java se ejecute multihilo se tomó porque era la única opción viable. Para ser una alternativa, se debe asegurar que se puede construir aplicaciones que pueden correr en un contexto multihilo de manera segura. El problema de sincronización existe principalmente porque existe algo que quiero sincronizar, como por ejemplo un estado, un archivo, etc. que se quiere resguardar. Si no tuviésemos estados compartidos, por definición no deberíamos tener problemas de sincronización. La mejor manera de que una clase sea thread-safe, debe ser inmutable, es decir que no debe guardar un estado.

Cuando trabajemos en el desarrollo de aplicaciones web en Java, NUNCA debemos tener estados compartidos en nuestras clases, porque van a empezar a surgir estos problemas de sincronización que dijimos. Así, lograremos ahorrarnos todos estos problemas y, si bien va a correr en un contexto multihilo, para nosotros va a ser transparente. En la base de datos sí vamos a poder tener estados compartidos. La BD que usaremos es **ACID**, es decir que acepta concurrencia de requests.

## Estandarización

Con este plan de alto nivel de crear un server propio en Java corriendo sobre la JVM, delegando la invocación al código de la aplicación dentro de un thread particular, es necesario estandarizar un montón de cosas. Primero se debe establecer cómo será la comunicación. 
![[Pasted image 20260816161727.png|309]]

Hay dos herramientas para conectar lo estándar (servidor) con la aplicación.
- **Interfaz Conocida**: El servidor necesita saber lo que va a invocar, por lo que nuestra aplicación debe tener un contrato con los métodos existentes y sus tipos de devolución. 
- **Reflection**: Es un conjunto de APIs dentro de la JVM que permiten hacer un tipo de metaprogramación. 

```Java
class<?> c = Class.forName("org.mysql...MysqlDriver");
Object o = (c.newInstance());
```

Con estos dos elementos se hace posible con un mínimo de información provista, obtener en tiempo de ejecución una instancia de los objetos de nuestra aplicación e invocarlos. Se necesita reflection para poder acceder a esa interfaz nueva y conocerla para poder utilizarla.

Para evitar los mapeos, Java en los 90 comienza a utilizar XML, donde se mapea cada path con un **servlet** (interfaz conocida que dijimos antes) en vez de un ejecutable. 
```
Reflection:
/index.html => index.out
/profile.html => profile.out

Servlet:
/index.html => ar.edu.itba.paw.IndexServlet
/profile.html => ar.edu.itba.paw.ProfileServlet
```

Los servlets definen una serie de métodos estándar, que son todos "de la misma pinta", como por ejemplo:
- `void doGet(HttpServletRequest, HttpServletResponse)`
- `void doPost(HttpServletRequest, HttpServletResponse)`
- `void doDelete(HttpServletRequest, HttpServletResponse)`

Los objetos `HttpServletRequest` y `HttpServletResponse` son objetos que poseen acceso a por ejemplo los headers y que pueden escribir la respuesta.

## Aplicaciones en Servidores Java

Con estos bloques mínimos, estamos en condiciones de, usando Java, replicar todo lo que ofrecía CGI en un contexto de una única JVM, multithread, etc. en un servidor que no necesita conocer nuestra lógica particular. Para servir estas aplicaciones, se extiende la misma idea de servir cualquier aplicación. Una aplicación Java se empaqueta en un JAR, que es una sigla para "Java ARchive". El formato JAR no es más que un ZIP, que tiene una estructura particular de directorios. 

Para esto, se introduce un nuevo estándar, WAR (Web ARchive), que es también un ZIP con una estructura de directorios particular. Tiene, por ejemplo, los siguientes directorios:
```
classes/
  ar/edu/itba/paw/.../MyClass.class
libs/
  dependencies.jar
META-INF/
WEB-INF/
  web.xml
```

En el viejo mundo de los servidores HTTP, era posible que bajo un mismo servidor físico y por lo tanto un mismo proceso, se vieran múltiples sitios. Java quería replicar esto mismo, buscando tener múltiples aplicaciones en paralelo. Para diferenciar un request que va a una aplicación u otra, se implementó el web context, que básicamente es el primer segmento del path. De esta forma se puede encontrar ela web app que va a recibir el request.

Se necesitaba una solución mucho más enterprise, y que la elección de Java sea porque realmente el ecosistema aportaba valor. Entonces, dentro del servidor estándar HTTP se empiezan a agregar muchos mecanismos adicionales como por ejemplo mecanismos de sincronización. Todo esto se empaquetó en lo que se conoció como la Java Enterprise Edition (JavaEE). 

Las aplicaciones que necesitaban todos estos servicios adicionales eran muy pocas, por lo que empiezan a surgir implementaciones mucho más simples open source sin todas estas features. El que ofrece todos estos servicios se conoció como Application Server, y se diferenció del Application Container que contiene únicamente lo necesario y son los que más se usan hoy en día.

## Frameworks

El ecosistema de desarrollo de Java se puso muy engorroso con todas estas versiones. Toda esta complejidad adicional resultó ser más de marketing para vender recursos avanzados. En la época de los 2000 surge una "contramovida" que reclamaba POJO (Plain Old Java Object), es decir que buscaban escribir código en función del caso de uso, no de la versión de Java, del container, etc. Con esto surge también el concepto de convention over configuration, que establece que si estamos usando el estándar, no deberíamos configurar nada, y si la configuramos, es porque queremos hacer "algo más". 

Los primeros frameworks que surgen, fueron pioneros en lograr estas estandarizaciones. Uno podía escribir sus aplicaciones enteras usando Java Standard Edition. Todo lo que tenía que ver con el container estaba provisto por el framework, permitiendo al programador preocuparse únicamente en el código de la aplicación. 

Estos frameworks lograban este desentendimiento introduciendo algunos patrones adicionales. En primer lugar, se adoptó un patrón de diseño conocido como **MVC (Model View Controller)**, y hace referencia a los tres componentes fundamentales que forman parte de esta arquitectura. Es un estilo de patrón habla de una forma de modelar la aplicación entera, no una clase. Tiene un nivel de abstracción mucho más grande que los patrones que vimos en Inge. Especifica comportamientos de toda nuestra aplicación.

Todos los request del usuario llegan al **controller**, que recibe el input, lo valida y le transmite al modelo lo que el usuario quiere hacer (lo ejercita). El **modelo** se refiere a la lógica de negocio con todas las reglas establecidas. El controller le indica lo que el usuario quiere hacer con todo lo que eso implica, para que luego lo transforme en la salida necesaria. Finalmente el **view** se encarga de la parte visual de la respuesta, como por ejemplo cómo se quiere ver. Se le da acceso de sólo lectura al modelo, porque sólo quiere los datos. 
![[Pasted image 20260816162525.png|center|365]]

MVC busca con estos tres componentes generar una separación de responsabilidades bien definidas. Esto quiere decir que se tienen que por ejemplo cambiar las reglas de negocios sin que las otras componentes se vean afectadas. Por esto es que decimos que es un estilo de muy alto nivel.

El uso masivo de MVC en aplicaciones web se dio por convención. En el caso de Java, el Servlet pasó a ejercer la función del controller. Para que el usuario pudiera utilizar también el patrón MVC y que no "choque" el servlet con el controller del usuario, se introdujo uno nuevo denominado Front Controller que actúa de la siguiente manera:

El Front Controller al ser el que interactúa con el servidor web por lo que debe implementar la interfaz Servlet. El controller del usuario ahora puede contener un contrato distinto y hace más fácil la configuración.

## Mailing

Vamos a usar una librería, la recomendada por la cátedra es **Thymeleaf** para templates y javax mail. El formato es tener un tipo header con la web, un body con la razón del mail y un call to action con redirección a la página, y un footer (opcional) con información de la página. Los mails son requisito obligatorio para la materia. Los mails tienen que contener información que el usuario no conozca. 

Los mails tienen que estar internacionalizados, es recomendable probar con la página en distintos idiomas para verificar que no haya errores. Un error conceptual clave es desde dónde se envían los mails. Los mails se envían SIEMPRE desde la capa de servicios, no desde webapp o alguna otra capa. Los mails deben ser además no bloqueantes, es decir que el mail no bloquee el uso de la aplicación mediante el `@async` (hay que habilitarlo en la configuración - webconfig).

## Imágenes

El TP pide tener manejo de imágenes, para lo que vamos a separar las entidades y las imágenes en dos tablas, una con `id`, `name` y `image.id`, y otra con `id` y `content`, donde `image.id` será clave foránea. No usar Base64 para imágenes, sino de manera plana en esta tabla que dijimos. Nunca hacer `join` de la tabla de imáges porque es lo mismo que haberlo puesto en una sola tabla.
