## Introducción

**REST** es una palabra que está muy mal usada en el contexto de desarrollo web, ya que se usa en un montón de casos que no cumplen con las normas. La sigla significa **Representational State Transfer**, ya que la aplicación ya no transmite la presentación, sino únicamente la información solicitada.

Ahora, es una responsabilidad del cliente (el que consume la API), cómo quiere mostrar la información que pidió. Nuestra SPA va a pasar a encargarse de todo esto. La información vendrá en un formato libre de representación, como por ejemplo un JSON. Sí va a tener una estructura, pero no un modelo de representación.

REST está fuertemente apalancada sobre los principios de HTTP, lo que quiere decir que va a hacer un uso extensivo de este protocolo, abrazando conceptos que son naturales allí. Por ejemplo, la **API REST** es stateless, al igual que el protocolo. Como no hay estados, no va a haber sesiones. Además, va a abrazar la idea de la negociación de contenido, lidiando con problemas de las APIs con los headers. 

Al igual que con los headers, Rest hace un uso muy semántico de los "status codes". Hasta ahora no usamos muchos más que los tradicionales `404`, `402`, etc., cosa que va a cambiar.

REST es además completamente agnóstico del dominio. Esto quiere decir que no se necesita desarrollar un cliente específico que la consuma, ya que son genéricos. Cambia el payload que viaja en cada request. Los endpoints y la navegación de la API deben ser genéricos.

## Principios de Diseño

Hay dos principios de diseño importantes además de los mencionados, que son:
- Las entidades están hipervinculadas: La manera de navegar el grifo de objetos que existen en la aplicación va a ser por medio de hipervínculos.
- Todo tiene una URN: Recordemos que describe un recurso en forma universal. Es fundamental para la parte de hipervínculos.

Tomemos el ejemplo de `www.myapp.com/me`, que debería devolvernos nuestro usuario. Esto es un problema que rompe con el último principio que vimos, porque me no es una URN. Vemos que si hay un “depende”, entonces estamos rompiendo con los conceptos de API REST.

Nosotros vamos a querer darle una estructura bastante predecible a nuestra API. Vamos a querer que las distintas entidades y objetos estén representados por una URN y un path. Una buena aproximación es definir al comienzo del path el nombre de las entidades fuertes, como por ejemplo `/users`, `/posts/`, `/issues`, etc. Cada una de estas colecciones vive bajo uno de estos paths. Podemos tener entonces `/users/{id}` para buscarlo de manera individual. 

En caso de que haya entidades débiles, las vamos querer tener como entidades hijas en la relación, como por ejemplo `/users/{id}/addresses`. De esta forma, el path define la estructura jerárquica que se mapea directamente a la estructura jerárquica de las entidades de nuestro dominio. Los recursos que definimos se mapean uno a uno, es bastante directo.

## Operaciones Sobre Recursos

Como REST se para sobre HTTP, existen dos cosas fundamentales:
- Recursos, como ya vimos. Son siempre sustantivos.
- Operaciones sobre los recursos. Se hace por medio de los métodos (o verbos) HTTP.

Vemos entonces que en los path no tenemos acciones, sino que estas vienen marcadas por los verbos HTTP. Si mi diseño de la API contiene algo como `/users/{id}/validate`, ya es un indicio de que no es REST, porque validate no es un recurso. 

Entonces:
- `GET /users`: Se está intentando que te traiga todos los usuarios
- `POST /users`: Se está creando un nuevo usuario.
- `DELETE /users`: Se está borrando la lista entera. 
- `PUT /users`: Se está reemplazando la lista completa. 

Vemos que la semántica está bien definida para las acciones que realiza cada verbo. Como tienen una semántica estándar, los status codes que se reciben son también bastante estándar. 

Para `GET`:
- `200 OK`.
- `204 No Content`. El pedido es correcto y lo que pedimos existe, pero está vacío.
- `404 Not Found`.
- `403 Forbidden`. Se sabe quién es el solicitante, pero no tiene permisos.
- `401 Authorization Required`. No se sabe quién es el solicitante. 

Para `POST`:
- `201 Created + Location: /users/{id}`. No lo debiera devolver un 201 OK, porque el POST se hace a /users.
- `404 Not Found`.
- `405 Method Not Allowed`. La URN existe pero el método no se puede usar.
- `403 Forbidden`. Se sabe quién es el solicitante, pero no tiene permisos.
- `401 Authorization Required`. No se sabe quién es el solicitante. 

Para `PUT` y `DELETE` (muy parecidas a `GET`):
- `200 OK` (`PUT`).
- `204 No Content` (`DELETE`).
- `405 Method Not Allowed`. Por ejemplo un `DELETE` a `/users`.
- `404 Not Found`.
- `403 Forbidden`.
- `401 Authorization Required`.

Tomemos otro caso. Para el `GET` a `/users`, lo mejor sería que el resultado venga paginado, pero la información sobre esto no debería venir en la respuesta, ya que debe ser lo más genérica posible. El retorno que se espera es una lista de usuarios, no algo del estilo:
```json
{
	pagination: {
		Next: “...”,
		Prev: “...”,
		…
	},
	Data: [
		{ user1 },
		{ user2 },
		…
	]
}
```

Se debería obtener en su lugar algo de la forma:
```json
Data: [
	{ user1 },
	{ user2 },
	…
]
```
Y todo el resto debería llegar por medio de los headers. El payload es solamente la data que se ve ahí, y el resto en el header estándar Link. Los nombres que se usan en el campo rel son también estándar

Headers:
```
Link: URN, rel="first"
…, rel="prev"
…, rel="next"
…, rel="last"
```

## Hipervínculos

En los objetos vamos también a querer tener entidades hipervinculadas, para lo que vamos a tener cosas del estilo: 
```http
GET /users/{id}
```

```json
{
	"Username": "PAW"	
	…,
	"links": {
	"created_issues": "/issues?reportedBy=xxx",
	"self": "/users/xxx"
}
}
```

Vemos que no embebemos los issues, sino que los hipervinculamos. En la respuesta anterior, no necesitamos ni saber qué significa el id de `reportedBy`, o si tiene que matchear con el anterior, pasa a ser un detalle de implementación. Notemos que podemos hacer búsquedas usando los query params.  

Si embebiéramos entidades, estaríamos yendo en contra de los lineamientos de API REST. Tomemos el siguiente caso:
```http
GET /users/{id}
```

```json
{
  "username": "PAW",
  ...,
  "addresses": [
    {
      "street": ...,
      "postal_code": ...
    }
  ]
}
```

Surge un problema, que las direcciones ya no viven en un único lugar con una única URN que permite accederlas, sino que hay múltiples formas de interactuar con ellas. Nosotros podemos hacer un `POST` a `/users/{id}/addresses` y un `DELETE` a `/users/{id}/addresses` borrando todas, bajo el esquema REST. Si además hacemos:
```http
PUT /users/{id}
```

```json
{
  "username": "PAW",
  ...,
  "addresses": null
}
```

Vemos que se borran las addresses de un usuario, lo que es exactamente lo mismo que con el `DELETE`, es decir que estamos haciendo lo mismo de dos maneras diferentes, lo que está MAL. Además, esto dificulta el control de acceso a los recursos, como por ejemplo modificar algunos atributos del usuario pero NO la dirección.

## Negociación de Contenido

Nuestros recursos en el caso anterior son por ejemplo `/users` y `/issues`, NO `/v1/users` como hacen muchas APIs que se consideran REST pero no lo son. Los usuarios existen independientemente de cuántas versiones haya. Manipular un usuario sobre la primera versión y sobre la quinta debería ser lo mismo. No es URN si tenemos dos maneras de referenciar a la misma entidad. 

El otro problema del versionado es que si se hace un cambio a users, o existe una v2 pero `/issues` tiene la v1 o hay que migrar todo a la v2. Esto genera inconsistencias en las operaciones. El registro que se levanta de la base de datos es el mismo, lo que cambia es cómo se presenta la información. 

Como el problema es de representación, tiene sentido solucionarlo con la forma en la que HTTP resuelve representación y formato, que es a través de la negociación de contenido. Esto se hace por medio de los headers accept. 

Una buena práctica es asociarles a estos recursos un MIME type propio. El estándar para definir uno custom es `application/vnd.userlist.v1+json` donde `vnd` se refiere a vendor, que explicita que es particular de quien provee la API. Otras opciones son:
- `application/vnd.userlist.v1+xml`
- `application/vnd.userlist.v2+json`

Ahora, es el cliente el que sabe el versionado para realizar las operaciones. 

Estos MIME types funcionan en ambas direcciones, porque el usuario los puede usar también para informarle a la API por ejemplo el formato en el que se está enviando el nuevo usuario. Esto se usa, como dijimos, con los headers `Accept` en un `GET` y `Content-Type` en un `POST`.

Dijimos que un cliente REST solamente conoce HTTP y los verbos, y navega hipervínculos. Entonces, es completamente agnóstico de la implementación de la API. Asume que conozco un primer recurso, y para esto se define un estándar donde en el `GET /`, se puede dar un descriptor de la aplicación con todas las entidades que contiene de la siguiente forma:
```http
GET /
```

```json
{
  "users": "/users{?page}...",
  "posts": "/posts{?page}{?author}",
  ...
}
```

Vemos que se incluyen los parámetros opcionales que se pueden usar. No es obligatorio para el final, pero es bienvenido para una API completamente REST.

## Autenticación

Dijimos que ya no van a haber más sesiones ni cookies, porque vamos a usar los tokens **JWT (JSON Web Token)** en el header `Authorization` de cada request, haciendo que sea autocontenido, lo que quiere decir que tiene toda la información para saber de quién vino y su validez.

Sabemos que no podemos ejecutar un verbo a `/login`, porque además de ser un verbo, no es una entidad de nuestro dominio. Entonces, no debería existir nunca, se usa un `POST` como vimos. Entonces la autenticación va a ser a través de metadata, al igual que en HTTP.
```http
Authorization: Basic base64(user:pass)
```

Si el request es válido, debe enviarse en un header el token JWT. 
```http
Paw-auth-token: …
Paw-refresh-token: …
```
De ahora en adelante, se puede tomar ese token en vez de mandar el Authorization:
```http
Authorization: Bearer {token}
```

Esto se puede hacer contra cualquier endpoint, no existe uno específico.
