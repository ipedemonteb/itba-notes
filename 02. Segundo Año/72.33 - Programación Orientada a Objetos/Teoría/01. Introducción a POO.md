## Tipo Abstracto de Datos (TAD)

Recordemos las ventajas del [[15. Tipo Abstracto de Datos#Definición|Tipo Abstracto de Datos (TAD)]], que nos servía principalmente para ocultar información al usuario:
- **Hiding (Ocultamiento de información):** Permite lograr alta cohesión (los elementos y operaciones de un módulo permanecen juntos) y bajo acoplamiento (el cual mide el grado de dependencia o relación entre distintos módulos).
- **Packaging (Encapsulamiento):** Empaquetamiento de datos y funciones en un módulo.
- **Contrato:** La especificación formal de la interfaz definida en el archivo de cabecera (`.h`).

Si queríamos implementar un `listADT`, contábamos con una serie de funciones (`newList`, `add`, `remove`, `freeList`, `toBegin`, `hasNext`, `next`). Lo mismo sucedía al diseñar un `queueADT` (`newQueue`, `enQueue`, `deQueue`, `freeQueue`, `toBegin`, `hasNext`, `next`).

Sin embargo, el manejo de TADs en C presenta ciertas limitaciones. Por ejemplo, si en un mismo programa queremos utilizar simultáneamente dos TADs distintos (como `listADT` y `queueADT`), no podemos tener funciones públicas declaradas con el mismo nombre en ambos `.h`. Surge un conflicto de nombres al intentar compilar o enlazar si ambos definen `hasNext`, ya que C no posee espacios de nombres (_namespaces_) ni sobrecarga de funciones. En el paradigma de la Programación Orientada a Objetos (POO), este problema queda resuelto mediante el **polimorfismo**.

Otro problema aparece cuando necesitamos, por ejemplo, una función que exporte elementos a un archivo `.csv`. En C vamos a necesitar escribir una función específica para procesar los elementos de una lista y otra función distinta para los de una cola, a pesar de que la lógica de exportación sea exactamente la misma. El paradigma procedural de C no nos permite definir una sola función que opere genéricamente sobre ambas estructuras. En POO, esta duplicación se soluciona mediante la **herencia** (y el uso de interfaces o clases base comunes).

## Objetos y Clases

Supongamos que queremos modelar una lámpara inteligente. En C, primero tendríamos que armar la estructura de la siguiente manera:
```c
typedef struct lamp {
    char isOn;
    char * name;
    // ...
} TLamp;
````

Si ahora queremos usarla en nuestro programa:
```c
TLamp cocina;
cocina.isOn = 1;
```

Si quisiéramos encender varias lámparas mediante una función, tendríamos que escribir:
```c
void turnOn(TLamp * lamp) {
    lamp->isOn = 1;
}
```

Este enfoque es totalmente imperativo o procedural, ya que la función recibe la estructura como parámetro, accede a su contenido y modifica su estado. En cambio, en el paradigma de la Programación Orientada a Objetos (POO), modelamos entidades como **objetos** a los cuales les enviamos mensajes para que ellos mismos realicen sus cambios internos. 

Por ejemplo, le enviamos el mensaje "encendete" a la instancia para que modifique su estado interno. Sería conceptualmente equivalente a invocar una función ligada a la propia estructura:
```c
TLamp cocina;
cocina.turnOn(); // Recordar que esta sintaxis NO existe nativamente en C
```

Una clase es el molde o plantilla que contiene la definición de los campos (atributos) y el código asociado (métodos) de los objetos de ese tipo. En este paradigma conservamos todas las ventajas del TAD y le sumamos pilares como la herencia y el polimorfismo.

Gráficamente podemos definir la clase y su comportamiento de la siguiente forma:
```Java
class Lamp {
    // Campo / Atributo
    char isOn;

    // Comportamiento / Método
    void turnOn() {
        isOn = 1;
    }
}
```

Y para instanciar y utilizar un objeto de esta clase:
```Java
Lamp dorm = new Lamp();
dorm.turnOn();
```

>[!TIP] Definición de Clase
>Una **clase** es el modelo o molde a partir del cual se instancian objetos, definiendo las características y el comportamiento de los objetos de su tipo.

Para modelar clases gráficamente utilizaremos el lenguaje de modelado UML:![[Pasted image 20260731120629.png|420]]
Cada caja en UML representa una clase con su nombre, sus campos y sus métodos. El método `get` sirve para consultar el estado interno del objeto desde afuera, garantizando el principio de ocultamiento (encapsulamiento). La idea es evitar el acceso directo a campos como `isOn`, definiéndolos como privados (`private`).

El código equivalente en Java quedaría desarrollado de la siguiente manera:
```Java
public class Date {
    private int year;
    private int month;
    private int day;

    public Date(int y, int m, int d) {
        year = y;
        month = m;
        day = d;
    }

    public int getYear() {
        return year;
    }

    public int getMonth() {
        return month;
    }

    public int getDay() {
        return day;
    }
}
```

Al declarar el constructor `Date` como público (`public`), permitimos que pueda ser invocado al instanciar un nuevo objeto mediante el operador `new`:
```Java
Date d1 = new Date(2023, 2, 1);
```

>[!INFO] Gestión de Memoria en Java
>En lenguajes como Java no es necesario gestionar la memoria manualmente: el entorno se encarga de la liberación de memoria mediante el recolector de basura (_Garbage Collector_), por lo que no debemos usar `calloc()`, `realloc()` ni `free()`.

Dentro del constructor `Date(int y, int m, int d)`, podríamos nombrar los parámetros con el mismo nombre que los campos (`year`, `month`, `day`) para darles mayor claridad. Sin embargo, esto genera una ambigüedad entre las variables locales recibidas como parámetro y los campos de la clase. Para resolver la superposición de nombres (_shadowing_), utilizamos la palabra reservada `this`:
```Java
public class Date {
    private int year;
    private int month;
    private int day;

    public Date(int year, int month, int day) {
        this.year = year;
        this.month = month;
        this.day = day;
    }

    public int getYear() {
        return year;
    }

    public int getMonth() {
        return month;
    }

    public int getDay() {
        return day;
    }
}
```

Usamos `this.year` para hacer referencia de forma explícita al atributo privado de la instancia (`private int year`), eliminando así cualquier ambigüedad con el parámetro recibido.

## Instancias

Una instancia es una ocurrencia concreta de una determinada clase. Si declaramos dos variables de referencia y asignamos una a la otra:
```Java
Date d1 = new Date(2020, 6, 20);
Date d2 = d1;
```

En este caso, `d1` y `d2` son dos variables distintas en la pila (stack), pero ambas referencian a una única instancia en la memoria dinámica (heap). Ambas apuntan al mismo objeto, por lo que si modificamos la instancia mediante `d2`, ese cambio se verá reflejado de forma inmediata al consultar `d1`. Si quisiéramos obtener una copia independiente del objeto, tendríamos que invocar nuevamente al constructor pasándole los mismos valores como parámetros para reservar un espacio de memoria distinto.

Las **variables de instancia** son variables que se relacionan con una única instancia de una clase, y equivalen a lo que en C conocíamos como campos de una estructura. Cada objeto en memoria conserva su propio estado y sus propios valores para estas variables:
```Java
Date d1 = new Date(2020, 6, 20);
Date d2 = new Date(2020, 5, 25);
```

En este ejemplo, la variable de instancia `year` de `d1` tiene el mismo valor que la variable de instancia `year` de `d2`, mientras que la variable de instancia `month` de `d1` vale `6` y la de `d2` vale `5`.

Por otro lado, las **variables de clase** (que en Java se declaran mediante la palabra reservada `static`) son compartidas por todos los objetos de esa misma clase. Un ejemplo típico podría ser el formato global de la fecha. Todos los objetos de la clase comparten un único valor almacenado para esa variable. No es necesario que exista un objeto instanciado para que la variable exista y pueda ser utilizada, ya que pertenece a la clase y se accede a ella directamente a través de su nombre:
```Java
String s = Date.format;
```
![[Pasted image 20260731120859.png|259]]
En el estándar del diagrama UML, cuando el nombre de un atributo o método aparece subrayado (como ocurre con `format` en la clase `Date`), significa que representa una variable o método de clase (estático).

## Herencia

La **herencia** consiste en definir una nueva clase en base a una clase existente. La subclase o clase hija hereda los atributos y métodos de la clase padre o superclase. Por ejemplo, teniendo la clase `Date`, podemos crear la clase `DateTime` agregando los atributos y comportamientos correspondientes a las horas, minutos y segundos. La herencia nos permite tanto agregar nuevo comportamiento como modificar el existente. En Java, todas las clases heredan implícitamente de la clase `Object` cuando no se especifica explícitamente otra clase padre.

Respecto a la **herencia múltiple**, lenguajes como Java o Ruby no permiten que una clase herede directamente de múltiples clases padre. Sin embargo, proveen otros mecanismos (como las interfaces) para simular este comportamiento. 

Para definir la herencia en Java utilizamos la palabra reservada `extends`:
```Java
public class DateTime extends Date {
    private int hour;
    private int minute;
    private int second;

    public DateTime(int year, int month, int day, int hour, int minute, int second) {
        super(year, month, day);
        this.hour = hour;
        this.minute = minute;
        this.second = second;
    }
}
```

Al escribir el constructor de la subclase, la llamada al constructor de la superclase mediante `super(...)` debe ser estrictamente la primera línea de código del cuerpo del constructor. De lo contrario, el código no compilará, ya que el estado del objeto padre debe inicializarse antes de asignar los atributos propios de la subclase. Esto evita la duplicación de código y respeta el encapsulamiento de los campos privados de la clase base.

Una vez declarada la subclase, podemos instanciarla asignándola a una variable de su propio tipo o de la superclase:
```c
DateTime dt = new DateTime(2023, 8, 5, 19, 30, 35);
Date d = dt;
```

Cuando guardamos una instancia de `DateTime` en una variable de tipo `Date`, el compilador limita las operaciones visibles a las definidas en la clase `Date` (su tipo estático). Intentar invocar un método propio de la subclase como `d.getMinutes()` provocará un error de compilación. Para forzar la llamada a un método específico de la subclase sería necesario realizar un casteo explícito como `((DateTime) d).getMinutes()`, aunque esta práctica suele considerarse un mal diseño.

Cuando una subclase redefine un método heredado de su superclase, se produce una sobreescritura de métodos (_method overriding_):
```Java
public class Date {
    public String getName() {
        return "soy una fecha";
    }
}

public class DateTime extends Date {
    public String getName() {
        return "soy una fecha y hora";
    }
}
```

Si ejecutamos la llamada a través de la subclase:
```Java
DateTime dt = new DateTime(2023, 7, 5, 19, 30, 35);
dt.getName();
```

El método devolverá el texto "soy una fecha y hora". Java busca la implementación del método desde la clase hija hacia arriba en la jerarquía. Si `getName()` no estuviera definido en `DateTime`, continuaría la búsqueda en la clase `Date`.

Si en cambio ejecutamos la llamada asignando el objeto a la superclase:
```Java
Date d = dt;
d.getName();
```

La llamada devolverá nuevamente "soy una fecha y hora". En Java el comportamiento de los métodos polimórficos depende del tipo real del objeto instanciado en tiempo de ejecución (tipo dinámico), y no del tipo de la variable de referencia (tipo estático).

Por este motivo, no es posible asignar una instancia de una clase padre a una variable declarada con el tipo de la subclase:
```Java
DateTime dt2 = new Date(2020, 1, 2); // Error de compilación
```

Esta asignación no es válida porque al instanciar `Date` solo se reserva memoria para sus propios atributos, omitiendo los atributos requeridos por `DateTime`. Un objeto de una subclase puede guardarse en una referencia de la superclase, pero la relación inversa no es válida.

Las asignaciones permitidas entre variables de tipo `Date` (`d1`) y `DateTime` (`d2`) son:
- `d1 = new DateTime(...);`
- `d1 = new Date(...);`
- `d1 = d2;`

Mientras que resultan en error de compilación las siguientes asignaciones:
- `d2 = new Date(...);`
- `d2 = d1;`

## Polimorfismo

El término **polimorfismo** proviene del griego y significa "que posee varias formas diferentes". En este paradigma se destacan principalmente tres tipos:
- **De sobrecarga:** Métodos con el mismo nombre que están definidos en clases distintas sin relación de herencia entre sí (por ejemplo, `Date#print()` y `Appointment#print()`).
- **Paramétrico (Sobrecarga de métodos / Overloading):** Métodos con el mismo nombre dentro de una misma clase, pero con distinta cantidad o tipo de parámetros en su firma.
- **De redefinición (Sobreescritura / Overriding):** Una clase hija reimplementa o sobreescribe un método heredado de la clase padre.

Para evitar la duplicación de código en el manejo de constructores, se puede hacer que un constructor llame a otro dentro de la misma clase mediante delegación. Esto se logra utilizando la sintaxis `this(...)`:
```Java
public class Date {
    private int year;
    private int month;
    private int day;

    public Date(int y, int m, int d) {
        this.year = y;
        this.month = m;
        this.day = d;
    }

    public Date(int y, int m) {
        this(y, m, 1);
    }
}
```

Al invocar `this(y, m, 1)`, el segundo constructor delega la inicialización al primer constructor pasando un valor por defecto para el día. Al igual que ocurre con `super(...)`, la llamada delegada mediante `this(...)` debe ser estrictamente la primera sentencia dentro del cuerpo del constructor.

Para que el compilador pueda diferenciar entre múltiples constructores o métodos sobrecargados dentro de una misma clase y evitar conflictos de ambigüedad, la firma de cada método debe variar necesariamente en la cantidad de parámetros o en sus tipos de datos.![[Pasted image 20260731130427.png|265]]

## Métodos y Mensajes

Un **mensaje** es enviado por un objeto para invocar un comportamiento determinado. Un **método** se implementa dentro de una clase y define cómo debe actuar el objeto al recibir dicho mensaje.

Los objetos interactúan entre sí enviándose mensajes. Tras la recepción de un mensaje, el objeto ejecuta una acción, la cual puede consistir en enviar otros mensajes, modificar su estado interno o llevar a cabo cualquier otra tarea que se le requiera. Conceptualmente, "enviar un mensaje" es invocar un método de instancia.

Los métodos de clase (declarados con la palabra clave `static` en Java) pueden ser invocados sin que exista una instancia de la clase. Resultan útiles para la lectura y escritura de variables de clase o para realizar operaciones generales:
```Java
public class Date {
    private static String format;
    private int year, month, day;

    public static String getFormat() {
        return format;
    }

    public static Date today() {
        return ...;
    }
}
```

Por su parte, los métodos de instancia son invocados sobre una instancia específica. Pueden alterar el estado interno de esa instancia o retornar un valor en función de dicho estado:![[Pasted image 20260731130710.png|452]]
En las representaciones UML, las distintas visibilidades se indican gráficamente (por ejemplo, verde o `+` para miembros públicos, rojo o `-` para privados y amarillo o `#` para protegidos).

Dadas las siguientes firmas de métodos, se busca determinar si corresponden a métodos de instancia o de clase, considerando:

>[!TIP] Regla de Diseño
>Siempre que un método pueda implementarse como de instancia, conviene hacerlo así para minimizar la cantidad de parámetros explícitos.

Firmas a analizar:
1. `int diffDays(Date fromDate, Date toDate)`
2. `int compare(Date toDate)`
3. `int compare(Date fromDate, Date toDate)`
4. `boolean isValid(int year, int month, int day)`
5. `boolean changeYear(Date date, int newYear)`
6. `String toString()`
7. `int weekOfYear(Date date)`

**1. `int diffDays(Date fromDate, Date toDate)`**
- _Como método de clase:_
    ```Java
    public static int diffDays(Date from, Date to) {
        return to.getDays() - from.getDays();
    }
    // Invocación: Date.diffDays(d1, d2);
    ```
- _Como método de instancia:_
    ```Java
    public int diffDays(Date to) {
        return to.getDays() - this.getDays();
    }
    // Invocación: d1.diffDays(d2);
    ```
Por como está redactado en la consigna, la firma original corresponde a un método de clase, pero es mejor refactorizarlo a método de instancia reduciendo un parámetro.

**2. `int compare(Date toDate)`**

Por su firma es un método de instancia, ya que recibe solo una fecha y la compara contra el objeto actual (`this`). Se mantiene así.

**3. `int compare(Date fromDate, Date toDate)`**

Está planteado como método de clase al recibir ambas fechas por parámetro. Conviene cambiarlo a método de instancia como el caso anterior.

**4. `boolean isValid(int year, int month, int day)`**

Es de instancia o método auxiliar de validación. Es correcto mantenerlo así, siendo muy útil para invocarse dentro del propio constructor.

**5. `boolean changeYear(Date date, int newYear)`**

Está planteado como método de clase al recibir la instancia de la fecha por parámetro. Conviene cambiarlo a método de instancia (`changeYear(int newYear)`) para que modifique directamente su propia fecha.

**6. `String toString()`**

Es un método de instancia y es correcto que se mantenga así para devolver la representación en texto del objeto receptor.

**7. `int weekOfYear(Date date)`**

Al recibir la fecha explícitamente como parámetro está expresado de forma redundante si se busca un método de instancia; se debe refactorizar a método de instancia sin parámetros (`weekOfYear()`) para calcular la semana en base a su propio estado.

Consideremos la siguiente implementación de una calculadora:
```Java
public class Calculator {
    public double eval(char op, double n1, double n2) {
        switch (op) {
            case '+': return n1 + n2;
            case '-': return n1 - n2;
            case '*': return n1 * n2;
            case '/': return n1 / n2;
        }
        return 0; // ERROR
    }
}
```

Tal como está escrito, el método `eval` es de instancia (no utiliza el modificador `static`), por lo que obliga a instanciar la clase para poder utilizarlo:
```Java
Calculator cal = new Calculator();
System.out.println(cal.eval('+', 1.5, 2.3));
```

Este diseño es inadecuado porque el método no requiere ni utiliza ningún estado interno de la clase `Calculator`. Debería ser un método de clase (`public static double eval(...)`).

Mantenerlo como método de instancia solo tendría sentido si la calculadora tuviera un estado interno que afecte la evaluación; por ejemplo, si creáramos instancias separadas para operar en un modo específico (una calculadora configurada en radianes y otra en grados).
