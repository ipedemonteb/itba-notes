## Definición de Calidad

La **calidad** tiene distintas definiciones:
- Diccionario: Propiedad o conjunto de propiedades inherentes a algo que permiten juzgar su valor.
- Deming: Conformidad con requisitos y confiabilidad en el funcionamiento.
- ISO 9001: Grado en el que un conjunto de características inherentes cumple con los requisitos.

Entonces, podemos definir la calidad como la suma de todos aquellos aspectos o características de un producto o servicio que influyen en su capacidad para satisfacer las necesidades, explícitas o implícitas. Es el grado con el cual el cliente o usuario percibe que el software satisface sus expectativas.

Es importante tener en cuenta que:
- No es absoluta, pues no podemos pensar que existe un producto que cumple con todos los aspectos definidos.
- Está sujeta a restricciones
- Trata de compromisos aceptables
- Es multidimensional
- Los criterios de calidad no son independientes

## Calidad de Software

La calidad no es una fase que simplemente se agrega a nuestro proyecto, sino que se diseña, se verifica y se monitorea. Es decir, se gestiona. 

Dentro del contexto del software, debemos contemplar:
- **Conformidad**: El software cumple requisitos explícitos: funcionales, no funcionales, regulatorios y contractuales.
- **Adecuación al uso**: El usuario puede resolver su problema real con niveles aceptables de satisfacción, eficiencia y aprendizaje.
- **Riesgo controlado**: Los defectos residuales, vulnerabilidades y degradaciones quedan dentro de umbrales aceptados.

>[!INFO] Puntos de Vista
>Debemos comprender que se tienen distintos puntos de vista, y no es lo mismo lo que es calidad para el desarrollador que para el cliente o usuario.

Las iniciativas en mejora de la calidad se centran en procesos. Cumplir un modelo de procesos asegura la estandarización de las actividades, la uniformidad en la salida de los procesos y en consecuencia la calidad de los productos. Aquello que no se mide, no se puede mejorar.

## Actividades

La **Gestión de Calidad** especifica cómo integrar las diferentes tareas en un Modelo de Proceso de Desarrollo Software que sigue la organización o el proyecto. Define un plan que debe identificar los diferentes criterios de calidad que se consideran para cada fase del desarrollo, relativos al producto y al proceso, así como los métodos y recursos que se utilizarán. En síntesis, define política, objetivos, estándares, responsabilidades, métricas y umbrales de aceptación.

Se basa el sistema de gestión de calidad en un Modelo de Proceso o de Calidad reconocido, que ayude en la selección de propiedades y métricas de calidad a utilizar. La Calidad se gestiona a través de “Sistemas de Calidad” que establecen:
- El tipo y número de actividades de calidad que es necesario adoptar en un proyecto.
- Las diferentes estrategias, actividades y herramientas de calidad que se deben utilizar.
- La forma en que deben distribuirse las tareas y responsabilidades de calidad entre las diferentes unidades organizativas del proyecto.

En el **Aseguramiento de Calidad (QA)** se busca mejorar los procesos. No involucra producto, habla solamente de procesos. Esto demuestra que no se puede tener calidad sin procesos. Busca defectos, no errores. El defecto es la diferencia entre lo que sucede y lo que debería estar sucediendo. Formalmente, es la planificación, estimación y supervisión de las actividades de desarrollo, que se realizan de forma independiente al equipo de desarrollo, de forma tal que los productos software resultantes cumplen los requisitos establecidos.

La aseguración es el proceso de revisar objetivamente los entregables, identificar defectos y hacer las recomendaciones para mejorarlo. Su resultado es asegurar que el software es de alta calidad. El proceso además tiene que describir los mecanismos para dejar la evidencia de que se respeta un Modelo, para todo lo relacionado con certificaciones.

El **Control de Calidad (QC)** se rige por los siguientes principios:
- Un desarrollador debe probar su propio código.
- Inspeccionar objetivamente el resultado de cada prueba.
- Los casos de prueba deben ser escritos tanto para condiciones de entrada válidas inesperadas como para condiciones válidas esperadas.
- No probar con la suposición de que no se van a encontrar defectos.
- Las pruebas constituyen una tarea altamente creativa y son un desafío intelectual.
- Cada requerimiento (CU, HU, RQ) debe tener asociados sus criterios de aceptación. Es muy importante.

Para este control se tienen dos tipos métodos:
- Caja blanca: Pruebas basadas en la estructura interna del código.
	- Búsqueda en profundidad: Recorrido exhaustivo de caminos internos posibles.
	- Camino básico: Prueba de caminos independientes mínimos del programa.
- Caja negra: Pruebas basadas en entradas y salidas esperadas.
	- Funcionalidad: Verificación del cumplimiento de funciones requeridas.
	- Regresión: Verificación de que cambios no rompan funciones previas.

El testing no es lo único que se puede realizar para el control de calidad. El objetivo no es “tener muchos tests”: es aumentar evidencia confiable sobre el comportamiento del sistema. La cobertura sirve, pero sola no prueba calidad. Puede haber 90% de cobertura y un diseño inmantenible.

Para hacer testing estratégico, se debe priorizar por riesgo (funcionalidades críticas, frecuencia de uso, impacto económico, seguridad, complejidad y cambios recientes) y combinar automatización con pruebas exploratorias (lo que no sabemos formular como test todavía también importa).
![[Pasted image 20260721205349.png|center|411]]

Para estas tres actividades, podemos resumir lo siguiente, ya que es importante no confundirlas:
- Gestión de calidad: Define política, objetivos, estándares, responsabilidades, métricas y umbrales de aceptación.
- Aseguramiento de calidad: Evalúa si el proceso seguido da confianza suficiente mediante auditorías, revisiones, cumplimiento de prácticas.
- Control de calidad: Mide productos concretos mediante pruebas, inspecciones, análisis estático, defectos, performance, seguridad.

## Modelos de Calidad

Los **Modelos de Calidad de Producto de Software** son marcos que ofrecen una definición más operacional en la puesta en práctica de los conceptos de calidad. Definen la calidad en forma jerárquica, y se evalúa a través de un conjunto de métricas. Además, establecen relaciones entre características, atributos y esas métricas.

Los **Factores de Calidad (Atributos de Calidad Externos)** son las características que componen la calidad representada desde el punto de vista del usuario. El modelo se basa en 11 factores de calidad que se organizan en torno a tres ejes:
- Operación del producto
- Revisión del producto
- Transición del producto

![[Pasted image 20260721205536.png|center|402]]

Los **Criterios de Calidad (Atributos de Calidad Internos)** son los atributos que contribuyen al aspecto de la calidad que el factor asociado representa. Cada uno de los factores se descompone en criterios. Define un total de 23 criterios:
1. Facilidad de uso:
	1. Facilidad de operación: ejecutar tareas dentro del sistema.
	2. Facilidad de comunicación: cómo el sistema informa estados, errores y resultados.
	3. Facilidad de aprendizaje: aprender a usar el sistema correctamente.
2. Integridad (seguridad):
	1. Control de accesos: permisos, roles o credenciales.
	2. Facilidad de auditoría: revisar acciones, cambios y eventos del sistema.
3. Corrección:
	1. Completitud: funciones y requisitos esperados.
	2. Consistencia: uniforme y coherente frente a situaciones similares.
	3. Trazabilidad: vincular requisitos, diseño, código y pruebas.
4. Fiabilidad:
	1. Precisión: exactitud de los resultados
	2. Consistencia
	3. Tolerancia a fallos: seguir operando ante errores o fallas
5. Eficiencia:
	1. Eficiencia en ejecución: rapidez y bajo consumo
	2. Eficiencia en mantenimiento: corregir o modificar con bajo esfuerzo
6. Facilidad de mantenimiento:
	1. Modularidad: partes independientes y bien delimitadas
	2. Simplicidad: baja complejidad en diseño, código o uso
	3. Consistencia
	4. Concisión: Ausencia de elementos innecesarios o redundantes
	5. Auto descripción: explicar su estructura o funcionamiento
7. Facilidad de prueba:
	1. Modularidad
	2. Simplicidad
	3. Auto descripción
	4. Instrumentación: mecanismos para observar, medir o registrar comportamientos.
8. Flexibilidad:
	1. Auto descripción
	2. Capacidad de expansión: agregar nuevas funciones o capacidades.
	3. Generalidad: servir en distintos casos o contextos.
	4. Modularidad
9. Portabilidad:
	1. Modularidad
	2. Auto descripción
	3. Independencia entre sistema y software: baja dependencia entre el software y su entorno operativo.
	4. Independencia del hardware: baja dependencia respecto del equipamiento físico utilizado.
10. Reusabilidad:
	1. Auto descripción
	2. Generalidad
	3. Modularidad
	4. Independencia entre sistema y software
	5. Independencia del hardware
11. Interoperabilidad:
	1. Modularidad
	2. Compatibilidad de comunicaciones: intercambiar mensajes mediante protocolos compatibles.
	3. Compatibilidad de datos: compartir e interpretar datos correctamente.

Las **Métricas del Producto** son medidas cuantitativas de ciertas características del producto que indican el grado en que dicho producto posee un determinado atributo de calidad. Para medir los criterios, el modelo propone un conjunto de métricas, no hay métodos formales que cubran todos los criterios.
- Métricas de exactitud: intentan aportar información sobre la validez y precisión del software y su estructura, incluyendo la etapa de despliegue, la de pruebas y la función de mantenimiento.
	- Cantidad de defectos detectados
	- Defectos por módulo
	- Porcentaje de casos de prueba exitosos
	- Cantidad de errores en producción
	- Defectos corregidos vs. defectos reportados
- Métricas de usabilidad: ayudan a determinar si la solución cumple con los requisitos del usuario.
	- Tiempo promedio para completar una tarea
	- Cantidad de errores cometidos por usuarios
	- Porcentaje de tareas completadas correctamente
	- Nivel de satisfacción del usuario
	- Cantidad de clics para realizar una acción
- Métricas de configuración: mide las limitaciones, el estilo de código y todos los datos relativos al desarrollo y cualidades del producto.
	- Cantidad de líneas de código
	- Complejidad ciclomática
	- Cantidad de módulos o componentes
	- Nivel de acoplamiento entre módulos
	- Nivel de cohesión interna
- Métricas de eficiencia: mide velocidad de respuesta y capacidad. Es un enfoque similar al de la productividad pero con un matiz un poco distinto, que añadido a aquél, aporta una visión mucho más completa de la solución.
	- Tiempo de respuesta
	- Uso de CPU
	- Uso de memoria
	- Cantidad de transacciones por segundo
	- Tiempo de carga de una pantalla

## Era IA Generativa

Hoy en día, contamos con la asistencia de la IA generativa, que modifica por completo nuestros procesos de desarrollo. Es importante primero notar que más velocidad no significa más calidad. La IA puede producir más código, tests y documentación. Eso aumenta la necesidad de filtrar, verificar y priorizar. Además, esto trae una nueva superficie de defectos, como alucinaciones, dependencias dudosas, vulnerabilidades, tests superficiales y falsa confianza. Ahora, el foco se mueve de “generar artefactos” a demostrar comportamiento, seguridad, mantenibilidad y alineación con requisitos.

>[!QUESTION] Pregunta
>¿Qué evidencia independiente tengo de que lo generado por IA es correcto, seguro y mantenible?

Podemos usar IA para los siguientes casos:
- Generación asistida de casos de prueba: útil para ideación, bordes y regresiones, pero requiere revisión humana y ejecución real.
- Revisión de código asistida: ayuda a encontrar smells o riesgos, pero no reemplaza criterios de arquitectura, dominio y seguridad.
- Pruebas de requisitos: prompts para detectar ambigüedades, inconsistencias y criterios de aceptación incompletos.
- Testing de sistemas con IA: evaluar robustez, sesgos, seguridad, privacidad, explicabilidad, trazabilidad y degradación en producción.
- Gobierno: declarar uso de IA, registrar prompts críticos, mantener trazabilidad entre requisito, código, test y evidencia.

Con esto aparecen riesgos específicos, ya que el “parece que anda” se vuelve más peligroso. La IA puede generar artefactos plausibles pero incorrectos. Algunos son:
- Tests débiles: Tests que verifican lo obvio, copian la implementación o no cubren casos límite.
- Errores correlacionados: Una IA puede generar código y otra IA revisarlo con sesgos similares. No alcanza con “que lo mire otro bot”.
- Benchmarks engañosos: Pasar tests funcionales no garantiza seguridad, mantenibilidad ni cumplimiento de requisitos.

Algunas maneras de mitigarlos son: especificaciones ejecutables, análisis estático, revisión humana experta, pruebas de seguridad y observabilidad.

En el proceso de QA, surge un nuevo paradigma. Antes, QA verificaba trabajo humano, pero ahora también tiene que verificar trabajo generado por IA.
1. ¿Cómo validamos el código generado?
2. ¿Cómo auditamos prompts?
3. ¿Cómo garantizamos trazabilidad?
4. ¿Cómo sabemos qué parte hizo un humano y cuál un agente?
5. ¿Cómo prevenimos la degradación arquitectónica por generación automática?

Además, la IA produce código “correcto superficialmente” pero puede duplicar lógica, romper convenciones, crear dependencias innecesarias, degradar arquitectura o generar código difícil de mantener. Entonces, mejora la productividad local pero puede empeorar la calidad sistémica.

Por otro lado, se debe contemplar la calidad del pipeline de desarrollo, ya que la IA empieza a participar en:
- refinement,
- documentación,
- generación de historias de usuario,
- code review,
- estimación (recordar los agentes haciendo Poker Planning),
- análisis de incidentes,
- retrospectives,
- DevOps.

>[!INFO] Tradeoff
>Esto se podría pensar como un nuevo tradeoff, ya que aumenta throughput pero baja comprensión colectiva del sistema.

En la ingeniería moderna entonces empiezan a aparecer prácticas como logging de prompts, versionado de prompts, auditoría de outputs, métricas de aceptación de código IA, trazabilidad de decisiones generadas, etc. Un sistema tradicional sabemos que tiene outputs deterministas, pero un LLM es estocástico (probabilístico). Aparecen dimensiones nuevas:
1. factualidad: ¿la respuesta sea verdadera y verificable?
2. toxicidad: ¿contenido ofensivo, discriminatorio, violento?
3. estabilidad semántica: ¿respuestas similares ante preguntas equivalentes?
4. reproducibilidad parcial: ¿resultados suficientemente consistentes?
5. alineación: ¿comportamiento del modelo coincide con objetivos, reglas y valores esperados?
6. robustez: ¿resistencia frente a prompts maliciosos, engañosos?
7. grounding: ¿respuesta apoyada en fuentes y datos disponibles?
8. drift del modelo: ¿hay degradación del comportamiento del modelo?
