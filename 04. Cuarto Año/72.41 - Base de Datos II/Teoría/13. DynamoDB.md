## Introducción

**Amazon DynamoDB** es un servicio de base de datos NoSQL de tipo clave-valor y documentos, totalmente administrado y que ofrece un rendimiento rápido y predecible, así como una perfecta escalabilidad. Su objetivo principal es ofrecer un rendimiento rápido y predecible junto con una escalabilidad transparente. El sistema permite crear tablas capaces de almacenar y recuperar cualquier volumen de datos y soportar cualquier nivel de tráfico de solicitudes. 

Para lograr esto, DynamoDB distribuye automáticamente tanto los datos como el tráfico de la tabla entre un número suficiente de servidores, gestionando la capacidad de solicitud especificada por el cliente y el almacenamiento de datos, manteniendo siempre un desempeño uniforme y de baja latencia.

Aunque DynamoDB deriva su nombre y expone un modelo de datos similar al sistema descrito en el famoso paper académico "Dynamo" de Amazon, posee una implementación subyacente diferente.

## Modelo de Datos

En términos de modelos de datos, el servicio soporta estructuras de tipo clave-valor (key-value) y de documentos. A nivel de almacenamiento lógico, la unidad básica es el **ítem**, que funciona como el equivalente a una fila (row) en una base de datos SQL relacional. Una tabla puede almacenar una cantidad ilimitada de ítems, y cada ítem puede contener tantos atributos como se necesiten. 

>[!INFO] Restricción Técnica
>Existe una restricción técnica fundamental en el diseño de esquemas: hay un límite estricto (hard limit) de tamaño de 400 KB por cada ítem individual.

La jerarquía de organización de datos comienza con la **tabla**, que actúa como el contenedor principal. Dentro de esta tabla se almacenan los Ítems (elementos). Cada uno se compone de atributos, que son los elementos de datos individuales. A diferencia de las bases de datos relacionales, no es necesario definir todos los atributos de antemano, salvo la clave primaria; los ítems dentro de una misma tabla pueden tener atributos diferentes, lo que aporta flexibilidad al esquema.

La definición de la Clave Primaria (Primary Key) es el aspecto más crítico del diseño en DynamoDB y puede ser de dos tipos. El primer tipo es la **Clave de Partición (Partition Key)** simple, la cual es obligatoria. Esta clave determina la distribución física de los datos a través de los servidores mediante una función hash interna. Un diseño eficiente requiere elegir una clave de partición que tenga una gran cardinalidad para evitar "puntos calientes" de acceso y distribuir la carga uniformemente. El acceso a los datos mediante esta clave es de tipo clave-valor, optimizado para búsquedas directas de un ítem específico.

El segundo tipo de clave primaria es la compuesta, formada por una **Clave de Partición** y una **Clave de Ordenamiento (Sort Key)**. La Sort Key es opcional, pero cuando se utiliza, permite modelar relaciones de uno a muchos $(1:N)$ bajo una única clave de partición. Esto habilita capacidades de consulta enriquecidas, permitiendo realizar búsquedas de rangos y ordenamientos sobre los datos que comparten la misma clave de partición. Gracias a la Sort Key, se pueden ejecutar operaciones lógicas complejas como mayor que, menor que, "comienza con", "entre" (between), y búsquedas de contención, además de obtener resultados ordenados o realizar conteos y filtros de top/bottom $N$ valores.

Podemos establecer la siguiente comparación con SQL:

## Consistencia

Respecto a la **consistencia** de los datos, un punto fundamental es que DynamoDB garantiza consistencia únicamente a nivel de ítem (**item-level consistency**). Esto es análogo a la consistencia a nivel de fila en una base de datos relacional (RDBMS). Según el modelo base presentado, no existen operaciones atómicas nativas que abarquen múltiples ítems o tablas simultáneamente en las operaciones estándar, ni consistencia garantizada en operaciones por lotes (batch). 

Si se ejecutan consultas contra índices o tablas completas, el conjunto de resultados puede no estar 100% actualizado en tiempo real debido a la replicación. Si la consistencia transaccional entre múltiples ítems es un requisito estricto para el caso de uso, se suele sugerir evaluar otras bases de datos o utilizar funcionalidades avanzadas específicas.

## Índices

En la arquitectura de DynamoDB, el acceso estándar a los datos se rige por la clave de partición (hash key) y la clave de ordenamiento (range key). No obstante, para ampliar las capacidades de recuperación de información más allá de estas claves primarias, el sistema introduce el concepto de **[[06. Bases de Datos#DynamoDB|índices secundarios]]**. Estos índices son fundamentales porque permiten acceder a los datos utilizando atributos diferentes a los definidos en la clave principal. Existen dos categorías de índices secundarios: los Índices Secundarios Locales, referidos como **LSI (Local Secondary Indexes)**, y los Índices Secundarios Globales, referidos como **GSI (Global Secondary Indexes)**.

Profundizando en los Índices Secundarios Locales (LSIs), su función específica es permitir la ejecución de consultas (queries) o escaneos sobre atributos que están fuera de la clave primaria hash y sort original. Esto significa que se puede mantener la misma clave de partición que la tabla base pero definir una clave de ordenamiento diferente para facilitar patrones de búsqueda alternativos sobre los mismos datos, sin necesidad de duplicar la información manualmente en otras tablas.

## Throughput

En DynamoDB, la capacidad de procesamiento se mide en unidades específicas que diferencian lectura y escritura. Una **Unidad de Capacidad de Lectura (RCU)** equivale a un bloque de 4KB por segundo, mientras que una **Unidad de Capacidad de Escritura (WCU)** equivale a un bloque de 1KB por segundo. Es importante considerar que las lecturas fuertemente consistentes son aproximadamente el doble de costosas que las lecturas eventualmente consistentes en términos de consumo de estas unidades.

La configuración de rendimiento de una tabla no es fija, por lo que se puede actualizar a voluntad; una estrategia válida es comenzar con valores mínimos de `RCU=1` y `WCU=1 y` modificarlos si se necesita mayor performance.

## Procesamiento Batch y Data Streams

En Amazon DynamoDB, el **[[06. Bases de Datos#DynamoDB|procesamiento batch]]** se instrumenta mediante operaciones de API específicas diseñadas para minimizar la latencia de red y optimizar el throughput al manipular múltiples elementos en una única solicitud HTTP. 

Las operaciones principales son **BatchGetItem**, que permite recuperar hasta 100 ítems de una o varias tablas, y **BatchWriteItem**, que permite insertar o eliminar hasta 25 ítems simultáneamente. A nivel de ingeniería, es crucial entender que, aunque estas operaciones agrupan las solicitudes para eficiencia, no garantizan atomicidad transaccional a nivel de lote; es decir, dentro de un mismo BatchWriteItem, algunos ítems pueden procesarse exitosamente mientras que otros fallan debido a limitaciones de capacidad provisionada, requiriendo que la aplicación cliente maneje la lógica de reintento para los fallos parciales (usando algoritmos como exponential backoff). 

Este enfoque es el estándar para cargas masivas de datos iniciales, migraciones o procesos de extracción periódica donde la consistencia instantánea en toda la base de datos no es el requisito principal.

Por el contrario, el procesamiento de flujos de datos (data streams) se implementa a través de la funcionalidad nativa llamada DynamoDB Streams, la cual actúa como un sistema de Captura de Datos de Cambios (CDC o Change Data Capture). Cuando se habilita esta opción en una tabla, DynamoDB captura una secuencia ordenada en el tiempo de cada modificación a nivel de ítem (creación, actualización o eliminación) y almacena esta información en un log duradero por un periodo de 24 horas. 

A diferencia del procesamiento Batch que es iniciado por el cliente, los Streams permiten una arquitectura reactiva y desacoplada: cada vez que ocurre un evento de escritura, el stream puede disparar automáticamente una función AWS Lambda para procesar ese cambio casi en tiempo real. Dentro del registro del stream, se puede configurar para ver solo las claves, la imagen nueva del ítem, la imagen antigua, o ambas. Esta arquitectura es fundamental para casos de uso avanzados como la replicación de datos entre regiones (tablas globales), la actualización de cachés, la indexación en motores de búsqueda como OpenSearch, o el cálculo de métricas agregadas en vivo sin impactar el rendimiento de la tabla principal.

## Fortalezas y Debilidades

Una de las fortalezas de DynamoDB es que permite omitir todos los pasos de instalación y configuración y comenzar a construir de inmediato. Si se construye algo pequeño, hay pocos límites intrínsecos a lo grande que puede llegar a ser (si, por supuesto, tienes el presupuesto para ello).

DynamoDB puede ser complicado en algunos lugares, especialmente cuando se trata de cosas como el aprovisionamiento de capacidad, la planificación de índices y la creación de un modelo de datos que le permita aprovechar el rendimiento y la escalabilidad de DynamoDB. Pero superar las partes difíciles abre muchas posibilidades.

Aunque DynamoDB requiere que se renuncie al poder de consulta de las bases de datos relacionales, sus datos y modelos de consulta proporcionan algunas construcciones poderosas, como índices y consultas de rango, que no se encuentran en muchas bases de datos NoSQL. Y si se encuentran barreras, como la incapacidad de escribir consultas de estilo SQL para tablas, se puede usar un servicio externo para llenar los vacíos. Más allá de todo esto, el conjunto de características de DynamoDB continúa expandiéndose, al igual que la constelación de servicios que rodean a DynamoDB en el ecosistema de AWS.

Los inconvenientes presentados por DynamoDB recuerdan directamente a otras bases de datos NoSQL. A pesar de algunas interesantes construcciones de consulta y modelado, probablemente sea mejor usar Postgres u otra base de datos relacional a menos que sepa con certeza que está lidiando con un problema en forma de DynamoDB (o tal vez un problema en forma de HBase, o Mongo, y así). Incluso si se tiene un caso de uso que realmente requiera una gran base de datos NoSQL, es posible que se tengan problemas para que su modelo de datos se adapte bien al sistema de particionamiento de DynamoDB. Y como siempre, está el costo.

Cualquier base de datos que se use va a costar dinero de alguna manera, pero DynamoDB y otros no siempre tienen sentido financiero. Puede haber ocasiones en que tenga sentido ejecutar bases de datos usted mismo, tal vez en su propio hardware y tal vez en la nube. El comprador asume el riesgo.
