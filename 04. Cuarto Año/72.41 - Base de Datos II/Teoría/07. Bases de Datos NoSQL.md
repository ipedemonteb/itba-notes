## Surgimiento

Las bases de datos NoSQL surgen para perfeccionar las BD con exceso de datos, que necesitan un gran indexado de documentos. Con el crecimiento de la web en tiempo real existía una necesidad de proporcionar información procesada a partir de grandes volúmenes de datos. Las bases de datos que veníamos estudiando asignaban muchos recursos a la consistencia y dejaban de lado ciertos aspectos de performance. 

Surgen por los siguientes motivos:
- Poca eficiencia en aplicaciones en las BD relacionales
- Aumento de operaciones de lectura y escritura
- Gran conjunto de transacciones
- Sentencias complejas
- Dificultades en la escalabilidad del sistema

## Modelo No Relacional

Este modelo es también un sistema de almacenamiento de información pero que no cumple con el esquema entidad-relación. Además, no impone una estructura de datos y los almacena en diferentes formatos.

Las bases de datos NoSQL tienen las siguientes propiedades:
- **Ausencia de esquema en los registros de datos**: Vemos en el siguiente caso la equivalencia entre un esquema relacional (izquierda) y uno del nuevo paradigma (derecha), con un documento JSON.
![[Pasted image 20260809203445.png|center|459]]
- **Alta velocidad de respuesta a peticiones.**
- **Estructura distribuida**: La información se recupera por la memoria de otros nodos. La respuesta se da en un tiempo casi imperceptible para el usuario.
![[Pasted image 20260809203534.png|center|463]]
- **Escalabilidad**: la vertical (upgrade de un servidor) está relacionada con el aumento de las características en el servidor, como por ejemplo la CPU o la RAM. Si pasa la época de alto consumo, se subutilizan los recursos. La horizontal consiste en multiplicar las unidades del servidor con la misma capacidad.
![[Pasted image 20260809203618.png|center|453]]

Estos sistemas responden a las necesidades de escalabilidad horizontal que tienen cada vez más empresas, ya que pueden manejar enormes cantidades de datos y no generan cuellos de botella, además de presentar un escalamiento sencillo. Se suele tener diferentes DBs NoSQL para diferentes proyectos, y se ejecutan en clusters de máquinas baratas.

Pero también presentan ciertas desventajas, como por ejemplo, no ser suficientemente maduros para algunas empresas, la falta de experiencia, el hecho de que no trata con datos críticos que requieren ACID y algunos problemas de compatibilidad.

## Modelo CAP

Un compromiso fundamental que afecta a cualquier sistema distribuido obliga a los diseñadores de bases de datos a elegir solo dos de estas tres propiedades:
- **Consistencia de datos**: Si se cumple, se garantiza que una vez que se escriben los datos están disponibles y actualizados para cada usuario que utilice el sistema.
- **Disponibilidad del sistema**: Se refiere a ofrecer el servicio ininterrumpidamente y sin degradación dentro de un cierto porcentaje de tiempo
- **Tolerancia a las particiones de red**: Si el sistema cumple con ella, entonces una operación puede ser completada incluso cuando alguna parte de la red falla.

Esta limitación intrínseca de los sistemas distribuidos se conoce como Teorema CAP o teorema de Brewer: Es imposible garantizar simultáneamente dichas propiedades en un sistema distribuido. Gráficamente se ve de la siguiente manera:
![[Pasted image 20260809203734.png|center|315]]

Como se puede ver en el gráfico, el teorema sólo garantiza:
- **CP (Consistency & Partition)**: El sistema aplicará los cambios de forma consistente y aunque se pierda la comunicación entre nodos ocasionando el particionado, no se asegura que haya disponibilidad.
- **AP (Availability & Partition)**: El sistema siempre estará disponible a las peticiones aunque se pierda la comunicación entre los nodos ocasionando el particionado, y en consecuencia por la pérdida de comunicación existirá inconsistencia porque no todos los nodos serán iguales.
- **CA (Consistency & Availability)**: El sistema siempre estará disponible respondiendo las peticiones y los datos procesados serán consistentes. En este caso no se puede permitir el particionado

Podemos establecer la siguiente clasificación según CAP:
![[Pasted image 20260809203814.png|center|383]]

Las siglas **BASE** significan **Basically Available Soft-State Eventual Consistency**. La principal propiedad BASE es la disponibilidad todo el tiempo, un estado flexible y consistencia eventual, por lo que en preciso momento puede que no sea consistente pero a lo largo del tiempo será eventualmente consistente.

>[!INFO] Conclusión
>Los sistemas ACID fuerzan la consistencia de la base de datos en todo momento sacrificando parte de la disponibilidad. Sin embargo BASE gana disponibilidad perdiendo parte de la consistencia, otorgando un estado de los datos más flexible.

## Taxonomía NoSQL

En el contexto de bases de datos NoSQL, la **taxonomía** se refiere a la clasificación o tipología de las diferentes clases de bases de datos NoSQL según cómo almacenan, organizan y consultan los datos. Dado que NoSQL no sigue el modelo relacional tradicional (tablas y SQL), surgieron distintos enfoques para resolver necesidades específicas (gran volumen de datos, flexibilidad de esquema, escalabilidad horizontal).

En las **bases de datos orientadas a grafos**, la información es representada en nodos y ya está normalizada. No es necesario definir cantidad de atributos, y los registros son de longitud variable. Algunas bases son Neo4j y HyperGraphDB. Por ejemplo:

## Cuándo Usar SQL y Cuándo NoSQL

Para tomar esta decisión, podemos establecer los siguientes puntos. Vamos a usar bases de datos SQL:
- Cuando el volumen de mis datos no crece o lo hace poco a poco.
- Cuando las necesidades de proceso se pueden asumir en un solo servidor.
- Cuando no tenemos picos de uso del sistema por parte de los usuarios más allá de los previstos.

Vamos a usar bases de datos NoSQL:
- Cuando el volumen de mis datos crece muy rápidamente en momentos puntuales.
- Cuando las necesidades de proceso no se pueden preveer.
- Cuando tenemos picos de uso del sistema por parte de los usuarios en múltiples ocasiones.
