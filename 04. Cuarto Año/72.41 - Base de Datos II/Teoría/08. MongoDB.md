## Características y Propiedades

**MongoDB** es una base de datos NoSQL orientada a documentos que almacena la información en formato JSON/BSON (Binary JSON - estructuras de tipo clave–valor pero más complejas). Presenta las siguiente características:
- Escalable, alto rendimiento y disponibilidad
- Puede trabajar en modo maestro-esclavo
- Posee un rico y sencillo sistema de consulta
- Soporte de índices
- Replicación y soporte a prueba de fallos

Una de las principales propiedades de MongoDB es la **escalabilidad horizontal** (Auto-Sharding), ya que permite dividir automáticamente los datos en fragmentos (shards) y distribuirlos en varios servidores. Así, cuando la cantidad de datos o consultas crece, se agregan más máquinas en lugar de depender de una sola más potente.

Otra  propiedad es la **replicación para alta disponibilidad**, ya que mantiene varias copias de los datos en diferentes servidores (replica set). Si el servidor principal falla, otro asume automáticamente el rol, garantizando que el sistema siga funcionando sin interrupciones.
![[Pasted image 20260809204955.png|center|510]]

Los principales componentes de MongoDB son los siguientes:
- **Mongod (Núcleo de la base de datos)**: Es el proceso principal de MongoDB. Se encarga de manejar las operaciones de lectura/escritura, la gestión de datos y la comunicación con los clientes.
- **Mongos (Controlador de particionamiento)**: Actúa como un router cuando hay sharding. Recibe las consultas de las aplicaciones y las dirige al shard correspondiente donde están los datos.
- **GridFS (Función de almacenamiento)**: Es un mecanismo de MongoDB para almacenar y recuperar archivos grandes (imágenes, audios, videos, etc.) dividiéndolos en fragmentos que se guardan como documentos.

Podemos ver la siguiente diferenciación con SQL:

| **SQL**                                                                                                                          | **MongoDB**                                                                               |
| -------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `CREATE TABLE users ( id MEDIUMINT NOT NULL AUTO_INCREMENT, user_id Varchar(30), age Number, status char(1), PRIMARY KEY (id));` | `db.users.insert({user_id: "abc123", age: 55, status: "A"})odb.createCollection("users")` |
| `DROP TABLE users`                                                                                                               | `db.users.drop()`                                                                         |
| `INSERT INTO users(user_id,age, status) VALUES ("bcd001", 45, "A")`                                                              | `db.users.insert( { user_id: "bcd001", age: 45, status: "A" } )`                          |
| `SELECT * FROM users`                                                                                                            | `db.users.find()`                                                                         |
| `SELECT COUNT(*) FROM users`                                                                                                     | `db.users.count()odb.users.find().count()`                                                |
| `SELECT * FROM users WHERE status = "A" ORDER BY user_id DESC`                                                                   | `db.users.find( { status: "A" } ). sort( { user_id: -1 } )`                               |
| `UPDATE users SET status = "C" WHERE age > 25`                                                                                   | `db.users.update( { age: { $gt: 25 } }, { $set: { status: "C" } }, { multi: true })`      |
| `DELETE FROM users WHERE status = "D"`                                                                                           | `db.users.remove( { status: "D" } )`                                                      |

La variable `db` apunta siempre a la base con la que vamos a trabajar. Luego de la base, se trabaja a nivel de colección. Lo que para SQL eran tablas, para Mongo van a ser colecciones, y lo que para el primero eran registros, para el segundo son documentos. 

En el primer caso, vemos que Mongo permite insertar a una colección inexistente, por lo que hace las dos operaciones de SQL (crear tabla e insertar) en una sola, con una sintaxis que parece orientada a objetos.

En el update, vemos que con el `$` podemos usar los operadores propios de mongo, como `$gt` (greater than) o el `$set`.

En MongoDB, un **ensamble de colecciones** se refiere a cómo se organizan los documentos dentro de una colección, que es como una "tabla" en SQL pero sin esquema fijo.
* Una colección agrupa documentos relacionados (por ejemplo, usuarios, productos).
* Cada documento puede tener una estructura diferente, pero comparten un contexto común.
* El "ensamble" permite manejar los datos de forma flexible, sin necesidad de definir columnas rígidas.

El siguiente ejemplo muestra cómo en MongoDB se pueden ensamblar (unir) colecciones parecidas a un `JOIN` en SQL:
* Hay una colección de posts (`post collection`) con los títulos y autores de las publicaciones.
* Y una colección de comentarios (`comment collection`) donde cada comentario se relaciona con un post a través del campo `postTitle`.

Con la operación `$lookup` en una agregación, se pueden unir ambas colecciones:
* `localField: "title"` $\rightarrow$ campo de la colección de posts.
* `foreignField: "postTitle"` $\rightarrow$ campo de la colección de comentarios.
* `as: "comments"` $\rightarrow$ nombre bajo el cual se guardan los comentarios relacionados dentro de cada post.
![[Pasted image 20260809223340.png|center|459]]

Se utiliza:
```javascript
db.posts.aggregate([
  {
    $lookup: {
      from: "comments",
      localField: "title",
      foreignField: "postTitle",
      as: "comments"
    }
  }
])
```

## Vistas

Para crear **vistas**, tenemos dos formas, ya que se pueden crear como colecciones:
- Opción 1: `db.createCollection()`
```javascript
db.createCollection(
  "<viewName>",
  {
    "viewOn": "<source>",
    "pipeline": [<pipeline>],
    "collation": { <collation> }
  }
)
````
- Opción 2: `db.createView()`
```Javascript
db.createView(
  "<viewName>",
  "<source>",
  [<pipeline>],
  {
    "collation": { <collation> }
  }
)
```

Una diferencia fundamental con SQL es que NO son actualizables. Tomemos el siguiente caso:
- Collection: `Survey`
```json
{ _id: 1, empNumber: "abc123", feedback: { management: 3, environment: 3 }, department: "A" }
{ _id: 2, empNumber: "xyz987", feedback: { management: 2, environment: 3 }, department: "B" }
{ _id: 3, empNumber: "ijk555", feedback: { management: 3, environment: 4 }, department: "A" }
```
- View: `managementFeedback`
```Javascript
db.createView(
  "managementFeedback",
  "survey",
  [ { $project: { "management": "$feedback.management", department: 1 } } ]
)
```

Para usar la vista, tenemos el siguiente caso para la vista anterior:
```Javascript
db.managementFeedback.find()
```

Lo que devuelve lo siguiente:
```json
{ "_id" : 1, "department" : "A", "management" : 3 }
{ "_id" : 2, "department" : "B", "management" : 2 }
{ "_id" : 3, "department" : "A", "management" : 3 }
```

## Diseño del Modelo de Datos

Los modelos de datos efectivos satisfacen las necesidades de la aplicación. La consideración clave para la estructura de sus documentos es la decisión de embeberlos o utilizar referencias.

Con MongoDB, se puede **embeber** datos relacionados en una única estructura o documento. Estos esquemas generalmente se conocen como modelos "desnormalizados" y aprovechan los documentos de MongoDB. Tomemos el siguiente diagrama:
![[Pasted image 20260809223743.png|center|437]]

Los modelos de datos embebidos permiten que las aplicaciones almacenen información relacionada en el mismo registro de la base de datos. Como resultado, es posible que las aplicaciones deban emitir menos consultas y actualizaciones para completar las operaciones comunes. 

En general, debemos utilizar modelos de datos incrustados cuando:
- Tengamos relaciones "contiene" entre las entidades.
- Tengamos relaciones de uno a muchos entre entidades. En estas relaciones, los "muchos" o documentos secundarios siempre aparecen con o se ven en el contexto de "uno" o documentos principales.

Los documentos embebidos proporcionan un mejor rendimiento para las operaciones de lectura, así como la capacidad de solicitar y recuperar datos relacionados en una sola operación de base de datos. Los modelos de datos embebidos permiten actualizar los datos relacionados en una sola operación de escritura atómica.

Debemos tener en cuenta que el tamaño máximo del documento BSON es de 16 megabytes. MongoDB no admite más de 100 niveles de anidamiento para documentos BSON.

## Modelo de Datos Normalizado

Los **modelos de datos normalizados** describen relaciones usando referencias entre documentos.
![[Pasted image 20260809223903.png|center|432]]

En general, debemos utilizar modelos de datos normalizados:
- Cuando la incorporación resultaría en una duplicación de datos pero no proporcionaría suficientes ventajas de rendimiento de lectura para superar las implicaciones de la duplicación.
- Para representar relaciones más complejas de muchos a muchos.
- Para modelar grandes conjuntos de datos jerárquicos.

Las referencias proporcionan más flexibilidad que el modelo embebido. Sin embargo, las aplicaciones del lado del cliente deben emitir consultas de seguimiento para resolver las referencias. En otras palabras, los modelos de datos normalizados pueden requerir más viajes de ida y vuelta al servidor.

## Modelo de Relaciones One-to-One con Documentos Embebidos

Tomemos el siguiente ejemplo que mapea las relaciones de usuario y dirección. El ejemplo ilustra la ventaja de embeber sobre las referencias si necesita ver una entidad de datos en el contexto de la otra. En esta relación de one-to-one entre el usuario y los datos de la dirección, la dirección pertenece al usuario. En el modelo de datos normalizado, el documento de dirección contiene una referencia al documento del usuario.
```json
{
  "_id": "joe",
  "name": "Joe Bookreader"
}

{
  "patron_id": "joe",
  "street": "123 Fake Street",
  "city": "Faketon",
  "state": "MA",
  "zip": "12345"
}
```

Si los datos de la dirección se recuperan con frecuencia con la información del nombre y luego con la referencia, la aplicación debe emitir varias consultas para resolver la referencia. El mejor modelo de datos sería incrustar los datos de dirección en los datos del usuario, como en el siguiente documento:
```json
{
  "_id": "joe",
  "name": "Joe Bookreader",
  "address": {
    "street": "123 Fake Street",
    "city": "Faketon",
    "state": "MA",
    "zip": "12345"
  }
}
```

Con el modelo de datos embebidos, la aplicación puede recuperar la información  completa del usuario con una consulta.

## Agregaciones

En MongoDB, las agregaciones permiten ejecutar consultas complejas que van más allá de un simple find, mediante una tubería de etapas (pipeline), donde cada etapa recibe documentos de la anterior, los procesa, y envía el resultado a la siguiente.

**`Lookup`** se usa para hacer joins entre colecciones (similar a un JOIN en SQL). Tomemos el siguiente caso:
```Javascript
db.orders.insert([
  { "_id" : 1, "item" : "almonds", "price" : 12, "quantity" : 2 },
  { "_id" : 2, "item" : "pecans", "price" : 20, "quantity" : 1 },
  { "_id" : 3 }
])

db.inventory.insert([
  { "_id" : 1, "sku" : "almonds", description: "product 1", "instock" : 120 },
  { "_id" : 2, "sku" : "bread", description: "product 2", "instock" : 80 },
  { "_id" : 3, "sku" : "cashews", description: "product 3", "instock" : 60 },
  { "_id" : 4, "sku" : "pecans", description: "product 4", "instock" : 70 },
  { "_id" : 5, "sku": null, description: "Incomplete" },
  { "_id" : 6 }
])

db.orders.aggregate([
  {
    $lookup: {
      from: "inventory",
      localField: "item",
      foreignField: "sku",
      as: "inventory_docs"
    }
  }
])
```

Y se obtiene:
```json
{
  "_id" : 1,
  "item" : "almonds",
  "price" : 12,
  "quantity" : 2,
  "inventory_docs" : [
    { "_id" : 1, "sku" : "almonds", "description" : "product 1", "instock" : 120 }
  ]
}
{
  "_id" : 2,
  "item" : "pecans",
  "price" : 20,
  "quantity" : 1,
  "inventory_docs" : [
    { "_id" : 4, "sku" : "pecans", "description" : "product 4", "instock" : 70 }
  ]
}
{
  "_id" : 3
}
```

Además, se tienen:
- **`$sort`**: Ordena los documentos en el pipeline según un campo (ascendente o descendente).
- **`$match`**: Filtra documentos según una condición (similar a `WHERE` en SQL).
- **`$unwind`**: Descompone un arreglo en múltiples documentos (cada elemento del arreglo genera un documento separado).
- **`$project`**: Permite dar forma a los documentos, eligiendo qué campos mostrar, renombrarlos o incluso crear nuevos calculados (como `SELECT campo1, campo2 AS otro_nombre` en SQL).
