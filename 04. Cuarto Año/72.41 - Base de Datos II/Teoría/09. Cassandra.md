## Bases de Datos Tabulares

Las bases de datos tabulares son un tipo de sistema NoSQL diseñado para manejar grandes volúmenes de información distribuidos en múltiples nodos. Su modelo se basa en tablas con filas y columnas, similar a una base de datos relacional, pero con una estructura más flexible que permite escalar de forma masiva.

Algunas de las implementaciones más conocidas son Cassandra, HBase, Accumulo, Hypertable y SimpleDB, que se utilizan en escenarios donde se requieren cargas masivas de datos y alta disponibilidad.

Estas bases de datos se destacan en varios aspectos:
- **Gestión de tamaño**: están optimizadas para almacenar y manejar cantidades enormes de información, distribuyéndola de manera eficiente entre nodos del clúster.
- **Cargas de escritura masivas orientadas al stream**: permiten procesar inserciones o actualizaciones de datos a gran escala en tiempo real, lo que las hace ideales para sistemas con flujo constante de información (por ejemplo, registros de sensores, logs o transacciones online).
- **Alta disponibilidad**: su diseño distribuido garantiza que los datos sigan estando accesibles incluso si uno o varios nodos fallan.
- **MapReduce**: se integran fácilmente con frameworks de procesamiento distribuido, lo que facilita realizar análisis masivos y operaciones complejas sobre grandes volúmenes de datos.

Las equivalencias con el esquema relacional son:

|    RDBMS     |             Tabular              |
| :----------: | :------------------------------: |
|  Instancia   |             Cluster              |
| Base de Dato |             KeySpace             |
|    Tabla     |       Familia de Columnas        |
|     Fila     |               Fila               |
|   Columna    | Columna (distinto por cada fila) |
Un uso muy común de este tipo de bases es el registro de eventos o logs de aplicaciones, ya que pueden manejar flujos continuos de información y guardar datos de manera eficiente. Además, las familias de columnas permiten organizar la información en conjuntos lógicos que pueden incluir datos, etiquetas, categorías, vínculos y otros metadatos, lo que aporta gran versatilidad.

Otra característica importante es que estas bases permiten establecer referencias hacia otros keyspaces, ampliando la forma en que se relacionan y organizan los datos dentro del sistema. Además, son útiles para tareas de análisis estadístico, ya que posibilitan contar y clasificar accesos, generar métricas y extraer información valiosa a partir de los registros almacenados.

Las bases de datos tabulares no siempre son la mejor opción en todos los contextos. Existen escenarios donde su uso puede traer más desventajas que beneficios. En primer lugar, no resultan adecuadas para sistemas que requieran transacciones ACID (Atomicidad, Consistencia, Aislamiento y Durabilidad) en operaciones de lectura y escritura. Estas bases priorizan la escalabilidad y la disponibilidad por sobre la consistencia estricta, lo cual limita su aplicación en entornos donde la integridad transaccional es crítica, como los sistemas financieros.

Tampoco son convenientes para consultas de agregación de datos (por ejemplo, sumatorias o promedios), ya que dichas operaciones no suelen estar optimizadas dentro del motor de la base de datos y deben resolverse del lado del cliente, aumentando la complejidad y el consumo de recursos.

Otra limitación es que no son ideales en prototipos tempranos, cuando aún no se tiene certeza sobre los patrones de consulta. Esto se debe a que la estructura de datos en bases tabulares está muy vinculada a cómo se van a realizar las consultas, por lo que una definición inadecuada desde el inicio puede traer problemas de rendimiento.

Finalmente, los cambios en el esquema pueden resultar costosos, ya que modificar la forma en que se almacenan o acceden los datos suele implicar reestructurar o redistribuir información a gran escala.

## Cassandra

**Cassandra** es una de las bases de datos más destacadas dentro del ecosistema Big Data, debido a su capacidad para manejar grandes volúmenes de información de manera distribuida y escalable.

Se trata de una base de datos NoSQL que fue diseñada para funcionar sin un único punto de fallo, permitiendo que los datos estén replicados en varios nodos y que la arquitectura pueda crecer horizontalmente a medida que aumentan las necesidades de almacenamiento y procesamiento.

Uno de sus aportes más importantes es el soporte para multi data center, lo que permite desplegar la base de datos en diferentes ubicaciones geográficas manteniendo la disponibilidad y la replicación entre ellas. Además, su modelo de comunicación peer-to-peer evita la dependencia de un nodo central y garantiza que todos los nodos de un clúster sean iguales, lo que contribuye a la tolerancia a fallos y a la eficiencia en la distribución de la carga.

El desarrollo inicial de Cassandra tiene su origen en Facebook, que lo diseñó para potenciar la funcionalidad de búsqueda en el inbox. En 2008 fue liberado como proyecto open source y en febrero de 2010 se convirtió en un proyecto top-level de la fundación Apache. Está inspirado e influenciado por los papers de Amazon Dynamo de 2007 y de Google BigTable de 2006. Hoy en día está mantenido y desarrollado por la compañía Datastax.

## Arquitectura y Características

La arquitectura de Cassandra está diseñada para ofrecer alta disponibilidad y escalabilidad sin comprometer el rendimiento, aunque sacrificando en parte la consistencia estricta, tal como plantea el teorema CAP.

En primer lugar, Cassandra ofrece **tolerancia a particiones y disponibilidad**, pero los datos son eventualmente consistentes. Esto significa que, aunque las actualizaciones pueden tardar un tiempo en propagarse por todos los nodos, el sistema garantiza que finalmente todos tendrán el mismo valor.

Un aspecto muy interesante es que el **nivel de consistencia es configurable**. El desarrollador puede decidir si priorizar velocidad (menos consistencia) o exactitud (mayor consistencia) según las necesidades de cada consulta (query).

La base es **distribuida**, lo que implica que los datos se reparten entre los nodos del clúster. Esto asegura que si un nodo falla, el servicio no se interrumpe y sigue disponible, reforzando así la tolerancia a fallos.

En cuanto a **escalabilidad**, Cassandra escala linealmente: a medida que se agregan nodos, la capacidad de procesamiento crece de manera proporcional. Por ejemplo, si con 2 nodos se soportan 100.000 operaciones por segundo, con 4 nodos se soportarían 200.000. Esto aporta predictibilidad al crecimiento del sistema. Su **escalabilidad horizontal** permite añadir nuevos nodos con facilidad, incluso en hardware económico. Gracias a ello, Cassandra puede adaptarse a sistemas en constante crecimiento sin necesidad de infraestructuras costosas.

La arquitectura se basa en un **modelo peer-to-peer**, lo que significa que no existe un nodo maestro central ni una jerarquía maestro-esclavo. Gracias a esto, se eliminan los puntos únicos de fallo y se mejora la tolerancia a errores, ya que todos los nodos son equivalentes.

En este esquema, cualquier nodo puede actuar como coordinador de una consulta. Es el driver del cliente el que decide a qué nodo dirigirse para que cumpla ese rol. Esto brinda flexibilidad y evita la dependencia de un nodo específico para coordinar operaciones.

La distribución de datos se realiza mediante un **token** único generado por una función hash para cada fila. Este mecanismo garantiza que la información se reparta de manera uniforme a lo largo del clúster. El espacio total de tokens va desde -2⁶³ a 2⁶³, y cada nodo recibe un rango de esos tokens, lo que define qué datos debe almacenar como primarios. A partir de esta asignación, Cassandra replica automáticamente los datos en otros nodos según el factor de replicación configurado, lo que asegura disponibilidad y redundancia.

Además, Cassandra introduce el concepto de **data center**, que permite agrupar nodos de manera lógica y geográfica. Esto posibilita acercar los datos a los usuarios finales, optimizando tiempos de respuesta y mejorando el rendimiento en sistemas distribuidos a gran escala.

## Modelo de Datos

El **Cassandra Query Language (CQL)** es el lenguaje utilizado para interactuar con Cassandra. Está inspirado en SQL, aunque es una versión reducida y adaptada al modelo NoSQL de esta base de datos.

Una de las principales diferencias con respecto a SQL tradicional es que en Cassandra los datos se encuentran **desnormalizados**, por lo que no existen operaciones como joins o subqueries. En lugar de eso, la modelación de datos se diseña pensando en las consultas específicas que se van a realizar, duplicando información si es necesario para optimizar el rendimiento.

Para trabajar con CQL podemos hacerlo mediante la herramienta de línea de comandos cqlsh, que actúa como una shell interactiva para ejecutar sentencias directamente contra la base de datos.

Además, existen herramientas gráficas como DevCenter que facilitan la administración y la escritura de consultas. También es posible usar Cassandra desde distintos lenguajes de programación gracias a los drivers oficiales, que permiten integrar CQL dentro de aplicaciones en entornos productivos.

El **modelado de datos** en Cassandra tiene un enfoque muy particular que combina características de las bases de datos clave-valor y las orientadas a columnas. Esto significa que cada fila está identificada por una clave única, y a esa clave se le asocian múltiples pares de columna-valor, lo que brinda flexibilidad y eficiencia para organizar la información.

>[!INFO] Diferencia con BDs Relacionales
>Una diferencia importante respecto a las bases de datos tradicionales es que en Cassandra el diseño no se centra en la normalización, sino en cómo se accederá a los datos. Por eso, a la hora de modelar, es fundamental pensar primero en las consultas que queremos realizar.

El hecho de que los datos se organicen de esta manera implica que debemos prestar especial atención al diseño de las claves de partición, ya que de ellas depende la distribución de la información entre los nodos del clúster. Una clave mal definida puede provocar concentraciones de datos en pocas particiones y, por lo tanto, pérdida de rendimiento.
![[Pasted image 20260809225938.png|center|476]]

Cuando diseñemos nuestro modelo debemos de guiarnos por el **patrón de acceso a los datos**, hay que hacer un análisis de las queries que pretendemos ejecutar contra nuestro sistema y de esta forma podremos diseñar un modelo eficiente que pueda sacar partido de las ventajas de Cassandra.

Es importante también **definir adecuadamente la clave de partición de nuestro datos**, ya que Cassandra se basará en esta clave para distribuir los datos a lo largo del cluster. Si queremos aprovechar nuestro cluster debemos pensar en distribuir los datos para evitar cuellos de botella.

También es recomendable, dado nuestro patrón de consulta, intentar **minimizar el número de particiones** a las que hay que acceder durante una lectura. 

Un ejemplo:
```sql
CREATE KEYSPACE MiEspacioClaves
  WITH REPLICATION = { 'class' : 'SimpleStrategy', 'replication_factor' : 3 };

USE MiEspacioClaves;

CREATE COLUMNFAMILY MisColumnas (id text, Apellido text, Nombre text, PRIMARY KEY(id));

INSERT INTO MisColumnas (id, Apellido, Nombre) VALUES ('1', 'Perez', 'Juan');

SELECT * FROM MisColumnas;
```
Resultado:
```
id | nombre | apellido
---+--------+----------
  1| Juan   | Perez

(1 fila)
```

## Cuándo Usar Cassandra

Cassandra destaca principalmente en escenarios donde la alta disponibilidad es un requisito fundamental. Gracias a su arquitectura distribuida y a la forma en que maneja la replicación de datos, garantiza que el sistema siga funcionando incluso si uno o varios nodos fallan. Esto es clave para aplicaciones donde una caída puede implicar pérdidas económicas o pérdida de información crítica.

Otra situación donde Cassandra es ideal es cuando se manejan grandes volúmenes de datos y se prioriza la velocidad de acceso sobre la normalización. A diferencia de las bases relacionales, Cassandra está optimizada para consultas rápidas y masivas, lo que la convierte en una buena opción para sistemas con cargas intensivas de lectura y escritura.

Sin embargo, es importante tener en cuenta que trabajar con Cassandra implica un cambio de mentalidad respecto al modelo relacional. Aquí no se busca normalizar los datos ni usar joins, sino diseñar el modelo a partir de los patrones de consulta. Esto requiere acostumbrarse a un enfoque diferente, más orientado a la eficiencia y la escalabilidad que a la consistencia transaccional clásica.

En el mundo relacional estamos acostumbrados a pensar en relaciones de tablas y la normalización de estas. Sin embargo, en el mundo Cassandra, hay que pensar en el almacenamiento en columnas. De modo que lo que llamaríamos una tabla, se va a convertir en una familia de columnas. 

Para acceder de forma más rápida y eficaz manejando grandes volúmenes de datos, diseñaremos familias de columnas sin importar el número de éstas. Así pues, podemos tener un registro en una familia de columnas que cuente con 50 columnas, y otro registro de la misma familia que tenga 300 columnas, ya que accederemos por el llamado Row Key.

Es cierto que quizás la parte más compleja de la adopción de esta base de datos sea cambiar la forma de pensar a la hora de diseñar el modelo, pues éste se debe basar en las consultas que haremos en la aplicación, y no en la relación de datos entre sí. Recordemos que en Cassandra NO existen los JOIN entre tablas.

## Replicación

La **replicación** en Cassandra es uno de los mecanismos clave que garantizan su alta disponibilidad y tolerancia a fallos. En un clúster, uno o más nodos almacenan copias (réplicas) de un mismo dato, distribuyéndolas de acuerdo al factor de replicación configurado. Esto asegura que, si un nodo falla, los datos puedan ser recuperados desde otro nodo que contenga la réplica.

Cuando un cliente realiza una consulta, Cassandra puede detectar si alguna de las réplicas devuelve un valor desactualizado. En esos casos, el sistema aplica un proceso llamado **read repair**, el cual garantiza que se devuelva al cliente el valor más reciente y, además, actualiza las réplicas que estuvieran desincronizadas.

De esta manera, Cassandra mantiene un equilibrio entre disponibilidad y consistencia, permitiendo que los datos estén siempre accesibles aunque no todos los nodos estén sincronizados al instante. Esto responde al principio de consistencia eventual del teorema CAP, donde la prioridad está en que el sistema nunca deje de responder.

Cuando un cliente solicita un dato, Cassandra devuelve siempre el valor más reciente disponible. Luego, en segundo plano, ejecuta una reparación de lectura (read repair) para actualizar aquellas réplicas que estuvieran desfasadas o contenían valores obsoletos. Este proceso asegura que, con el tiempo, todas las copias converjan hacia el mismo estado.

Otro componente clave es el **protocolo gossip**. Este mecanismo permite que los nodos del clúster se comuniquen de manera continua y descentralizada, compartiendo información sobre su estado y sobre los cambios que se producen en el sistema. La idea es similar a cómo se propagan las epidemias: cada nodo transmite información a sus vecinos, quienes a su vez la difunden al resto. Gracias a este procedimiento, Cassandra puede detectar rápidamente si un nodo falla y reorganizar la carga sin necesidad de un coordinador central.

## Elementos

Los elementos de Cassandra son los siguientes. Un **nodo** es una instancia de Cassandra que almacena datos y responde a las solicitudes de lectura/escritura. Cada nodo es responsable de una parte específica del conjunto de datos. En términos simples, un nodo es un servidor que forma parte del sistema distribuido y tiene una copia de los datos que le corresponde según el algoritmo de partición de la base de datos.

Un **data center** es un conjunto de nodos agrupados lógicamente. Puede estar ubicado en una única ubicación física o distribuido geográficamente para replicación y alta disponibilidad. En Cassandra, los data centers se utilizan principalmente para separar nodos por motivos de rendimiento o para replicación en distintas zonas geográficas. Puedes tener diferentes data centers para manejar cargas de trabajo distintas, como uno para operaciones de análisis y otro para procesamiento en tiempo real.

Un **clúster** es el conjunto completo de todos los nodos de Cassandra organizados bajo una configuración común. Un cluster incluye uno o más data centers y está diseñado para brindar redundancia, alta disponibilidad y escalabilidad. Los nodos en un cluster trabajan juntos para almacenar y replicar datos, lo que asegura la resistencia a fallas.

Un **commit log** es el registro de confirmación, que sirve como mecanismo de recuperación de fallas en Cassandra. Cada operación de escritura se escribe en el registro de confirmación.

Una **MemTable** es una estructura de datos residente en la memoria. Después del registro de confirmación (Commit log), los datos se escribirán en la SSTable desde MemTable. La **SSTable** es un archivo de disco en donde se guarda el contenido de la MemTable cuando alcanza un valor determinado. Cada fichero SSTable es inmutable una vez creado.

Los **Filtros de Bloom** no son más que algoritmos rápidos, no deterministas, para probar si un elemento es miembro de un conjunto. Es un tipo especial de caché. Se accede a los filtros Bloom después de cada consulta.

## Actividad de Escritura

La **actividad de escritura** en Cassandra está diseñada para ser muy eficiente, priorizando la velocidad y la durabilidad de los datos. A diferencia de otros sistemas, las escrituras en Cassandra son consideradas “baratas”, ya que no implican operaciones costosas en disco en el momento de la inserción.

El proceso sigue estas etapas:
1. **Commit log**: cada vez que llega una escritura, se registra primero en el commit log. Este archivo secuencial en disco garantiza la durabilidad, ya que si el sistema falla, los datos pueden recuperarse desde allí.
2. **MemTable**: luego, la escritura se almacena en memoria en una estructura llamada MemTable, organizada por familia de columnas. Aquí los datos permanecen temporalmente para poder responder consultas de manera rápida.
	1. Gracias a este mecanismo, Cassandra evita acceder directamente a disco en cada operación, lo que hace que las escrituras sean muy rápidas.
	2. Si ocurre una caída, los datos que estaban en memoria pueden reconstruirse usando el commit log.
3. **Flush de la MemTable**: cuando la MemTable alcanza un tamaño límite, su contenido se vuelca (flush) al disco en forma de un archivo inmutable llamado SSTable (Sorted String Table). De esta manera se libera la memoria y se conserva la información de forma permanente.
![[Pasted image 20260809230538.png|center|362]]

En Cassandra, la actividad de escritura culmina con el proceso de volcado de la información en disco a través de los SSTables (Sorted String Tables). Cuando una MemTable se llena, sus datos se escriben en un fichero SSTable, y luego la MemTable se borra para liberar memoria. Los SSTables son inmutables, es decir, una vez creados no se modifican: si se generan nuevas escrituras o actualizaciones, estas se almacenan en nuevas MemTables y, posteriormente, en nuevos SSTables.

>[!INFO] Costo de Lecturas
>Este proceso implica que los datos de una misma partición pueden terminar repartidos en múltiples SSTables diferentes. Como consecuencia, las lecturas suelen ser más costosas que las escrituras, ya que para recuperar la información solicitada, Cassandra puede tener que acceder a varias SSTables y combinarlas para devolver el resultado correcto.

Por eso, aunque las escrituras en Cassandra son muy rápidas y eficientes, las lecturas requieren más procesamiento, y es aquí donde entran en juego procesos de optimización como la compactación, que fusiona múltiples SSTables para reducir la dispersión de los datos.

La **compactación** en Cassandra es un proceso fundamental que se ejecuta de forma periódica con el objetivo de mejorar la eficiencia en las lecturas. Como los SSTables son inmutables, los datos de una misma partición pueden estar distribuidos en múltiples ficheros. Esto obliga a Cassandra a consultar varios SSTables al realizar una lectura, lo que incrementa el costo de la operación.

Para resolver este problema, Cassandra realiza la compactación, que consiste en unir varios SSTables en uno solo, eliminando datos obsoletos, valores sobrescritos o marcados como borrados (tombstones). El resultado de este proceso es:
- Menos ficheros SSTables que consultar por cada lectura.
- Reducción de la redundancia, ya que se descartan datos antiguos o repetidos.
- Lecturas más rápidas y eficientes, al disminuir el número de accesos necesarios en disco.

En Cassandra, la **actividad de escritura a nivel de clúster** sigue un proceso coordinado entre los nodos para asegurar la replicación y la consistencia según la configuración establecida.
1. **Nodo coordinador**: cuando un cliente envía una petición de escritura, esta llega a un nodo del clúster (no necesariamente el que guarda los datos). Ese nodo asume el rol de coordinador y se encarga de distribuir la petición a los nodos que contienen las réplicas correspondientes a esa fila.
2. **Escritura en réplicas**: los datos se escriben en todos los nodos disponibles que forman parte del conjunto de réplicas. Así se garantiza la redundancia y la disponibilidad de la información.
3. **Nivel de consistencia**: Cassandra permite configurar cuántos nodos deben confirmar la escritura para considerarla exitosa. Este valor puede variar:
	1. **ONE**: basta con que un nodo confirme la escritura.
	2. **QUORUM**: la mayoría de los nodos deben confirmar.
	3. **ALL**: todos los nodos con réplicas deben responder afirmativamente.

El nivel de consistencia define el equilibrio entre rendimiento, disponibilidad y seguridad de los datos. Por ejemplo, un nivel bajo como ONE mejora la velocidad, mientras que uno más alto como ALL asegura mayor consistencia pero puede penalizar el rendimiento si hay nodos caídos.

La actividad de escritura a nivel de clúster tiene algunas particularidades clave que garantizan tanto la durabilidad de los datos como la flexibilidad del sistema:
- **Confirmación del éxito**: una escritura se considera exitosa cuando el dato ha sido almacenado en el Commit log (para asegurar durabilidad) y en la MemTable (para accesos rápidos en memoria). Esto asegura que, incluso en caso de caída, la información no se pierda.
- **Todos los nodos pueden ser coordinadores**: no existe un nodo maestro fijo. Cualquier nodo del clúster puede recibir la petición del cliente y asumir el rol de coordinador, lo que elimina puntos únicos de fallo y mejora la disponibilidad del sistema.
- **Selección del coordinador**: la elección de qué nodo actúa como coordinador en cada petición no es aleatoria, sino que se realiza según una política predefinida en la base de datos. Esto permite balancear la carga y mantener la eficiencia en la distribución de peticiones.

En conjunto, este modelo de escritura distribuida refuerza la filosofía de Cassandra: un sistema descentralizado, tolerante a fallos y altamente disponible, en el que cada nodo puede cumplir múltiples roles según las necesidades del clúster.

## Actividad de Borrado

Cuando una fila es **eliminada**, no se borra del disco (SSTables inmutables), sino que se marca como eliminada (tombstone). Durante la compactación, las filas marcadas son eliminadas definitivamente del disco. Hay un **tiempo de gracia**: si un nodo que contiene la fila a ser eliminada se encuentra caído en ese momento, aún tiene la posibilidad de recibir la orden de eliminación si se recupera en un intervalo de tiempo predefinido.

Si no se recupera en ese tiempo, la fila no será marcada como eliminada, por lo que pueden existir inconsistencias en las réplicas. Por ello, se recomienda que los administradores realicen cada cierto tiempo tareas de mantenimiento en Cassandra.

Los datos pueden tener una "fecha de caducidad" (LLTS), a partir de la cual son marcados por Cassandra como eliminados.

## Actividad de Lectura

En Cassandra, cada vez que un nodo recibe una **petición de lectura**, primero se consulta la MemTable utilizando la clave correspondiente. Allí se intentan recuperar los datos solicitados directamente desde la memoria, lo que permite un acceso más rápido.

Si los datos no se encuentran completos en la MemTable, entonces se recurre a las SSTables almacenadas en disco. Dado que estas tablas son inmutables, la información de una misma fila puede estar repartida en varias de ellas.

Cuando no se ha realizado una compactación recientemente, este fenómeno se intensifica, ya que Cassandra puede necesitar acceder a múltiples SSTables para devolver un único resultado, lo que ocasiona un incremento en los tiempos de lectura.

Para afrontar este problema, Cassandra implementa tres mecanismos diferentes de lectura, diseñados para optimizar el acceso a los datos y mantener un buen rendimiento incluso en escenarios con alta fragmentación.
- **Direct Read Request**: el nodo coordinador contacta con un nodo que contenga la réplica requerida y la recupera.
- **Background Read Repair Request**: en caso de existir inconsistencias en las réplicas, las réplicas con un timestamp más antiguo son sobrescritas con los datos de la réplica “más actual”.
- **Digest Request**: contacta con tantos nodos con réplicas como se determine en el nivel de consistencia. Se comprueba la consistencia de los datos retornados por el nodo contactado mediante Direct read request.
	- Se envía la consulta aquellos nodos que estén respondiendo “más rápido”.
	 Si existen inconsistencias, se consideran como válidos las réplicas con un timestamp más reciente. Estos serán los retornados al cliente.
	- Una vez contactados los nodos determinados por el nivel de consistencia, se envía un Digest request al resto de réplicas, para determinar si son también consistentes.

## Consistencia

La **consistencia** en Cassandra es reconfigurable a través del `consistency_level`. Al momento de realizar una escritura, este nivel determina en cuántas réplicas debe almacenarse el dato para que la operación se considere confirmada frente a la aplicación cliente. De manera similar, al leer, se especifica cuántas réplicas deben responder con el dato solicitado para que la respuesta sea aceptada como válida y consistente.

El nivel de consistencia que se desea aplicar se puede elegir tanto en las operaciones de lectura como en las de escritura. Esto permite definir cuántas réplicas deben responder para considerar que un dato es válido, ajustando el equilibrio entre rendimiento, disponibilidad y consistencia. Un ejemplo de consulta que utiliza consistencia es el siguiente:
```sql
SELECT * FROM users WHERE state='TX' USING CONSISTENCY QUORUM;
```

Los niveles de consistencia de lectura son:

|          Nivel          |                                                                                                           Descripción                                                                                                            |
| :---------------------: | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------: |
| `ONE` / `TWO` / `THREE` | Devuelve una respuesta de una/dos/tres réplicas más cercanas, según lo determinado por el coordinador. Por defecto, se ejecuta una "reparación de lectura" en segundo plano para hacer que las otras réplicas sean consistentes. |
|        `QUORUM`         |                                                                       Devuelve el registro después de un quórum cuando (n/2)+1 réplicas hayan respondido.                                                                        |
|     `LOCAL_QUORUM`      |                  Devuelve el registro después de un quórum cuando (n/2)+1 réplicas hayan respondido en el mismo *datacenter* que el nodo coordinador. Evita la latencia de comunicación entre el *datacenter*.                   |
|      `EACH_QUORUM`      |                                                          Devuelve el registro una vez que el quórum de réplicas en cada *datacenter* de la agrupación haya respondido.                                                           |
|          `ALL`          |                                                                             Devuelve el registro después de que todas las réplicas hayan respondido.                                                                             |
Donde `Quorum = (sum_of_replication_factors / 2) + 1`

Para la escritura:

| Nivel                   | Descripción                                                                                                                                                                                                                       |
| :---------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ANY`                   | Una escritura debe ser escrita en al menos un nodo disponible.                                                                                                                                                                    |
| `ONE` / `TWO` / `THREE` | Una escritura debe escribirse en el registro de commit y memtable de al menos un/dos/tres nodos de réplica.                                                                                                                       |
| `QUORUM`                | Una escritura debe escribirse en el registro de commit y memtable en un quórum de nodos de réplica. Proporciona una fuerte consistencia si se puede tolerar cierto nivel de fracaso. Se determina por `(replication_factor/2)+1`. |
| `LOCAL_QUORUM`          | Una escritura debe escribirse en el registro de commit y memtable en un quórum de nodos de réplica en el mismo *datacenter* que el nodo coordinador. Evita la latencia de comunicación entre el *datacenter*.                     |
| `EACH_QUORUM`           | Consistencia fuerte. Una escritura debe escribirse en el registro de commit y memtable en un quórum de nodos de réplica en **todos** los *datacenter*.                                                                            |
| `ALL`                   | Una escritura debe escribirse en el registro de commit y memtable de todos los nodos de réplica en el cluster. Proporciona la más alta consistencia y la menor disponibilidad de cualquier otro nivel.                            |

Ante la posibilidad de encontrar datos inconsistentes en los nodos a pesar de tombstones, se recomienda realizar tareas rutinarias de mantenimiento. Existe una operación llamada **repair**, que puede utilizarse por parte del usuario para asegurar que todos los nodos son consistentes.

## Seguridad

En Cassandra la seguridad se gestiona en varios niveles. A nivel de usuarios, el sistema permite el uso de logins con contraseñas y la asignación de permisos mediante sentencias de administración como `GRANT` y `REVOKE`. Esto posibilita controlar qué acciones puede realizar cada usuario dentro de la base de datos.

- **Roles (Roles)**
```sql
CREATE ROLE alice WITH PASSWORD = 'password_a' AND LOGIN = true;
GRANT report_writer TO alice;
REVOKE report_writer FROM alice; 
LIST ROLES;
```
- **Usuarios (Users)**
```sql
CREATE USER alice WITH PASSWORD 'password_a' SUPERUSER;
```
- **Permisos (Permissions)**
```sql
GRANT SELECT ON ALL KEYSPACES TO data_reader;
REVOKE SELECT ON ALL KEYSPACES FROM data_reader;
LIST ALL PERMISSIONS ON keyspace1.table1 OF bob;
```

Además, Cassandra ofrece opciones de encriptación tanto en la comunicación entre clientes y clústeres como en la que ocurre entre nodos, garantizando así la protección de los datos en tránsito. Otro aspecto clave son las opciones de respaldo o backup, que se recomienda realizar de manera regular para prevenir la pérdida de información en casos de fallos o borrados accidentales.

Existen también herramientas externas, como DataStax Enterprise, que amplían las capacidades de seguridad de Cassandra. Estas permiten, por ejemplo, integrar autenticación externa, aplicar encriptación directamente a las tablas y realizar auditorías completas de datos, ofreciendo un entorno más robusto y alineado con las necesidades de aplicaciones empresariales.

## Estructura de Datos

En Cassandra, la estructura contiene los siguientes elementos. El primero es la **Columna (Columns)** unidad básica de almacenamiento. Consistente en una estructura de tres valores: 
- Name: nombre de la columna.
- Value: valor almacenado en la columna.
- Timestamp: fecha y hora de escritura.
![[Pasted image 20260809232002.png|center|351]]

Una **Super Column** es una columna cuyos valores son una o más columnas, que en este contexto se llamarán subcolumnas. Las subcolumnas están ordenadas y el número de columnas que se puede definir es ilimitada. Las super columnas, a diferencia de las columnas, no tienen un timestamp definido. Además no son recursivas, es decir, solamente tienen un nivel de profundidad. Esquema visual del modelo de datos:
![[Pasted image 20260809232046.png|center|569]]

Una **fila** es una agregación de columnas con un nombre para referenciarlo (rowKey). Es equivalente a la fila en el modelo relacional.
![[Pasted image 20260809232145.png|center|523]]

La **RowKey (RK)** es el equivalente a la clave primaria del modelo relacional. Tienen dos partes (claves):
- **De particionado (partition key)**: las filas con el mismo valor de clave de particionado se almacenan en la misma partición del disco (físicamente juntas).
- **De agrupamiento (clustering key)**: determina el orden físico en el que se almacenan las filas.

La **familia de columnas** es una agregación de filas donde cada ColumnFamily es guardada en un fichero separado y ordenado por la RowKey (equivale a las tablas en el modelo relacional). Los tipos de columnas son:
- Standard Columns
- Counter Columns
- Collection Columns: `SET`, `LIST`, `MAP`
- User-defined type
- Tuple-type
- Timestamp type
![[Pasted image 20260809232257.png|center|508]]

Un **Keyspace** es la unidad lógica más grande de agrupación de datos dentro de Cassandra, equivalente a lo que sería una base de datos en un sistema relacional. Los atributos básicos de un keyspace son:
- `Replication_factor`: Número de nodos que almacenarán una copia de cada fragmento de datos.
- `SimpleStrategy`: Utilizada para configuraciones simples o de un solo centro de datos.
- `NetworkTopologyStrategy`: (varios centros de datos).

```sql
CREATE KEYSPACE nombre WITH replication = 
  {'class':'SimpleStrategy', 'replication_factor' : 3};
```

## Particionado

El **particionado** en Cassandra es el mecanismo mediante el cual se decide cómo se distribuyen los datos entre los distintos nodos del clúster. Su objetivo es garantizar que la carga de almacenamiento y consultas esté balanceada y, a la vez, permitir un acceso eficiente según el tipo de consultas que se van a realizar. Existen dos estrategias principales.

**RandomPartitioner** utiliza un algoritmo de hash sobre las claves de partición. Esto hace que las filas se distribuyan de manera aleatoria a lo largo de todos los nodos del clúster. La principal ventaja es que se logra un equilibrio uniforme de los datos, evitando que ciertos nodos se saturen con más información que otros. Sin embargo, al desordenar las claves, se pierde la noción del orden natural, lo cual limita ciertos tipos de consultas por rango.

**OrderPreservingPartitioner**, en cambio, mantiene el orden natural de las claves. Esto significa que las claves con valores cercanos en el espacio de claves se almacenan en el mismo nodo o en nodos adyacentes. La ventaja es que permite consultas por rangos de claves de manera más directa. La desventaja es que puede generar desbalance en la carga: si las claves no están bien distribuidas, ciertos nodos pueden concentrar más datos que otros, afectando la escalabilidad.

---
## Índices

Los **índices primarios** en Cassandra son únicos para cada fila y cumplen un rol central en cómo se organiza y recupera la información dentro del clúster. Cada fila se identifica mediante este índice, lo que permite localizarla de manera precisa.

La asignación de filas a los nodos del clúster no se hace de forma arbitraria, sino que depende de dos mecanismos: el **partitioner**, que determina cómo se calculan y distribuyen los rangos de claves, y la **replica placement strategy**, que define cómo y dónde se replican los datos en función del índice primario.

Gracias a esta organización, cada nodo conoce qué rango de valores de índices primarios almacena. Esto permite que, al realizar consultas, el sistema pueda dirigirse directamente a los nodos que contienen los índices relevantes y escanear únicamente las réplicas necesarias. Como resultado, las búsquedas se vuelven más eficientes, ya que no es necesario recorrer la totalidad de los datos del clúster, sino solo los rangos en los que se espera encontrar las filas solicitadas.

Los **índices secundarios** son índices que se crean sobre columnas distintas al índice primario. A diferencia del primario, que organiza directamente la distribución de los datos en el clúster, los secundarios permiten realizar búsquedas basadas en valores de otras columnas que no forman parte de la clave principal.

Internamente se implementan como una tabla oculta y separada de la tabla original que contiene los valores. Esto significa que, al realizar una consulta con un índice secundario, Cassandra accede a esta estructura auxiliar para encontrar las filas que coinciden con el valor buscado y luego recupera los datos correspondientes de la tabla principal.

Sin embargo, su uso no es recomendado cuando las consultas deben revisar un gran volumen de datos para devolver solo un conjunto pequeño de resultados. En esos casos, los índices secundarios pueden volverse ineficientes, ya que generan una sobrecarga importante al distribuir la búsqueda entre múltiples nodos del clúster.

## Operaciones

Para crear una tabla:
```sql
CREATE TABLE usuarios (
    idusuario text,
    nombre text,
    mes int,
    registro time,
    PRIMARY KEY (idusuario, nombre)
  );
```
- `usuarios`: Nombre de la tabla (familia de columnas).
- `idusuario`, `nombre`, `mes`, `registro`: Nombre de las columnas.
- `text`, `int`, `time`: Tipo de dato de las columnas (texto, entero, hora, ...).
- `(idusuario, nombre)`: Campos que forman parte de la _KEY_ de la familia de columnas. 
    - La primera parte de la _KEY_ define la _partition key_ o clave de partición. En el ejemplo, `"idusuario"`.
    - La segunda parte de la _KEY_ define la _clustering key_ o clave de ordenamiento. En el ejemplo, `"nombre"`.

En Cassandra, la **primary key** es fundamental porque define cómo se almacenan y organizan los datos en el clúster. Esta clave está formada por dos componentes: la partition key y la clustering key.

La **partition key** es el primer valor que se declara en la primary key. Su función es determinar en qué nodo del clúster se almacenará la fila, ya que Cassandra utiliza esta clave para calcular un hash y así distribuir los datos. Por eso, es clave para el particionado y balanceo de carga.

  La **clustering key** corresponde a los valores que siguen a la partition key dentro de la primary key. Su rol es ordenar las filas dentro de cada partición. Es decir, una vez que Cassandra determina en qué nodo va a guardar la partición, la clustering key define el orden físico de las filas dentro de esa partición.

El orden en que se definen estos valores es muy importante. Por ejemplo, en `PRIMARY KEY (mes, idusuario)`, la partition key es `mes`, y la clustering key es `idusuario`. Esto implica que los datos se distribuyen entre nodos según el mes, y dentro de cada partición de mes, los registros se ordenan por `idusuario`.

Tanto la partition key como la clustering key pueden ser simples (un único valor) o compuestas (varios valores agrupados). En un caso compuesto, como `PRIMARY KEY ((idusuario, mes), nombre, registro)`, la partition key está formada por el conjunto `(idusuario, mes)`, lo que significa que el particionado depende de ambos campos en conjunto. Luego, las clustering keys son `nombre` y `registro`, que definen el orden de los datos dentro de cada partición.

En el siguiente ejemplo de **asignación de espacio** en Cassandra se ve claramente cómo funciona la combinación de partition key y clustering key en la organización de los datos.
```sql
CREATE TABLE usuarios (
  idusuario text,
  nombre text,
  mes int,
  registro time,
  PRIMARY KEY (mes, nombre)
)
```
Donde:
- **Partition key:** `mes`
- **Clustering key:** `nombre`

Las réplicas de las filas de una partición se encuentran físicamente juntas. Las diferentes particiones de las filas de una familia de columnas (tabla) pueden residir físicamente en nodos diferentes.
![[Pasted image 20260810085445.png|center|521]]

La clave primaria está compuesta de la forma `PRIMARY KEY (mes, nombre)`. Esto significa que:
- **Partition key**: es mes. Todas las filas que tienen el mismo valor en mes se agrupan en la misma partición. Esa partición puede residir en un nodo específico del clúster.
- **Clustering key**: es nombre. Dentro de cada partición, las filas se ordenan físicamente por el valor de nombre.

En el ejemplo, los registros con `mes = 5` forman la `Partition 1`. En ella se almacenan Albert y John, ambos ordenados por la clave de clustering (nombre), lo cual permite que las búsquedas dentro de esa partición sean rápidas y estén indexadas. De forma similar, los registros con `mes = 11` forman la `Partition 2`, que contiene a John y Peter, también ordenados alfabéticamente por nombre.

Esto también explica cómo Cassandra distribuye los datos en un clúster: las diferentes particiones (como la del mes 5 y la del mes 11) pueden vivir en nodos distintos, pero todas las filas con el mismo valor de partition key siempre se mantienen juntas en un mismo nodo. Además, las réplicas de una partición se guardan físicamente juntas para garantizar la disponibilidad y la tolerancia a fallos.

Si no tenemos clustering key:
```sql
CREATE TABLE usuarios (
  idusuario text,
  nombre text,
  mes int,
  registro time,
  PRIMARY KEY (idusuario)
)
```
Donde la partition key es `idusuario`. En este caso, al ser el `idusuario` único, todas las particiones de la tabla contienen una sola fila. No hay _clustering key_.
![[Pasted image 20260810085237.png|center|507]]

Para las consultas, el formato es el siguiente:
```sql
SELECT idusuario FROM usuarios 
WHERE idusuario='1p67' ORDER BY nombre
```
- **`SELECT idusuario` (Proyección):** Indica qué columnas se devuelven. Un `*` indica que se devuelven todas las columnas.
- **`FROM usuarios` (Tabla/Familia de columnas):** Tabla consultada. Solo se puede consultar una tabla (no hay _JOINs_).
- **`WHERE idusuario='1p67'` (Criterios de búsqueda):** Criterios a cumplir. En el `WHERE`, sólo se pueden utilizar columnas que formen parte de la _partition key_ o sobre las que se haya definido un índice secundario. Si la _partition key_ es compuesta y se incluye en el `WHERE`, han de incluirse todos sus campos.
- **`ORDER BY nombre` (Criterios de ordenamiento):** Siempre han de ser sobre columnas que estén incluidas en la _clustering key_.

Tomemos el siguiente ejemplo:
```sql
CREATE TABLE usuarios (
  idusuario text,
  nombre text,
  mes int,
  registro time,
  PRIMARY KEY ((idusuario, mes), nombre)
)
```
- **Partition key (compuesta):** `(idusuario, mes)`
- **Clustering key:** `nombre`

Al consultar es obligatorio identificar una partición de manera unívoca. En una partition key compuesta esto implica incluir todos sus componentes con igualdad en el `WHERE`. La consulta `SELECT idusuario FROM usuarios WHERE mes = 9` falla porque solo filtra por mes y Cassandra no puede resolver a qué partición ir: aún falta idusuario. En cambio, `SELECT idusuario FROM usuarios WHERE mes = 9 AND idusuario = 'agp88'` sí es válida, porque especifica completamente la partition key y el coordinador puede dirigir la lectura a la partición exacta.

Una vez elegida la partición (es decir, con la partition key completa), sí se puede filtrar y ordenar por la clustering key (nombre), incluyendo rangos y órdenes compatibles con el diseño de la tabla. Si necesitás consultar por un solo componente de la partition key o sin conocerlos todos, lo correcto es modelar otra tabla orientada a ese patrón de acceso; usar índices secundarios o `ALLOW FILTERING` para "forzar" esa consulta suele ser ineficiente y no es recomendable en producción.

La cláusula `ALLOW FILTERING` se utiliza cuando se intenta ejecutar una consulta que no puede resolverse directamente a partir de la clave primaria (partition key y clustering key) o de un índice. Normalmente, Cassandra está diseñada para acceder a los datos de manera eficiente usando las claves de partición y clustering. Pero si hacemos un `WHERE` sobre una columna que no forma parte de esas claves, el motor no sabe cómo ubicar rápidamente los registros, entonces debe recorrer todas las filas y filtrarlas después. Eso puede ser muy costoso en rendimiento.

Por eso, al ejecutar algo como:
```sql
SELECT * FROM blogs WHERE time1 = 1418306451235;
```
Si `time1` no es parte de la clave de partición ni clustering, Cassandra devuelve un error advirtiendo que la consulta implica filtrado. Solo se puede forzarla agregando `ALLOW FILTERING`:
```sql
SELECT * FROM blogs WHERE time1 = 1418306451235 ALLOW FILTERING;
```

Esto básicamente le dice al sistema: "Sé que esta consulta puede ser ineficiente, pero quiero ejecutarla igual." El riesgo es que si la tabla tiene millones de filas y solo unas pocas cumplen la condición, Cassandra tendrá que leer prácticamente todo para descartar lo que no sirve, lo que puede generar lentitud e imprevisibilidad.

Una **Materialized View** en Cassandra es una vista derivada de una tabla base que permite reorganizar los datos de forma automática para soportar consultas alternativas sin tener que duplicar manualmente la información.
```sql
CREATE MATERIALIZED VIEW monkeySpecies_by_population AS
  SELECT * FROM monkeySpecies
  WHERE population IS NOT NULL AND species IS NOT NULL
  PRIMARY KEY (population, species)
  WITH comment='Allow query by population instead of species';
```

El punto clave es que las materialized views se mantienen sincronizadas automáticamente: cada vez que se actualiza, inserta o borra un registro en la tabla base, Cassandra replica ese cambio en la vista correspondiente. Por eso, no se pueden modificar directamente, ya que dependen totalmente de la tabla original.

El lenguaje CQL soporta principalmente dos categorías de funciones. Las **funciones escalares** toman uno o varios valores de entrada y producen un único valor de salida. Son útiles para operaciones directas sobre datos individuales. Por ejemplo, se puede obtener la información de los últimos dos días utilizando la función `currentDate()` y restándole un intervalo de tiempo, como en la consulta:
```sql
SELECT * FROM myTable WHERE date >= currentDate() - 2d;
```

Las **funciones agregadas**, en cambio, operan sobre múltiples filas y producen un resultado único a partir de ese conjunto de datos. Son utilizadas para cálculos de agregación como sumas, promedios, conteos, mínimos o máximos. Un ejemplo es la consulta:
```sql
SELECT SUM(players) FROM plays;
```
Donde se suman todos los valores de la columna `players` en la tabla `plays`.

En Cassandra, los **triggers** permiten ejecutar lógica adicional automáticamente cuando ocurre una operación sobre una tabla. Para crearlos, se utiliza la instrucción:

La lógica real del trigger se implementa en una clase Java (cualquier lenguaje que corra sobre la JVM) y se almacena fuera de la base de datos, en el directorio lib/triggers de la instalación de Cassandra. Esa clase se carga al iniciar el clúster y está disponible en todos los nodos que participan en él.

El trigger se dispara antes de que se ejecute una sentencia DML sobre la tabla (por ejemplo, `INSERT`, `UPDATE` o `DELETE`), lo que garantiza la atomicidad de la transacción.
```sql
CREATE TRIGGER myTrigger
ON myTable
--(java class)
USING 'org.apache.cassandra.triggers.AuditTrigger';
```

En caso de que se desee eliminar un trigger, se utiliza:
```sql
DROP TRIGGER myTrigger;
```
