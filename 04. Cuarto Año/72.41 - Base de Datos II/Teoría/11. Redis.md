## Introducción

**Redis (Remote Directory Service)** es una base de datos clave-valor pensada para ser extremadamente rápido y simple de usar. A diferencia de una base relacional, donde se modelan tablas y `joins`, en Redis se trabaja con claves y estructuras de datos muy eficientes (cadenas, hashes, listas, conjuntos, etc.) que viven principalmente en RAM. Esta decisión de diseño le permite responder con latencias muy bajas y un throughput alto, lo que lo hace ideal para escenarios donde la velocidad es crítica.

## Bases de Datos Clave-Valor

Una estructura de clave valor es una tabla hash simple utilizada cuando todos los accesos a la base de datos se hacen por una clave primaria. Las operaciones que se pueden realizar son:
- `PUT`: Asignar un valor asociado a una clave
- `GET`: Obtener un valor dada una clave
- `DEL`: Borrar una clave

>[!TIP] Utilidad
>Son las bases de datos más simples para usar desde una aplicación.

El valor almacenado en la base de datos corresponde a un **BLOB (Binary Large OBject)**, que se almacena sin que la base de datos conozca que hay adentro.  La aplicación es responsable de definirlo. Usan un acceso por clave primaria, por lo que generalmente tienen muy buena performance y escalan rápidamente.

Algunos casos en los que es conveniente usar este tipo de base de datos:
- **La sesión web de un usuario**: Todo el contenido de la sesión puede almacenarse con una sola operación `PUT` o recuperarse con un solo `GET`. La información de la sesión se almacena en un único objeto.
- **Perfiles de Usuarios/Preferencias**: En base al userId, todos los atributos asociados al usuario (paleta de colores, zona horaria, etc.) pueden recuperarse con un único acceso.
- **Carros de Compra**: Los carros de compra de los ecommerce están asociados al usuario, la información del usuario asociado al carro de compra puede almacenarse como un único objeto.

En cambio, no es conveniente usarlas cuando se tienen relaciones entre datos o transacciones multioperación, cuando se tienen consultas por los valores almacenados dentro del campo valor o cuando pueden existir operaciones que abarcan diferentes conjuntos de datos.

## Redis

**Redis** se pensó originalmente como un broker de mensajería, aunque luego se empezó a usar como base de datos en memoria. Es un almacén de estructuras de datos en memoria, de código abierto con licencia BSD y escrito en ANSI C. Su modelo es sencillo: organiza la información como pares clave–valor que residen principalmente en RAM, lo que le permite responder con latencias de milisegundos y un rendimiento muy alto. En lugar de pensar en tablas y joins, conviene imaginar a Redis como un "servidor de estructuras de datos" al que accedemos por red con comandos atómicos y de costo bien definido.

Utiliza las siguientes estructuras de datos: Cadenas, Hashes, Listas, Conjuntos (ordenados o no), mapas de bits, HiperLogLogs e índices geoespaciales. Además, posee distintos tipos de persistencia y replicación.

Redis soporta:
- Transacciones.
- Cómputo de intersección, unión y diferencia de conjuntos.
- Operaciones sobre conjuntos ordenados.
- Operaciones probabilísticas sobre datos.
- Expiración de datos.

En Redis, una transacción permite la ejecución de un grupo de comandos garantizando:
- Todos los comandos de una transacción se serializan y ejecutan secuencialmente (se ejecuten como una única operación aislada).
- Ninguna solicitud emitida por otro cliente será atendida en medio de la ejecución de una transacción.
- No posee Rollback (posibles fallas de sintaxis no encontrados antes de ingresar en la cola de comandos o claves que contienen el tipo de datos incorrecto).

Una transacción en Redis es **atómica** (se procesan todos los comandos o ninguno). El comando `EXEC` desencadena la ejecución de todos los comandos en la transacción y todas las operaciones se realizan. Si el servidor de Redis falla, es posible que solo se registre una cantidad parcial de operaciones (aunque es poco probable). A partir de la versión 2.2, Redis permite un bloqueo optimista.

Redis provee los siguientes comandos:
- `MULTI`: Inicio de un lote de operaciones. Siempre responde OK ya que solo encola los comandos.
- `EXEC`: Ejecuta todos los comandos encolados.
- `DISCARD`: Vacía la cola de transacciones y finalizará la transacción.
- `WATCH`: Las claves observadas se monitorean para detectar cambios en ellas y si una clave se modifica, toda la transacción se aborta.

## Replicación y Persistencia

En Redis, la **replicación** utilizada es la de maestro-esclavo. Las instancias de las réplicas de Redis son exactas copias de las instancias maestras. En caso de falla, la réplica se volverá a conectar automáticamente al maestro e intentará ser una copia exacta del mismo. En un maestro y esclavo bien conectados, el maestro envía una secuencia de comandos al esclavo para replicar los efectos en el conjunto de datos debido a escrituras del cliente, claves caducadas o desalojado.
- **Resincronización parcial**: Rotura del enlace por problemas de red o por time-out en el maestro o el esclavo, el esclavo tratará de obtener la parte de la secuencia de comandos que perdió durante la desconexión.
- **Resincronización total**: Cuando no es posible una resincronización parcial, el esclavo solicitará una resincronización completa. El maestro creará una instancia de todos sus datos y la enviará al esclavo continuando con el proceso normal.

En Redis, se puede desactivar la **persistencia** completamente, y los datos existirán sólo en el servidor que se está ejecutando. Existen sino dos técnicas:
- **RDB (Redis DataBase Backup)**: realiza snapshots de su conjunto de datos en intervalos especificados.
- **AOF (Append On File)**: registra cada operación de escritura recibida por el servidor, que se reproducirá al inicio de la instancia reconstruyendo el conjunto de datos.

>[!INFO] Sobreecritura en Background
>Si el registro de operaciones es demasiado grande puede sobrescribirse en background.

Es posible combinar AOF y RDB, pero cuando se reinicia Redis, el archivo AOF será el utilizado para reconstruir el conjunto de datos original porque será el más completo. Usar AOF y RDB brinda un grado de seguridad de datos comparable a un RDBM. Lo aconsejable es usar AOF y poseer una instantánea de RDB de vez en cuando (copias de seguridad de la base de datos) permitiendo reinicios más rápidos en caso de errores en el motor AOF.

Las ventajas de RDB son:
- Es una representación muy compacta de un punto en un archivo de sus datos.
- Perfectos para copias de seguridad.
- Es posible guardar sus archivos RDB cada hora durante las últimas 24 horas y guardar una instantánea RDB todos los días durante 30 días.
- Bueno para la recuperación de desastres, fácil de transferir a otros centros de datos.
- RDB maximiza el rendimientos de Redis ya que nunca hace I/O (el proceso de grabación es un proceso secundario de Redis).
- Reinicia más rápido en comparación con AOF en grandes volúmenes.

Las desventajas de RDB son:
- No es conveniente para minimizar la posibilidad de pérdida de datos en caso de que fallas (corte de energía).
- Si bien el tiempo es configurable (cada 5 minutos por ejemplo) en caso de falla debe estar preparado para perder los últimos minutos de datos.
- El I/O genera procesos secundarios para persistir en el disco si el conjunto de datos es grande y el rendimiento de la CPU no es muy bueno.

Las ventajas de AOF son:
- Puede tener diferentes políticas de fsync (sincronización del file system):
	- Ninguna (NO)
	- Por Segundos (SECOND)
	- Cantidad de consultas (ALWAYS): llama a fsync en cada escritura.
- En la política predeterminada "por segundo" las operaciones de escritura son muy buenas (se realiza con un hilo en background y el hilo principal intentará realizar escrituras cuando no hay ninguna operación en progreso) lo máximo que se perdería sería un segundo.
- El registro es de append por lo que no hay problemas de búsqueda, ni corrupción si hay un corte de energía.
- Cuando se vuelve demasiado grande, mientras continúa añadiendo al archivo anterior, se produce uno completamente nuevo con el conjunto mínimo de operaciones necesarias para crear el conjunto de datos actual y una vez que este segundo archivo está listo los cambia.
- Contiene un registro de todas las operaciones de manera secuencial en un formato fácil de entender y analizar.

Las desventajas son:
- Los archivos AOF suelen ser más grandes que los archivos RDB para el mismo conjunto de datos.
- AOF puede ser más lento que RDB dependiendo de la política fsync utilizada; con fsync desactivado, debe ser exactamente tan rápido como RDB, incluso con carga alta.
- AOF trabaja actualizando incrementalmente un estado existente, como MySQL o MongoDB, mientras que la captura de RDB crea todo desde cero una y otra vez, eso es conceptualmente más robusto.

La indicación general es que debe usar ambos métodos de persistencia si desea un grado de seguridad de datos comparable al que PostgreSQL puede proporcionarle. Si le importan mucho sus datos, pero aún puede vivir con unos pocos minutos de pérdida de datos en caso de desastres, puede simplemente usar RDB.

## Cluster

La naturaleza de los datos en REDIS hace que deban estar permanentemente accesibles. La manera de configurar un cluster es mediante Sentinel. Está conformado por:
- **Servidor Redis**: Proceso encargado de almacenar y mantener los datos en memoria. Ej. a la instancia Maestra de Redis la llamaremos M, y las réplicas R.
- **Procesos Sentinel**: Procesos encargados de monitorizar las instancias de Redis (maestras y réplicas) y de iniciar el proceso de conmutación por una falla en la réplica a maestra. Los llamaremos S. 
- **Procesos Cliente**: Procesos encargados de comunicar la aplicación con el servidor de Redis. Los llamaremos C.

>[!INFO] Coexistencia
>A pesar de que todos pueden coexistir en la misma máquina, no es conveniente. Los componentes citados pueden encontrarse en cualquier número, salvo la instancia maestra (única). El resto de los componentes pueden existir en cualquier número (según arquitectura o comportamiento deseado).

El **quórum** es el número de instancias que tiene que estar “de acuerdo” a la hora de marcar un nodo como caído y promocionar un Slave a Master. En caso de haber al menos 3 instancias de Sentinel, debemos tener al menos un quórum de 2.

## Seguridad

Los principales problemas de seguridad son:
- Control de acceso
- Seguridad del código
- Entradas maliciosas

Redis está diseñado para ser accedido por clientes de confianza dentro de entornos de confianza. No exponer la instancia de Redis directamente a Internet o acceder directamente al puerto o al socket.

Por otro lado, no está optimizado para la máxima seguridad sino para un máximo rendimiento y simplicidad. Las aplicaciones que utilicen Redis como base de datos, caché o sistema de mensajería son las encargadas de mediar entre este y los clientes que no son de confianza. El acceso no confiable a Redis siempre debe estar mediado por una capa que implementa ACL, valide la entrada del usuario y decide qué operaciones realizar contra la instancia de Redis.

Un cliente puede autenticarse enviando el comando `AUTH` seguido de la contraseña. Cuando la capa de autorización está habilitada, Redis rechazará cualquier consulta realizada por clientes no autenticados. `AUTH` ayuda a garantizar que las entidades conocidas en la organización no accedan y modifiquen la instancia de Redis de forma involuntaria. `AUTH` no brinda seguridad durante el transporte de datos.

## Scripting

Redis posee la capacidad de interpretar **scripts** realizados en [LUA](https://www.lua.org/) de forma nativa. LUA es un lenguaje multiparadigma, su semántica puede ser extendida y modificada redefiniendo funciones de las estructuras de datos utilizando metatablas. Redis garantiza que un script se ejecuta de forma atómica. 

>[!INFO] Scripts lentos
>Tener en cuenta que mientras el script se está ejecutando ningún otro cliente puede ejecutar comandos.
