## Introducción

Las vistas son un recurso para la protección y la facilitación de ofrecer datos de manera más sintética, a partir de una tabla mucho más compleja. Forman parte del esquema externo de la base de datos. Presentan una parte de la BD que es de interés para grupos particulares de usuarios (ocultando el resto de la información).

## Concepto de Vista

La **vista** es una relación derivada de una o más tablas y/o vistas definidas previamente. Su contenido se define dando un nombre a una expresión de consulta. Se considera una tabla virtual (habitualmente no materializada), donde las tuplas se generan al operar sobre la vista.
- Pueden consultarse como cualquier tabla.
- Para poder realizar actualizaciones deben cumplirse ciertas condiciones (que surgen de su carácter de datos derivados).
- La característica genérica que define la posibilidad de actualización es la **preservación de la clave** (reconocimiento de la tabla que "hereda" su clave a la vista)
- No se puede modificar el esquema de la vista una vez creada como sí se puede con las tablas. En este caso se debe dropear y volver a crear.

Se crean de la siguiente manera:
```sql
CREATE VIEW nom_vista [(n_col_1, ..., n_col_n)]
AS expresión_consulta
[WITH [opción] CHECK OPTION];
```

Donde:
- `nom_vista`: nombre de la vista
- `(n_col_1,..., n_col_n)`: nombres de columnas de la vista
	- Las columnas de la vista se pueden renombrar especificando la lista completa de atributos de la vista entre paréntesis.
	- Si no, los nombres son los de las columnas de las tablas especificadas en la sentencia `SELECT`.
	- Se debe especificar con diferente nombre las columnas provenientes de distintas tablas pero con igual nombre.
- `expresión_consulta`: consulta SQL que define la relación derivada.

Tomemos el siguiente ejemplo:
![[Pasted image 20260806165203.png|center|254]]

Podemos crear las siguientes vistas:
- `PROV_COMP` con el identificador, nombre y ciudad de proveedores del rubro computadoras:
```sql
CREATE VIEW PROV_COMP AS
    SELECT id_proveedor, nombre, ciudad
    FROM PROVEEDOR
    WHERE rubro = 'Computadoras';
```
- `PROV_COMP_TANDIL` con los proveedores de computadoras de Tandil (usando la vista previa):
```sql
CREATE VIEW PROV_COMP_TANDIL AS
    SELECT *
    FROM PROV_COMP
    WHERE ciudad = 'Tandil';
```

Vemos en este último caso que podemos usar directamente la vista previa porque se pide lo mismo pero únicamente filtrando por una ciudad específica.
- `PROV_ENVIOS_TANDIL` que contenga el identificador y nombre de los proveedores de computadoras de Tandil y los identificadores de artículos enviados por cada uno. Tenemos dos casos:
```sql
CREATE VIEW PROV_ENVIOS_TANDIL AS
    SELECT P.id_proveedor, P.nombre, E.id_articulo
    FROM PROVEEDOR P JOIN ENVIO E
    ON P.id_proveedor = E.id_proveedor
    WHERE P.rubro = 'Computadoras'
    AND P.ciudad = 'Tandil';
```

```sql
CREATE VIEW PROV_ENVIOS_TANDIL AS
    SELECT P.id_proveedor, P.nombre, E.id_articulo
    FROM PROVEEDOR P JOIN ENVIO E
    ON P.id_proveedor = E.id_proveedor
    WHERE P.rubro = 'Computadoras'
    AND P.ciudad = 'Tandil';
```

Recordemos que una vista se consulta igual que una tabla, como por ejemplo en el caso anterior, si queremos listar alfabéticamente los proveedores de |.
```sql
SELECT nombre
FROM PR_COMP_TANDIL
ORDER BY nombre;
```

Para eliminar una vista del esquema de la BD:
```sql
DROP VIEW nom_vista [opción];
```
Con opción:
- `RESTRICT` $\rightarrow$ se rechaza si hay objetos que hacen referencia a la vista (opción por defecto).
- `CASCADE` $\rightarrow$ procede siempre y se eliminan también los objetos dependientes.

## Actualizaciones

Al **actualizar** las tuplas de una tabla, los cambios se reflejan automáticamente sobre las vistas definidas a partir de ella. Las vistas no mantienen copias de los datos (salvo que sean materializadas). El SGBD asegura que las vistas siempre estén actualizadas:
- **Por recálculo**: las tuplas actualizadas se generan al acceder a la vista.
- **Por mantenimiento incremental**: vistas materializadas.

Las operaciones de actualización sobre una vista deberían propagarse automáticamente a las tablas base. Sin embargo, al propagarse podrían generarse ambigüedades o carecer de sentido o provocar efectos no deseados. Tomemos los siguientes casos:
- Borrar una tupla en una vista: ¿borrar la tupla de la tabla base?  (una modificación también podría hacerla “desaparecer” de la vista)
- Insertar una fila en una vista: ¿insertar una tupla en la tabla base? (si se actualiza alguna tupla también podría incorporarse en la vista)
- ¿Cómo se propaga una actualización en caso de: 
	- una vista resultante de un ensamble?
	- un campo derivado?
	- una función de agregación?
	- una tupla que no conserva la clave?
	- una selección con distinct?

Cada actualización de una tupla en una vista debe poder propagarse sin ambigüedades a la/s tabla/s base o subyacente/s. Puede ser otra vista, que debe ser actualizable. Si se si tienen definidas vistas a partir de vistas: $T→ V_1→ V_2→ … →V_n$. $V_i$ será actualizable si $V_{i-1}$ lo es y así sucesivamente.

Esto es sólo es factible cuando una actualización de la/s tabla/s base puede lograr el efecto deseado sobre la vista. No toda vista se puede actualizar automáticamente, pues cuando una actualización sobre la vista pueda generar distintas posibilidades de actualización a la/s tabla/s base, se deberá recurrir a algún procedimiento específico para implementar la que sea requerida.

La **propiedad de preservación de clave** establece la condición para que una vista sea actualizable:
- Debe tratarse de una única actualización y del mismo tipo en la/s tabla/s base, cuya clave “heredó‟ la vista.
- Se satisface si cada fila en la tabla aparece como máximo una vez en la vista.
	- La clave de la vista es la clave de la tabla(\*) de la cual procede (vistas de una tabla).
	- La clave de la vista es la de alguna de las tablas(\*) de las cuales procede (vistas de ensamble)

>[!INFO] Nota
>En una jerarquía de vistas, basta que una de las vistas involucradas no preserve la clave, para que esta propiedad ya no se cumpla.

La propiedad NO depende de los datos actuales en las tablas, sino que es una propiedad estructural de su esquema. Este concepto ha sido explicado por distintos autores (ej: `Date`), aplicado por el estándar SQL como forma de operar, y popularizado por Oracle que lo implementó y denominó propiedad "key-preserved" (los SGBD suelen hacer interpretaciones particulares).

Según el estándar SQL, una vista definida sobre una tabla base (u otra vista actualizable) es actualizable si:
- Conserva todas las columnas de la clave (primaria).
- No contiene funciones de agregación o información derivada
- No incluye la claúsula `DISTINCT`
- No incluye subconsultas en el `SELECT`

Estas vistas se denominan **vistas σ-π** (se obtienen a partir de selección de tuplas y proyección de columnas). 

El SGBD traduce una actualización de una vista definida a partir de una tabla/vista en una única operación de actualización del mismo tipo sobre la tabla/vista. 

>[!IMPORTANT] Importante: 
>La actualización ocurre siempre que no se viole ninguna restricción de integridad definida sobre dicha relación (ej: afectando campos que no aceptan nulos o no tienen valores por defecto definidos). 

*Nota*: Algunos SGBDs soportan otras posibilidades que las especificadas por el estándar SQL.

Retomemos el ejemplo anterior.
![[Pasted image 20260806165203.png|center|254]]
Podemos crear `PROV_TANDIL` que contenga el identificador y nombre de los proveedores de Tandil:
```sql
CREATE VIEW PROV_TANDIL AS
SELECT id_proveedor, nombre
FROM PROVEEDOR WHERE ciudad = 'Tandil';
```
Es actualizable porque preserva la clave y no tiene funciones de agregación. Nos damos cuenta porque id_proveedor está en el SELECT.

Luego, podemos crear `PROV_COMP` con nombre y ciudad de proveedores de computadoras:
```sql
CREATE VIEW PROV_COMP
AS SELECT nombre, ciudad
FROM PROVEEDOR WHERE rubro =
'Computadoras';
```
No es actualizable porque no se preserva la clave.

Otra posibilidad es `TOTAL_ARTICULO`, que liste, para cada artículo, su identificador y la cantidad total enviada:
```sql
CREATE VIEW TOTAL_ARTICULO (articulo, total) AS
SELECT id_articulo, sum(cantidad)
FROM ENVIO
GROUP BY id_articulo;
```
No es actualizable porque tiene una función de agregación (`sum`).

## Migración de Tuplas

Al efectuar actualizaciones en una vista, podría ocurrir que las tuplas afectadas dejen de pertenecer a la vista. Tomemos el siguiente ejemplo:
```sql
CREATE VIEW PROV_TANDIL AS
SELECT * FROM PROVEEDOR
WHERE ciudad = 'Tandil';
```

Vemos que es actualizable porque en el `*` se contiene la clave. Pero, ¿cuál sería el resultado de la siguiente operación?
```sql
UPDATE PROV_TANDIL SET ciudad='Azul';
```

Todas las tuplas pasarían a tener ciudad Azul y dejarían de pertenecer a la vista, que pierde sentido. La solución a la migración de tuplas es incluir la cláusula **`WITH CHECK OPTION (WCO)`**.
```sql
CREATE VIEW nom_vista [(n_col_1, ..., n_col_n)]
AS expresión_consulta
[WITH [opción] CHECK OPTION];
```

Si se especifica `WCO`, una actualización sobre la vista procede si satisface la condición de consulta que la define (se rechaza cualquier inserción o actualización que haga migrar una tupla de la vista). Tenemos opción:
- **`CASCADED`**: las tuplas son chequeadas contra las condiciones de la vista y aquellas de las vistas subyacentes (opción por defecto). Aparece cuando hay vistas de vistas, y se usa para propagar el chequeo.
- **`LOCAL`**: sólo se chequean contra las condiciones definidas en la misma vista.


Volviendo al ejemplo anterior. Creamos la vista `ENVIOS500` con los envíos de 500 o más unidades de algún artículo (a partir de `ENVIO`):
```sql
CREATE VIEW Envios500 AS
SELECT * FROM ENVIO
WHERE cantidad>=500;
```

Ahora, hacemos:
```sql
INSERT INTO Envios500 VALUES ('P1', 'A1', 500);
```
Si ponemos `WCO` o no, se añade a la vista y a la tabla, siempre y cuando no se viole la integridad de la tabla.

Tomemos ahora:
```sql
INSERT INTO Envios500 VALUES ('P2', 'A2', 300);
```

Si ponemos `WCO`, no se va a agregar a la vista porque no se cumple con la condición de `cantidad>=500`. Si no ponemos `WCO`, se va a insertar en la tabla pero no se va a ver en la vista.

Por último:
```sql
UPDATE Envios500 SET cantidad=100 WHERE id_proveedor= 'P1';
```

Si ponemos `WCO`, no se va a ejecutar porque no cumple con la condición. Si no tuviera WCO, se produce la migración y no tendría sentido el nombre de la vista. Se elimina la tupla de la vista y se actualiza en la tabla.

Ahora, vamos a crear una nueva vista en base a la anterior:
```sql
CREATE VIEW Envios500-999 AS
SELECT * FROM ENVIO500
WHERE cantidad < 1000;
```

Veamos qué sucede si ejecutamos:
```sql
UPDATE Envios500-999 SET cantidad=300 where (id_proveedor='P1'
and id_articulo='A1');
```

Si ponemos `WCO` y cascada, cuando hacemos la operación se va a chequear que la condición se cumpla también en la vista `Envios500`, y esto va a generar que no se produzca el update porque no se cumple con la condición de `cantidad>=500` de dicha vista. En la segunda sí podría, porque se chequea solamente que `cantidad<1000`. Por este motivo, con local se insertaría y perdería sentido el nombre de la vista.

## Vistas Actualizables

Según el estándar SQL:1999, la actualización sobre una vista definida a partir de más de una tabla/vista sólo puede modificar una de las tablas base: la que cumpla la propiedad de preservación de la clave (la que tiene la misma clave de la vista, y entonces aparece a lo sumo una vez en la vista). Puede ser otra vista, que en este caso debe ser actualizable. Si $T \rightarrow V_1 \rightarrow V_2 \rightarrow \dots \rightarrow V_n$: $V_i$ será actualizable si $V_{i-1}$ lo es y así sucesivamente.

Además, no debe definirse en base a Unión, Intersección o Diferencia (Manifiestos para SQL:1999 y versiones posteriores $\rightarrow$ incluir otras operaciones, por ej. Intersección). Se denominan **vistas $\sigma$-$\pi$-$\bowtie$**: se obtienen mediante condiciones de ensamble sobre los pares $\text{FK} \rightarrow \text{PK}$ especificados en las RIRs. La actualización no se realizará si se viola alguna restricción definida sobre la relación base a actualizar.

Las posibles ubicaciones de la FK en relación al esquema de la relación son:
1. $\text{FK} \equiv K \rightarrow$ procede de la representación de relaciones de tipo-subtipo.
2. $\text{FK} \equiv Z_1,\dots,Z_r$ (atrib. secundarios); con $\text{FK} \cap K = \emptyset \rightarrow$ proviene de la abstracción de relaciones 1:1, N:1 o n-arias con al menos una cardinalidad 1.
3. $\text{FK} \equiv K_1,\dots,K_q$; con $\text{FK} \subset K \rightarrow$ resulta de las relaciones $N:N$, $n-\text{arias}$ en general y las correspondientes a los vínculos entidad fuerte-entidad débil (relaciones identificatorias).
![[Pasted image 20260806171413.png|center|458]]

Veamos el caso 2 en el siguiente ejemplo:
![[Pasted image 20260806171429.png|center|247]]

Creamos una vista ensamble proveniente de relación $N:1$.
```sql
CREATE VIEW EMPL_SISTEMAS AS
SELECT E.id_empleado, E.apellido, E.id_dpto, D.nombre
FROM DEPARTAMENTO D, EMPLEADO E
WHERE D.id_dpto = E.id_dpto
    AND D.nombre= 'Sistemas';
```

La clave de `EMPL_SISTEMAS` es `E.id_empleado` (análisis de dependencias funcionales). Aunque en la vista hubiera sólo un empleado en cada departamento (y entonces `id_dpto` sería único) igualmente la tabla `Departamento` NO sería de la cual se preserva la clave (no depende de los datos sino de la estructura del esquema).

De ser actualizable la vista y realizar un update, ¿cuál tabla se va a actualizar? Primero, vemos que es actualizable, y vemos que si se actualiza impacta a la tabla de empleado porque es la tabla cuya clave se está conservando.

Tomemos ahora el caso 3, creando la siguiente vista:
```sql
CREATE VIEW EMPL_PROY AS
SELECT T.id_empleado, T.id_proyecto, T.tarea, E.apellido
FROM TRABAJA T, EMPLEADO E
WHERE T.id_empleado = E.id_empleado
    AND E.cantidad_horas <3000;
```

La clave de `EMPL_PROY` es `T.id_empleado, T.id_proyecto` (análisis de dependencias funcionales). Vemos que la clave foránea es la clave principal de `TRABAJA`. Es una relación asociativa y se declara que es identificatoria. Si la vista es actualizable, queremos plantearnos nuevamente el interrogatorio anterior. Como se preserva la tabla de `TRABAJA`, se modifica dicha tabla y no `EMPLEADO`. No se va a poder insertar cosas que no existen previamente, como por ejemplo un empleado que no existe en la tabla `EMPLEADO`.

Finalmente, vamos al caso 1:
```sql
CREATE VIEW ING_TANDIL AS
SELECT I.id_empleado, I.titulo, E.apellido, E.nombre
FROM INGENIERO I, EMPLEADO E
WHERE I.id_empleado = E.id_empleado
    AND E.ciudad = 'Tandil';
```

La clave de `ING_TANDIL` es `I.id_empleado` (tabla subtipo). En cualquier actualización que hagamos, se va a conservar la de que tenga el dominio más restrictivo. Se preserva la clave de `INGENIERO`, pero no se podría utilizar para insertar un ingeniero porque `id_empleado` es foránea. En la vista Empleado e Ingeniero se corresponden con sólo una persona, o sea que `id_empleado` es único en la vista (resultado del ensamble), pero `Empleado` no sería la tabla de la cual se preserva la clave (porque es esperable que su dominio de definición sea más extenso).

## Actualización Via Triggers

Los **triggers** son un recurso que permite la actualización de vistas que no son automáticamente actualizables. Se deben definir triggers `INSTEAD OF` (opción especial para vistas) para las distintas operaciones requeridas (eventos críticos). Se pueden “interceptar” las operaciones de actualización: el trigger se dispara automáticamente en lugar de la sentencia disparadora, en forma "invisible" para el usuario. Por defecto, los triggers `INSTEAD OF` son `for each row`.

>[!INFO] Nota
>Queda en manos del usuario la responsabilidad de implementar las actualizaciones necesarias y de la manera que las considere “adecuadas”.

Tomemos el siguiente ejemplo, cuyas tablas son:
```sql
create table alumnos(
  documento char(8),
  nombre varchar(30),
  nota decimal(4,2),
  codigoprofesor int,
  primary key(documento)
);

create table profesores (
  codigo int auto_increment,
  nombre varchar(30),
  primary key(codigo)
);
```

Vamos a crear la vista:
```sql
CREATE VIEW info_tutores (nro_al, nom_al, id_tutor, nom_tut)
AS SELECT A.nro_al, A.nombre, A.id_tutor, P.nombre
   FROM Alumno A JOIN Profesor P
   ON A.id_tutor = P.id_prof;
```

Una posible semántica para el insert sobre info_tutores podría ser (no significa que sea la única, dependerá de los requerimientos):
```sql
CREATE TRIGGER insert_info_tutores
INSTEAD OF INSERT ON info_tutores
FOR EACH ROW
BEGIN
  IF NOT EXISTS (SELECT * FROM Alumno A WHERE A.nro_al= :new.nro_al)
    THEN INSERT INTO Alumno VALUES(:new.nro_al, :new.nom_al, :new.id_tutor);
    ELSE UPDATE Alumno SET id_tutor= :new.id_tutor WHERE nro_al= :new.nro_al;
  END IF;
  IF NOT EXISTS (SELECT * FROM Profesor P WHERE P.id_prof= :new.id_tutor)
    THEN INSERT INTO Profesor VALUES (:new.id_tutor, :new.nom_tut);
    ELSE UPDATE Profesor SET nombre= :new.nom_tut WHERE id_prof= :new.id_tutor;
  END IF;
END;
```

Deberían plantearse triggers similares para las operaciones de `UPDATE` y `DELETE` (en PostgreSQL la función podría implementar el comportamiento para todos los eventos)

## Vistas Actualizables en MySQL

Una vista en MySQL no es actualizable si:
- Contiene funciones de agregación, `DISTINCT`, `GROUP BY` o `HAVING`.
- Usa `UNION` o `UNION ALL`.
- Usa subconsultas en el `SELECT`.
- Subconsultas independientes en el `SELECT` (solo falla el `INSERT`).
- ENSAMBLES (`JOINS`).
- Referencia una vista no actualizable en el `FROM`.
- Subconsulta en el `WHERE` que referencia a una tabla en el `FROM`.
- Referencia sólo a valores literales (sin tabla subyacente para actualizar).
- `ALGORITHM = TEMPTABLE` (el uso de una tabla temporal siempre hace que una vista no sea actualizable).
- Múltiples referencias a cualquier columna de una tabla base (falla en `INSERT`, ok para `UPDATE` y `DELETE`).

Tomemos el siguiente caso:
```sql
CREATE TABLE t1 (x INTEGER);
CREATE TABLE t2 (c INTEGER);
CREATE TABLE vmat AS SELECT SUM(x) AS s FROM t1;
CREATE VIEW vup AS SELECT * FROM t2;
CREATE VIEW vjoin AS SELECT * FROM vmat JOIN vup ON vmat.s=vup.c;
```

Veamos las siguientes sentencias para el **INSERT**:
```sql
// Esta sentencia no es válida porque un componente de la vista ensamble (join) no es actualizable.
INSERT INTO vjoin (c) VALUES (1);

// Esta sentencia es válida; la vista no contiene componentes materializados.
INSERT INTO vup (c) VALUES (1);
```

Para el **UPDATE**:
```sql
// Esta sentencia es válida; la columna c proviene de la parte actualizable de la vista ensamble.
UPDATE vjoin SET c=c+1;

// Esta sentencia no es válida; la columna x proviene de la parte no actualizable.
UPDATE vjoin SET x=x+1;

// Esta sentencia es válida; la referencia de tabla actualizada del UPDATE de múltiples tablas es una vista actualizable (vup).
UPDATE vup JOIN (SELECT SUM(x) AS s FROM t1) AS dt ON ...
SET c=c+1;

// Esta sentencia no es válida; intenta actualizar una tabla derivada materializada
UPDATE vup JOIN (SELECT SUM(x) AS s FROM t1) AS dt ON ...
SET c=c+1;
```

Para el **DELETE**:
```sql
// Esta sentencia no es válida porque la vista es una vista ensamble (join).
DELETE vjoin WHERE ...;

// Esta sentencia es válida porque la vista es una vista combinada/fusionada (actualizable).
DELETE vup WHERE ...;

//Esta sentencia es válida porque elimina desde una vista combinada/fusionada (actualizable).
DELETE vup FROM vup JOIN (SELECT SUM(x) AS s FROM t1) AS dt ON ...;
```

## Vistas Materializables

Algunas aplicaciones pueden requerir alto grado de respuesta por parte de la BD (no siendo suficiente la optimización de la/s consulta/s). Una vista puede ser **materializada**. El SGBD pre-calcula y almacena su contenido (físicamente, como sucede con una tabla), puede ser usada como si fuera una relación común (incluso crear índices para mejorar la performance de consultas) y se genera duplicación de datos y necesidad de mantener la consistencia respecto del contenido de las tablas base.

Algunas consideraciones que se deben tener:
- ¿Qué vistas deberían materializarse? (decisión compleja)
- ¿Cómo debe ser la sincronización entre vistas materializadas y tablas base?
	- ¿Aplicar actualización por regeneración de la vista? o incremental?
	- ¿En forma inmediata (al darse algún cambio)? ¿periódicamente? ¿forzado?

|      SGBD      |                                                                                              **Cómo funcionan las vistas materializadas**                                                                                              |
| :------------: | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------: |
| **PostgreSQL** |                     Con PostgreSQL, se debe actualizar manualmente la vista materializada y volver a calcular la vista completa. La vista materializada se completa con datos en el momento exacto en que se crea.                     |
|   **MySQL**    |                                                                                               MySQL no admite las vistas materializadas.                                                                                               |
|   **Oracle**   | Oracle actualiza automáticamente las vistas materializadas, pero también ofrece la opción de actualizarlas a pedido. También puede escribir una instrucción SQL que solicite que las vistas se actualicen antes de generar resultados. |
| **SQL Server** |                                     SQL Server usa el nombre "vistas indexadas", ya que la materialización es un paso para crear un índice de una vista normal. Solo puede realizar consultas SQL                                      |
En PostgreSQL:
```sql
CREATE MATERIALIZED VIEW view_name
AS query
WITH [NO] DATA;
```

Donde:
- `view_name` es el nombre de la vista materializada en Postgres.
- `query` es la consulta compleja que provee los datos para la vista materializada.
- `WITH DATA / WITH NO DATA` es el parámetro que especifica si la consulta debe cargar los datos (los resultados de la consulta) de inmediato durante la creación del objeto. Si los necesitamos al momento de crear la vista materializada en Postgres, especificamos el parámetro `WITH DATA`. De lo contrario, utilizamos `WITH NO DATA`.

Entonces podemos tomar el siguiente ejemplo:
```sql
CREATE MATERIALIZED VIEW alumnos_2017
AS select * from alumno where añoDeIngreso=2017
WITH LOCAL CHECK OPTION
WITH DATA;
```

## Ventajas y Desventajas

En síntesis, podemos establecer la siguiente serie de **ventajas** para el uso de vistas:
- Simplifican la percepción que los usuarios tienen de la BD, presentando la información necesaria y ocultando el resto.
- Presentan diferentes datos a distinto tipo de usuarios, aún cuando los estén compartiendo (sobre la misma BD). 
- Permiten definir consultas complejas/frecuentes para no tener que especificarlas cada vez que se utilizan. 
- Facilitan la independencia de los datos (ocultando a los usuarios cambios en la estructura en las tablas base).
- Permiten aplicar políticas de seguridad (privacidad): dando privilegios selectivamente sobre distintas vistas (control de acceso).
	- Vistas sobre algunas columnas, ocultando otras reservadas para usuarios específicos (ej. antecedentes penales)
	- Vistas sobre determinadas filas, ocultando otras reservadas para usuarios específicos (ej. películas no aptas para público infantil)

Las **desventajas** son:
- Actualizaciones VISTA → Tabla BASE restringidas: hay varias limitaciones sobre la estructura de las vistas para asegurar que resulten automáticamente actualizables (debido a posibles anomalías).
- Cuestiones de Rendimiento: el proceso de resolución de la vista puede exigir el acceso a múltiples tablas cada vez que se accede a ella. Evaluar si podría justificarse su materialización (técnicas de mantenimiento de vistas).
- Necesidad de sincronización en caso de vistas materializadas (y duplicación de datos).
- Modificaciones a la estructura de tablas base (ej. agregado de columnas) no serán advertidos por la vista, salvo que sea re-creada.
