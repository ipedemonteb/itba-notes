## Tipos de Bases de Datos

Primero podemos preguntarnos, ¿cuál es la diferencia entre S3 y una base de datos? En primer lugar, S3 es un servicio de almacenamiento altamente escalable y duradero para objetos, como imágenes, videos, documentos y copias de seguridad. Contiene datos que requieren almacenamiento y recuperación a largo plazo. Es ideal para almacenar datos no estructurados que no requieren transacciones o consultas complejas. Veamos ahora el caso de las bases de datos.

>[!TIP] Bases de Datos Relacionales y No Relacionales
>Las bases de datos están diseñadas para almacenar datos facilitando consultarlos, actualizarlos y trabajar con ellos. Las bases relacionales permiten trabajar con relaciones complejas entre los datos brindando integridad, control de concurrencia y transaccionalidad. Las bases no relacionales prestan funcionalidades específicas para múltiples tipos de tareas, simplificando el desarrollo.

Existen distintos tipos de bases de datos. Como vimos, las **relacionales** organizan la información en tablas, con filas y columnas, y permiten vincular datos entre sí de manera clara y consistente. Son la mejor opción cuando importa mucho mantener integridad, relaciones bien definidas y transacciones confiables, como en sistemas de facturación, inventario, ERP o CRM. En AWS, ejemplos de este grupo son RDS y Aurora, mientras que Redshift se orienta más al análisis y almacenamiento de datos para consultas analíticas.

Las **bases key-value** almacenan cada dato asociado a una clave única. Su gran ventaja es la simplicidad y la velocidad: si se conoce la clave, se accede al valor muy rápidamente. Son muy útiles para sesiones de usuario, preferencias, configuraciones o cargas que requieren mucha escalabilidad horizontal. En AWS, el servicio más representativo de este modelo es DynamoDB.

Las **bases in-memory** guardan la información directamente en memoria RAM, lo que permite tiempos de respuesta muy bajos. Se usan cuando la velocidad es crítica, por ejemplo para caché, manejo de sesiones, rankings en tiempo real o datos temporales que deben leerse y actualizarse continuamente. En AWS, esto se resuelve con ElastiCache.

Las **bases de tipo documento** almacenan la información como documentos, generalmente en formatos flexibles como JSON. A diferencia de una base relacional, no obligan a que todos los registros tengan exactamente la misma estructura. Eso las hace convenientes para perfiles de usuarios, catálogos, sistemas de contenido o aplicaciones donde el esquema puede cambiar con frecuencia. En AWS, un ejemplo es DocumentDB.

Las **bases de grafos** están pensadas para representar entidades y, sobre todo, las relaciones entre ellas. Son ideales cuando el problema principal no es solo guardar datos, sino entender cómo se conectan entre sí, como en redes sociales, motores de recomendación, rutas o detección de fraude. En AWS, el servicio asociado a este modelo es Neptune.

## Elección de Bases de Datos

A la hora de elegir una base de datos debemos contemplar distintos aspectos de los datos que se manejarán y el uso que se le dará, así como otras características. Lo primero que hay que mirar es la **estructura de los datos**. Si los datos tienen un esquema claro, fijo y bien definido desde el principio, suele convenir un modelo más estructurado, como una base relacional. En cambio, si el dominio no está totalmente cerrado o si los datos pueden cambiar de forma con el tiempo, puede ser mejor una base más flexible, como una documental. En otras palabras, una de las primeras preguntas es si la información tiene una forma estable o si necesita adaptarse a cambios frecuentes.

Otro factor importante es la **escalabilidad**. Hay que pensar cuánto va a crecer el volumen de información y cómo va a crecer la carga del sistema. No es lo mismo una aplicación pequeña con pocos usuarios que una plataforma que puede multiplicar sus consultas y datos rápidamente. También conviene anticipar si el sistema necesitará crecer verticalmente, agregando más capacidad a un solo nodo, o horizontalmente, distribuyendo la carga entre varios nodos.

Otro criterio clave al elegir una base de datos es cómo se va a **acceder a los datos** y si la aplicación necesita transacciones ACID.
- **Atomicidad**: significa que una transacción se trata como una sola unidad: o se ejecutan correctamente todas sus operaciones, o no se aplica ninguna. Esto evita estados intermedios o parciales, por ejemplo cuando una operación depende de varias escrituras que deben completarse juntas.
- **Consistencia**: implica que cada transacción lleva a la base desde un estado válido hacia otro estado válido, respetando las reglas e integridad definidas. Es decir, después de una operación, los datos no deben quedar contradictorios ni violar restricciones del sistema.
- **Aislación**: asegura que varias transacciones ejecutándose al mismo tiempo no se interfieran entre sí. Cada una debe comportarse como si estuviera corriendo sola, para evitar lecturas o escrituras incoherentes por concurrencia.
- **Durabilidad**: significa que, una vez que una transacción fue confirmada, sus cambios quedan almacenados de manera permanente, incluso si después ocurre una falla del sistema.

Luego, es importante decidir qué dos aspectos del **Teorema CAP** se escogerán para la Base de Datos. El teorema CAP dice que en un sistema distribuido no se pueden garantizar al mismo tiempo estas tres propiedades cuando hay problemas de comunicación entre nodos. En una situación de partición de red, hay que priorizar solo dos de las tres.
- **Consistencia**: significa que todos los nodos ven la misma información al mismo tiempo. Si un dato cambia, cualquier lectura posterior debería devolver ya ese valor actualizado, sin importar desde qué nodo se consulte.
- **Availability**: significa que el sistema siempre responde a las solicitudes. Esa respuesta puede llegar aunque no necesariamente contenga la versión más reciente de los datos, pero el sistema no queda bloqueado ni deja de contestar.
- **Partition Tolerance**: significa que el sistema sigue funcionando aunque haya fallas de red o pérdida de comunicación entre algunos nodos. Es decir, aunque una parte del sistema no pueda hablar con otra, el sistema distribuido intenta seguir operando.

![[Pasted image 20260629121326.png|center|225]]

Otro factor importante al elegir una base de datos es el **conocimiento y soporte disponible**. No alcanza con que una tecnología sea muy buena en teoría si el equipo no tiene experiencia usándola o manteniéndola en producción. Primero, conviene evaluar qué expertise tiene el equipo. Si ya domina cierto tipo de base de datos, eso reduce errores, acelera el desarrollo y facilita la operación diaria. Elegir una tecnología completamente distinta puede agregar complejidad innecesaria.

También hay que considerar la **curva de aprendizaje**. Si la base elegida es nueva para el equipo, hay que pensar cuánto tiempo va a tomar aprenderla bien, modelar correctamente los datos, optimizar consultas y resolver problemas. A veces una opción técnicamente ideal no es la más conveniente si el costo de adopción es muy alto.

Por último, importa mucho el **soporte técnico y el ecosistema**. Es decir, si existen buenas herramientas, documentación, comunidad, soporte del proveedor y facilidad para encontrar ayuda ante problemas. En la práctica, una base de datos no se elige solo por sus características técnicas, sino también por qué tan bien el equipo puede implementarla, operarla y sostenerla en el tiempo.

## Bases de Datos Relacionales

Las **bases de datos relacionales** se caracterizan por almacenar la información en tablas con filas y columnas, donde cada tabla representa una entidad y puede vincularse con otras mediante claves. Su punto fuerte es que permiten trabajar con datos bien estructurados y mantener integridad referencial, es decir, asegurar que las relaciones entre tablas sean válidas y consistentes.

También se destacan por soportar transacciones ACID, lo que las hace muy adecuadas cuando importa que las operaciones sean confiables, consistentes y permanentes. Esto es clave en sistemas donde no puede haber errores parciales, duplicaciones o inconsistencias en los datos.

Por eso suelen usarse en sistemas de inventario, CRM y en general en sistemas transaccionales, donde hay muchas operaciones de alta importancia sobre datos estructurados y relacionados entre sí.

---
## Amazon RDS

**Amazon RDS** es el servicio administrado de AWS para bases de datos relacionales. Su objetivo es simplificar el despliegue y la operación de motores conocidos, para que el equipo no tenga que encargarse de toda la infraestructura y mantenimiento manual.

La idea principal es que, en vez de instalar y administrar una base relacional por cuenta propia, AWS se ocupa de muchas tareas operativas, como el aprovisionamiento, los backups, los parches, parte de la alta disponibilidad y varias tareas de mantenimiento. Así, el usuario puede concentrarse más en el modelo de datos y en la aplicación, y menos en administrar servidores.
![[Pasted image 20260629121615.png|center|443]]

RDS soporta varios motores relacionales populares, como MySQL, PostgreSQL, MariaDB, Oracle, SQL Server y también opciones de la familia Aurora. Eso permite elegir el motor según las necesidades del sistema, pero manteniendo la comodidad de un servicio administrado.

En RDS, una forma de escalar es mediante **read replicas**, que son copias de sólo lectura de la base principal. La aplicación sigue haciendo las operaciones de escritura sobre la instancia principal, pero puede enviar parte de las lecturas a esas réplicas para repartir la carga. RDS permite hasta 5 read replicas. Algunos casos de uso son:
- Data warehousing
- Disaster recovery
- Escalabilidad

Esto sirve para mejorar la performance, porque evita que todas las consultas recaigan sobre un único nodo, y también puede ayudar en escenarios de disaster recovery o análisis, donde conviene tener copias disponibles para consulta. AWS permite varias réplicas de lectura, lo que da más margen para escalar cuando hay muchas consultas de lectura.
![[Pasted image 20260629121726.png|center|207]]

>[!TIP] Ventajas y Desventajas
>Por un lado, aumenta el rendimiento al distribuir lecturas; por otro, mejora la disponibilidad operativa, porque hay más de una instancia con los datos replicados. Sin embargo, la replicación suele ser asíncrona, así que las réplicas pueden ir un poco atrasadas respecto de la base principal.
>
>Por eso, la desventaja es que no ofrecen consistencia fuerte. Si se escribe un dato en la instancia principal y enseguida se lee desde una réplica, podría no verse todavía el cambio más reciente. En resumen, las read replicas son muy útiles para escalar lecturas, pero no deben pensarse como una copia perfectamente sincronizada en tiempo real.

**RDS Multi-AZ** se usa para mejorar la alta disponibilidad de una base de datos. La idea es que no exista una sola instancia principal aislada, sino que haya una copia de respaldo en otra Availability Zone dentro de la misma región. Así, si falla la infraestructura de la instancia principal, AWS puede hacer un failover automático hacia la instancia secundaria. Se encuentra preparada para asistir en un caso de emergencia, pero no está operando.

La replicación entre la principal y la standby se hace de forma sincrónica, por lo que la copia de respaldo se mantiene mucho más alineada que una read replica. Por eso Multi-AZ no está pensado principalmente para escalar lecturas, sino para asegurar continuidad del servicio ante fallas.

Otra ventaja es que ayuda a reducir el impacto de tareas de mantenimiento y backups, ya que varias de esas operaciones pueden apoyarse en la instancia secundaria para disminuir la latencia o la interrupción percibida sobre la principal.
![[Pasted image 20260629121919.png|center|273]]

Los **snapshots de RDS** son copias de respaldo de la base de datos que sirven para restaurar su estado en caso de pérdida, error o necesidad de recuperación. La idea es guardar una imagen de la base en un momento determinado para poder recrearla más adelante.

En un despliegue con Multi-AZ, la base principal replica de forma sincrónica hacia una secundaria, y a partir de esa infraestructura RDS puede generar snapshots y conservar también logs de transacciones. Esos respaldos se almacenan en S3 administrado por Amazon RDS, no en un bucket que uno maneje directamente.

Además, esos snapshots pueden copiarse a otra región, lo cual es útil para estrategias de recuperación ante desastres. Así, si hubiera un problema grande en una región completa, existe una copia del respaldo en otra ubicación desde la cual se podría restaurar la base.
![[Pasted image 20260629121956.png|center|491]]

**RDS Proxy** es un intermediario entre la aplicación y la base de datos RDS. En vez de que cada cliente o cada función Lambda abra su propia conexión directa a la base, las conexiones se hacen contra el proxy, y el proxy administra un pool de conexiones hacia la base real.

Esto es especialmente útil en arquitecturas serverless, donde muchas ejecuciones de Lambda pueden arrancar al mismo tiempo. Si cada una abriera una conexión propia, la base podría saturarse rápidamente. Con RDS Proxy, esas conexiones se reutilizan, se reduce la cantidad de conexiones simultáneas reales sobre la base y mejora la estabilidad. Esto se produce dado que los puertos de las Bases de Datos son limitados.

>[!TIP] Ventaja Principal
>La ventaja principal es entonces el connection pooling: menos sobrecarga, mejor escalabilidad y menor riesgo de agotar conexiones. Además, simplifica la conectividad entre Lambda y RDS, porque no hace falta que cada ejecución gestione una conexión nueva completa contra la base.

Para **securizar** RDS, lo primero es aislarlo en red. Lo recomendable es ejecutar la base dentro de una VPC y, preferentemente, en una subred privada, de modo que no quede expuesta directamente a Internet. Después, el acceso se controla con security groups, definiendo exactamente qué aplicaciones, instancias o servicios pueden conectarse y por qué puerto. La idea es seguir el principio de mínimo privilegio, permitiendo solo lo necesario y dejando denegado por defecto todo lo demás.

También puede integrarse con IAM para controlar autenticación y permisos en ciertos escenarios, agregando una capa más de seguridad sobre quién puede acceder y cómo. A eso se suma el soporte de cifrado, tanto en tránsito, para proteger los datos mientras viajan por la red, como en reposo, para protegerlos cuando están almacenados.

## Aurora

**Amazon Aurora** es la base de datos relacional de AWS diseñada para ofrecer más rendimiento, disponibilidad y tolerancia a fallos que una base relacional administrada tradicional, manteniendo compatibilidad con MySQL o PostgreSQL. Es un servicio fully managed, así que AWS se encarga de gran parte de la operación, igual que con RDS. 

Una de sus ideas centrales es que combina la compatibilidad de motores conocidos con una arquitectura propia de AWS. Según AWS, puede ofrecer hasta 5 veces el throughput de MySQL y hasta 3 veces el de PostgreSQL en benchmarks estándar, y además permite escalar lecturas con hasta 15 réplicas. También está pensado para alta disponibilidad y durabilidad. Aurora replica los datos en 6 copias distribuidas en 3 Availability Zones, lo que le permite soportar fallos de infraestructura con más resiliencia. Además, realiza backup continuo en Amazon S3. En seguridad, se apoya en el aislamiento dentro de una VPC y soporta cifrado en reposo y en tránsito, por lo que puede proteger tanto los datos almacenados como los que circulan por la red.

Aurora no siempre es más barato en precio base, pero puede terminar costando menos que RDS si para lograr el mismo rendimiento RDS necesita más recursos o configuraciones extra. El tema es que Aurora se puede empezar a usar a partir de ciertas instancias de EC2 que son más potentes y por ende más caras. 

**Aurora Serverless v2** es una modalidad de Aurora pensada para aplicaciones cuya carga cambia mucho con el tiempo. En lugar de tener una instancia de base de datos con capacidad fija, el servicio ajusta automáticamente el cómputo y la memoria según la demanda real.

>[!TIP] Ventaja Principal
>La ventaja principal es que escala automáticamente y uno paga por la capacidad efectivamente usada, en vez de dejar recursos sobredimensionados todo el tiempo. Así, no hace falta elegir de antemano un tamaño fijo de servidor para cubrir el peor caso.

Aurora puede funcionar como **Global Database**, lo que significa que una base de datos puede abarcar varias regiones de AWS. En ese esquema, una región actúa como primaria para escrituras y las demás como secundarias, recibiendo replicación cross-region administrada por AWS. Esto permite tener lecturas más cercanas a los usuarios en distintas partes del mundo y también contar con una mejor estrategia de recuperación ante desastres frente a la caída de una región completa. Esto no está disponible en RDS.

## OLAP vs OLTP

Existen dos tipos de cargas de trabajo sobre bases de datos. **OLTP** está pensado para operaciones transaccionales del día a día: insertar, actualizar, borrar o consultar pocos registros rápidamente. Se usa en sistemas como ventas, bancos, inventarios o CRM, donde importan mucho la consistencia y las transacciones ACID.

**OLAP** está pensado para análisis. En vez de registrar operaciones pequeñas, busca leer grandes volúmenes de datos para hacer reportes, métricas, agregaciones y consultas complejas. Se usa en data warehouses, business intelligence y analítica.

---
## Data Warehousing

**Amazon Redshift** es el servicio de data warehouse de AWS. No está pensado para transacciones del día a día, sino para análisis de grandes volúmenes de datos mediante consultas OLAP usando SQL. Es decir, sirve para explorar información histórica, cruzar muchas tablas, calcular métricas y obtener reportes o tableros analíticos. Se tiene como una gran tabla central  (fact) que referencia todas las otras.
![[Pasted image 20260629122637.png|center|542]]

Una característica importante es que usa un **almacenamiento columnar**. En lugar de guardar la información por filas, la organiza por columnas, lo que hace mucho más eficiente leer solo los campos necesarios en consultas analíticas. Por eso Redshift funciona bien cuando se quieren hacer agregaciones, filtros y reportes sobre muchísimos datos.

También es un servicio escalable, porque está diseñado para crecer cuando aumenta el volumen de información o la complejidad de las consultas. La idea es que pueda soportar cargas analíticas grandes sin estar orientado al mismo tipo de uso que una base transaccional como Aurora o RDS.

**Amazon Athena** es un servicio serverless de análisis que permite hacer consultas SQL directamente sobre datos almacenados en S3, sin tener que moverlos a una base de datos tradicional ni administrar infraestructura. La idea principal es que los datos quedan en S3 tal como están, y Athena los consulta aplicando el esquema al momento de leerlos, lo que se conoce como schema on read. Eso lo vuelve muy útil para exploración de datos, consultas puntuales o análisis ad hoc, especialmente cuando no vale la pena cargar toda esa información en un data warehouse.

También sirve mucho para consultar logs, archivos históricos o datasets que solo se usan ocasionalmente. En vez de mantener una base dedicada para datos que casi no se consultan, se los deja en S3 y se los analiza cuando hace falta. Además, los resultados pueden integrarse o enviarse a otros servicios de AWS.

En cuanto al modelado, en una base transaccional suele haber muchas tablas normalizadas y relaciones más detalladas para operar el negocio día a día. En Redshift, en cambio, es común usar esquemas analíticos como estrella o snowflake, con una tabla de hechos central y varias tablas de dimensiones alrededor. Eso facilita consultas de negocio, métricas y análisis.

## Data Migration Service

**AWS Database Migration Service (DMS)** es el servicio que se usa para migrar datos desde una base de datos origen hacia un destino en AWS, o incluso entre distintos motores y ubicaciones. La idea es facilitar el traslado de información sin tener que exportar e importar todo manualmente.

Puede usarse en una **migración homogénea**, cuando el motor de origen y destino es el mismo, por ejemplo de una base Oracle on-premise hacia RDS for Oracle. En ese caso, lo que cambia es principalmente el lugar donde corre la base, no tanto la tecnología.

También puede usarse en una **migración heterogénea**, donde el motor cambia, por ejemplo de MySQL a Aurora. Ahí la migración no solo mueve los datos, sino que acompaña un cambio de plataforma o de motor de base de datos.

Además, DMS sirve para migrar entre bases alojadas on-premise, en EC2, en RDS o incluso hacia S3, lo que lo vuelve bastante flexible. En resumen, DMS es la herramienta de AWS para mover datos entre bases de datos y entornos distintos, ya sea manteniendo el mismo motor o cambiándolo.
![[Pasted image 20260629122813.png|center|455]]

## DynamoDB

**DynamoDB** es una base de datos NoSQL de tipo key-value/document, totalmente administrada por AWS. Es serverless, lo que significa que no hay que administrar servidores, sistemas operativos ni instancias de base de datos: uno define la tabla y AWS se encarga de la infraestructura.

No es una base relacional, así que no trabaja con tablas relacionadas mediante joins como una base SQL tradicional. En cambio, está pensada para acceso muy rápido y escalable a datos usando una clave primaria, y opcionalmente una sort key para organizar mejor los registros dentro de esa misma partición.
- **Partition Key**: indica en qué partición se guarda la información. Una partición podría ser, por ejemplo, el país.
- **Sort Key**: permite ordenar los elementos dentro de una misma partición y realizar búsquedas por rangos.

También es un servicio regional, es decir, la tabla vive en una región de AWS determinada. Desde ahí puede escalar automáticamente y soportar grandes volúmenes de lectura y escritura con muy poca administración manual.

Dynamo tiene dos flavours para las escrituras:
- Con **eventual consistency**, después de escribir un dato puede pasar un pequeño intervalo hasta que ese cambio se refleje en todas las copias. Entonces, si justo se hace una lectura enseguida después de la escritura, existe la posibilidad de que todavía se obtenga una versión vieja o que parezca que el dato aún no está. La base va convergiendo y, pasado ese pequeño retraso, todas las réplicas terminan viendo el mismo valor.
- Con **strong consistency**, en cambio, una lectura hecha después de una escritura devuelve el valor más reciente confirmado. Es decir, cuando se consulta, DynamoDB se asegura de mostrar el estado actualizado del dato y no una copia atrasada.

DynamoDB está pensado para manejar un gran volumen de datos y una cantidad enorme de requests concurrentes con muy baja latencia. La idea es que, detrás de escena, los datos se reparten entre particiones y nodos de almacenamiento, por lo que el servicio puede escalar horizontalmente a gran escala sin que el usuario tenga que administrar esa distribución manualmente.
![[Pasted image 20260629122920.png|center|371]]
También se sugiere que no todas las operaciones tienen el mismo costo en latencia. Operaciones simples como Get o Put suelen ser más rápidas, mientras que operaciones transaccionales como TransactWriteItems o TransactGetItems agregan más coordinación y por eso suelen tener mayor latencia.

En **seguridad**, DynamoDB se protege usando IAM roles y policies, aplicando el principio de menor privilegio para que cada aplicación solo pueda hacer lo estrictamente necesario. También puede usarse mediante VPC Endpoints, evitando salir a Internet pública, y soporta cifrado en tránsito y en reposo para proteger los datos tanto cuando viajan como cuando están almacenados.

DynamoDB ofrece **alta disponibilidad** de forma nativa porque AWS se encarga automáticamente de la replicación entre múltiples zonas de disponibilidad dentro de una misma región. Eso significa que, aunque falle parte de la infraestructura, la tabla puede seguir operando sin que el usuario tenga que administrar manualmente réplicas o failover.

Además, si se necesita disponibilidad a nivel global, existen las **Global Tables**, que permiten replicar la misma tabla entre distintas regiones de AWS. Así, una aplicación puede tener datos cercanos a usuarios en varias partes del mundo y también mejorar su estrategia de recuperación ante desastres regionales.

En cuanto a respaldo, DynamoDB ofrece dos mecanismos principales. Uno es **On-Demand Backup**, que crea copias bajo demanda y resulta útil para archivado o retención más prolongada. El otro es **Point-In-Time Recovery (PITR)**, que permite restaurar la tabla a un momento específico dentro de una ventana de tiempo reciente, lo cual sirve mucho para recuperarse de borrados o cambios accidentales.

Los elementos básicos son tablas, ítems y atributos. La tabla es el contenedor principal, los ítems serían los registros y los atributos son los campos de cada ítem. A diferencia de una base relacional, no hay un esquema rígido que obligue a que todos los ítems tengan exactamente los mismos atributos.

Lo único que sí es obligatorio definir es la **primary key**, porque es la que identifica y organiza los datos dentro de la tabla. Esa clave puede ser simple, cuando está formada por un único atributo, o compuesta, cuando combina una partition key con una **sort key**. La simple alcanza para identificar cada ítem, mientras que la compuesta además permite agrupar ítems bajo una misma partición y ordenarlos dentro de ella.

La `SK` puede armarse con varias partes concatenadas. Por ejemplo, en una tabla Pedidos:
- `PK = CLIENTE#123`
- `SK = PEDIDO#2024-06-01#0001`

Acá la `PK` sigue agrupando todo lo del cliente 123, y la `SK` tiene más información: el tipo de dato (PEDIDO), la fecha y el identificador del pedido. Eso sirve porque después se pueden buscar cosas como:
- todos los ítems del cliente 123
- todos los pedidos del cliente 123
- todos los pedidos del cliente 123 a partir de cierta fecha

Esta granularización en la `SK` tiene que ir de lo más grande a lo más chico. No podríamos tener `BARRIO#PROVINCIA`. También aparece el límite de tamaño del ítem, que en DynamoDB es de 400 KB. Entonces, cada registro puede ser flexible en su estructura, pero no puede superar ese tamaño máximo.

En DynamoDB hay distintas operaciones según cómo se quiera acceder o modificar los datos. `Get`, `Put`, `Update` y `Delete` son las operaciones básicas sobre un ítem individual. `Get` trae un registro puntual a partir de su clave, `Put` inserta uno nuevo, `Update` modifica atributos de uno existente y `Delete` lo elimina.

`Query` se usa cuando se conoce la partition key y se quiere traer uno o varios items relacionados, opcionalmente filtrando también por la sort key. Es una operación eficiente porque busca dentro de una partición concreta. `Scan`, en cambio, recorre toda la tabla o un índice completo buscando coincidencias. Es mucho más costosa y menos eficiente, porque no parte de una clave específica sino que inspecciona todos los datos. El problema es que Dynamo cobra por cuántas filas leyó para devolver las que retornó. 

`BatchGetItems` y `BatchWriteItems` permiten agrupar varias lecturas o escrituras en una sola llamada, lo que mejora eficiencia cuando hay que operar sobre muchos ítems a la vez. Por último, `TransactWriteItems` y `TransactGetItems` agregan soporte transaccional. Sirven cuando querés leer o escribir varios ítems garantizando consistencia tipo transacción, por ejemplo asegurando que varias operaciones se hagan todas juntas o ninguna.

Podemos comparar las operaciones compuestas:

|     **Feature**      |     **Bulk (Batch)**     |       **Transactional**        |
| :------------------: | :----------------------: | :----------------------------: |
|       **API**        | `BatchGet`, `BatchWrite` | `TransactGet`, `TransactWrite` |
|    **Atomicity**     |           ❌ No           |             ✅ Yes              |
|    **Max items**     |    100 get, 25 write     |               25               |
| **Tables supported** |         Multiple         |            Multiple            |
|  **Error handling**  |     Partial success      |         All or nothing         |
|     **Use case**     |    Speed & efficiency    |         Data integrity         |
Un **Local Secondary Index (LSI)** es un índice secundario de DynamoDB que mantiene la misma partition key que la tabla principal, pero permite usar una sort key diferente. Eso sirve para consultar los mismos datos con otro criterio de ordenamiento dentro de una misma partición. La restricción importante es que solo se puede crear al momento de crear la tabla; después no se puede agregar. La idea es que, si ya sabés desde el diseño que vas a necesitar otra forma de ordenar o consultar los items bajo una misma partition key, definís un LSI desde el principio.

Un **Global Secondary Index (GSI)**, es un índice secundario de DynamoDB que permite consultar la misma información usando otra combinación de clave distinta a la de la tabla principal. A diferencia del LSI, el GSI sí puede crearse después de haber creado la tabla. Además, funciona casi como si fuera una vista indexada separada de los datos, con su propia partition key y opcionalmente su propia sort key. Eso permite acceder a los items con otros patrones de consulta que la tabla original no soportaba bien.

**Single Table Design** en DynamoDB es una forma de modelar datos donde, en vez de separar cada entidad en tablas distintas, se guarda todo lo relacionado en una sola tabla, diseñando la PK y la SK para que una sola consulta traiga juntos los datos que la aplicación necesita.
![[Pasted image 20260629123604.png|center|569]]

Esto hace que el acceso sea más eficiente, porque DynamoDB está optimizado para leer por clave, no para hacer joins como una base relacional. Entonces, en vez de pensar primero en entidades separadas, se piensa primero en los **patrones de acceso**: qué quiero consultar y cómo hago para que eso salga con la menor cantidad de lecturas posible.

## Otras Bases de Datos

**Amazon DocumentDB** es la base de datos documental administrada de AWS. Está pensada para trabajar con información en formato tipo JSON, con una estructura más flexible que una base relacional tradicional, y es compatible con cargas de trabajo que usan APIs y herramientas de MongoDB.

Al ser fully managed, AWS se encarga de gran parte de la operación de la base. Además, está diseñado para ofrecer alto rendimiento, baja latencia y alta disponibilidad, por lo que puede usarse en aplicaciones que necesitan escalar sin administrar toda la infraestructura manualmente.

Otra idea importante es el **auto-scaling del almacenamiento**. AWS indica que el storage crece automáticamente según la necesidad del clúster, sin tener que aprovisionarlo de antemano. Hoy ese almacenamiento puede crecer hasta 128 TiB en clústeres basados en instancias, y mucho más en elastic clusters, así que el “hasta 64 TiB” de la slide quedó viejo.

**Amazon ElastiCache** es el servicio administrado de AWS para trabajar con cachés en memoria. Su objetivo es guardar datos que se consultan muy seguido en un sistema mucho más rápido que una base de datos en disco, para que la aplicación responda en tiempos muy bajos.

La idea central es el rápido acceso. En vez de ir cada vez a la base principal, la aplicación puede leer ciertos datos desde la memoria, que es mucho más veloz. Por eso se usa para caché de consultas frecuentes, sesiones de usuario, rankings, contadores o datos temporales que necesitan responder casi instantáneamente.

A cambio de esa velocidad aparece el trade-off de durabilidad. Como está orientado a memoria y rendimiento, no está pensado como reemplazo de una base de datos persistente principal, sino como complemento. Es decir, prioriza rapidez por encima de la permanencia absoluta del dato. También es un servicio fully managed, así que AWS se encarga de gran parte de la administración de la infraestructura. Además, puede escalar para soportar muchas lecturas, más memoria y más carga, manteniendo un rendimiento alto y constante.

Cuando los datos están altamente conectados, lo más importante no es solo guardar entidades aisladas, sino entender cómo se relacionan entre sí. En esos casos conviene un **modelo de grafos**, donde cada nodo representa una entidad —por ejemplo una persona, un producto o una cuenta— y cada arista representa una relación, como amistad, compra, dependencia o transferencia. Este tipo de modelado es útil en redes sociales, porque permite recorrer relaciones entre usuarios de manera natural, por ejemplo amigos de amigos. También sirve en motores de recomendación, donde interesa descubrir conexiones entre usuarios, gustos, productos o comportamientos similares.

En grafos de conocimiento, el objetivo es representar entidades y sus vínculos para poder consultar información conectada de forma inteligente. En detección de fraude, ayuda a encontrar patrones sospechosos entre cuentas, dispositivos, pagos o identidades aparentemente separadas pero relacionadas. En ciencias de la vida y en redes informáticas, también es muy útil porque muchas veces el problema central consiste justamente en analizar interacciones, dependencias y caminos entre elementos.

**Amazon QuickSight** es la herramienta de business intelligence (BI) de AWS para conectar datos, analizarlos y armar visualizaciones y dashboards interactivos. Sirve para transformar datos crudos en gráficos, métricas e insights que después se pueden compartir con otras personas de la organización. AWS además lo presenta hoy como el componente de visualización y análisis dentro de Amazon Quick, aunque QuickSight sigue existiendo como pieza central y mantiene sus funciones de BI.

La idea práctica es esta: se conecta QuickSight a la fuentes de datos, se prepara datasets, se construye análisis y luego se los publica como dashboards. Esos dashboards pueden compartirse con usuarios, incrustarse en aplicaciones y consumirse incluso desde el celular. También soporta seguridad empresarial, control de acceso por roles, auditoría con CloudTrail y modelos de pago por uso para lectores de dashboards.
