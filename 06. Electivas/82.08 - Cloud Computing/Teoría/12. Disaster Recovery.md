## Definiciones

Un **desastre** puede ser alguna de las siguientes opciones:
- Corrupción de una base de datos.
- Colapso de servicios de cómputo.
- Pérdida de conexión con servidores propios o externos.
- Caída en la infraestructura donde corren nuestros servicios.

Se pueden deber a grandes volúmenes de información, ataques informáticos, problemas con proveedores de servicios (internet, luz, servicios externos, etc.), desastres climáticos, equipos deficientes o errores humanos.

**Disaster recovery** se asocia al conjunto de estrategias, políticas y herramientas diseñadas para restaurar el servicio a la normalidad, ante uno de estos eventos. Para definir qué medidas tomar se definen un RTO y un RPO.
- **RTO - Recovery Time Objective**: Tiempo máximo tolerable que puede estar un sistema o servicio fuera de línea tras un incidente, antes de que cause un impacto inaceptable al negocio.
- **RPO - Recovery Point Objective**: Cantidad máxima de información que se puede perder (medida en tiempo) sin afectar gravemente al negocio.

## Estrategias

La primera estrategia es **Cold Standby**, que consiste en tener un sitio alternativo preparado pero sin infraestructura activa. No hay servicios corriendo ni datos en tiempo real. Todo debe activarse y restaurarse tras el desastre. Se activan servidores, se restauran respaldos y se configuran servicios después del evento. Es la opción más barata, pero tanto RTO como RPO van a ser muy altos.

Otra estrategia es **Pilot Light**, que consiste en una versión mínima funcional del entorno principal, que se mantiene encendida con los componentes esenciales. Los servicios críticos están corriendo, aunque en un estado de bajo consumo. En caso de desastre, se encienden o escalan los demás componentes para restaurar el servicio completo. Si bien es una opción barata, el tiempo de recuperación suele ser alto.

**Warm Standby** consiste en un entorno parcialmente activo que mantiene actualizados los datos clave (como bases de datos replicadas) y tiene servidores en modo reducido pero listos para escalar. Esta estrategia implica:
- Sincronización constante de datos importantes.
- Algunos servicios están disponibles o pueden encenderse rápidamente.
- Se requiere un escalamiento moderado para tener el entorno completo activo.

>[!INFO] Balance
>Es una opción con un buen balance entre costos moderados y tiempos de recuperación aceptables para servicios no críticos. Es un balance entre el tiempo que tardo en recuperarme versus el costo.

La estrategia de **Hot Standby** consiste en una réplica completa y constantemente sincronizada del entorno productivo, siempre activa y lista para recibir tráfico inmediatamente. Implica:
- Todo el entorno (aplicaciones, datos, red) está corriendo y sincronizado.
- El tráfico puede ser redirigido de forma automática (failover) o manual.
- Si bien es una alternativa cara pero es la única que ofrecen RPO y RTO casi nulos.

Por último, **Multi Site** consiste en tener dos o más entornos totalmente activos y balanceados, recibiendo tráfico al mismo tiempo. Cada sitio puede asumir el 100% de la carga si el otro falla.
- Balanceo geográfico o a nivel de DNS.
- Alta redundancia y sincronización en tiempo real.

>[!WARNING] Tradeoff
>Ofrece alta disponibilidad y resiliencia total, pero la complejidad y el costo son muy altos.

## Servicios Específicos

**AWS Backup** sirve para automatizar y centralizar los respaldos de datos en servicios de AWS y en entornos on premises, garantizando su recuperación ante fallos o desastres. Es totalmente administrado y automatiza copias de seguridad de datos. Es compatible con EBS, RDS, DynamoDB, EFS, FSx, S3 y más. Permite definir políticas de backup (frecuencia, retención, ciclos de vida) y soporta backups entre regiones y cuentas, útil para estrategias multi-región. Incluye cifrado, auditoría y cumplimiento normativo (HIPAA, ISO, etc.). Integración con AWS Organizations para gestión centralizada de backups.

**AWS Data Migration Service (DMS)** es un servicio que se utiliza para migrar o replicar bases de datos entre entornos (on-premises a AWS o entre servicios de AWS), con mínimo downtime, ideal para mantener bases sincronizadas en DR. Permite replicación continua o migración única de bases de datos y es compatible con motores como Aurora, RDS, MySQL, PostgreSQL, Oracle, SQL Server, MongoDB, entre otros. Realiza la migración mientras la base original sigue activa. Útil para sincronizar bases en sitios secundarios (por ejemplo, entre regiones AWS) e ideal para Pilot Light o Warm Standby, donde se requiere mantener datos actualizados.
![[Pasted image 20260629173432.png|center|82]]

**AWS Elastic Disaster Recovery (DRS)** sirve para replicar continuamente servidores físicos, virtuales o en la nube hacia AWS, permitiendo una recuperación rápida tras un desastre con mínima pérdida de datos (RPO/RTO bajos). Replica en tiempo real máquinas completas (Windows/Linux) desde on-premises o nubes externas. Ofrece failover y failback automáticos hacia/desde AWS y mantiene una copia actualizada de los sistemas productivos en una región secundaria. Permite probar planes de recuperación sin afectar la operación. Integra métricas de RPO (Recovery Point Objective) y RTO (Recovery Time Objective). Es ideal para escenarios Warm o Hot Standby, donde la continuidad es crítica.
