## Necesidad de IaC

Pensemos en cómo sería tener que mantener e iterar lo que hicimos para el TP2 en una empresa ¿Qué problemas surgen? ¿Es viable esto para una empresa grande? No, claramente no escala. Se hace difícil otorgar distintos permisos a distintos usuarios, para que no puedan modificar todo.

Necesitamos una configuración escalable, robusta, dinámica y lograr inmutabilidad.
- Robusta: permite testing, versionado, control de cambios, consistencia, automatización y eliminación de errores humanos
- Escalable: puedo replicar, crear y modificar entornos de forma rápida y consistente. Podemos agregar recursos rápido sin tener que configurar manualmente los componentes.
- Dinámica: porque se puede modificar mucho más rápido, hacer rollback, replicar, etc.

Que algo sea inmutable significa que no cambia. En este contexto, significa que para llevar a cabo los cambios, se deploya un nuevo servidor como queremos y luego se migra a ese. No se realizan cambios directamente en el servidor corriendo sin dejar registro. Lo que tiene de bueno, es que todo es reproducible, no como en el caso que un desarrollador se metió e hizo cambios. El rollback es también mucho más fácil, ya que simplemente debemos volver a la versión anterior. No tenemos configuration drift, que significa que pensamos que hay algo deployado y en realidad hay otra cosa.

## Definición

**Infrastructure as Code** consiste en utilizar código para automatizar la administración de infraestructura. Usando archivos de configuración vamos a definir el estado en el
que queramos que esté nuestra infraestructura. Esto es mucho más útil hoy en día con los agentes de programación, ya que son mucho mejores en código que manejando una UI.

Nos va a proveer:
- Reconfigurabilidad: todo es más fácil de cambiar en masa, como por ejemplo pasar de t2.micro a t3.micro en un montón de instancias EC2.
- Reusabilidad
- Distribución: Se puede colaborar con el equipo aunque no tengan todos los mismos accesos.

Lo que vamos a usar como código para la configuración debe ser **idempotente**, es decir que aunque hagamos algo muchas veces, debe realizar siempre lo mismo. Por ejemplo, si se envía 5 veces la instrucción de cambiar una configuración, se debe realizar una única vez. No debe crear dos veces cosas.

El **approach declarativo**, se le indica lo que se quiere. Cómo lo hace depende del framework, sólo interesa el resultado final. En el approach imperativo, se explican exactamente los pasos que se quieren tener.

## Ventajas

La primera ventaja es la *automatización* y *velocidad*, ya que provee aprovisionamiento rápido y repetible de entornos. Reducción drástica del tiempo de despliegue. Esto es cierto para cambios grandes, porque por ejemplo cambiar únicamente un tag es más pesado con este enfoque.

Otra ventaja es la *consistencia* y *estandarización*, ya que elimina el “configuration drift”, entornos idénticos reduciendo problemas de “en mi compu anda”. Esto es fundamental en el TP3, ya que en la evaluación se deberá correr directamente a través de una github action, ni siquiera en la computadora de un docente.

Provee además *control de versiones*, dado que se versiona la infraestructura como cualquier otro código con git. Historial de cambios, rollbacks sencillos, colaboración mejorada. También brinda una reducción de costos, ya que trae una optimización de recursos al poder crear y destruir entornos bajo demanda, menos errores manuales.

IaC trae también *escalabilidad* y *reusabilidad*, dada la facilidad de escalar la infraestructura. Aporta componentes reutilizables (módulos) para diferentes proyectos. Además, se genera una mejora en la seguridad mediante las políticas de seguridad definidas como código, auditables y replicables, sumado a la integración con herramientas de análisis estático.

Por último, IaC aporta *documentación viva*, ya que el código es la fuente de verdad de la infraestructura, sirviendo como documentación actualizada.

## Herramientas

El **aprovisionamiento** se enfoca en crear y definir la infraestructura base desde cero. Es decir, aquí es donde uno describe qué recursos quiere en la nube: máquinas virtuales, redes, bases de datos, balanceadores, etc. Herramientas como Terraform o CloudFormation permiten escribir esa infraestructura como código, de modo que se puede versionar, repetir y automatizar. En esta capa todavía no se entra en cómo se configura el software dentro de esas máquinas, sino simplemente en “qué infraestructura existe”.

Luego aparece la **gestión de configuración**, que trabaja sobre infraestructura ya creada. En este nivel, el problema cambia: ya no es crear servidores, sino configurarlos. Por ejemplo, instalar paquetes, desplegar aplicaciones, modificar archivos de configuración o asegurar que un servicio esté corriendo. Herramientas como Ansible o Puppet permiten declarar el estado deseado de un sistema y garantizar que los servidores lo cumplan. Es una capa más cercana al sistema operativo y al software. Cada vez es menos relevante, ya que se están utilizando servicios fully managed. 

Finalmente, el tercer enfoque combina lo mejor de ambos mundos mediante **herramientas basadas en SDKs o lenguajes de programación**. En lugar de usar archivos declarativos, se utiliza código en lenguajes como Python o TypeScript para definir la infraestructura. Esto permite mayor flexibilidad, reutilización y lógica más compleja. Herramientas como Pulumi o AWS CDK permiten definir tanto la infraestructura como su configuración usando código tradicional, lo que resulta muy potente para proyectos grandes o equipos de desarrollo.

## Terraform

**Terraform** es una herramienta de software de código abierto para construir, cambiar y versionar infraestructura de forma segura y eficiente. Tiene las siguientes características:
- Agnóstico de la Nube (y otros proveedores): Soporta múltiples proveedores de nube (AWS, Azure, GCP, etc.), así como servicios on-premise (VMware) y SaaS (Datadog, GitHub).
- Lenguaje Declarativo (HCL - HashiCorp Configuration Language): Describe el estado deseado de la infraestructura. Terraform no es un lenguaje, sino que HCL es el que usa terraform para operar.
- Gestión de Estado: Mantiene un archivo de estado (terraform.tfstate) que mapea los recursos del mundo real con la configuración.
- Plan de Ejecución: Permite previsualizar los cambios antes de aplicarlos (terraform plan).
- Grafo de Recursos: Resuelve dependencias entre recursos de forma inteligente.

El flujo de trabajo es:
1. Write (Escribir): Definir la infraestructura en archivos .tf usando HCL.
2. Init (Inicializar): terraform init
	1. Descarga los plugins de los proveedores necesarios.
	2. Configura el backend para el estado (si se usa uno remoto).
3. Plan (Planificar): terraform plan
	1. Compara la configuración actual con el estado almacenado.
	2. Muestra qué se creará, modificará o destruirá.
4. Apply (Aplicar): terraform apply
	1. Ejecuta el plan para alcanzar el estado deseado.
	2. Pide confirmación antes de aplicar.
5. (Opcional) Destroy (Destruir): terraform destroy
	1. Elimina todos los recursos gestionados por la configuración actual.

Los componentes claves son:
- **Proveedores (Providers)**: Plugins que interactúan con las APIs de los servicios (AWS, Azure, Docker, etc.). Es una librería que adapta el código de HCL a lo que pueda tener la API.
- **Recursos (Resources)**: Componentes de infraestructura (VMs, buckets S3, bases de datos).
- **Variables de Entrada (Input Variables)**: Personalizan la configuración.
- **Valores de Salida (Output Values)**: Extraen información de la infraestructura desplegada.
- **Módulos (Modules)**: Contenedores reutilizables de configuraciones de Terraform.

El **state file** (`terraform.tfstate`) es un archivo JSON que Terraform usa para almacenar información sobre la infraestructura gestionada. Mapea los recursos de la configuración a los recursos reales en el proveedor. Contiene metadatos como dependencias de recursos y punteros a la configuración del proveedor. Este archivo no se pushea al repo, primero porque es de texto plano, no se encripta. Tampoco se hace porque pueden surgir inconvenientes de versiones entre dos distintos colaboradores si uno no lo pusheó. Podríamos usar Dynamo y S3. Guardaríamos el archivo en este último, y con la DB armaríamos un lock casero para cuando hay alguien modificándolo. Pero, ¿cuál se crea primero, el Dynamo o el Terraform? Se suelen hacer dos Terraforms, uno muy chiquito para esta funcionalidad que dijimos. 

Formalmente:
- Local (default). Por defecto se almacena en el directorio raíz del proyecto.
	- Riesgo de que múltiples personas apliquen cambios simultáneamente sin conocer el estado actual, llevando a corrupción o pérdida de recursos.
	- No hay control de acceso robusto
	- Dificultad de compartir el estado de forma segura.
	- El archivo puede contener información sensible
- Remoto (backends). Almacenamiento compartido y seguro
	- Colaboración segura permitiendo a equipos trabajar juntos en la misma infraestructura
	- Bloqueo de estado (State locking): Evita que múltiples usuarios ejecuten apply al mismo tiempo, previniendo corrupción.
	- Seguridad: Se puede integrar con mecanismos de encriptación y control de acceso del backend.
	- Versionado: algunos backends permiten versionar el archivo de estado para recuperación.
	- Operaciones remotas: Algunos backends permiten ejecutar terraform remotamente.

Para importar cosas que creamos en la terminal al Terraform, se usa lo que se llama como import. Para ver bien la sintaxis de HCL, usar el siguiente documento: [HCL Syntax](https://drive.google.com/file/d/1sgFAqabF6XG6yg3_J-a2CQjpa9rKcJ6Q/view?usp=sharing)
