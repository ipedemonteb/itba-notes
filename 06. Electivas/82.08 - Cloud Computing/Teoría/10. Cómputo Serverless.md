## Serverless

Hasta ahora vimos Amazon EC2, que me permite tener mucho control sobre la infraestructura desplegada.
![[Pasted image 20260629165815.png|center|389]]

Recordemos que una instancia EC2 nos permite elegir el tipo de instancia a desplegar según el caso de uso y el tipo de contrato según nuestra demanda. No nos teníamos que ocupar de comprar hardware, mantenerlo y asegurarnos de su integridad física, pero aún es nuestra responsabilidad gran parte del mantenimiento de la máquina virtual: networking, actualizaciones, seguridad.

**Serverless** es una forma de construir y correr aplicaciones y servicios sin tener que preocuparnos sobre los servidores en los que estos corren (FaaS). Esto no quiere decir que nuestra aplicación no está corriendo en un servidor, sino que AWS se ocupa del aprovisionamiento de capacidad, parches de seguridad, mantenimiento del sistema operativo, etc. 

Vamos a tener:
- **Low Management**: AWS se encarga de proveer la infraestructura necesaria.
- **Scalability**: AWS se encarga de escalar automáticamente para cumplir la demanda.
- **Pay per use High**: Solo pago por las llamadas a mi código. Sirve para las etapas tempranas, porque al principio poca gente va a usar la página.
- **High Availability**: AWS se encarga de que mi servicio siempre se encuentre disponible.

De esta forma, podemos:
1. Concentrarnos en nuestra aplicación
2. Disminuir el total cost of ownership: Por ejemplo, no vamos a necesitar tener a alguien que mantenga la EC2.
3. Emplear arquitecturas de microservicios: Permite salir de una estructura monolítica.

## AWS Lambda

**Lambda** es el servicio estrella de AWS para serverless, y tiene las siguientes características y se caracteriza por ser fully managed. Permite correr código ya sea de forma pre-programada o en respuesta a distintos eventos, teniendo la capacidad de desplegar múltiples copias automáticamente para poder procesar todos los eventos recibidos de forma simultánea.

Además, ofrece soporte para diversos lenguajes como Java, Python, Node.js y Go, operando bajo límites técnicos de 15 minutos como tiempo máximo de duración y 10 GB de memoria máxima. En cuanto a los costos, el modelo es de pago por uso, donde se abona únicamente por la cantidad de requests, la duración de la ejecución y la cantidad de memoria utilizada.

Como sabemos, las lambdas se ejecutan frente a  un evento (trigger), que puede ser un cambio en Dynamo, una subida de un archivo a S3, etc. Con casi todos los servicios hay un evento que pueda disparar esta lambda. AWS busca una máquina virtual muy chica para correr ese código que subimos en un runtime. Una vez que hace lo que tiene que hacer, que puede involucrar llamar a otros servicios de AWS, va a devolver el response, que es el que tienen que devolverse antes de los 15 mins. 

El **cold start** es el tiempo que tarda en inicializarse esta pequeña instancia, y es un problema si tenemos pocos usuarios, ya que la instancia usada se mantiene viva durante un tiempo por si llegan nuevos request. 

>[!INFO] Aislamiento
>Es importante notar que están aisladas en software, no saben de la ejecución de las otras. Entonces, todo lo que tengamos en Lambda debe ser stateless, por lo que no vamos a tener memoria compartida.

![[Pasted image 20260629170134.png|center|464]]

Las partes de una lambda son las siguientes. Los *permissions* nos permite asignarle un role, que en nuestro caso va a ser el del lab. Luego, definimos qué *eventos* la van a disparar, que es lo que vimos antes. Luego se le da el *deployment package*, que involucra tanto el código como las dependencias. Finalmente se incluye la *configuración*. 
![[Pasted image 20260629170203.png|center|491]]

Pensemos en un sistema para que un usuario pueda comprar un pasaje de avión. ¿Qué acciones debe realizar el usuario? Lo pensamos desde el backend:
1. Conseguir vuelos/filtrar vuelos/buscar vuelos
2. Obtener detalles de un vuelo
3. Elegir asiento
4. Datos para la reserva
5. Servicios extra
6. Pagar
7. Confirmación al usuario

En nuestra aplicación, nosotros vamos a definir la lambda. Por ejemplo, podemos hacer que todos estos pasos sean una lambda o que cada una sea una lambda. Incluso, podemos tener sublambdas en cada ítem de acción.

## API Gateway

**API Gateway** es el servicio de AWS que permite crear, publicar, mantener, monitorear y segurizar APIs. Puede soportar desde cientos a miles de pedidos concurrentes y permite manejar trabajos que corran en:
- AWS Lambda
- Amazon EC2
- Cualquier web application

Puede tener múltiples versiones de nuestras APIs y múltiples ambientes, y se paga por la cantidad de request recibidos y la cantidad de información saliente. Brinda manejo de *throttling* (para limitar la cantidad de requests que hacen los usuarios a nuestra API), que se puede hacer a nivel general o a nivel usuario. Es un servicio regional, pero las lambdas pueden vivir en subredes privadas o en la región, y podemos elegir si por ejemplo queremos que accedan a internet o no. En el caso de ser privadas, entonces se puede hacer un API Gateway privado.

## Step Functions

**Step Functions** es un servicio de AWS que nos permite realizar y orquestar múltiples tareas. Es básicamente una máquina de estados para manejar las lambdas. Permite coordinar el llamado de múltiples lambda functions usando workflows visuales. 

Entonces, se definen máquinas de estado que expresan el workflow de la aplicación frente a distintos escenarios. Brinda soporte para manejar errores y timeouts, y permite manejar retries. Además, mantiene el estado de la aplicación (hasta que paso se llegó). Utiliza el Amazon States Language basado en JSON.

## Simple Queue Service (SQS)

Una solución es utilizar una **queue**, que permite almacenar las requests hasta que el cómputo esté listo para procesarlos. 
![[Pasted image 20260629170802.png|center|442]]

- El Producer es quien enviará el mensaje a la queue.
- Un mensaje es una comunicación entre dos componentes de Software.
- El Consumer es quien recibirá y procesará el mensaje.

Los consumidores usan un mecanismo de **poll**, lo que significa que al consumer no le llega un mensaje, sino que tiene que estar constantemente preguntándole a la queue si hay un nuevo mensaje.

La implementación de AWS se conoce como SQS, y es fully managed. Los mensajes son encriptados y guardados hasta ser procesados. Funciona como buffer entre productores y consumidores, y estos usan el mecanismo de polling para obtener los mensajes de la queue. Permite procesamiento asincrónico y ayuda a manejar picos de demanda permitiendo incrementar el número de productores. Brinda sos modos: 
- Standard Queues:
	- At least once delivery. Puedo llegar a tener duplicación de mensajes, aunque no es común. Simplemente no lo pueden garantizar. 
	- Orden Best Effort: No garantiza que los mensajes se procesan en orden.
	- Throughput casi ilimitado.
- FIFO Queues:
	- Exactly once delivery
	- Orden FIFO
	- Throughput alto.

Algunas features de las queues son:
- **Dead-letter queue**: Van los mensajes que los consumers no pudieron procesar
- **Visibility timeout**: Es un tiempo que se da para que, si un consumer está procesando el mensaje, otros no lo puedan ver. Luego, borrarlo de la queue es responsabilidad del consumer. Lo bueno de las lambdas es que esto se implementa automáticamente.
- **Long polling**: La queue tarda en responder al consumer por si aparecen nuevos mensajes. Baja el número de requests.

## Simple Notification Service (SNS)

Ahora, pensemos cómo hacemos para mandarle a muchos consumidores un mismo mensaje. Lo que vamos a hacer, es utilizar la técnica de **Pub-Sub**. Se tienen publishers que publican mensajes al topic, donde no importa si hay subscribers (quienes reciben el mensaje) o no. Este mecanismo se denomina **push**.
![[Pasted image 20260629171156.png|center|438]]

El servicio de Amazon para este mecanismo es **SNS**, y es fully managed. Es un sistema pub-sub altamente disponible y seguro, que usa mecanismo push. Soporta tópicos encriptados. El mensaje se envía una sola vez, sin posibilidad de recall y el orden no está garantizado. Puede mandar Email o Email-JSON, HTTP o HTTPS y SMS, así como mandar mensajes hacia una función Lambda que los procese o hacia una queue de SQS.
