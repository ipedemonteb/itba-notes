## AWS Cost Explorer

**AWS Cost Explorer** es una herramienta dentro de la Consola de Administración de AWS que  permite visualizar, comprender y administrar los costos y uso de AWS a lo largo del tiempo. Cuando activamos la consola y empezamos a utilizar servicios, explorer se activa y empieza a funcionar automáticamente. 

Es un servicio gratuito salvo que se quiera exportar la data, y se cobra U\$S0.01 por *API request*. La información es diaria, pero si se quiere un mayor control, se cobra U\$S0.01 por cada 1.000 registros. Tiene un algoritmo que aprende cómo vamos gastando y nos permite tanto obtener proyecciones como detectar anomalías. 

Trae los siguientes beneficios:
- Visualizar patrones de gasto: Identifica tendencias y qué servicios consumen más.
- Analizar en detalle: Profundiza en los costos usando filtros y agrupaciones.
- Pronosticar gastos futuros: Ayuda a prever costos para una mejor planificación.
- Identificar áreas de ahorro: Detecta anomalías o recursos que podrían optimizarse.

Al abrir Cost Explorer, aparece un gráfico de barras que muestra los costos mensuales de los últimos seis meses. Cada barra representa el costo total del mes, desglosado por servicio (diferentes colores). Debajo del gráfico, una tabla muestra los costos por servicio.

Cost Explorer ofrece varios informes listos para usar, como:
- Costos mensuales por servicio (vista por defecto).
- Costos diarios.
- Uso de Instancias Reservadas (RI).

Se puede cambiar el periodo de tiempo (últimos meses, rango personalizado, etc.) y el tipo de visualización (barras, líneas, tabla).
![[Pasted image 20260629173801.png|center|624]]

Se usa para hacer análisis del gasto que uno tiene, permitiendo además establecer una serie de filtros (además de por servicio como ya vimos). La herramienta más poderosa es taggear los recursos. Con una buena política, se puede filtrar más fácil. Se puede taggear por flujos, por proyecto, por unidades de negocio, etc. 

Entonces, se puede filtrar por:
- Servicio: Ver costos de un servicio específico (ej., Amazon EC2, Amazon S3).
- Cuenta (Linked Account): Si se usa AWS Organizations, se puede filtrar por cuenta miembro.
- Región: Analizar costos por región geográfica.
- Etiquetas (Tags): Filtra por etiquetas que se hayan aplicado a nuestros recursos (ej., proyecto:Alfa, ambiente:Desarrollo).
- Tipo de Uso (Usage Type): Detalles granulares del consumo.

Luego, la **agrupación** permite organizar los datos de diferentes maneras en el gráfico y la tabla. Se puede agrupar por las mismas dimensiones que los filtros.

Algunas funcionalidades adicionales que provee son:
- Pronósticos (Forecast): Cost Explorer puede predecir nuestros gastos futuros basándose en tendencias históricas.
- Guardar Informes: Guarda nuestras configuraciones de filtros y agrupaciones como informes personalizados para acceso rápido.
- Descargar Datos: Exporta los datos en formato CSV.

>[!TIP] Importancia
>Cost Explorer es fundamental para la visibilidad financiera en AWS. Permite tomar decisiones informadas para optimizar costos y mantenerse dentro del presupuesto.

## AWS Budgets

**AWS Budgets** es un servicio que permite establecer presupuestos personalizados para monitorear nuestros costos y uso de AWS. Ayuda a estar informado si los gastos exceden (o se pronostica que excederán) los umbrales que se definieron previamente. Puede tomar acciones, como por ejemplo enviar mails de alerta sobre porcentajes de uso de presupuestos. El objetivo es proporcionar control proactivo sobre tus finanzas en la nube.

Se pueden crear presupuestos de costos basados en el gasto monetario (es el más común), presupuestos de uso basados en la cantidad de uso de un servicio (ej. GB de almacenamiento en S3, horas de ejecución de EC2) y presupuestos de instancias reservadas (RI) y savings plans para monitorear la utilización y cobertura de los compromisos de gasto.

Para utilizarlo, se debe primero definir el **alcance**:
- Nombre del Presupuesto: Un identificador claro (ej. "pres_dev_mes").
- Periodo: Mensual, trimestral, anual.
- Fecha de Inicio: (y opcionalmente, de finalización).
- Monto Presupuestado: La cantidad que no deseas exceder (ej. $500 USD).
- Alcance (Filtros): Puedes aplicar filtros para que el presupuesto cubra toda la cuenta, servicios específicos, cuentas vinculadas, etiquetas, regiones, etc. (similar a Cost Explorer).

Luego, se definen las **alertas** mediante umbrales de notificación:
- Define umbrales para recibir notificaciones por correo electrónico o a través de Amazon Simple Notification Service (SNS).
- Se pueden basar las alertas en el costo actual (ej. alertar cuando se alcance el 80% del monto presupuestado) o en el costo pronosticado (ej. alertar si se prevé que superarás el 100% del presupuesto).

Además de crear alertas, AWS Budget permite configurar acciones, como por ejemplo cortar un servicio si un dev se pasa del umbral establecido. Entonces, estas acciones permiten configurar respuestas automáticas cuando un presupuesto alcanza un umbral específico. Algunos ejemplos son aplicar una política IAM restrictiva a un usuario o rol (ej. denegar el lanzamiento de nuevas instancias EC2), aplicar una Service Control Policy (SCP) a una OU (si usas AWS Organizations) o ejecutar un objetivo de Systems Manager (SSM) Automation.

Los beneficios clave de AWS Budgets son:
- Control Proactivo de Costos: Evita gastos inesperados y sorpresas en la factura.
- Toma de Decisiones Informadas: Las alertas te dan tiempo para reaccionar y ajustar el consumo.
- Fomenta la Responsabilidad: Ayuda a los equipos a ser conscientes de sus gastos.
- Optimización Continua: Facilita la identificación de áreas donde se puede reducir el gasto.

## AWS Organizations

**AWS Organizations** es un servicio gratuito de gestión que permite consolidar múltiples cuentas de AWS en una organización creada y administrada de forma centralizada. Facilita la gestión de políticas, la facturación consolidada y el control de acceso a través de nuestras cuentas. Es fundamental para escalar las cargas de trabajo en AWS de manera organizada y segura.

Típicamente, la estructura que tiene el Organizations es:
- **Cuenta de Administración (Management Account)**: Crea la organización y administra las cuentas miembro. Paga las facturas de todas las cuentas (facturación consolidada). Es importante no desplegar cargas de trabajo acá.
- **Cuentas Miembro (Member Accounts)**: Cuentas estándar de AWS que pertenecen a la organización. Aquí residen las cargas de trabajo.
- **Raíz (Root)**: El contenedor padre para todas las cuentas en la organización.
- **Unidades Organizativas (OUs - Organizational Units)**: Contenedores para agrupar cuentas. Se pueden anidar OUs (hasta 5 niveles).

![[Pasted image 20260629174310.png|center|556]]

El primer beneficio que trae esto, es la facturación consolidada y gestión de costos. Entonces, se recibe una única factura para todas las cuentas, y facilita el seguimiento del gasto agregado. Permite compartir descuentos por volumen (Reserved Instances, Savings Plans) entre cuentas. Luego, AWS Cost Explorer puede mostrar costos por cuenta, OU o etiquetas. Es más fácil asignar costos a proyectos o departamentos.

El segundo beneficio, es la agrupación lógica con Unidades Organizativas (OUs). Estas sirven para agrupar cuentas con funciones, requisitos de seguridad o necesidades operativas similares. NO deben replicar necesariamente la estructura jerárquica de la empresa. Permiten aplicar políticas comunes a grupos de cuentas. Algunos ejemplos de agrupación son:
- Por ambiente: OU-Prod, OU-Dev, OU-Test.
- Por departamento: OU-Marketing, OU-Finanzas.
- Por conformidad: OU-PCI, OU-HIPAA.
- Por función central: OU-Security, OU-Infrastructure

![[Pasted image 20260629174356.png|center|569]]

El tercer beneficio es el Control Centralizado con Políticas de Servicio (SCPs). Las **Service Control Policies (SCPs)** son políticas que gestionan los permisos máximos disponibles para las identidades IAM (usuarios/roles) en las cuentas de una OU o una cuenta individual (excepto la cuenta de administración). Las SCPs NO otorgan permisos. Definen un "techo" o "barrera". Los permisos se siguen concediendo con políticas IAM. Si una SCP deniega una acción, nadie en la cuenta afectada podrá realizarla. Para aplicarse, se adjuntan a la raíz, OUs o cuentas miembro.

Vemos el siguiente caso, donde supongamos que se define una policy que, por ejemplo, permite “crear instancias en Asia”. En el primer caso, se otorga un allow en root y en el OU, y por ende la Account B puede realizar esta creación. En el segundo, se otorga el allow al root, pero no se hace explícitamente en la OU. Entonces, la Account B no va a poder crear instancias en Asia. En el tercer caso se bloquea explícitamente en la OU, y por ende la Account B no puede. 
![[Pasted image 20260629174531.png|center|578]]

Las cuentas sandbox son entornos aislados para que los desarrolladores y equipos experimenten con servicios de AWS. Normalmente desconectadas de redes corporativas y datos sensibles. Se pueden aplicar presupuestos para controlar el gasto. Los beneficios son:
- Fomenta la experimentación sin riesgo para entornos productivos.
- Acelera el aprendizaje y la adopción de nuevos servicios.

Aislamiento de Cuentas:
- Cada cuenta de AWS es una barrera de seguridad y recursos por defecto.
- Un problema en una cuenta (error de configuración, incidente de seguridad) tiene menos probabilidad de afectar a otras cuentas.

Al separar cargas de trabajo (ej. producción vs. desarrollo) en diferentes cuentas y OUs, se limita el "radio de explosión".

**AWS Control Tower** es un servicio que facilita la configuración y gobierno de un entorno AWS multi-cuenta seguro y conforme a las mejores prácticas. ## Cuenta Admin

Es recomendable tener una cuenta de administrador, donde se aplica el principio de mínimo privilegio, que siga los siguientes parámetros:
- Acceso Estrictamente Controlado: Solo un número muy reducido de individuos de confianza. Aplicar principio de mínimo privilegio.
- No desplegar cargas de trabajo. Esta cuenta es solo para administrar la organización.

## Observabilidad

La observabilidad va más allá del simple monitoreo, ya que es la capacidad de entender lo que sucede dentro de un sistema complejo a partir de los datos que genera. Podemos ver una analogía con un auto. No solamente sabemos que funciona, sino que en el tablero podemos ver:
- Velocidad (Métrica)
- Nivel de Combustible (Métrica)
- Alertas del motor (Eventos/Logs)

Los Pilares de Datos en la Nube son:
- Métricas: ¿Cómo está el rendimiento? (Uso de CPU, latencia).
- Logs: ¿Qué ha sucedido? (Registros de errores, accesos).
- Trazas: ¿Cuál fue el camino de una solicitud? (Seguimiento en microservicios).

En AWS, contamos con los siguientes servicios:

|     **Servicio**      |             **Función Principal**             |             **Pregunta que Responde**             |
| :-------------------: | :-------------------------------------------: | :-----------------------------------------------: |
| **Amazon CloudWatch** | Monitoreo de rendimiento y estado operativo.  |      _¿Mi aplicación está funcionando bien?_      |
|  **AWS CloudTrail**   |     Auditoría de actividad de la cuenta.      |          _¿Quién hizo qué en mi cuenta?_          |
|    **AWS Config**     | Cumplimiento de la configuración de recursos. | _¿Mis recursos están configurados correctamente?_ |
**Amazon CloudWatch** es el servicio central de monitoreo y observabilidad de AWS. Recopila datos de monitoreo y operativos en forma de métricas, registros y eventos. Proporciona una vista unificada de los recursos, aplicaciones y servicios que se ejecutan en AWS y en entornos on-premise. Permite visualizar datos, establecer alarmas y tomar acciones automatizadas para mantener las aplicaciones funcionando sin problemas.

Una **métrica** es la base del monitoreo. Para entenderla, necesitamos conocer sus componentes:
- Métrica: La variable que se monitorea a lo largo del tiempo.
	- Ejemplo: CPUUtilization.
- Namespace: Un "contenedor" para las métricas que evita que se mezclen.
	- Ejemplo: AWS/EC2, AWS/Lambda.
- Dimensión: Un par nombre/valor que identifica una métrica de forma única. Es como una etiqueta.
	- Ejemplo: InstanceId = i-1234567890abcdef0.
- Timestamp: La hora asociada a un punto de datos específico.
- Unidad: La unidad de medida de la métrica.
	- Ejemplo: Percent, Bytes, Count.

Cloudwatch sirve también para servidores on premise a través de un agente, lo que es útil para tener un único punto de monitoreo frente a un esquema híbrido por ejemplo.

Es muy común que uno defina una serie de indicadores para visualizar la salubridad del sistema al deployarla. Estos se suelen agrupar en **paneles (dashboards)**, que son vistas personalizables para visualizar tus métricas y alarmas más importantes. Se pueden combinar gráficos de diferentes servicios en una sola pantalla para una vista operativa completa. Existe también un explorador de métriques, que permite navegar por Namespace y Dimensiones para encontrar y graficar cualquier métrica de tus recursos. Se pueden aplicar funciones matemáticas a las métricas para obtener cálculos más avanzados.

El **CloudWatch Logs** centraliza los registros de todos nuestros sistemas (EC2, Lambda, VPC Flow Logs, etc.). El Logs Insights es la herramienta para buscar y analizar interactivamente tus datos de registro. Utiliza un lenguaje de consulta para filtrar, agregar y visualizar la información, como por ejemplo SQL.

CloudWatch tiene también una **consola de alarmas**. Estas permiten responder automáticamente a los cambios en las métricas. El proceso de creación es el siguiente:
Seleccionar la Métrica: Elige la métrica a vigilar (ej. CPUUtilization).
1. Definir la Condición: Establece el umbral (ej. > 80%) y el período (ej. durante 5 minutos consecutivos).
2. Configurar la Acción: ¿Qué sucede cuando la alarma se activa?
3. Enviar una notificación a un tema de Amazon SNS (para email, SMS).
	1. Ejecutar una acción de Auto Scaling.
	2. Reiniciar o detener una instancia EC2.
	3. Estados de la Alarma: OK, ALARM, INSUFFICIENT_DATA.

CloudWatch combina una capa gratuita con un modelo de pago por uso:

| **Componente** | **Se cobra por...**                                                                     |
| -------------- | --------------------------------------------------------------------------------------- |
| **Métricas**   | Número de métricas personalizadas y detalladas; y por las llamadas a la API.            |
| **Logs**       | **Ingesta** (GB ingeridos), **Almacenamiento** (GB/mes) y **Análisis** (GB escaneados). |
| **Alarmas**    | Número de alarmas por mes (las de alta resolución son más caras).                       |
| **Paneles**    | Por panel/mes (los 3 primeros son gratuitos)                                            |
>[!INFO] Tip de optimización: 
>Enviar logs de VPC directamente a S3 puede ser hasta un 50% más barato que a CloudWatch Logs.

**AWS CloudTrail** es el servicio que registra la actividad como eventos para la gobernanza, el cumplimiento y la auditoría de nuestra cuenta. Un evento es el registro de una acción realizada por un usuario, rol o servicio de AWS. Contiene quién hizo la solicitud, qué servicio se utilizó, qué acción se realizó, los parámetros de la acción y la respuesta. Está activado por defecto en todas las cuentas de AWS.

El **Historial de Eventos** es una vista consultable de los últimos 90 días de actividad. Es ideal para la resolución de problemas operativos rápidos. Para un registro a largo plazo y auditorías de seguridad, crea una "ruta" para enviar los registros a Amazon S3 o CloudWatch Logs. El primer "Trail" que entrega una copia de los eventos de gestión a S3 es gratuito, pero luego se cobra:
- Registrar eventos de datos.
- Habilitar CloudTrail Insights.
- El almacenamiento en S3 y el análisis con otros servicios.

Los tipos de eventos son los siguientes:
- **Eventos de Administración (Management Events)**: Proporcionan información sobre las operaciones de gestión en los recursos de su cuenta de AWS (también conocidas como operaciones del plano de control). Ejemplos: Configuración de seguridad (CreateSecurityGroup), configuración de reglas para el enrutamiento de datos, configuración del registro. Por defecto, los "trails" están configurados para registrar estos eventos.
- **Eventos de Datos (Data Events)**: Proporcionan información sobre las operaciones de recursos realizadas en un recurso o dentro de él (también conocidas como operaciones del plano de datos). Ejemplos: Actividad a nivel de objeto de S3 (GetObject, PutObject), invocación de funciones de AWS Lambda (Invoke). Son de alto volumen y están desactivados por defecto debido a su costo.
- **Eventos de CloudTrail Insights (Insights Events)**: Se generan sólo cuando CloudTrail detecta una actividad inusual en su cuenta, como picos en el aprovisionamiento de recursos o brechas en la actividad periódica de mantenimiento. Ayudan a identificar y responder a comportamientos anómalos sin necesidad de analizar todos los eventos manualmente.

**AWS Config** es un servicio que permite evaluar, auditar y valorar las configuraciones de nuestros recursos de AWS de forma continua. Permite automatizar la evaluación de las configuraciones registradas con respecto a las configuraciones deseadas. Responde a la pregunta: "¿Mis recursos están configurados correctamente según mis políticas?".

Su funcionamiento es el siguiente:
1. Registro: Descubre nuestros recursos y registra su estado de configuración como un "Elemento de Configuración".
2. Evaluación: Utiliza Reglas para comparar la configuración actual con la deseada.
3. Alerta: Marca los recursos como "Conformes" o "No Conformes" y notifica sobre cambios. Puede disparar cambios automáticos para hacer correcciones.
4. Agregación: Configura un agregador para recopilar datos de configuración y cumplimiento de varias cuentas y regiones en una sola cuenta.

Ejemplos de Reglas: 
- La regla `s3-bucket-public-read-prohibited` verifica que ningún bucket de S3 permita el acceso de lectura público.
- `ec2-instance-detailed-monitoring-enabled`: Esta regla gestionada de AWS Config comprueba si la monitorización detallada está habilitada para las instancias de Amazon EC2.
- `rds-enhanced-monitoring-enabled`: Esta regla comprueba si la monitorización mejorada está habilitada para las instancias de base de datos de Amazon RDS.
- `cloudwatch-alarm-action-check`: Esta regla verifica que las alarmas de CloudWatch tengan al menos una acción de alarma configurad

El modelo es de pago por uso, basado en:
- Número de Elementos de Configuración registrados en nuestra cuenta.
- Número de evaluaciones de Reglas de Config activas ejecutadas.
- Número de evaluaciones de reglas de Paquetes de Conformidad.

>[!INFO] Capa Gratuita
>También cuenta con una capa gratuita mensual para poder empezar a evaluar los recursos sin costo inicial.

Estos tres servicios se pueden resumir en las siguientes analogías:

|  **Servicio**  |       **Analogía**        |                   **Pregunta Clave**                    |
| :------------: | :-----------------------: | :-----------------------------------------------------: |
| **CloudWatch** |       **El Médico**       |       _¿Está mi sistema sano y funcionando bien?_       |
| **CloudTrail** |     **El Detective**      |           _¿Quién hizo qué, cuándo y dónde?_            |
|   **Config**   | **El Auditor de Calidad** | _¿Mis recursos cumplen con las políticas establecidas?_ |

## AWS System Manager

**AWS System Manager** es una solución de gestión segura de extremo a extremo que da visibilidad y control sobre la infraestructura. Provee:
- Gestión Centralizada: Unifica la gestión de recursos en AWS, en las instalaciones (on-premise) y en otras nubes.
- Visibilidad Operativa: Agrupa datos operativos de múltiples servicios de AWS, permitiendo tener una vista consolidada.
- Automatización Segura: Permite automatizar tareas operativas de forma segura para diagnosticar y resolver problemas rápidamente.

Las capacidades clave que brinda son:
- Gestión de Operaciones:
	- Explorer: Un panel de control personalizable que muestra datos operativos agregados de los recursos para poder entender la salud y el rendimiento del entorno.
	- OpsCenter: Un lugar centralizado para ver, investigar y resolver "OpsItems" (elementos de trabajo operativos). Si una alarma de CloudWatch se dispara, puede crear un OpsItem automáticamente para que el equipo correspondiente lo gestione.
- Gestión del Cambio:
	- Automation: Simplifica tareas comunes de mantenimiento e implementación, como la creación y actualización de AMIs (Amazon Machine Images).
	- Maintenance Windows: Te permite definir un horario recurrente para ejecutar tareas administrativas (como aplicar parches) sin interrumpir  las operaciones críticas.
- Gestión de Nodos (Instancias):
	- Run Command: Te permite ejecutar comandos de forma remota y segura en grandes grupos de instancias, sin necesidad de iniciar sesión manualmente.
- Patch Manager: Automatiza el proceso de aplicación de parches de seguridad y de otro tipo en las flotas de instancias.
	- Session Manager: Proporciona un acceso de shell o CLI interactivo y seguro basado en navegador a tus instancias, sin necesidad de abrir puertos de entrada como el 22 (SSH) o 3389 (RDP), mejorando drásticamente la seguridad.
- Recursos Compartidos:
	- Parameter Store: Ofrece un almacenamiento centralizado y seguro para datos de configuración y secretos, como contraseñas de bases de datos o claves de API.

Algunos ejemplos de uso son:
- Contexto 1: Necesitamos acceder a una instancia de forma segura para solucionar un problema.
- Contexto 2: Debemos aplicar parches de seguridad a cientos de servidores.
- Contexto 3: Necesitamos ejecutar un script en toda la flota de servidores.
- Contexto 4: Nuestra aplicación necesita acceder a una contraseña o clave de API de forma segura.
- Contexto 5: Queremos tener una visión general del estado de tus operaciones.

## AWS Trusted Advisor

**AWS Trusted Advisor** es una herramienta en línea que actúa como experto en la nube personalizado, proporcionando orientación en tiempo real para ayudar a seguir las mejores prácticas de AWS.
- Inspección Continua: Revisa el entorno de AWS de forma proactiva.
- Recomendaciones Claras: Ofrece recomendaciones específicas para mejorar nuestra infraestructura.

Está basado en 5 pilares:
1. **Optimización de Costos**. Ejemplo: Identifica instancias EC2 con baja utilización o balanceadores de carga inactivos.
2. **Rendimiento**. Ejemplo: Alerta sobre volúmenes de EBS sobreutilizados o si uno se acerca a las cuotas de servicio.
3. **Seguridad**. Ejemplo: Comprueba permisos abiertos en buckets de S3 o si falta la Autenticación Multifactor (MFA) en la cuenta raíz.
4. **Tolerancia a Fallos (Resilience)**. Ejemplo: Recomienda distribuir las instancias en múltiples Zonas de Disponibilidad (AZ) o realizar copias de seguridad de los volúmenes EBS.
5. **Cuotas de Servicio**. Avisa cuando el uso de un servicio supera el 80% de su cuota.

## AWS Well Architected

**AWS Well Architected** no es una herramienta, sino una guía que ayuda a construir la infraestructura más segura, de alto rendimiento, resiliente y eficiente posible. Tiene un enfoque coherente, ya que proporciona un método consistente para evaluar arquitecturas y tomar decisiones informadas. Está basado en la experiencia, ya que contiene las mejores prácticas recopiladas por los arquitectos de soluciones de AWS tras revisar miles de arquitecturas de clientes. Evoluciona constantemente, se actualiza a medida que AWS lanza nuevos servicios y aprende más sobre arquitecturas en la nube.

Los 6 pilares en los que se basa este framework son:
- Excelencia Operativa: Ejecutar y monitorear sistemas para entregar valor de negocio y mejorar continuamente los procesos.
- Seguridad: Proteger la información, los sistemas y los activos.
- Fiabilidad (Reliability): Asegurar que una carga de trabajo funcione correctamente y de manera consistente cuando se espera.
- Eficiencia del Rendimiento: Usar los recursos de computación de manera eficiente para cumplir con los requisitos.
- Optimización de Costos: Entregar valor de negocio al precio más bajo posible.
- Sostenibilidad: Abordar el impacto ambiental, económico y social a largo plazo de tus cargas de trabajo en la nube.

Veamos un ejemplo. Un equipo de desarrollo acaba de lanzar una nueva aplicación de comercio electrónico en AWS. La arquitectura es la siguiente:
- Varias instancias EC2 para el servidor web.
- Un Balanceador de Carga de Aplicación (ALB) para distribuir el tráfico.
- Una base de datos Amazon RDS para almacenar los datos de productos y pedidos.

El equipo quiere asegurarse de que su arquitectura es robusta, segura y optimizada. Deciden usar el AWS Well-Architected Framework para evaluarla.
1. Pilar de Seguridad:
	1. Pregunta de la herramienta: "¿Cómo proteges tus datos en reposo?".
	2. Discusión del equipo: Revisan su base de datos RDS y se dan cuenta de que, durante la configuración inicial, no activaron la opción de cifrado. También notan que los volúmenes de disco (EBS) de sus instancias EC2 no están cifrados.
	3. Respuesta en la herramienta: Marcan esta práctica como "no implementada" y la identifican como un riesgo alto.
2. Pilar de Optimización de Costos:
	1. Pregunta de la herramienta: "¿Cómo seleccionas el tipo y tamaño de recurso apropiado?"
	2. Discusión del equipo: Abren Amazon CloudWatch y revisan las métricas de CPUUtilization de sus instancias EC2 durante la última semana. Observan que el uso promedio de la CPU nunca supera el 20%. Esto indica que las instancias son mucho más potentes (y caras) de lo que necesitan.
	3. Respuesta en la herramienta: Marcan esta práctica como "no implementada" y la señalan como una oportunidad de mejora clave para reducir costos.
