## Gestión de Seguridad en AWS

AWS tiene un modelo de responsabilidad compartida, porque tenemos que especificar a quién le vamos a dar acceso a qué, y AWS se va a encargar de que se cumpla. Es importante seguir el principio de mínimo privilegio. Con esto nos garantizamos de que la aplicación esté lo más segura posible. 

---
## Identity and Access Management (IAM)

El primer servicio es I**dentity and Access Management (IAM)**, el cual permite gestionar las identidades y los accesos a los recursos de AWS. Este servicio se utiliza internamente y no se le da acceso a ningún cliente. Entre sus funciones principales, IAM beca credenciales de seguridad temporales para las cargas de trabajo que acceden a sus recursos de AWS y se encarga de analizar continuamente el acceso para ajustar el tamaño de los permisos en el viaje hacia el mínimo privilegio. Finalmente, se destaca por ser un servicio de AWS integrado con la gran mayoría de los otros servicios.

Lo primero es definir quién, luego el si accede y a qué:
![[Pasted image 20260629124531.png|center|511]]

Tiene 4 componentes principales:
- Users
- Roles
- Groups
- Policies

Las **IAM policies** son documentos JSON que define el nivel de acceso que tienen los principals por recurso. Los principals pueden ser users, roles y servicios. El chequeo de permiso verifica si primero hay un deny. Luego, se contempla la existencia de una explicit allow. Si no existe ninguno, se hace un deny por default. Existen dos tipos:
- **Identity Based**: ¿Qué acciones puede realizar la identidad y sobre qué recursos y bajo qué condiciones? Se asignan a usuarios, grupos o rol de IAM.
- **Resource Based**: ¿Qué acciones puede realizar un principal sobre el recurso y bajo qué condiciones? Se asignan a recursos.

![[Pasted image 20260629124627.png|center|356]]

Las partes de las policies son:
- `"Effect"`: Allow o deny.
- `"Action"`: acción particular a la que se aplica el effect. Get por ejemplo en un S3.
- `"Condition"`: Por ejemplo, tal usuario puede levantar instancias EC2, pero t2.micro.
- `"Resource"`: Arns de recurso sobre los cuales aplicar.
- `"Principal"`: Para resource-based policies hay que indicar cuenta, usuario o rol sobre el que aplica. 

![[Pasted image 20260629124712.png|center|525]]

Tomemos el siguiente caso. En él, vemos que tenemos un `deny` y luego un `NotIpAdress`. Es decir, no se pueden apagar instancias que sean otras que las especificadas. Lo podríamos haber hecho simplemente con un `allow`. Esto nos muestra que hay distintas maneras de hacer lo mismo.
```JSON
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:TerminateInstances"
      ],
      "Resource": [
        "*"
      ]
    },
    {
      "Effect": "Deny",
      "Action": [
        "ec2:TerminateInstances"
      ],
      "Condition": {
        "NotIpAddress": {
          "aws:SourceIp": [
            "192.0.2.0/24",
            "203.0.113.0/24"
          ]
        }
      },
      "Resource": [
        "*"
      ]
    }
  ]
}
```

Tomemos el siguiente caso resource-based, donde se le permite solamente acceder al bucket las direcciones provenientes de la determinada.
```JSON
{
  "Version": "2012-10-17",
  "Id": "S3PolicyId1",
  "Statement": [
    {
      "Sid": "IPAllow",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:*",
      "Resource": [
        "arn:aws:s3:::examplebucket",
        "arn:aws:s3:::examplebucket/*"
      ],
      "Condition": {
        "NotIpAddress": {
          "aws:SourceIp": "54.240.143.0/24"
        }
      }
    }
  ]
}
```

>[!INFO] Restricciones a Servicios
>Esto nos muestra que no solo restringimos accesos a otros usuarios, sino que también lo podemos hacer con servicios propios de AWS. Por ejemplo, si tenemos una aplicación de pagos, queremos que el backend escriba la base de datos, pero que no pueda borrar nada. 

Los **IAM Roles** permiten dar permisos temporales a los servicios y puede asumirse por una persona, aplicación o mismo un servicio. Un rol no tiene credenciales permanentes como un usuario. En cambio, se asume temporalmente y otorga permisos según lo definido en sus policies.
![[Pasted image 20260629125106.png|center|435]]

El rol tiene policies linkeadas donde se establece qué se puede hacer y qué no. Podemos tener distintos roles asignados, pero vamos intercambiando entre ellos según la actividad a realizar. 

Los **IAM Groups** son formas de agrupar users. Esto se puede hacer:
- **Role-Based**: a todos los developers los agrego a un group y les doy un mismo acceso con los mismos roles.
- **Attribute-Based**: funciona en función de *tags* que podemos asignar a la hora de levantar los servicios.

![[Pasted image 20260629125152.png|center|498]]

## Cognito

Todo lo que hablamos hasta ahora es interno, pero también tenemos que gestionar el acceso de los clientes, es decir del usuario final. **Cognito** es un servicio que facilita la integración de armar un login con, por ejemplo, cuenta de Google. Entonces, Cognito permite una gestión segura y sencilla de la identidad y el acceso de los clientes.

Este servicio cuenta con las siguientes características: funciona como una plataforma de identidad para web y mobile y permite autenticar desde proveedores propios o federados como Google o Facebook. Además, ofrece seguridad avanzada y de alta disponibilidad, junto con una interfaz de usuario integrada y flexible que tiene soporte de API y SDK. Finalmente, provee herramientas de desarrollo ágiles con análisis de clientes integrado y una AuthN y AuthZ extensible a los demás servicios de AWS.

El flujo es el siguiente:
1. El usuario se registra o inicia sesión a través del Hosted UI o mediante nuestra propia app usando el SDK.
2. Cognito user pool: valida las credenciales y devuelve un conjunto de tokens (ID, Access, Refresh).
3. La aplicación usa el Access Token para realizar solicitudes a nuestro backend (por ejemplo, API Gateway + Lambda).
4. Si se usa Identity Pools, se puede intercambiar el token por credenciales IAM temporales que permiten acceder a servicios como S3, DynamoDB, etc.

Con Cognito se puede gestionar tanto **autenticación** (confirmar la identidad del usuario - con el login - se ocupan los user pools) como la **autorización** (decide si puedo accionar o no sobre un recurso - se ocupa los identity pools). Cognito solo autentica, no autoriza directamente el acceso a otros servicios. Se puede combinar con IAM para realizar esto. 

Como dijimos, los user pools autentican usuarios, mientras que los identity pools autorizan accesos a servicios.

|                **Aspecto**                |                                         **User Pool**                                         |                                **Identity Pool**                                 |
| :---------------------------------------: | :-------------------------------------------------------------------------------------------: | :------------------------------------------------------------------------------: |
|           **Función principal**           |                        Autenticación de usuarios (verifica quién sos)                         |     Autorización para acceder a servicios de AWS con credenciales temporales     |
|            **¿Qué devuelve?**             |                       Tokens JWT: ID Token, Access Token, Refresh Token                       |      Credenciales temporales de IAM (Access Key, Secret Key, Session Token)      |
|         **¿Administra usuarios?**         |  Sí. Permite registrar, autenticar, verificar emails, resetear contraseña, agrupar usuarios   | No. Solo recibe identidades desde un proveedor externo (User Pool, Google, etc.) |
|       **Login con redes sociales**        |               Sí. Directamente desde Hosted UI o integración (OAuth/SAML/OIDC)                |              Sí, si se configura con User Pool o proveedor externo               |
| **Permite acceder a S3, DynamoDB, etc.?** |           No directamente. Necesita combinarse con Identity Pool o definir una API            |                Sí. Otorga acceso a recursos AWS vía políticas IAM                |
|         **Asigna permisos IAM?**          |                                              No                                               |     Sí. A través de roles IAM asociados a usuarios autenticados o invitados      |
|              **Uso típico**               | Aplicaciones que necesitan login, verificación, atributos personalizados, UI de autenticación |  Aplicaciones que necesitan acceso controlado a recursos AWS como S3 o DynamoDB  |
|              **Integración**              |                       Se puede usar solo o combinado con Identity Pool                        |           Requiere un proveedor de identidad (puede ser un User Pool)            |
>[!TIP] Síntesis
>User Pool es quién sos, mientras que el identity pool es qué podés hacer. Juntos forman un sistema completo de gestión de identidad y control de acceso.

>[!INFO] Tener Otro Método de Autenticación
>Puede ser útil tener más de un método de autenticación, como por ejemplo Cognito y también un sistema interno que genere JWT como en PAW, por si se cae uno. Es importante para el TP4 no tener endpoints públicos que no tienen que serlo. 

Existe un problema, y es que el bucket S3 no puede manejar redirecciones dinámicas ni headers. Usamos Lambda como intermediario para procesar el login.
- Cognito Hosted UI redirecciona a una URL fija con los tokens en la URL (#id_token=... o ?code=...).
- Si esa URL apunta a S3, el bucket no puede procesar ni extraer los tokens.

Lambda resuelve eso: procesa el code, obtiene tokens, y redirige al frontend estático con los tokens (si querés en la URL, cookies, etc.).

La solución es la siguiente:
1. Usuario accede al frontend en S3.
2. Frontend redirige a Cognito Hosted UI.
3. Cognito redirige a /callback (un endpoint de API Gateway que invoca una Lambda).
4. Lambda:
	1. Intercambia el code por los tokens.
	2. Redirige al frontend (ej: https://mi-app.com/#token=...).
5. Frontend lee los tokens desde la URL y los guarda (en localStorage, etc.).
6. Usa el Access Token para llamar APIs.

## Manejo de Claves 

**AWS Key Management Service (KMS)** permite crear, gestionar y controlar las claves criptográficas en sus aplicaciones. Está incorporado en más de 100 servicios de AWS para cifrar datos confidenciales y crear firmas digitales. Es un servicio totalmente gestionado. Funciona de la siguiente manera. Primero crea la clave y luego puede:
- Cifrar y descifrar datos
- Firmar y verificar
- Generar y exportar claves de datos
- Generar y verificar los códigos de autenticación de mensajes (MAC)

Las claves están integradas en S3, EC2, EBS, y otros servicios más. Tiene los siguientes beneficios:
- Centralmente gestionar llaves y definir políticas para todos los servicios y aplicaciones integrados desde un solo punto.
- Actuar operaciones de firma utilizar pares de claves asimétricas para validar las firmas digitales.
- Cifrar datos en sus aplicaciones con la biblioteca de cifrado de datos del AWS Encryption SDK.
- Genere de forma segura la autenticación de mensajes basada en hash Code (HMAC) que proporcionan mensajes integridad y autenticidad.

AWS KMS es un servicio rentable y de alta disponibilidad que gestiona las claves de cifrado en AWS. Permite gestionar de una manera muy simple las claves de cifrado.
![[Pasted image 20260629130154.png|center|344]]

Algunos casos de uso son:
- Proteja sus datos en reposo
- Cifrar y descifrar datos
- Firmar y comprobar firmas digitales
- Validar los tokens web JSON mediante HMAC

**Cloud HSM (Hardware Security Module)** es un servicio cloud para tener hardware dedicado para almacenar mis claves criptográficas. Los clientes utilizan los HSM en AWS porque necesitan acceso de baja latencia a un raíz segura de confianza que está por debajo de su control. Claramente no sabemos donde está, pero confiamos en AWS de que se nos está asignando ese hardware dedicado.
![[Pasted image 20260629163429.png|center|319]]

**Secrets Manager** es un servicio administrado para gestión segura de credenciales y secretos. Almacena y protege claves, contraseñas, tokens y certificados y ofrece rotación automática de credenciales (ej. DB, APIs). Se integra con otros servicios AWS (RDS, Lambda, ECS, etc.). Evita guardar secretos en código, repositorios o variables de entorno. Es el servicio que vamos a usar casi seguro si usamos AWS.
![[Pasted image 20260629163514.png|center|113]]

## Gestión de Amenazas

**Shield** consiste en una protección gestionada contra amenazas que bloquea DDoS ataques, explotación de vulnerabilidades y bots maliciosos. Detección dinámica y mitigaciones automáticas de downtime y latencia AWS Shield. Tiene 2 tiers:
- Standard
- Advanced

![[Pasted image 20260629163604.png|center|96]]

**Web Application Firewall (WAF)** protege las aplicaciones web al permitirle escribir reglas personalizadas o elegir reglas gestionadas de AWS o AWS Marketplace. Permite agregar reglas para bloquear, permitir y monitorear requests. Está integrado con Cloudfront, ALB, API Gateway, App Sync y sirve para protegerse de ataques comunes como SQL Injection, XSS, Bot control.

**Guard Duty** es un servicio gestionado de detección de amenazas que utiliza aprendizaje automático (ML), detección de anomalías e inteligencia de amenazas integrada para identificar y priorizar las posibles amenazas.
![[Pasted image 20260629163647.png|center|526]]

Se activa con simplemente un clic en toda la organización y provee supervisión continua de las cuentas y los recursos de AWS. Como dijimos usa aprendizaje automático para detectar técnicas de ataque evasivo.
![[Pasted image 20260629163721.png|center]]

**AWS Macie** es un servicio totalmente gestionado que provee seguridad y privacidad de datos que utiliza el aprendizaje automático y la coincidencia de patrones para descubrir, supervisar y proteger sus datos confidenciales en Amazon S3. En el gráfico se coloca conectado al bucket que afecta.
![[Pasted image 20260629163759.png|center|617]]

Implementa identificadores de datos. Mantiene una lista cada vez mayor de tipos de datos confidenciales que incluyen información de identificación personal (PII) común y otros tipos de datos confidenciales tal como se definen en las normas de privacidad de datos, como el RGPD, el PCI-DSS, la CCPA y la HIPAA.

Cuando Amazon Macie analiza los datos de un bucket S3, realiza una inspección exhaustiva que tiene en cuenta el formato de archivo o almacenamiento de los datos. Macie puede analizar y detectar datos confidenciales en muchos formatos diferentes, incluidos los formatos de compresión y archivo más utilizados.

**AWS Inspector** es un servicio automatizado de gestión de vulnerabilidades que analiza continuamente las cargas de trabajo de AWS en busca de vulnerabilidades de software y exposición no deseada a la red. Los servicios para los que funciona son:
- EC2
- ECR
- Lambda

>[!WARNING] Diagrama de Arquitectura
>En el diagrama de arquitectura, este servicio se debe incluir conectado al cómputo, no puede ir suelto.

**AWS Certificate Manager (ACM)** es un servicio administrado para gestión de certificados [[05. Protocolos Criptográficos#Canal Seguro TSL|SSL/TLS]]. Emite y renueva automáticamente certificados públicos y privados. Facilita la implementación de HTTPS en servicios como ELB, CloudFront y API Gateway. Elimina la necesidad de manejar claves privadas y renovaciones manuales. Es gratis.

**AWS Config** es un servicio para monitorear y auditar la configuración de recursos AWS. Registra y almacena el historial de configuración de recursos (EC2, S3, IAM, etc.). Permite definir reglas de compliance (ej: “todos los buckets S3 deben tener cifrado”). Detecta cambios no autorizados o desviaciones de las políticas de seguridad. Se integra con CloudTrail, Security Hub y EventBridge para alertas y remediación.

**Security Hub** es un servicio centralizado para gestión de seguridad y cumplimiento en AWS. Consolida hallazgos de seguridad de múltiples servicios (GuardDuty, Inspector, Macie, Config, etc.), proporciona un panel unificado con el estado de seguridad de la cuenta/organización reduce el trabajo de correlacionar alertas dispersas.

**AWS Detective** es un servicio para investigar y analizar incidentes de seguridad en AWS. Analiza datos de múltiples fuentes (CloudTrail, VPC Flow Logs, GuardDuty, etc.). Construye una vista unificada del comportamiento de usuarios, IPs y recursos. Permite entender qué ocurrió, cómo y qué recursos fueron afectados.
