## Tipos de Almacenamiento

Existen tres tipos de almacenamiento de datos. **Block Storage** guarda la información como bloques crudos, sin estructura de archivos visible para el almacenamiento en sí. El almacenamiento está dividido en bloques iguales e independientes que el sistema de almacenamiento ofrece como piezas sueltas de espacio. No sabe qué bloque pertenece a qué archivo ni entiende carpetas o nombres. Esa organización la hace después el sistema operativo o el sistema de archivos del servidor. Se usa cuando se necesita bajo nivel, alto rendimiento y comportamiento similar al de un disco tradicional.

![[Pasted image 20260629112054.png|center|86]]

**File Storage** organiza los datos mediante un sistema de archivos, con carpetas, nombres de archivo y jerarquías. Acá no se ve solo una grilla de bloques aislados, sino una capa lógica que organiza esos bloques en carpetas y archivos. La idea es que distintos clientes pueden conectarse y ver el mismo sistema de archivos compartido. Es la opción más natural cuando varios usuarios o servidores necesitan acceder a archivos compartidos de una forma conocida y sencilla.
![[Pasted image 20260629112141.png|center|109]]

**Object Storage** guarda los datos como objetos independientes. Cada objeto es una unidad completa que incluye los datos y su información asociada, como identificador y metadatos. No se accede como un disco o carpeta tradicional, sino normalmente mediante APIs, y está pensado para gran escalabilidad, almacenamiento masivo y gestión flexible basada en metadatos y políticas.

## Elastic Block Storage

Como ya vimos, los datos se dividen en un arreglo de bloques numerados y permite a los sistemas accederlos individualmente. Los bloques se tratan como dispositivos de almacenamiento separados. Permite escribir y leer bloques individuales de datos. Se utiliza típicamente para almacenar datos estructurados, como sistemas operativos, bases de datos y aplicaciones que requieren acceder a bajo nivel.

AWS proporciona el servicio de **Elastic Block Storage**. Dos instancias de EC2 no pueden tener asociadas el mismo volumen. Puede ser compartido, pero no se puede usar el mismo block storage por dos instancias a la vez. 

Hay varios tipos, definidos según lo que uno quiera hacer:
- SSD para alta performance de I/O aleatorio
	- gp3 (General Purpose SSD): Bases de datos tradicionales, volúmenes de arranque.
	- io2/io2 Block Express: Bases transaccionales críticas.
- HDD para lecturas secuenciales y almacenamiento barato.
	- st1 (Throughput Optimized HDD): Se usa para data warehousing. 
	- sc1 (Cold HDD): Para datos poco accedidos, con costos mínimos. Por ejemplo archivos de logs para auditoría.

## Elastic File System

Vimos que el file system se basa en bloques no relacionados que se organizan en una jerarquía de carpetas y archivos, similar a cómo funcionan en los sistemas operativos tradicionales. Este tipo de almacenamiento es adecuado para compartir archivos y colaborar en red, ya que permite el acceso simultáneo a los mismos archivos por parte de múltiples usuarios. Los archivos se acceden a través de protocolos de red como NFS y SMB. El servicio de AWS se llama **Elastic File System**.

## Simple Storage Service

Como vimos, en el *object storage* los datos se organizan como objetos, donde cada uno contiene datos, metadatos y un identificador único. Estos son almacenados en un único plano y se puede acceder a través de una API. Es muy eficiente para el almacenamiento de grandes cantidades de datos no estructurados, como imágenes, videos, documentos y archivos multimedia en general. El servicio de Amazon se conoce como **Simple Storage Service (S3)**. 

Entonces, **Amazon S3** es el servicio de object storage de AWS. Sirve para guardar y recuperar archivos u objetos, como imágenes, videos, backups, documentos o archivos estáticos de una aplicación, con alta durabilidad y gran escalabilidad. La información no se organiza como un disco o carpeta tradicional montada en un servidor, sino como objetos dentro de buckets. Cada objeto tiene su contenido, una clave o nombre y metadatos asociados. Se accede normalmente mediante API, por lo que es ideal para almacenar grandes volúmenes de datos de forma simple, segura y muy escalable. 

>[!INFO] Importante
>Los buckets de S3 tienen nombres únicos. No pueden existir dos distintos con el nombre `cloud-prueba`.

Amazon S3 se caracteriza por ofrecer un almacenamiento ilimitado de datos no estructurados, los cuales se guardan como objetos dentro de un bucket. Es importante destacar que es un servicio regional y compartido, razón por la cual no puede estar dentro de la VPC, (ubicarlo allí se considera un error grave en el examen). En cuanto a sus métricas de fiabilidad, el servicio provee 11 nueves de durabilidad y 9 de disponibilidad; esta durabilidad se genera debido a que, al subir un archivo, el sistema por detrás lo sube a tres buckets diferentes.

Respecto a su capacidad y acceso, los archivos individuales pueden tener un tamaño máximo de hasta 5TB y todos los objetos quedan disponibles para ser accedidos globalmente mediante una URL unívoca. Además, S3 permite hostear sitios estáticos y cuenta con funciones integradas de versionado y encriptación, sumado a un modelo de control de accesos que es totalmente flexible para el usuario.

Vimos que todos los archivos:
- Tienen identificador único: Cada objeto contará con una clave que lo diferencia de todos
- Son privados por default: Al ser creados, no son accesibles públicamente.
- Accesibles globalmente: Pueden ser accedidos mediante una URL unívoca de manera global. 
- Parámetros adicionales: Los objetos contarán también con metadata y un id de versión.

>[!TIP] Sistema de Privacidad
>El **sistema de privacidad** permite hacer archivos completamente públicos y dar acceso según los roles de los usuarios que entran a la plataforma. También se pueden usar URLs prefirmadas que permiten acceso durante un tiempo.

La **encriptación** permite utilizar una clave secreta para que los objetos, por más que puedan ser accedidos, sean ilegibles sin dicha clave.
- **Client Side Encryption**: El usuario se encarga de encriptar los datos antes de subirlos a AWS. El usuario maneja la clave con la que se encripta y esta nunca está en poder de AWS.
- **Server Side Encryption**: Los datos se encriptan una vez llegan a AWS, antes de ser almacenados, y son desencriptados cuando el usuario los pide. En S3 puedo usar la opción default, con una clave de AWS o usar una KMS key.

La **transferencia de datos** a S3 se puede hacer de tres formas. La primera es a través de la consola de AWS. Es como dropear archivos a drive. Otras opciones son usar SDKs (para aplicaciones) o el CLI de AWS. Usando **Multipart Upload** los archivos son subidos como un set de partes contiguas del objeto. Al terminar de subir todas las partes S3 las junta, recuperando el objeto subida. Se recomienda usar para archivos de más de 100 MB.

**S3 Transfer Acceleration** mejora la velocidad de subida y bajada de archivos hacia un bucket de S3 cuando el cliente está lejos geográficamente. En lugar de enviar los datos directamente al bucket por Internet, el tráfico entra primero por una Edge Location cercana de la red global de AWS y desde ahí viaja por la backbone network de AWS hasta S3, usando una ruta más optimizada y estable.

Sumado a esto, **AWS Snowball** permite transportar múltiples TBs de datos sin la necesidad de que los mismos viajen a través de internet. Se envía un servicio con una valija física donde se cargan los datos y se llevan al lugar deseado. Si tuviéramos que transferir 10 PetaBytes de datos (10 millones de GBs) incluso teniendo una conexión de 10 Gbs por segundo (que no existe casi), tomaría 100 días. Para pedirlo se debe crear un job en la consola de AW y para utilizarlo se debe instalar un cliente. Si tengo una base de datos distribuida, se tiene que enviar uno a cada región.

Pero además, existe **Snowmoblie**, que es un camión de 14 metros. Permite transferir 100 PB por camión. Con el mismo caso anterior, tardaríamos 3 años. Ofrece múltiples medidas de seguridad como:
- Tracking por GPS
- Vigilancia de video
- Patrulla de seguridad
- Altísimos niveles de encriptación

El **versionado** consta en mantener múltiples versiones de un mismo objeto para evitar las pérdidas indeseadas ya sea por borrado o sobrescritura, sin costo de performance. Activando el versionado, podemos recuperar de manera fácil versiones previas del objeto. El versionado no está activado por default, y una vez hecho, ya no podrá quitarse, aunque sí podrá suspenderse. El borrado de una versión no se persiste, se marca la versión como borrada y se debe acceder nuevamente a borrarlo.

S3 provee los que se llama **Read After Write Consistency**, lo que significa que una vez escrito el archivo, inmediatamente está listo para lectura. Sin embargo, esto mismo no ocurre en el caso de subirse nuevas versiones de los objetos (si se tiene versionado activo y ya hay un archivo). Si leemos una versión posterior justo después de subirla, AWS puede devolver la nueva o la vieja.

En S3 se puede replicar todo lo que hay en un bucket a otro (generalmente en otra región) usando **Cross Region Replication**. Podemos replicar todos los objetos de un bucket fuente a un bucket destino en otra región, ya sea de una cuenta nuestra o no. Esta replicación puede ser de un solo lado o bilateral (todo lo de uno está en el otro pero el otro puede tener cosas extra). Para poder activarlo, debemos tener el versionado activado en todos los buckets. 

S3 cuenta con distintos niveles de almacenamiento, que permitirán ahorrar costos en base a los patrones de acceso a los objetos. Existen 5 alternativas. La primera es **S3 Standard**, que sirve para data accedida frecuentemente. Se almacena en al menos 3 zonas de disponibilidad. **S3 Infrequent Access** se utiliza para data accedida en menor medida y que persiste en el tiempo, al menos 30 días. Se almacena también en al menos 3 zonas de disponibilidad. Es un poco más barato y un poco más lento. **S3 One Zone IA** es igual que IA pero es almacenada en una sola zona, con lo cual se usa para data poco crítica. Se usa por ejemplo en bases de desarrollo.

**S3 Glacier** se usa para objetos accedidos extremadamente poco. Es muy barato, y funciona como un archivo de datos. Sirve por ejemplo para registros de cámaras de seguridad. Tiene 3 patrones de acceso:
- Expedited (1-5 min)
- Standard (3-5hs)
- Bulk (5-12hs)

Si por ejemplo cae una inspección y necesitamos los datos, se pide un expedited. Si hay una auditoría pesada en unos días, se utiliza bulk. Para data que no se accede casi nunca, existe **Deep Archive**. Son archivos que ya no sirven pero no se pueden borrar por ley. Se usa casi siempre para compliance.

**S3 Intelligent-Tiering** ajusta automáticamente el costo de almacenamiento según cómo se accede a cada objeto. Cuando un objeto se sube, queda primero en la capa de acceso frecuente. Si pasan 30 días sin acceso, S3 lo mueve a la capa de acceso infrecuente; si pasan 90 días sin acceso, puede moverlo a la Archive Instant Access tier, que sigue teniendo acceso en milisegundos pero a menor costo. Además, se pueden habilitar capas de archivo opcionales: Archive Access, para objetos sin acceso durante al menos 90 días según la configuración, y Deep Archive Access, para objetos sin acceso durante al menos 180 días, también configurable.

>[!TIP] Importante
>Los objetos sí pueden volver a una capa superior. Si un objeto almacenado en una capa de acceso inmediata vuelve a usarse, S3 lo mueve automáticamente otra vez a la capa de acceso frecuente. En cambio, si el objeto ya está en Archive Access o Deep Archive Access, primero hay que hacer un restore para poder accederlo, y luego vuelve a la capa frecuente dentro de Intelligent-Tiering. AWS además cobra un pequeño cargo de monitoreo y automatización por objeto para gestionar estos movimientos automáticos.

Se puede configurar que los objetos, dado cierto tiempo sin ser accedidos, se muevan automáticamente de nivel. Esto se configura en los lifecycle policies.

## Hosting de Static Sites

Uno de los casos de uso más comunes de S3 es para hostear páginas web estáticas, sin la necesidad de manejar un servidor, permitiendo almacenar.
- Contenido HTML y CSS
- Client-Side scripts (Javascript sí, PHP no)
- Imágenes y videos del sitio

PHP permitía cambiar la aplicación dinámicamente, y había lógica de construcción dentro de la página, lo que S3 no maneja. En S3 deben guardarse archivos que no se modifican, y por eso no tolera PHP. La página web estática no corre en el S3, porque no tiene lógica ni cómputo. Corre en el browser del usuario. 

>[!INFO] Versionado
>Un bucket no tiene que tener versionado si está hosteando el front end, porque para el versionado ya se está usando git.
