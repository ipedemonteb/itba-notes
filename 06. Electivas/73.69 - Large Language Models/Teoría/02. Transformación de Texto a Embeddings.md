## Tokenización

La **tokenización** es la división de los elementos de un texto (frase, documento, etc.) de acuerdo a un vocabulario predefinido. Mediante ella, se generan las unidades que consume un Transformer, por lo que es importante para analizar los costos. 

En la siguiente imagen se puede observar que se compone de un encoder, un decoder y un train, que se refiere al proceso mediante el cual se define el vocabulario
![[Pasted image 20260818125435.png|center|549]]

Pero, ¿cuál es la diferencia con embedding?
- **Tokenizer**: Parte el texto en unidades más pequeñas para que pueda ser procesado por un modelo.
- **Algoritmo de Embedding**: Crea vectores densos que representan unidades de texto (con el objetivo de capturar representaciones de interés).
![[Pasted image 20260818125802.png|center|246]]

Existen dos tipos de tokens:
- **Básicos**: tokens comunes que representan palabras, sub-palabras, puntuación, espacios, etc.
- **Especiales** (reservados): aquellos que tienen un significado especial o función asignada (como por ejemplo el `eof`).
![[Pasted image 20260818125908.png|center]]

El algoritmo **Byte-Pair Encoding (BPE)** es el inicial utilizado para realizar el proceso de tokenización. Consiste en el armado de nuevos tokens basado en la frecuencia de aparición de los tokens originales. Funciona de la siguiente manera. Supongamos que tenemos el siguiente corpus de texto:
```
Hola, hoy tengo mucha hambre 🍔🍔🍔🍔🍔🍔
```

El texto se pasa a UTF-8 y se obtiene lo siguiente:
```
\u0048\u006f\u006c\u0061\u002c\u0020\u0068\u006f\u0079\u0020\u0074\u0065
\u006e\u0067\u006f\u0020\u006d\u0075\u0063\u0068\u0061\u0020\u0068\u0061
\u006d\u0062\u0072\u0065\u0020\ud83c\udf54\ud83c\udf54\ud83c\udf54\ud83c
\udf54\ud83c\udf54\ud83c\udf54
```

El resultado luego se traduce a enteros (0-255):
```
72-111-108-97-44-32-104-111-121-32-116-101-110-103-111-32-109-117-99-104-
97-32-104-97-1-09-98-114-101-32-240-159-141-148-240-159-141-148-240-159-
141-148-240-159-141-148-240-159-141-148-240-159-141-148
```

El algoritmo recorre la entrada anterior y observa que se repiten algunos pares, como por ejemplo `159-241`. Entonces, "mergea" ambos valores de la siguiente forma `159-241 -> 256`, creando así un nuevo token que reemplaza en la cadena:
```
72-111-108-97-44-32-104-111-121-32-116-101-110-103-111-32-109-117-99-104-
97-32-104-97-109-98-114-101-32-240-256-148-240-256-148-240-256-148-240-
256-148-240-256-148-240-256-148
```

El procedimiento se repite, y ahora encuentra el par `256-148`, generando un nuevo token, y vuelve a aplicar el algoritmo. 

Si bien funciona muy bien en la práctica, trae ciertas ineficiencias que luego deben resolverse en el modelo. Tomemos el caso de las variantes de la palabra `egg`, como por ejemplo `Egg` o `eGg`. Vemos que estos genera distintos tokens:
![[Pasted image 20260818131142.png|center|532]]
El modelo deberá aprender la que todos estos tokens representan la misma palabra.

Además, deben agregarse decisiones de diseño, como por ejemplo en el caso de un fragmento de código:
```python
def hello(x):
	return x
```
Todos los espacios previos al return deben calcularse juntos y representar  un único token.

Estos problemas se observan en el paper original:
![[Pasted image 20260818131555.png|center|533]]

Existe otro problema con este algoritmo que son los conocidos como **glitch tokens**, que ocasionan comportamientos raros en el modelo. Lo que sucede por detrás es que el tokenizador crea tokens a partir de datos del entrenamiento, pero durante el entrenamiento del LLM esos tokens casi nunca aparecen. Al no haber aprendido qué significan ni cómo usarlos, sus embeddings quedan desalineadas o "incompletos", provocando que el modelo responda de forma errática, alucine o repita palabras aleatorias cuando los encuentra.
![[Pasted image 20260818131717.png|center|586]]

Los tradeoffs de agrandar el vocabulario son:
- Permite obtener secuencias más cortas, útil para la capa de atención.
- Términos poco frecuentes pueden modelarse como tokens individuales.
- Permiten modelar mejor otros lenguajes (si acompaña el dataset).
Pero:
- Ocupa más espacio en memoria.
- Da más lugar a glitch tokens / tokens poco entrenados.
- Mayor libertad de composición lingüística. 
- El modelo tiene "menos tiempo para pensar" (lo vamos a ver más adelante).

Como usuario, nos conviene una cantidad menor de tokens. Esto trae problemas por ejemplo en los cambios de idioma, ya que en aquello muy poco representados consumen muchos tokens y por ende son más caros de usar. Por esto también funcionan mucho mejor en inglés para programar.

## Embeddings

La motivación para usar los **embeddings** es lograr entender el significado de una palabra (o mejor dicho, unidad lingüística, ya que podría ser también un documento o una subpalabra). Queremos modelar distintos aspectos contemplados dentro del campo de *lexical semantics*:
- ¿Qué palabras son sinónimos?
- ¿Cuáles antónimos?
- ¿Cuáles tienen connotación positiva?
- ¿Y negativa?
- ¿Cuáles son palabras que pertenecen al mismo concepto base?
- Etc.

El precursor de embeddings se conoce como **vector semantics**, y surge a partir de la convergencia de dos ideas:
- Joos (1950), Harris (1954) y Firth (1957), definen el significado por su **distribución**: "You shall know a word by the company it keeps". Es probable que se pueda entender la palabra de la que se está hablando viendo una ventana del contexto.
- Osgood (1957), quien usa un **vector en $R^3$** para representar connotaciones. Por ejemplo: ![[Pasted image 20260818133519.png|center|280]]

Las primeras implementaciones fueron las siguientes:
- **Matriz Término-Documento**: Se utilizan vectores para representar documentos en el espacio. Entonces, se analizaban todas las apariciones de una palabra en cada documento y se contabilizaban en una tabla: ![[Pasted image 20260818133549.png|center|554]]
- **Matriz Término-Término**: Parte de la misma idea que el caso anterior pero con palabras, definiendo ventanas de contexto y analizando qué palabras aparecen juntas, permitiendo así obtener matrices como la siguiente: ![[Pasted image 20260818133725.png|center|562]]Al observar estos vectores en el espacio, el ángulo entre ellos representaba la similitud entre palabras. En el siguiente caso, se toma "digital" e "information" como similares, aunque la segunda aparece muchas más veces: ![[Pasted image 20260818133948.png|center|557]]

Estas implementaciones traen una serie de problemas:
- Los vectores dispersos tienen mucho espacio vacío.
- La frecuencia sola no alcanza: ¿qué ocurre con palabras como "a", "de", "y"? Tienen mucha representación.
- ¿Y con palabras que se usan muy poco?

En este contexto, nacen los **embeddings**, que son vectores $n$-dimensionales que representan elementos discretos (palabras, caracteres, imágenes) en un espacio continuo. Buena parte de la literatura los define como densos.

Para medir la similitud entre embeddings se toma una métrica, como por ejemplo la **Cosine Similarity**:
$$\cos(\theta) = \frac{\mathbf{A} \cdot \mathbf{B}}{\Vert{}\mathbf{A}\Vert{} \Vert{}\mathbf{B}\Vert{}} = \frac{\sum_{i=1}^{n} A_i B_i}{\sqrt{\sum_{i=1}^{n} A_i^2} \sqrt{\sum_{i=1}^{n} B_i^2}}$$
Visto gráficamente:
![[Pasted image 20260818134646.png|center|286]]

Esta no es la única métrica, y tiene sus ventajas y desventajas. Por ejemplo, si importa la magnitud del vector (porque representa algo importante), entonces la similitud coseno trae un problema porque aplana esa característica considerada importante. Por ejemplo, supongamos un caso donde el eje vertical representa series de terror y el horizontal series románticas. La persona que mire 100 series de cada tipo, va a tener la misma similitud coseno que otra que vio 1 de cada una, lo que nos perjudica el estudio que queremos hacer, ya que la primera persona es un consumidor de series mucho más relevante. 

Pero tomemos el caso que queremos comparar las palabras "escarlata" y "rojo". No nos interesa tanto su frecuencia en el lenguaje, sino saber su similitud descriptiva en cuanto a un color.

Existen tres tipos de embeddings:
- **Static Embedding**: mantienen un valor fijo que se aprendió del contexto en el corpus de datos. Por ejemplo: word2vec (skip-gram y CBOW).
- **Dynamic Embeddings**: cambia su valor dependiendo del contexto en una instancia particular. Por ejemplo: BERT (palabras), SBERT (oraciones).
- **Learned Embeddings**: se entrenan junto con el modelo. No son muy comunies.

Supongamos que tenemos las siguientes frases:
- "I ate pizza"
- "This pizza is totally disgusting"

En el caso estático, el embedding para la palabra "pizza" será el mismo. Se posiciona en el lugar que se observa en el siguiente gráfico: ![[Pasted image 20260818135452.png|368]]
En cambio, en el caso de un algoritmo dinámico, podremos observar el siguiente comportamiento (supongamos que el eje horizontal representa qué tan rica es una comida):
![[Pasted image 20260818135741.png|center|373]]

Un algoritmo de embedding estático es **Skip-Gram** (de la familia word2vec). La idea básica consiste en entrenar un modelo con pares $[w,c]$, que actualiza sus parámetros de acuerdo a si el par es real o no:
- La palabra objetivo y sus vecinas en el contexto se consideran ejemplos positivos.
- Se toman palabras random fuera del contexto para formar ejemplos negativos.

Entonces, se entrena un clasificador que distinga estos ejemplos. Se usan los parámetros resultantes como embeddings para la palabra en cuestión. Tomemos el siguiente caso:
![[Pasted image 20260818163802.png]]
Vemos que la palabra en consideración ("passes") dentro del input tiene un `1` asignado en el primer vector. Luego, se tienen dos matrices. La primera, llamada $W_{input}$, tiene los embeddings como filas, lo que se refiere a la palabra como "word", es decir como centrada. La segunda, es la $W^T_{output}$, que tiene los embeddings como columnas pero refiriéndose como contexto. Entonces, vemos que tras algunos cálculos se obtiene el vector $y_{pred}$ donde se encuentran todas las probabilidades. Como "the" y "who" son parte del contexto, en el $y_{true}$ vamos a querer que las probabilidades sean en realidad $1$. Por lo tanto, se calcula la pérdida mediante el $y_{pred} - y_{true}$ y se ajustan los pesos de acuerdo a ese error que obtuvimos.

Notemos que la operación que hacemos entre $h$ y las columnas de $W_{output}^T$ consiste en un producto punto (dot product) para cada palabra del vocabulario. Este producto punto funciona como una medida de similitud entre la palabra centrada y las palabras de contexto, produciendo un puntaje elevado cuando los vectores apuntan en direcciones parecidas. Luego, al aplicar la función $\text{SoftMax}$ sobre estos valores, obtenemos el vector de probabilidades $y_{pred}$. Por lo tanto, al actualizar los pesos mediante la función de pérdida, lo que en realidad buscamos es aumentar el valor del producto punto (y por ende la similitud) entre la palabra en consideración y aquellas que realmente forman parte de su contexto.
![[Pasted image 20260818165042.png|center|494]]

Ahora, tomemos el caso dinámico y notemos que podríamos usar un **Encoder-Only Transformer**, porque recordemos que se caracteriza por lograr entender, tanto adelante como hacia atrás, con qué otros tokens está interaccionando lo que está recibiendo el modelo. Entonces, en los casos de traducción que vimos en la primera unidad podríamos remover el decoder y utilizar el Transformer como generador de embeddings.

El encoder tradicional basado en Transformers es el **BERT (Bidirectional Encoder Representations from Transformers)**. Como dijimos, procesa el texto basándose en el contexto previo y el futuro y sólo usa el stack de encoders (Encoder-Only Transformer). 
![[Pasted image 20260818165806.png|center|576]]

BERT consta de 3 componentes principales:
- **Atención**: sin enmascarar. No aplicamos la matiz con $-\infty$ .
- **Tarea de predicción**: NSP (Next Sentence Prediction) y MLM (masked Language Modelling).
- **Input**: Dos fragmentos con separador.
![[Pasted image 20260818170105.png|center|379]]

En esta imagen vemos dos tokens especiales en la entrada del Transformer:
- **CLS:** Token especial ubicado al inicio de la secuencia que agrega y resume la información contextual global de todo el texto para tareas de clasificación.
- **SEP:** Token especial que actúa como delimitador para separar dos oraciones distintas o indicar el final de una secuencia de entrada.

Para realizar el proceso de NSP, se alimenta al modelo con dos oraciones ($A$ y $B$) y se utiliza el vector de salida del token `[CLS]`, el cual atiende de forma bidireccional a toda la secuencia para resumir la relación entre ambas. El objetivo es clasificar si la oración $B$ es la continuación consecutiva real de $A$ (`IsNext`) o si fue tomada al azar (`NotNext`). Como la salida del `[CLS]` es un vector de embedding, se le aplica una capa lineal con $\text{SoftMax}$ para convertir ese vector en una probabilidad y determinar si corresponde a la clase $1$ (`IsNext`) o $0$ (`NotNext`).

Para realizar el proceso de MLM, se enmascaran partes de la oración que se le dará al transformer. Según el paper de BERT, se toman los siguientes parámetros:
- ¿Cuántos enmascaro? 15%.
- ¿Cómo? 80% `[MASK]`, 10% random, 10% idénticos.

Vemos que la `[MASK]` no se aplica siempre, sino que solamente en un 80%. Esto se hace porque el 10% random represente equivocaciones que puede cometer una persona al escribir, y el 10% idéntico permite evitar que el modelo aprenda a confiar plenamente en que si el token está, sea efectivamente ese, y que así aprenda información también del contexto.  Por ejemplo:
```
"Pizza is a dish made with a flat, usually circular, dough made from wheat flour , yeast , water, and salt (sometimes olive oil) that is traditionally topped with tomato sauce and …"

"Pizza is a [MASK] made with a flat, usually [CIRCULAR], dough made from wheat flour , yeast , water, and [MASK] (sometimes olive oil) that is [SUPERNOVA] topped with tomato sauce and …”
```

Para el input, ahora debemos realizar tareas más sofisticadas, ya que debemos obtener dos oraciones continuas (o no), aplicar el separador y al final ajustar combinaciones en la función de pérdida. Pero una situación positiva que surge en los espacios de embedding es que en realidad no necesitamos la parte de NSP. En el paper de BERT original se implementa igualmente porque tiene un objetivo mucho más amplio de campo de aplicación. 
![[Pasted image 20260819155422.png|center|364]]

## Positional Encoding

El **positional encoding** se volvió fundamental porque, previo a los Transformers, el estado del arte eran las redes neuronales recurrentes (RNNs), donde la variable de tiempo o secuencia se daba de forma inherente al procesar la secuencia paso a paso (unrolling de la red). Esto quiere decir que en cada paso temporal se hacía un forward pass y el estado oculto (representación interna) generado se retroalimentaba en el siguiente paso de la red. Por lo tanto, en lugar de necesitar un embedding posicional que se sume al vector de entrada como en los Transformers (que procesan todo en paralelo), en las RNNs el orden quedaba codificado al ir actualizando ese estado interno a lo largo de los sucesivos pasos temporales.
![[Pasted image 20260819160412.png|center|527]]

Ahora, podríamos preguntarnos, ¿qué nos interesa al elegir una estrategia de positional encoding? La respuesta son dos elementos prinicipales:
- Cómo se declaran las posiciones.
- Cómo impacta el esquema elegido en la generalización del transformer.
	- Hay un límite dado por el transformer, ya que se puede tener el algoritmo de positional encoding más generalizable del mundo, pero este lo debe tolerar en su estructura de atención y MLPs, para poder procesarlo.
	- Es importante que el algoritmo escogido no limite al transformer. En un momento donde los contextos cada vez son más grandes, el positional encoding toma un rol cada vez más relevante. 

Nosotros estudiamos previamente el **absolute positional encoding**, ya que no es relativo a nada. Se tiene el siguiente cálculo:
$$
\begin{aligned}
PE(\text{pos}, 2i) &= \text{sen}(\text{pos} / 10000^{2i/d}) \\[2ex]
PE(\text{pos}, 2i+1) &= \cos(\text{pos} / 10000^{2i/d})
\end{aligned}
$$
Donde:
- $\text{pos}$ es la posición del token en la secuencia
- $i$ es el índice del vector de posición
- $d$ es la dimensión de un embedding, la misma del vector de posición $p_i$
![[Pasted image 20260809200003.png|center|366]]
Veamos la motivación para esta cuenta anterior que planteamos. Tomemos un gráfico que muestra cómo cambian los valores para las posiciones 0 a 50 (aunque deberían ser 512, que es el tamaño del embedding usado en el paper), cambiando la dimensión.
![[Pasted image 20260819161527.png|center|453]]

Notemos que la dimensiones más bajas tienen cambios muy bruscos de una posición a la otra. A la hora de procesar, esto va a servir para reconocer que dos tokens son distintos. A medida que se avanza en las dimensiones, se van modelando relaciones de mayor distancia. Entonces, las distintas dimensiones del vector de positional encoding están tratando de modelar y dar una señal, algunos sobre relaciones de corta distancia y otros de larga.

¿Por qué es de interés procesar secuencias largas? La respuesta la podemos encontrar mismo en nuestro propio uso de LLMs, ya que todo lo que tiene que ver con razonamiento se correlaciona muy directamente con el uso de muchos tokens.
