## Introducción

La idea es convertir todos los elementos físicos que venimos estudiando hasta ahora en elementos de nube. Recordemos que tenemos distintas etapas en la ruta de un paquete.
![[Pasted image 20261006195212.png|center|584]]
1. Internet: Desde donde accede el usuario.
2. Cloud Provider Network (Edge): Se llevan a cabo las funciones de NAT, DNS resolution y DDoS protection, y es donde se encuentra el WAF.
3. Cloud Provider VPC: Se encuentra el load balancer, que redirecciona los paquetes según su funcionalidad, dependiendo si es de L3 o L7. Allí se encuentran también los security groups, los NACLs y las subredes privadas.
4. Cloud Infraestructure: Se encuentran los clusters de Kubernetes.

## Virtualización

Un **sistema operativo tradicional** se compone de una arquitectura en capas diseñada para abstraer el hardware y brindar soporte a las aplicaciones que corren sobre él. En su base se encuentra el kernel, núcleo esencial que gestiona la comunicación directa con los recursos físicos, complementado por módulos del kernel como `nfs` o `ip_tables` y controladores de dispositivos. Por encima de esta base operan las herramientas del sistema (shell, compiladores y utilidades de disco), las bibliotecas compartidas (socket, cifrado y ssl) y utilidades de gestión de archivos, conformando el entorno estándar sobre el cual se ejecutan los programas de usuario.
![[Pasted image 20261006201203.png|center|216]]

Para poder operar, las aplicaciones presentan una serie de dependencias con distintos niveles de acoplamiento respecto al sistema anfitrión:
![[Pasted image 20261006201441.png|center|236]]
- Kernel del sistema operativo, el cual constituye el único requisito estrictamente obligatorio e ineludible.
- Dependencias opcionales adicionales, que abarcan runtimes de lenguaje como Java o Node.js, módulos del kernel y herramientas del sistema.
- Bibliotecas compartidas de sistema y archivos específicos de configuración requeridos para la lógica de la aplicación.

El esquema clásico de instalar varias aplicaciones directamente sobre un mismo host compartiendo dependencias ofrece ciertas ventajas de eficiencia, como ejecutables de menor tamaño, un consumo reducido de memoria y almacenamiento, y una mayor tasa de utilización global del hardware. 
![[Pasted image 20261006201530.png|center|239]]
No obstante, genera serios inconvenientes operativos: las dependencias se entrelazan entre los distintos servicios y con el sistema anfitrión, dificultando la replicabilidad y dando lugar a disparidades entre entornos de desarrollo y producción bajo el típico conflicto de funcionamiento localizado. Asimismo, la falta de aislamiento permite que una aplicación defectuosa acapare los recursos de cómputo del equipo, degradando el rendimiento del resto de los procesos.

La **virtualización** surgió como la respuesta técnica para resolver los conflictos de dependencias compartidas y aislamiento, permitiendo particionar el hardware físico en múltiples máquinas virtuales independientes. Bajo este paradigma, cada máquina virtual empaqueta su propia aplicación, sus bibliotecas y una copia completa del kernel del sistema operativo, logrando abaratar los costos de infraestructura al consolidar varios entornos aislados sobre un mismo servidor físico. Para gestionar este ecosistema a escala, herramientas de automatización como Chef, Puppet, Ansible o Salt se volvieron comunes en la administración de hosts y aplicaciones, sumado al uso de imágenes de máquinas virtuales inmutables que aseguran implementaciones repetibles y reversiones enteramente predecibles ante fallos.
![[Pasted image 20261010123646.png|center|188]]

El principal inconveniente radica en la duplicación redundante de componentes: ejecutar un sistema operativo completo y un kernel por cada máquina virtual genera un desperdicio significativo de memoria, almacenamiento y capacidad de procesamiento debido a la alta sobrecarga del hipervisor. Asimismo, la necesidad de inicializar un sistema operativo completo desde cero provoca que las máquinas virtuales tarden minutos en encenderse, limitando la velocidad de escalado dinámico ante demandas abruptas de tráfico.

## Contenedores

Los **contenedores** se consolidan como una nueva solución arquitectónica implementando virtualización a nivel de sistema operativo en lugar de emular hardware completo. Son un método para empaquetar un ejecutable de aplicación y sus dependencias (tiempo de ejecución, herramientas del sistema, bibliotecas del sistema, configuración) y ejecutar el paquete como un conjunto de procesos aislados de recursos.

Mediante primitivas del kernel como los espacios de nombres y los grupos de control, este paradigma logra aislar los procesos tanto entre sí como respecto al host anfitrión, compartiendo un único núcleo común. Cada contenedor empaqueta su propia aplicación y bibliotecas junto con un sistema de archivos independiente, prescindiendo de la necesidad de inicializar sistemas operativos invitados redundantes y reduciendo drásticamente el consumo de recursos.
![[Pasted image 20261010124114.png|center]]

Esto además brinda:
- Portabilidad entre distribuciones de SO y nubes
- Entorno consistente desde el desarrollo hasta la producción
- Creación de una imagen inmutable en tiempo de compilación en lugar de en el de implementación

Entonces, los contenedores:
- Consumen menos recursos
- Consumen menos espacio en disco
- Son más rapidos, nuevos o cambios escenario.
- Son independientes del OS
- No requieren licencias por cada OS
- Son portables

Existen distintas distribuciones:
- **LXC**: pionero en implementar contenedores en Linux utilizando cgroups y espacios de nombres a nivel de sistema operativo.
- **Docker**: solución que popularizó el despliegue de contenedores a gran escala mediante una arquitectura centralizada basada en un demonio en segundo plano.
- **containerd**: runtime modular desacoplado del núcleo de Docker, adoptado como base de ejecución en Kubernetes e impulsor de los estándares abiertos de la OCI.
- **Podman**: alternativa desarrollada por Red Hat con arquitectura sin demonio (daemonless) que introduce la gestión nativa bajo el concepto de pods.

Los beneficios de los contenedores son:
- Crea un entorno completo que permite la construcción de un paquete ( build ) para que luego se pueda ejecutar en otro ambiente (deploy & run).
- Resuelve el problema de hacer el deploy & run de una aplicación sin tener que preocuparse por todas las dependencias que pueda tener.
- Si bien hay opciones usualmente son Linux

## Docker

**Docker** se consolidó como la herramienta dominante en el ámbito de los contenedores tras transformar la manera en que el software se empaqueta y distribuye en la nube. Su origen se remonta al año 2013, cuando la empresa DotCloud Inc., especializada en plataformas como servicio alojadas, liberó el proyecto bajo una licencia de código abierto. La propuesta simplificó drásticamente el flujo de trabajo técnico, facilitando y agilizando tanto la creación como la ejecución de imágenes de contenedores mediante un formato estándar y predecible.
![[Pasted image 20261010124751.png|center|140]]
El impacto de la herramienta produjo una rápida adopción en la industria, llevando a la compañía a vender su negocio de plataforma original para enfocarse de lleno en la tecnología. Como consecuencia directa de esta expansión acelerada, DotCloud Inc. cambió su denominación corporativa a Docker Inc., estableciendo los fundamentos para la contenerización moderna en infraestructuras distribuidas.

## Open Container Initiative (OCI)

La **Open Container Initiative (OCI)** surge como un proyecto de estandarización abierto para establecer especificaciones universales en la tecnología de contenedores. Su propósito central consiste en garantizar que cualquier formato de imagen y entorno de ejecución sea completamente compatible y portable a través de múltiples plataformas e infraestructuras, evitando el bloqueo o dependencia de un único proveedor comercial.
![[Pasted image 20261010124941.png|center|615]]

El ciclo de vida operativo de los contenedores se articula a través de un flujo de trabajo continuo y normalizado:
1. Creación y compilación de la imagen a partir del código y sus dependencias.
2. Publicación y descarga mediante repositorios a través de operaciones push y pull.
3. Instanciación y ejecución directa del contenedor en el entorno de destino.

Para sostener este ciclo, la iniciativa divide sus fundamentos en dos especificaciones técnicas concretas que definen el formato de empaquetado y la forma de ejecución en los sistemas. La **especificación de imágenes** establece la forma estándar de construir el paquete del sistema de archivos:
- Manifiesto descriptivo con el detalle de todas las capas que integran la imagen.
- Conjunto de capas inmutables que componen el contenido del sistema de archivos.
- Información de configuración requerida por el motor de ejecución para inicializar el contenedor.

Por su parte, la **especificación de tiempo de ejecución** define cómo ejecutar la imagen desempaquetada mediante motores de bajo nivel estandarizados como runc:
- Configuración de procesos, parámetros de entrada, variables de entorno y puntos de montaje.
- Parámetros de aislamiento relativos a seguridad, entornos de pruebas y redes virtuales.
- Operaciones del ciclo de vida que el motor puede ejecutar, tales como create, start, state, kill y delete.

## Container y Sistemas Operativos

Un contenedor no es una máquina virtual ni una entidad especial del kernel, sino que es un proceso más del sistema operativo host. No hay hipervisor ni kernel propio; el proceso contenerizado comparte el kernel del host y aparece en su tabla de procesos como cualquier otro. Lo que lo hace "contenedor" es que se lo lanza con una serie de restricciones y aislamientos que le dan la ilusión de estar solo en la máquina. Esa ilusión se construye combinando varias funciones que Linux ya ofrece por separado.

El **Overlay FileSystem** es un sistema de archivos de tipo union, que superpone varios directorios y los presenta como uno solo. Las capas de la imagen se montan como solo lectura (lowerdir) y encima se agrega una capa de escritura propia del contenedor (upperdir); el contenedor ve la vista combinada (merged). Cuando modifica un archivo que pertenece a una capa inferior, este se copia primero a la capa superior (copy-on-write). Esto permite que muchos contenedores compartan las mismas capas de imagen sin duplicarlas en disco, y explica por qué los cambios se pierden al eliminar el contenedor.

Los **CGroups (control groups)** limitan y contabilizan cuántos recursos puede usar un grupo de procesos, como ser CPU, memoria, I/O de disco, cantidad de procesos, etc. Son los que evitan que un contenedor consuma todos los recursos del host y afecte al resto. Por cada contenedor se genera un cgroup de CPU y otro de memoria, y a cada uno se le asigna una cuota. De esta manera el contenedor puede usar como máximo esa cantidad de recursos, sin importar cuánto haya disponible en el host, lo que evita que un contenedor acapare la máquina y afecte a los demás.

Los **Namespaces** aíslan lo que el proceso puede ver. Cada namespace virtualiza un recurso global del kernel, de modo que el proceso tiene su propia vista de él:
- `PID`: árbol de procesos propio (el proceso principal se ve como PID 1).
- `NET`: interfaces, tabla de ruteo, reglas de firewall y puertos propios.
- `MNT`: puntos de montaje propios.
- `UTS`: hostname propio.
- `IPC`: colas de mensajes y memoria compartida propias.
- `USER`: mapeo de UIDs/GIDs (ser root adentro sin serlo afuera).

>[!INFO] Distinción
>Los namespaces definen qué puede ver el proceso; los cgroups, cuánto puede usar.

`seccomp_bpf` es un mecanismo de seguridad que filtra las syscalls que el proceso puede hacerle al kernel. `pivot_root` es la syscall que cambia el directorio raíz del proceso dentro de su mount namespace.

En cuanto a la red, el siguiente diagrama muestra cómo se conecta un contenedor en la red por defecto de Docker. El host (en el ejemplo, `192.168.1.10`) tiene su placa de red física con salida a Internet. El contenedor vive en su propio network namespace, por lo que tiene su propia interfaz `eth0` con una IP privada (`172.17.0.2`) que no pertenece a la red del host.
![[Pasted image 20261011154832.png|center|493]]
Para comunicar ese namespace con el exterior se usa un **veth pair**: un par de interfaces virtuales que funcionan como un cable, donde lo que entra por un extremo sale por el otro. Un extremo queda dentro del contenedor (es su `eth0`) y el otro queda en el host, conectado al bridge `docker0`.

`docker0` es un bridge virtual que actúa como un switch de capa 2 al que se conectan todos los contenedores de esa red, permitiendo que se comuniquen entre sí. Además tiene asignada una IP (`172.17.0.1`), que es el default gateway de los contenedores.

Docker ofrece distintos drivers de red, que determinan cómo se conecta el contenedor con el host, con otros contenedores y con el exterior:

No hay aislamiento de red.                                                                              |    Máximo rendimiento (omite la traducción de red), pero menos seguro y puede haber conflictos de puertos.    |

No hay bridge ni NAT.                                   | Aplicaciones que necesitan estar directamente en la red física (ej. integración con VLANs o sistemas legacy). |

En el modo bridge, la mejor práctica para la comunicación entre contenedores es crear una red
definida por el usuario en lugar de usar el puente por defecto (bridge).
1. Crear una red:
```bash
docker network create mi-red-app
```
2. Conectar contenedores a la red:
```bash
# Al ejecutar el primer contenedor (ej. la base de datos):
docker run -d --name db --network mi-red-app postgres

# Al ejecutar el segundo contenedor (ej. la aplicación web):
docker run -d --name web --network mi-red-app -p 8080:80 mi-app-imagen
```
3. Comunicación: El contenedor web puede referirse al contenedor de base de datos simplemente por su nombre: `db` (ej. la cadena de conexión a la base de datos sería `host=db`).

Para que un contenedor sea accesible desde el host o la red externa (navegador, otro servidor), es necesario publicar o mapear puertos. Esto le dice al motor de contenedores que redirija el tráfico de un puerto del host a un puerto específico del contenedor. La sintaxis es `-p <PUERTO_HOST>:<PUERTO_CONTENEDOR>`. Por ejemplo:
```bash
docker run -d -p 8080:80 --name mi-servidor nginx
```
- `8080` (Puerto del Host): El puerto por el que se accede desde el navegador del host.
- `80` (Puerto del Contenedor): El puerto interno donde la aplicación (Nginx) está escuchando dentro del contenedor.

El resultado es que al navegar a http://localhost:8080 en el host, el tráfico se redirigirá al puerto `80` del contenedor. Por defecto el entorno de containers se encuentra bloqueado, y por ende; a exposición de puertos hay que configurarla para brindar servicios.
```bash
docker run -d -p 8080:80 nginx
```
![[Pasted image 20261011163823.png|center|527]]

Un network namespace recién creado está aislado: solo tiene su interfaz de loopback y no puede comunicarse con nadie. Para conectar dos namespaces hay que crear un link entre ellos, que es un veth pair, como ya vimos.
![[Pasted image 20261011155652.png|center|408]]

Este esquema punto a punto no escala: para conectar muchos namespaces entre sí haría falta un veth pair por cada par. La solución es usar un Linux Bridge, un switch virtual de capa 2 que vive en el host. Cada namespace sigue teniendo su veth pair, pero ahora un extremo queda dentro del namespace (`veth-b`, `veth-y`, etc.) y el otro se conecta al bridge (`veth-br-b`, `veth-br-y`, etc.). Todos los namespaces quedan así en la misma subred (en el ejemplo, `192.168.10.0/24`) y pueden comunicarse entre sí a través del bridge.
![[Pasted image 20261011155743.png|center|475]]

La línea punteada entre el bridge y `eth0` indica que el bridge también es el punto de salida hacia el exterior. El host rutea el tráfico entre el bridge y su interfaz física, aplicando NAT. Esto es exactamente lo que hace Docker con `docker0` en la red bridge.

## Workflow de Contenedores

El flujo de trabajo con contenedores se divide en tres roles. En el **builder** se parte de un Dockerfile, un archivo de texto con las instrucciones para armar la imagen: imagen base, dependencias a instalar, archivos a copiar y comando a ejecutar al iniciar. Docker lo procesa con `docker build` y genera una imagen, que es un paquete inmutable compuesto por capas de solo lectura con todo lo necesario para correr la aplicación.
![[Pasted image 20261011160139.png|center|434]]

Esa imagen se sube con `docker push` a un **registry**, un repositorio centralizado de imágenes (Docker Hub, o uno privado). El registry es lo que desacopla la construcción de la ejecución: guarda las distintas imágenes y sus versiones, identificadas por nombre y tag, para que cualquier máquina autorizada pueda obtenerlas.

En el **runner**, que puede ser otra máquina totalmente distinta (un servidor de producción, por ejemplo), se descarga la imagen con `docker pull` y se la ejecuta con `docker run`, lo que crea un contenedor: una instancia en ejecución de esa imagen. De una misma imagen se pueden lanzar muchos contenedores.

>[!TIP] Ventaja
>La ventaja de este esquema es que la imagen que se prueba es exactamente la misma que se despliega, con las mismas dependencias y configuración, lo que elimina las diferencias entre entornos.

La nomenclatura clave de contenedores incluye:
- **Image**: paquete que incluye todo lo necesario para ejecutar un proceso.
- **Image Builder**: el que genera la imagen.
- **Container Runtime**: el que ejecuta el container.
- **Image Registry**: repositorio de imágenes.
- **Container**: proceso y ambiente que utilizan la imagen para ejecutar.

## Docker Images

Las **Image Layers** de Docker (o capas de imágenes) son la forma fundamental en que se construyen y almacenan las imágenes de Docker. Se pueden conceptualizar como un sistema de archivos apilado, donde cada capa es una plantilla de solo lectura que representa un conjunto de cambios realizados en el sistema de archivos de la imagen anterior.

Cada instrucción en un Dockerfile (el archivo de texto que contiene las instrucciones para construir una imagen) crea una nueva capa, siempre que modifique el sistema de archivos (ej. `FROM`, `RUN`, `COPY`, `ADD`). Las capas de metadatos o configuración (ej. `CMD`, `ENTRYPOINT`, `LABEL`) también forman parte de la imagen, pero generalmente no añaden tamaño significativo al sistema de archivos de la imagen.

Una imagen no es un bloque único sino una pila de capas de solo lectura, donde cada capa contiene los cambios respecto de la anterior. En general cada instrucción del Dockerfile que modifica el filesystem genera una capa: la imagen base, la instalación del intérprete, las librerías y finalmente el código de la aplicación. Cada capa se identifica por un hash de su contenido, lo que permite reconocer cuándo dos imágenes tienen una capa idéntica. Esto hace que las capas se puedan compartir. 
![[Pasted image 20261011160608.png|center|381]]

Todo lo que Docker almacena en el host (imágenes, contenedores, volúmenes, redes) está bajo `/var/lib/docker/`. Las capas de las imágenes se guardan en `/var/lib/docker/overlay2/<ID de layer>/`, con un directorio por capa. El nombre `overlay2` corresponde al storage driver, que usa el Overlay FileSystem para apilar las distintas capas en el momento de montarlas y presentarlas como un único filesystem.

Dentro del directorio de cada capa hay tres subdirectorios. `diff` contiene los datos propios de la capa, es decir, solo los archivos que esa capa agrega o modifica respecto de las inferiores. `work` es un directorio vacío que el overlay FS necesita internamente para preparar las operaciones de escritura antes de aplicarlas. `merged` es el punto de montaje donde se ve el resultado de apilar todas las capas, y es lo que el contenedor termina viendo como su raíz `/`.

Esto se relaciona directamente con el funcionamiento del overlay: los `diff` de las capas de la imagen se usan como capas inferiores de solo lectura, el `diff` de la capa del contenedor es la capa superior de escritura, y `merged` es la vista combinada.

## Docker Files

Un **Dockerfile** es el "guión" que utiliza Docker para construir una imagen, y cada instrucción en él se convierte en una capa de la imagen. Tomemos el siguiente ejemplo:
```dockerfile
FROM node:20-slim
WORKDIR /usr/src/app
COPY package*.json ./
RUN npm install
COPY . .
EXPOSE 8080
CMD [ "node", "server.js" ]
```
Donde:
- `FROM node:20-slim`: Descarga la imagen base y todas sus capas, que se convierten en las primeras capas de la nueva imagen.
- `COPY package*.json ./`: Crea una nueva capa que contiene sólo los archivos `package.json` y `package-lock.json`.
- `RUN npm install`: Crea la tercera capa. Esta capa contiene todas las dependencias (`node_modules`) instaladas.
- `COPY . .`: Crea la cuarta capa, que contiene el resto del código fuente de la aplicación.

El **registry** es el servicio donde se almacenan y distribuyen las imágenes. Docker Hub es el más usado y el que Docker consulta por defecto. Si se pide una imagen solo por su nombre (`docker pull redis`), se busca ahí. También es posible levantar un registry privado, dentro de la propia infraestructura, para no exponer las imágenes de una organización. Para usar un registry distinto de Docker Hub hay que indicar el origen explícitamente como prefijo del nombre de la imagen, por ejemplo `registry.miempresa.com/equipo/app:1.0`. En todos los casos el registry solo almacena: las imágenes siempre se bajan a la máquina local para ejecutarse.

**Docker Hub** (hub.docker.com) es un registry público, donde cualquiera puede acceder a las imágenes publicadas, incluyendo las oficiales de proyectos como Ubuntu, Redis o Nginx. Además de consumir imágenes ajenas, se pueden subir las propias, y estas pueden ser públicas o quedar en un repositorio privado dentro del mismo registry público, accesible solo para usuarios autorizados.

Las imágenes se versionan mediante tags, que son etiquetas que se agregan al nombre con el formato `nombre:tag`. En el siguiente ejemplo, las versiones 6.1, 6.2 y 7.0 de Redis se publican como `redis:6.1`, `redis:6.2` y `redis:7.0`, lo que permite elegir exactamente qué versión se quiere correr. Una misma imagen puede tener varios tags apuntando a ella (por ejemplo `7.4.1`, `7.4` y `7`), y también hay tags que indican variantes, como `alpine` o `bookworm`, según la distribución base. Si no se especifica ninguno, Docker usa el tag `latest` por defecto. 
![[Pasted image 20261011162557.png|center|254]]

El proceso de deploy muestra la arquitectura cliente-servidor de Docker, con tres componentes. El cliente es la línea de comandos `docker`, que no ejecuta nada por sí misma sino que envía pedidos al Docker daemon. El daemon (`dockerd`) corre en el Docker host y es quien realmente hace el trabajo, pues construye imágenes, las descarga y administra los contenedores. El registry es el repositorio remoto de imágenes.
![[Pasted image 20261011162642.png|center|424]]

Cada comando sigue un camino distinto. Con `docker build`, el daemon construye una imagen a partir de un Dockerfile y la guarda en el almacenamiento local de imágenes del host. Con `docker pull`, el daemon contacta al registry, descarga la imagen pedida y la guarda localmente. Con `docker run`, el daemon toma una imagen local y crea un contenedor a partir de ella; si la imagen no está en el host, primero la baja del registry. Como cliente y daemon están separados, pueden estar en la misma máquina o en máquinas distintas, lo que permite administrar un host remoto desde la terminal local.

## Volúmenes

Cuando se inicia un contenedor, utiliza los archivos y la configuración proporcionados por la imagen. Cada contenedor puede crear, modificar y eliminar archivos y lo hace sin afectar a ningún otro contenedor. Los **volúmenes** son un mecanismo de almacenamiento que brinda la capacidad de conservar datos más allá del ciclo de vida de un contenedor individual.

Existen distintos tipos:
- **Named Volumes**: los maneja internamente docker
- **Bind Mounts**: monta un directorio del host
- **tmpfs Mounts**: maneja data en memoria sin persistencia

Todos estos son locales al host. A través de volume drivers, se pueden manejar filesystems externos o compartidos como:
- Network Attached Storage ( NAS )
- Cloud Storage Providers
- Distributed FS como GlusterFS o Ceph

## Comandos de Docker CLI

Algunos de los comandos más comunes del CLI de Docker son:
- `docker save`/`docker load`: exporta una imagen a un archivo tar o la importa desde ese archivo.
- `docker pull`: descarga una imagen desde el registry.
- `docker images`: lista las imágenes almacenadas localmente.
- `docker run`: crea e inicia un contenedor a partir de una imagen.
- `docker ps`/`docker ps -a`: lista los contenedores en ejecución o, con `-a`, todos, incluidos los detenidos.
- `docker top`: muestra los procesos que corren dentro de un contenedor.
- `docker logs <container ID>`: muestra la salida (stdout/stderr) del contenedor.
- `docker start <container ID>`: vuelve a iniciar un contenedor detenido.
- `docker diff`: muestra los archivos agregados, modificados o borrados en el contenedor respecto de su imagen.
- `docker exec -it`: ejecuta un comando dentro de un contenedor en ejecución, de forma interactiva (típicamente una shell).

## Docker Compose

**Docker Compose** es una herramienta que facilita la ejecución de varios contenedores a la vez. Una aplicación real rara vez es un solo contenedor, ya que suele tener, por ejemplo, un frontend, un backend y una base de datos, y levantarlos a mano implicaría un `docker run` por cada uno, con sus puertos, variables de entorno, redes y volúmenes. Compose permite definir todo eso de forma declarativa en un solo archivo, `docker-compose.yml`.

En ese archivo cada contenedor se describe como un servicio, junto con su configuración, como de dónde sale la imagen, qué puertos publica, qué variables de entorno recibe, qué volúmenes monta y a qué redes se conecta. Como muestra el siguiente diagrama, un servicio puede partir de una imagen ya existente, que se baja del registry (`image: mysql:8.0`), o de un Dockerfile propio, en cuyo caso Compose primero construye la imagen (`build: ./app`) y después crea el contenedor.
![[Pasted image 20261011164256.png|center|550]]

Con el archivo definido, `docker compose up` levanta toda la aplicación y `docker compose down` la detiene y elimina. Compose crea además una red bridge propia para el proyecto, en la que los servicios se alcanzan entre sí por su nombre (el backend puede conectarse a la base usando `db` como hostname). Está pensado para un solo host; para distribuir contenedores entre varias máquinas se usan orquestadores como Swarm o Kubernetes.

Esta herramienta brinda:
- **Control simplificado**: Docker Compose permite definir y administrar múltiples contenedores en un solo archivo YAML.
- **Colaboración**: los archivos `docker-compose.yml` son fáciles de compartir, lo que facilita la colaboración entre desarrolladores, equipos de operaciones y otras partes interesadas.
- **Desarrollo rápido de aplicaciones**: tiene un caché de configuración usada para crear un contenedor. Cuando reinicia un servicio que sin cambios, Compose reutiliza los contenedores existentes.
- **Portabilidad**: permite variables en el `docker-compose.yml` y se pueden usar para personalizar en diferentes entornos o usuarios.

Tomemos el siguiente ejemplo de aplicación:
![[Pasted image 20261011164650.png|center]]
Con:
- 2 services
- 1 secret (HTTPS certificate)
- Configuración HTTP
- 1 persistent volume
- 2 networks

El archivo `docker-compose.yml` sería:
```yaml
services:
  frontend:
    image: example/webapp
    ports:
      - "443:8043"
    networks:
      - front-tier
      - back-tier
    configs:
      - httpd-config
    secrets:
      - server-certificate

  backend:
    image: example/database
    volumes:
      - db-data:/etc/data
    networks:
      - back-tier

volumes:
  db-data:
    driver: flocker
    driver_opts:
      size: "10GiB"

configs:
  httpd-config:
    external: true

secrets:
  server-certificate:
    external: true

networks:
  # The presence of these objects is sufficient to define them
  front-tier: {}
  back-tier: {}
```

Luego:
- Para iniciar todos los servicios definidos en su archivo compose.yaml:
```bash
docker compose up
```
- Para parar y borrar los servicios:
```bash
docker compose down
```
- Para monitorear la salida de sus contenedores en ejecución y ver logs
```bash
docker compose logs
```
Para listar los servicios
```bash
docker compose ps
```
