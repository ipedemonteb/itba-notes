## Introducción

Para la práctica usamos **Kind**, una herramienta que usa contenedores de Docker para simular los nodos de un clúster de Kubernetes y los configura con todos sus componentes. Hay alternativas como Minikube o K3d; todas crean clústers no productivos, de poca criticidad. En producción se usan nodos reales o el servicio de Kubernetes del cloud provider (en AWS, **EKS**). Kind requiere tener Docker instalado.

```bash
brew install kind
kind create cluster --name demo --config kind-config.yaml
kind delete cluster --name demo
```
- `--name`: nombre del clúster. Si no lo ponemos, se llama `kind`. Conviene ponerlo para después poder borrarlo por nombre.
- `--config`: archivo de configuración del clúster, con un formato muy parecido a los manifests de Kubernetes. Sin él, Kind crea un único nodo que funciona como control plane y como worker a la vez.

Por ejemplo, para tener un nodo de control plane y dos workers:
```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

Como cada nodo es un contenedor, con `docker ps` vemos tres contenedores: `demo-control-plane`, `demo-worker` y `demo-worker2`.

---
## kubectl

Para interactuar con el clúster usamos el CLI de Kubernetes, **kubectl** (`brew install kubectl` en macOS; para Linux y Windows, la guía de la página de Kubernetes). kubectl es solo un cliente de la **API server** del clúster: todo lo que hace se podría hacer con requests HTTP, con otro cliente o desde un servicio propio, incluso desplegado dentro del mismo clúster. Por eso hay que tener cuidado con quién tiene acceso.

Los comandos se ejecutan siempre dentro de un **contexto**, que tiene la información del clúster (dónde está el control plane) y las credenciales para autenticarse. Los contextos se guardan en `~/.kube/config`. Kind agrega ahí el contexto `kind-demo`, y si nos queremos conectar a otro clúster agregamos su información en ese archivo y cambiamos de contexto.

Todos los comandos tienen la forma:
```bash
kubectl <acción> <tipo de objeto> [nombre] [opciones]
```
- **Acción**: `get` (listar u obtener un objeto), `create`, `delete`, `describe`, `logs`, etc. `man kubectl` explica todas.
- **Tipo de objeto**: en Kubernetes todo es un objeto (`pod`, `service`, `namespace`, `daemonset`, etc.).
- **Nombre**: se puede escribir `tipo nombre` o `tipo/nombre` (por ejemplo `daemonset/kindnet`).

Para escribir menos se suele usar el alias `k` para `kubectl`.

---
## Namespaces

`kubectl get all` muestra los objetos más comunes (no todos), pero en un clúster recién creado solo aparece el service `kubernetes`. Esto pasa porque los comandos corren, además, dentro de un **namespace**, y si no lo especificamos se usa `default`.

Los namespaces dividen lógicamente al clúster: agrupan objetos que tienen sentido juntos y permiten controlar accesos y cuotas de recursos por namespace. Por ejemplo, con un namespace por equipo podemos limitar la RAM que usa cada uno y que nadie pueda borrar los servicios de otro equipo.
```bash
kubectl get namespaces            # default, kube-node-lease, kube-public, kube-system...
kubectl create namespace redes
kubectl delete namespace redes    # borra también todo lo que tenga adentro
kubectl get all -n kube-system
```
- `-n <namespace>`: namespace sobre el que corre el comando. Si un objeto está en otro namespace y no lo indicamos, el comando falla o no lo encuentra. Es un error común crear algo en un namespace y después buscarlo en `default`.
- Crear un namespace para cada ejercicio es práctico: al final borramos el namespace y se borra todo.

En `kube-system` están los componentes del propio Kubernetes: `etcd` (la base de datos clave-valor donde se guardan todos los objetos del clúster), el scheduler, el API server, y `kube-proxy` y `kindnet`, que tienen tres pods cada uno porque corren uno por nodo.

## Inspeccionar Objetos

```bash
kubectl describe daemonset kindnet -n kube-system
kubectl get daemonset kindnet -n kube-system -o yaml
```
- `describe`: muestra el estado del objeto (nombre, namespace, cuántos pods corren bien o fallan) y, al final, sus **eventos**. Es lo primero que miramos cuando algo falla.
- `-o yaml`: devuelve el manifest del objeto. Sirve para recuperar un manifest perdido o como base para crear uno parecido.

`kube-proxy` y `kindnet` son **DaemonSets**: objetos que se aseguran de que cada nodo del clúster (o los nodos que elijamos) tenga un pod con la configuración definida en su manifest. Se usan para procesos que administran cosas propias de cada nodo.

## Imagen de la Aplicación

La aplicación de ejemplo es un servidor en Go que escucha en el puerto 8080 (configurable con la variable de entorno `SERVER_PORT`) y tiene un endpoint `/hello` que responde `hello <nombre>`, con el nombre tomado de otra variable de entorno (por defecto `World`). En Kubernetes todo corre en contenedores, así que primero necesitamos su imagen. El Dockerfile es un multi-stage build: compila la app con la imagen `golang:1.22` y la copia a una imagen `scratch`, por lo que la imagen final pesa unos 7 MB y no tiene nada más que la app.
```bash
docker build -t demo-backend:latest .
docker run --rm -p 8080:8080 demo-backend:latest
curl localhost:8080/hello    # hello World (en "/" devuelve 404)
```

Para que Kubernetes cree un contenedor, la imagen tiene que estar en un registry al que tenga acceso. Como no la publicamos en ningún registry, usamos un atajo de Kind que la carga en el registry local de cada nodo:
```bash
kind load docker-image demo-backend:latest --name demo
docker exec -it demo-worker crictl images    # lista las imágenes del nodo
```
Esto no ejecuta nada: solo deja la imagen disponible en cada nodo. Cuando un nodo tenga que crear un contenedor con esa imagen, la usa si la tiene local; si no, la busca en un registry. Cada vez que modificamos la app hay que volver a hacer el build y el `kind load`, o los nodos siguen usando la imagen vieja.

## Manifests

Un **objeto** es algo que persistimos en el clúster y que define el estado deseado de algo. Kubernetes compara continuamente ese estado deseado con el actual y toma las acciones necesarias para igualarlos. Nosotros solo creamos objetos; el clúster hace el resto. Los objetos se definen con manifests, que siempre tienen:
- `apiVersion`: versión de la API que usa el objeto.
- `kind`: tipo de objeto.
- `metadata`: información para identificarlo, como `name` y `namespace`, y `labels`.
- `spec`: el estado deseado. Su contenido depende del tipo de objeto. La documentación oficial de Kubernetes detalla el spec de cada tipo.

En un mismo archivo podemos definir varios manifests separándolos con `---`; al aplicarlo se crean todos.

## Pods

Un **pod** es la unidad más chica de trabajo en Kubernetes y encapsula uno o más contenedores. Define un ambiente para ellos, con variables de entorno, volúmenes y configuración de red. Los contenedores de un pod **comparten la red**, por lo que se comunican por `localhost` (por eso dos cosas que no deberían comunicarse no van en el mismo pod).

Para tener varias réplicas de la aplicación se agregan pods, no contenedores dentro del mismo pod:
- Los objetos que administran réplicas manejan pods, no contenedores. Si un pod tuviera tres contenedores de la app, al bajarlo se caen los tres, y no se puede actualizar de a uno.
- Un pod pertenece a un nodo, así que todas sus réplicas estarían en el mismo nodo.
- Como comparten la red, no pueden escuchar todos en el mismo puerto.

Un pod pertenece a su nodo hasta que termina, se borra a mano, se borra automáticamente por alguna política (por ejemplo, falta de recursos) o falla el nodo. Si un contenedor falla o se reinicia continuamente, el pod sigue existiendo: lo que se reinicia son los contenedores, no el pod. Los pods están pensados para ser descartables (pueden cambiar de IP o de nodo), por lo que no debemos depender de un pod individual. En general no se crean a mano, sino con objetos que los administran.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: backend
  namespace: default
spec:
  containers:
    - name: application
      image: demo-backend:latest
      imagePullPolicy: IfNotPresent
      ports:
        - containerPort: 8080
```
```bash
kubectl apply -f pod.yaml
kubectl get pods             # READY, STATUS, RESTARTS (de los contenedores) y AGE
kubectl describe pod backend # IP, nodo, estado y eventos
kubectl delete -f pod.yaml
```
- `apply -f`: crea el objeto o, si ya existe uno con ese nombre (lo sabe por la metadata), intenta actualizarlo.
- `imagePullPolicy`: si la imagen usa el tag `latest` y no lo especificamos, vale `Always`, es decir, siempre la descarga del registry e ignora la local. Por eso la primera versión del pod falló al descargar la imagen de `docker.io`. Con `IfNotPresent` solo la descarga si no la tiene local.
- Casi todo el spec de un pod es inmutable: si cambiamos el `imagePullPolicy` y volvemos a hacer `apply`, falla. Hay que hacer `delete` y después `apply`.

## Debugging

```bash
kubectl logs backend -c application
kubectl get events
kubectl exec -it backend -c application -- sh
kubectl debug -it backend --image=busybox --target=application
kubectl port-forward pod/backend 8081:8080
```
- `logs`: logs de un pod; con `-c` indicamos el contenedor.
- `get events`: todos los eventos del clúster (nodos que pasan a ready, pods que fallaron o se crearon bien, etc.).
- `exec -it`: igual que en Docker, ejecuta un comando en un contenedor (`-i` conecta nuestro STDIN y `-t` abre una terminal). Puede ser `sh`, `bash` o cualquier comando, como `ls`. En nuestro caso falla, porque la imagen `scratch` no tiene ni `sh`.
- `debug`: agrega un **contenedor efímero** temporal a un pod existente, con la imagen que elijamos (`busybox` tiene shell), y `--target` indica el contenedor del pod al que se asocia. Como comparte la red del pod, desde ahí podemos hacer `wget -qO- localhost:8080/hello`. En el `describe` del pod aparece en la lista de ephemeral containers. Es útil, por ejemplo, para tener `psql` temporalmente en un pod que no lo tiene.
- `port-forward`: como el `-p` de Docker, abre el puerto 8081 en nuestra computadora y lo apunta al 8080 del pod, así que un `curl localhost:8081/hello` llega a la app.

Para ver los cambios en vivo hay dos opciones:
- `watch -n 1 kubectl get pods`: herramienta aparte que ejecuta el comando cada segundo y muestra solo la última salida.
- `kubectl get pods -w`: modo watch de kubectl, que va mostrando cada cambio (por ejemplo, `Pending`, `ContainerCreating`, `Running`).

## Probes

Kubernetes usa **probes** (health checks, como en los target groups de AWS) para conocer el estado de los contenedores:
- **Readiness**: determina únicamente si el pod está listo para recibir tráfico. La usan los objetos que distribuyen tráfico (los services) para decidir si le mandan tráfico a ese pod.
- **Liveness**: determina si el contenedor tiene que reiniciarse. Si falla, Kubernetes lo reinicia automáticamente.

Pueden ser comandos o requests HTTP (lo más común, porque hosteamos servicios). No hay probes por defecto: sin ellas, Kubernetes solo verifica que el contenedor esté levantado, por eso el pod aparecía ready al instante. Esto es un problema con aplicaciones que tardan en arrancar (Spring puede tardar minutos), porque recibirían tráfico antes de estar vivas. Hay que configurarlas con cuidado: si la readiness da bien pero la liveness falla, el pod se reinicia todo el tiempo y el tráfico que recibe falla (503).

```yaml
      readinessProbe:
        httpGet:
          path: /status
          port: 8080
        initialDelaySeconds: 15
        timeoutSeconds: 10
        periodSeconds: 10
        failureThreshold: 3
      livenessProbe:
        # misma configuración
```
- `initialDelaySeconds`: espera 15 segundos antes del primer chequeo.
- `timeoutSeconds`: si no hay respuesta en 10 segundos, cuenta como fallo.
- `periodSeconds`: chequea cada 10 segundos.
- `failureThreshold`: con 3 fallos seguidos falla el probe. En la liveness, se reinicia el contenedor; en la readiness, deja de recibir tráfico.

Lo común es usar el mismo endpoint para ambas, salvo que la app necesite hacer algo (descargar datos, preprocesar) entre estar viva y poder recibir tráfico.

En la demo, la app no tenía `/status`: el pod nunca pasó a ready, la liveness falló y se reinició varias veces hasta quedar en `CrashLoopBackOff`, donde Kubernetes deja de intentar. Agregamos un endpoint ping-pong que siempre devuelve 200, rehicimos la imagen, la cargamos con Kind, borramos y aplicamos el pod, y a los 21 segundos pasó a ready.

>[!TIP] Qué Chequear
>Los probes se ejecutan varias veces por minuto, así que el endpoint tiene que ser liviano. Un ping-pong ya verifica mucho: si el servidor responde, tiene memoria, CPU, threads y red. Se pueden agregar chequeos, como fallar la liveness si el pool de conexiones a la base está saturado, para que el reinicio empiece de cero. Lo mismo ayuda a zafar de un memory leak: cuando la app empieza a fallar, la liveness la reinicia.

## Configuración del Pod

Otras configuraciones del contenedor (el detalle queda para la guía):
- `securityContext`: reglas de seguridad, como `readOnlyRootFilesystem`, `privileged: false`, `allowPrivilegeEscalation: false` o `runAsUser` (el UID con el que corre). Son configuraciones base que hay en todos lados.
- `command` y `args`: sobrescriben el comando y los argumentos de la imagen, como el entrypoint y el CMD en Docker.
- `env`: variables de entorno. Si cambiamos `SERVER_PORT` a 8081, hay que cambiar también el puerto del pod y de los probes, o el probe va al 8080, falla y el contenedor se reinicia.

Un pod de `busybox` se cierra apenas arranca, porque su comando por defecto termina enseguida. Para tener uno siempre disponible desde donde correr comandos dentro del clúster, lo mantenemos vivo con un `sleep` (en segundos):
```yaml
spec:
  containers:
    - name: busybox
      image: busybox
      command: ["sleep", "1000"]
```
Cuando termina el `sleep`, el contenedor se reinicia, pero queda vivo lo suficiente para usarlo con `kubectl exec -it busybox -- sh`.

## ConfigMaps y Secrets

Para compartir configuración entre varios pods sin copiar las variables en cada uno, existen objetos que guardan información separada de la aplicación. Así, por ejemplo, la misma definición de pod puede usar una configuración en producción y otra en el clúster de pruebas.

Un **ConfigMap** guarda información no sensible en `data`, como pares clave-valor. Se puede usar como variables de entorno o montar como archivos:
```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-env
data:
  CLAVE: "valor"
---
apiVersion: v1
kind: ConfigMap
metadata:
  name: nginx-config
data:
  default.conf.template: |
    # configuración de Nginx
---
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  volumes:
    - name: config
      configMap:
        name: nginx-config
  containers:
    - name: nginx
      image: nginx
      envFrom:
        - configMapRef:
            name: nginx-env
      volumeMounts:
        - name: config
          mountPath: /etc/nginx/templates
```
- `envFrom.configMapRef`: publica todos los pares clave-valor del ConfigMap como variables de entorno.
- `volumes`: se define a nivel pod, por lo que está disponible para todos sus contenedores.
- `volumeMounts`: pertenece a cada contenedor e indica dónde montar el volumen. Un mismo volumen se puede montar en distintas ubicaciones en distintos contenedores.

En el ejemplo, la configuración de Nginx hace que `/` devuelva un error 500 en lugar de la página de bienvenida. Para probarlo, buscamos la IP del pod con `kubectl describe pod nginx`, entramos al busybox con `kubectl exec -it busybox -- sh` y hacemos una request a esa IP, que devuelve el HTML del error 500. Con `kubectl get configmaps` y `kubectl describe configmap <nombre>` vemos los ConfigMaps y su contenido.

Un **Secret** es lo mismo, pero para información sensible (contraseñas, claves privadas). Se usa igual, con `secretRef` en lugar de `configMapRef`. En el ejemplo, un Secret cambia la contraseña de un pod de Postgres.
```bash
kubectl edit secret postgres-secret
kubectl port-forward pod/postgres 5432:5432
psql -h localhost -U postgres    # se conecta con la contraseña del Secret
```
- `edit`: abre el objeto en un editor para modificarlo. Los valores aparecen en base64, y al modificarlos hay que escribirlos en base64.

>[!WARNING] Seguridad de los Secrets
>Por defecto los Secrets no son seguros: solo se codifican en base64, así que cualquiera con acceso al clúster puede leerlos y decodificarlos. Se pueden complementar con plugins para guardarlos de forma segura. Igualmente, la regla es usar Secrets para información sensible y ConfigMaps para la que no lo es.

Además, para darles acceso a disco a los contenedores existen distintos tipos de volúmenes, que se ven en la guía.

## Administradores de Pods

Manejar réplicas a mano (crearlas, nombrarlas, mantener la misma versión en todas) se vuelve tedioso enseguida. Para eso Kubernetes tiene objetos que administran pods:
- **Deployments y ReplicaSets**: para pods sin estado y descartables, que es el caso de la mayoría de los backends.
- **StatefulSets**: para pods con estado, identificables y no descartables.
- **DaemonSets**: un pod en todos los nodos (o en los que elijamos), por ejemplo, para agentes que leen logs.
- **Jobs**: crean un pod que se ejecuta hasta terminar.
- **CronJobs**: crean un Job cada cierto tiempo, según una expresión cron. Sirven para DB migrations o análisis periódicos.

---
## ReplicaSets

Un **ReplicaSet** mantiene una cantidad de réplicas de un pod. Su spec tiene:
- `replicas`: cuántos pods crear.
- `template`: la plantilla del pod, con su propia `metadata` y `spec` (los mismos contenedores de antes).
- `selector`: las condiciones que debe cumplir un pod para que el ReplicaSet lo administre. Funciona con labels.

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: backend
  labels:
    app: backend
spec:
  replicas: 3
  selector:
    matchLabels:
      app: backend
  template:
    metadata:
      labels:
        app: backend
    spec:
      containers:
        - name: application
          image: demo-backend:latest
          imagePullPolicy: IfNotPresent
```
Es fundamental que el template tenga el label del selector (`app: backend`); si no, los pods que crea no los administra.

Al aplicarlo, se crean tres pods con nombres que terminan en un ID aleatorio, sin que tengamos que nombrarlos uno por uno. Como el ReplicaSet compara todo el tiempo el estado deseado con el actual:
- Si creamos a mano un pod con el label `app: backend`, pasa enseguida a `Terminating`, porque habría cuatro réplicas.
- Si borramos uno de sus pods, crea otro al instante.
- Si cambiamos `replicas` a 2 y aplicamos, mata uno cualquiera, sin recrear los demás.
- Si borramos el ReplicaSet, se borran todos sus pods.

## Deployments

Un **Deployment** es una abstracción sobre los ReplicaSets: así como el ReplicaSet administra pods, el Deployment administra ReplicaSets. Al crear un Deployment, en el clúster quedan el Deployment, un ReplicaSet y sus pods (el nombre de cada pod incluye el ID de su ReplicaSet). En la práctica se usan Deployments en lugar de ReplicaSets. El manifest es casi igual: cambia el `kind` a `Deployment` y mantiene `replicas`, `selector` y `template`.

Además de las réplicas, el Deployment se fija en el template del pod. Si cambia (por ejemplo, la versión de la imagen), hace un **rollout**: crea un ReplicaSet nuevo y va reemplazando los pods de a uno. Crea un pod nuevo, espera a que esté ready, baja uno del ReplicaSet viejo, y así hasta que el viejo queda en 0. Así nunca hay downtime, a diferencia de bajar todo y levantar lo nuevo. Si solo cambian las réplicas, no hay rollout: se ajusta la cantidad en el mismo ReplicaSet.

En la demo, el cambio fue en los recursos del contenedor:
```yaml
          resources:
            requests:
              cpu: 200m
              memory: 100Mi
            limits:
              cpu: "1.5"
              memory: 200Mi
```
- `requests`: lo que el contenedor necesita sí o sí, y que Kubernetes le garantiza.
- `limits`: hasta dónde puede crecer. Si necesita más memoria, puede usar hasta 200 MiB, pero no más.
- `200m`: 200 milicores, es decir, 0,2 CPU virtuales.

```bash
kubectl rollout status deployment/backend
kubectl rollout undo deployment/backend
kubectl rollout undo deployment/backend --to-revision=2
kubectl rollout history deployment/backend
kubectl rollout history deployment/backend --revision=4
```
- `rollout status`: estado del rollout en curso.
- `rollout undo`: rollback al rollout anterior. Hace lo inverso: vuelve a subir el ReplicaSet viejo y baja el nuevo de a un pod. Con `--to-revision` volvemos a una revisión en particular.
- `rollout history`: lista las revisiones, y con `--revision` muestra el template del pod de esa revisión, es decir, qué cambio aplicaríamos al volver a ella.

Un rollback es un rollout nuevo, así que crea una revisión nueva: si hicimos las revisiones 1 y 2 y deshacemos, aparece la 3 (igual a la 1). El rollback no modifica el archivo del manifest; si volvemos a aplicarlo, hacemos un rollout hacia adelante, con un nuevo ReplicaSet. El uso típico es desplegar una versión nueva de la imagen (por ejemplo, `v50`) y, si hay problemas, hacer `undo` para volver a `v49`.

## Services

Como los pods se recrean en cada rollout con IPs nuevas, necesitamos un endpoint único que distribuya el tráfico entre ellos, como un load balancer de AWS. En Kubernetes es el **Service**. Selecciona los pods por labels y solo les manda tráfico a los que pasan la readiness probe. Dos aplicaciones distintas no pueden compartir labels, porque no habría forma de definir un service que apunte solo a una.

Hay cuatro tipos:
- **ClusterIP** (por defecto): una IP privada fija dentro del clúster que reparte el tráfico entre los pods. Es un load balancer interno, y se crea uno por cada servicio (backend, frontend, etc.).
- **NodePort**: un ClusterIP que además abre un puerto en todos los nodos, accesible desde fuera del clúster con `<IP del nodo>:<puerto>`.
- **LoadBalancer**: se integra con un load balancer externo (por ejemplo, crea uno en AWS) que dirige el tráfico a los pods.
- **ExternalName**: asigna un nombre de dominio.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: backend
spec:
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8081
```
- `selector`: a qué pods manda el tráfico.
- `port`: puerto del service.
- `targetPort`: puerto de los pods. En el ejemplo, el puerto 80 del service va al 8081 de los pods con `app: backend`.

Con `kubectl get services` vemos la IP del service, y con `kubectl describe service backend`, la lista de **endpoints**, que son las IPs de los pods a los que apunta. Desde el busybox, una request a `http://<IP del service>/hello` (sin puerto, porque 80 es el default) responde desde cualquiera de los pods.

Si cambiamos el template del Deployment (por ejemplo, el request de memoria a 150 MiB) y aplicamos, el service no cambia, pero sus endpoints sí: a medida que avanza el rollout, se agrega cada pod nuevo cuando pasa a ready y se quita cada pod viejo. Solo por un instante hay tres endpoints, porque apenas un pod nuevo está ready el Deployment baja uno viejo. Además, un pod que se está bajando deja de estar ready, y deja de recibir tráfico enseguida.

Para un **NodePort** agregamos `type: NodePort` y un tercer puerto:
```yaml
spec:
  type: NodePort
  selector:
    app: backend
  ports:
    - port: 80
      targetPort: 8081
      nodePort: 30010
```
El puerto 80 de la IP del service sigue yendo al 8081 de los pods, y además el 30010 de cada nodo va al service.

Las IPs de los nodos (`kubectl get nodes -o wide`) pertenecen a la red de Docker que crea Kind, llamada `kind`. Para probarlo desde afuera del clúster, corremos un contenedor conectado a esa red, por ejemplo `docker run --rm --network kind alpine wget -qO- <IP del nodo>:30010/hello`. Responde `hello World` con la IP de cualquiera de los nodos.

## Ingress

Un **Ingress** expone rutas HTTP fuera del clúster y las dirige a los services; básicamente es un Nginx. El objeto Ingress solo declara el estado deseado; el trabajo real lo hace un **ingress controller**, que el clúster no trae por defecto. Sin él, crear un Ingress no hace nada. Usamos `ingress-nginx`, el controller basado en Nginx. Ingress está siendo reemplazado de a poco por la **Gateway API**, más flexible, pero el concepto es el mismo.

Quedan así las capas: pods, ReplicaSet, Deployment, Service e Ingress.

Para instalar el controller:
```bash
kubectl get node demo-worker --show-labels
kubectl label node demo-worker ingress-ready=true
kubectl apply -f <URL del manifest de ingress-nginx>
kubectl wait --namespace ingress-nginx --for=condition=ready pod --selector=app.kubernetes.io/component=controller --timeout=90s
kubectl get all -n ingress-nginx
```
- `label node`: le agrega el label `ingress-ready=true` al nodo (lo hicimos en ambos workers), porque el controller solo corre en los nodos con ese label. Los labels se usan mucho en Kubernetes para indicar a qué nodos u objetos aplica algo.
- `apply -f <URL>`: igual que con un archivo local, pero tomando el manifest de GitHub.
- `wait`: espera hasta que los pods del controller cumplan la condición `ready`.
- En el namespace `ingress-nginx` quedan el pod del controller, su ReplicaSet, su Deployment y un par de services. Para desinstalarlo basta con borrar el namespace.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: backend
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /$2
spec:
  rules:
    - http:
        paths:
          - path: /backend(/|$)(.*)
            pathType: ImplementationSpecific
            backend:
              service:
                name: backend
                port:
                  number: 80
```
Una request a `/backend/hello` llega al ingress, que la manda al service `backend` en el puerto 80, y este a los pods con `app: backend` en el 8081. El `rewrite-target` quita el prefijo `/backend`, para que al servicio le llegue `/hello` y no `/backend/hello`.

Con `kubectl get ingress` y `kubectl describe ingress backend` vemos las rutas. Desde la red `kind`, una request a `<IP del nodo>/backend/hello` responde bien (solo en el nodo donde corre el controller), y desde el busybox también.

>[!INFO] Exposición del Ingress
>Que el puerto 80 del nodo responda es un efecto secundario de cómo se instala el controller en Kind. Un Ingress no publica nada fuera del clúster por sí solo: normalmente hay un service LoadBalancer (o NodePort) que apunta al ingress controller.
