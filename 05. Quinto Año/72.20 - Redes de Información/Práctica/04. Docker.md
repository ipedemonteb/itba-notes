## Introducción

Docker tiene dos partes grandes: la **generación de imágenes** (a partir de un Dockerfile) y la **ejecución de imágenes** (contenedores). Una imagen parte de una imagen base (Ubuntu, Debian, MariaDB, etc.), le vamos aplicando comandos y cada paso va generando imágenes intermedias que quedan cacheadas en la computadora. La imagen final es la que corremos con Docker o, como veremos en la siguiente unidad, con Kubernetes.

Antes de empezar, `docker info` muestra la versión instalada, la cantidad de contenedores e imágenes, el **storage driver** (el recomendado es `overlay2`; hay otros más antiguos con inconvenientes) y el directorio donde Docker guarda todo (`/var/lib/docker`, con carpetas para containers, imágenes, volúmenes, etc.).

---
## Ejecutar Contenedores

```bash
docker run -it --name myubuntu ubuntu bash
```

- `docker run`: crea y ejecuta un contenedor a partir de una imagen.
- `-i` (interactive) y `-t` (tty): juntos nos permiten escribirle al contenedor desde nuestra terminal. Sin ellos la terminal no queda interactiva.
- `--name`: nombre del contenedor. Debe ir antes de la imagen, porque todo lo que va a la derecha del nombre de la imagen se interpreta como argumento del contenedor. No puede haber dos contenedores con el mismo nombre, aunque uno esté detenido.
- `ubuntu`: la imagen. Si no está en la computadora, Docker la baja de Docker Hub.
- `bash`: el programa que se ejecuta dentro del contenedor.
- `--rm`: elimina el contenedor automáticamente cuando se detiene. Evita los conflictos de nombre, pero hay casos donde queremos que el contenedor siga existiendo.

Para comprobar que un contenedor es un proceso más del host, podemos crear un archivo y dejar un `tail -f foo` corriendo dentro del contenedor: desde otra terminal del host, `ps` muestra ese `tail`.

Otros comandos para administrar contenedores e imágenes:
- `docker ps`: lista los contenedores en ejecución. Con `-a` lista también los detenidos.
- `docker stop <nombre o ID>`: detiene un contenedor. Todos los recursos de Docker tienen un ID (hash), y en general podemos usar tanto el nombre como el ID.
- `docker rm <nombre o ID>`: elimina un contenedor detenido.
- `docker image ls`: lista las imágenes locales, con su tag, ID y tamaño.
- `docker inspect <recurso>`: muestra la información de cualquier recurso (contenedor, red, volumen): imagen que usa, límites de disco y RAM, configuración de red, mounts, etc.
- `docker system prune`: libera espacio eliminando los contenedores detenidos, las redes sin uso y las imágenes sin uso.

## Imágenes y Docker Hub

Cuando una imagen no está en local, Docker la busca por defecto en **Docker Hub** (hub.docker.com), un repositorio público de imágenes. Ahí hay imágenes oficiales de casi cualquier herramienta: `nginx` para un servidor web, `mysql` o `mariadb` para bases de datos, `phpmyadmin` para ver una base con una interfaz gráfica, `gcc` para tener el compilador de C ya instalado, o `python` en distintas variantes (por ejemplo `alpine`, una distribución de Linux muy liviana).

- **Tag**: versión o variante de la imagen, con el formato `imagen:tag`. Cada build se puede publicar con un tag distinto. Si no indicamos ninguno, Docker usa `latest`.
- `docker pull <imagen>`: descarga la imagen sin ejecutarla. Se puede configurar para usar un repositorio privado distinto de Docker Hub.
- `docker login`: necesario antes de hacer `docker pull usuario/imagen` de una imagen privada de nuestra cuenta de Docker Hub.
- `scratch`: imagen especial vacía, sin nada instalado. Sirve para armar una imagen base propia, aunque lo normal es partir de una imagen existente.

## Dockerfile

Un **Dockerfile** es el conjunto de instrucciones que genera una imagen. Siempre empieza con un `FROM` (imagen y tag de partida) y sigue con la lista de instrucciones. Solamente `FROM`, `RUN` y `COPY` generan capas nuevas para la imagen.
```dockerfile
# Imagen de la que vamos a partir
FROM

# Ejecutar un comando como si fuera la terminal
RUN

# Copiar archivos del host a la imagen
COPY

# Movernos de carpeta en la imagen (como si fuera cd)
WORKDIR

# Comando que ejecutamos al iniciar el contenedor
ENTRYPOINT

# Argumentos para el entrypoint
CMD

# Variables de entorno
ENV

# Usuario que ejecuta los comandos
USER
```

El rol de cada una en la práctica:
- `RUN`: ejecuta comandos dentro de la imagen durante el build, por ejemplo `RUN apt update && apt install -y curl`.
- `COPY . .`: copia todo lo que hay en la carpeta del build (el primer punto, que corresponde al contexto del build) a la carpeta actual de la imagen (el segundo punto, que es el `WORKDIR`). Los archivos copiados quedan siempre con dueño root, aunque antes haya un `USER`.
- `WORKDIR /app`: cambia la carpeta desde la que se ejecutan las instrucciones siguientes, y es la carpeta en la que queda parado el contenedor al iniciar.

Para construir la imagen:
```bash
docker build -f Dockerfile.example -t ubuntu-demo:v1 .
```
- `-f`: archivo a usar. Si no lo aclaramos, busca uno llamado `Dockerfile`.
- `-t`: nombre y tag de la imagen resultante. El nombre debe estar en minúsculas.
- `.` (al final): contexto del build, es decir, la carpeta desde donde se toman los archivos para los `COPY`.

Cada vez que modificamos el Dockerfile hay que volver a hacer el build. Después podemos ejecutar cualquiera de las versiones construidas (`ubuntu-demo:v1`, `ubuntu-demo:v2`, etc.).

---
## Caché de Capas

Cada paso que genera una capa queda cacheado. Si construimos `v1` con un `FROM` y un `RUN apt update && apt install ...`, y luego agregamos abajo otro `RUN` y construimos `v2`, los pasos 1 y 2 salen del caché y solo se ejecuta el paso 3.

La caché solo se reutiliza hasta el primer paso que cambió. Si agregamos un `RUN` arriba del primero, todos los pasos posteriores se vuelven a ejecutar, y solo se salva el `FROM`. Además, el caché de un `COPY` se invalida cuando cambian los archivos copiados.

>[!TIP] Orden de las Instrucciones
>Lo que es largo y casi no cambia (instalar paquetes) va arriba; lo que cambia seguido (el `COPY` del código) va abajo. Así, un cambio en el código no obliga a reinstalar todos los paquetes en cada build.

Como cada capa ocupa espacio en el host, conviene reducir su cantidad. Muchos `RUN apt install` seguidos pueden generar varias capas y, si la imagen base ya pesa 1 GB, el total puede crecer muchísimo. Hay dos formas de reducirlas:
- Juntar los paquetes en un solo `apt install`.
- Cuando no se puede juntar (por ejemplo, comandos distintos), encadenar los comandos con `&&` dentro de un único `RUN`, que sigue generando una sola capa:

```dockerfile
RUN apt update && apt install -y curl vim
```

## Entrypoint y CMD

Un Dockerfile tiene un `ENTRYPOINT` y un `CMD` como máximo. Trabajan juntos:
- **ENTRYPOINT**: qué comando se ejecuta al iniciar el contenedor.
- **CMD**: los argumentos por defecto de ese comando.

Veamos un ejemplo (reconstruido a partir de lo visto en clase) que instala `curl`, crea un usuario, copia los archivos y ejecuta `curl --help`:
```dockerfile
FROM ubuntu:24.04
WORKDIR /app
RUN apt update && apt install -y curl
RUN useradd appuser
USER appuser
COPY . .
ENTRYPOINT ["curl"]
CMD ["--help"]
```
```bash
docker build -f Dockerfile.example -t ubuntu-demo:final .
docker run --rm --name curl-demo ubuntu-demo:final
```

Todo lo que escribimos a la derecha del nombre de la imagen en el `docker run` reemplaza al `CMD`:
```bash
# Ejecuta "curl google.com" (devuelve un 301)
docker run --rm --name curl-demo ubuntu-demo:final google.com
```

El `ENTRYPOINT` no se reemplaza tan fácil, sino con la flag `--entrypoint`, que cambia el comando entero. Los argumentos que escribimos a la derecha de la imagen pasan a ser los del nuevo comando:
```bash
# Ejecuta "ls -la"
docker run --rm --name curl-demo --entrypoint ls ubuntu-demo:final -la
```

Para meternos a una terminal del contenedor podemos cambiar el entrypoint a `bash`, pero hay que agregar `-it`, porque si no la terminal no queda interactiva:
```bash
docker run --rm -it --name curl-demo --entrypoint bash ubuntu-demo:final
```

Por eso hay que entender cuál es el `ENTRYPOINT` de la imagen para saber qué estamos ejecutando y qué parte podemos modificar.

## Vida del Contenedor

Un contenedor vive mientras viva su proceso principal. Con `curl`, el programa empieza y termina, y el contenedor se apaga. Si cambiamos el entrypoint a `tail -f <archivo>`, el proceso queda corriendo y el contenedor sigue activo, visible con `docker ps`.

---
## Forma Exec y Shell

El `ENTRYPOINT` (y el `CMD`) se pueden escribir de dos formas:
```dockerfile
# Forma exec (con corchetes)
ENTRYPOINT ["curl"]

# Forma shell (sin corchetes)
ENTRYPOINT curl
```

- **Con corchetes (exec)**: Docker ejecuta directamente el programa, que pasa a ser el proceso raíz del contenedor. Cada elemento de la lista es un argumento separado. Si ponemos varios elementos, el primero es el comando y el resto son argumentos fijos que el `CMD` no pisa. Por ejemplo, `ENTRYPOINT ["run.sh", "--port", "8080"]` mantiene `--port 8080` aunque cambiemos el `CMD`.
- **Sin corchetes (shell)**: Docker lo envuelve en una shell (como un `sh -c "curl"`), por lo que el proceso raíz es la shell y nuestro programa corre como hijo. Esto cambia cómo reacciona el contenedor al `docker stop`.

En la demo se vio con `tail -f`. Sin corchetes, el `docker stop` tardó en detener el contenedor, mientras que con corchetes lo detuvo enseguida.

## Usuarios

Hasta que aparece un `USER`, todas las instrucciones del Dockerfile corren como root. A partir de `USER appuser`, los `RUN` siguientes y el contenedor al ejecutarse corren con ese usuario. En general no conviene dejar a root como usuario final, porque tiene permisos que no necesitamos y es más riesgoso, sobre todo si más adelante montamos carpetas del host (ver volúmenes), ya que ahí un contenedor sí podría afectar al host.

- El usuario tiene que existir: primero se crea (`RUN useradd appuser`) y después se lo selecciona con `USER`. Si no existe, el `USER` no sirve.
- Los archivos que crea un `RUN` después del `USER` pertenecen a ese usuario (por ejemplo, un `RUN touch hook` crea un archivo de `appuser`).
- `USER` no genera capa. En cambio, intentar cambiar de usuario con un `RUN` (por ejemplo `RUN su ...`) sí genera una capa extra, y el cambio no se mantiene para las instrucciones siguientes ni para el contenedor.
- Los archivos del `COPY` siguen siendo de root aunque haya un `USER` antes. Si queremos que sean del usuario, hay que agregar un `RUN chown -R appuser /app` (de la carpeta entera).
- En el `docker run`, la flag `--user <usuario>` pisa el usuario del Dockerfile (por ejemplo `--user root`). El usuario debe existir en la imagen.
- Si el `USER` nunca se cambió en el Dockerfile, al abrir una terminal (`--entrypoint bash`) estamos como root. Si se cambió, estamos como ese usuario.

## Redes

`docker network ls` lista las redes. Hay tres drivers por defecto:
- `host`: con `--network host` el contenedor comparte todas las interfaces de red del host. Elimina el aislamiento que es la gracia del contenedor, por lo que no se recomienda salvo situaciones muy específicas.
- `none`: con `--network none` el contenedor no tiene red, solo la interfaz de loopback.
- `bridge`: red virtual interna que crea Docker. Es la que se usa por defecto, y los contenedores que se conectan a ella pueden comunicarse entre sí.

```bash
docker run --rm -it --name demo1 --network bridge --entrypoint bash ubuntu-demo:final
```

Con `docker inspect demo1`, en `NetworkSettings`, vemos la red a la que está conectado, su IP, el gateway (`172.17.0.1`) y su MAC. Con `docker inspect bridge` vemos la red: su subnet (`172.17.0.0/16`), su gateway y los contenedores conectados con la IP de cada uno.

Dos contenedores en la red `bridge` por defecto se pueden hacer ping por IP, pero **no por nombre**: esa red no tiene resolución de nombres. Las redes bridge que creamos nosotros sí la tienen.
```bash
docker network create --driver bridge --subnet 172.28.0.0/16 mi-red
docker run --rm -it --name demo1 --network mi-red ubuntu-demo:final
docker run --rm -it --name demo2 --network mi-red ubuntu-demo:final
```
- `--driver`: tipo de red (`bridge` es el valor por defecto).
- `--subnet`: subred que usa la red.
- El nombre de la red va al final.

Desde `demo1`, `ping demo2` resuelve al nombre del otro contenedor.

Por último, con el driver **macvlan** el contenedor se conecta directamente al router como si fuera una computadora más de la red, con su propia IP. Es útil cuando el contenedor necesita acceder a un dispositivo de la red local.

## Publicar Puertos

Para no tener que darle al contenedor su propia IP en la red, publicamos puertos con `-p <puerto del host>:<puerto del contenedor>`. Eso hace un port forwarding: lo que llega al puerto del host se pasa al puerto del contenedor.
```bash
docker run --rm --name my-nginx -p 80:80 nginx
```
Un `curl localhost` ahora llega al puerto 80 del contenedor. Con `docker ps` vemos la columna de puertos como `0.0.0.0:80->80/tcp`. Si el puerto del host ya está en uso, el comando falla.

## Volúmenes

Todo lo que hacemos dentro de un contenedor es efímero: vive en una capa propia del contenedor que se elimina junto con él. Si creamos un archivo, borramos el contenedor y lo volvemos a correr, el archivo no está. Los **volúmenes** resuelven la persistencia. Se montan con `-v <origen>:<destino>`, donde el destino es la carpeta dentro del contenedor.

**Bind volume**: monta una carpeta del host dentro del contenedor.
```bash
docker run --rm -it --name demo -v /home/usuario/bind-volume:/mi-volumen ubuntu-demo:final
```
- El origen tiene que ser una **ruta absoluta**; no se pueden usar rutas relativas como `../carpeta`.
- La conexión es bidireccional: lo que creamos en la carpeta del host aparece en el contenedor y viceversa.
- Los archivos tienen asignado un UID numérico, y el nombre del usuario que se ve depende de la lista de usuarios de cada sistema. El host y el contenedor tienen listas distintas (por ejemplo, el UID 1000 puede ser un usuario distinto en cada uno), por lo que suele haber problemas de permisos. Si el UID no existe en el sistema, se muestra el número.
- Es más inseguro (afecta al host) y, según lo observado en clase, notablemente más lento que los otros tipos. Se usan sobre todo para desarrollo, por ejemplo para modificar el código en el host y que el contenedor lo vea al instante.

**Named volume**: lo crea y administra Docker.
```bash
docker volume create my-data
docker volume ls
docker volume inspect my-data
docker run --rm -it --name demo1 -v my-data:/mi-volumen ubuntu-demo:final
```
- Arranca vacío. Se le pueden configurar parámetros, como un límite de tamaño.
- `docker volume inspect` muestra dónde vive físicamente en el host.
- Persiste aunque se borre el contenedor: al volver a montarlo, los archivos siguen ahí.
- Se puede montar en varios contenedores a la vez, que comparten sus archivos.
- Con `docker inspect <contenedor>`, en `Mounts`, vemos qué volúmenes tiene y su modo. Por defecto es lectura y escritura, y se puede limitar a solo lectura agregando `:ro` (`-v my-data:/mi-volumen:ro`).
- Es el que conviene para datos que no queremos perder, por ejemplo los archivos de una base de datos.

**Volumen anónimo**: se declara solo el destino, sin origen (`-v /mi-volumen`), o con `VOLUME /mi-volumen` en el Dockerfile.
- Docker crea un volumen con un nombre aleatorio (un hash), distinto en cada ejecución.
- Con `--rm`, el volumen se elimina junto con el contenedor. Sin `--rm`, queda, y se puede reutilizar montándolo con su hash como si fuera un named volume.
- Es más incómodo de usar que un named volume.

## Multi-Stage Builds

Un Dockerfile puede tener más de un `FROM`; cada uno inicia una **stage**. La ventaja es que las herramientas de una stage no quedan en la imagen final. Con `AS` le damos nombre a una stage, y con `COPY --from=<stage>` copiamos archivos de una stage anterior.
```dockerfile
FROM gcc AS builder
WORKDIR /app
COPY hello_world.c .
RUN gcc hello_world.c -o hello_world

FROM debian
WORKDIR /app
COPY --from=builder /app/hello_world .
ENTRYPOINT ["./hello_world"]
```
Este ejemplo (reconstruido a partir de lo visto en clase) compila `hello_world.c` en la primera stage, que tiene el compilador, y la segunda parte de Debian y copia solo el binario. La ruta de origen del `COPY --from` es la de la stage anterior (`/app/...`), y el destino es la de la stage actual. Los `WORKDIR` de ambas stages se llaman igual, pero son completamente distintos.

```bash
docker build -f Dockerfile.multistage -t multistage-demo .
docker run --rm -it --entrypoint bash multistage-demo
```
Al entrar vemos que solo está el binario `hello_world`, sin el `.c` ni archivos intermedios (como los `.o`), y la imagen final queda limpia. Una stage sin nombre recibe uno automático (`stage-1`), y cada stage tiene sus propias capas en el caché. En la demo, un cambio en la primera stage que no alteraba los archivos copiados no invalidó los pasos de la segunda; en cambio, un `RUN rm hello_world` hizo fallar el `COPY`, porque ya no existía el archivo.

## EXPOSE

`EXPOSE 8080` en el Dockerfile es solo **declarativo**: indica que la aplicación escucha en ese puerto, pero no lo publica. En `docker ps` aparece como `8080/tcp` (solo el puerto del contenedor), a diferencia de un puerto publicado con `-p`, que aparece como `0.0.0.0:8081->8080/tcp` (puerto del host hacia puerto del contenedor).
```bash
docker run --rm --name demo -p 8081:8080 multistage-demo
```
Para que el puerto sea accesible desde el host hay que publicarlo con `-p`. Sirve como pista de qué puerto necesita una imagen que no conocemos (por ejemplo, `nginx` declara el 80).

## Docker Compose

Con tantos parámetros (`--network`, `-v`, `--user`, imagen, etc.) el `docker run` se vuelve largo. **Docker Compose** permite definir todo en un archivo YAML (por lo general `docker-compose.yaml`) que se puede guardar en un repositorio. Cada **servicio** equivale a un contenedor.
```yaml
services:
  curl-demo:
    image: ubuntu-demo:v3
    container_name: cool-demo
    user: appuser
    volumes:
      - mi-volumen:/my-data
      - /home/usuario/bind-volume:/bind-data
    networks:
      - mi-red

  nginx:
    image: nginx
    networks:
      - mi-red

volumes:
  mi-volumen:
    driver: local

networks:
  mi-red:
    external: true
```
- El nombre del servicio (`curl-demo`) no tiene que coincidir con el del contenedor (`container_name`).
- Se pueden usar bind volumes (ruta absoluta) y named volumes. Los named volumes hay que declararlos en la sección `volumes` del archivo, donde también se configura el driver. Lo mismo vale para las redes.
- Si la red ya está creada por fuera (por ejemplo, con `docker network create`), se la declara como `external: true`, y Compose no la crea.
- También se pueden configurar el `entrypoint`, el usuario y el resto de lo visto en la clase.
- Los recursos creados por Compose llevan como prefijo el nombre de la carpeta del proyecto (el volumen queda como `<carpeta>_mi-volumen`).

`docker compose up` levanta todos los servicios, volúmenes y redes definidos. Si un contenedor ejecuta un programa que termina (como el `curl`), lo vemos terminar mientras el resto sigue corriendo.
